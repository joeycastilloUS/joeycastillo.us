Hardware Power-Fail Early-Warning for Purcius Nodes

To: Norman Campbell (hardware)  ·  From: Joey Castillo, kASTIL Systems  ·  Re: can the board tell the runtime a power cut is coming?  ·  Status: forward-looking — not a work order

The one-paragraph context

Purcius is our bare-metal, pure-C runtime — it runs as firmware, first layer after BIOS, no legacy OS in the way. Its new distributed store already self-heals from an abrupt power loss in software: before any irreversible act it writes a durable, fsync'd intent, and on reboot a resume pass drives any unfinished act to completion exactly once. That's the floor, and it holds even if the plug is yanked mid-operation. The question for you is the ceiling: if the hardware could tell us a power cut is imminent — a few milliseconds' warning — the node could pause cleanly instead of recovering after the fact. Novel, and only possible because we own the stack down to the metal.

The idea

A supervisor / brownout-detector IC watches the rail. The instant it dips below threshold — while the bulk capacitors still hold charge for a short window — it asserts a power-fail interrupt (PFI / NMI) to the SoC. Because Purcius is pure C on bare metal, that interrupt lands directly in a tiny deterministic handler: flush the log, mark a clean checkpoint, park. To the system, power loss becomes "time paused cleanly"; on power return, "time unpauses" and it resumes. No legacy OS scheduler, no userland, no lost window between the interrupt and the flush.

  rail voltage
   good ─────────────┐
                     │ undervoltage
                     ▼ detected
        PFI/NMI asserted ──►  [ HOLD-UP WINDOW ]   ◄── bulk caps buy this time
                                (a few ms?)     │
                                                ▼
                              runtime: fsync log → checkpoint → PARK
                                                │
   Vcore collapses ─────────────────────────────┘
        · · · · · · · ·  (power out — clean pause)  · · · · · · · ·
   power restored ──►  boot ──►  resume from checkpoint (no loss, no dup)

The hold-up window is the whole game: how many milliseconds the caps buy us after the warning is exactly our flush budget. Our flush is tiny (a sealed append + fsync), so even a very small window is plenty — but we need to know it.

Where you come in — the hardware questions

  • Supervisor IC. Is there a brownout/undervoltage detector (or PMIC feature) on the target boards that can assert an interrupt line to the SoC on power dip? Threshold + response time?
  • Hold-up time. Given the bulk capacitance at our expected load, roughly how long after the PFI does Vcore stay valid? That number is our flush budget — even 1–2 ms likely suffices.
  • The line itself. A GPIO / NMI / power-good pin we can standardize on across node classes, so one firmware handler serves all boards?
  • Edge + custom silicon. For the small edge units — and eventually our own silicon — is it worth a dedicated power-fail domain and a small NV-backed flush region, so the "clean park" is guaranteed by design rather than by cap math?
  • Anything novel you'd reach for that we're not thinking of — supercap ride-through, a second rail, an early-warning from the PSU itself?

Scope + why it's not urgent

  • The software floor already covers us. An abrupt cut is survived today; this signal only upgrades "recover after" to "pause cleanly."
  • The node is small and portable — it can be moved on the fly without missing a beat — and it runs N-way replicated, so losing one node is a non-event. The power-fail signal is about making even a single node's local durability graceful, and about the differentiator: a runtime that shakes hands with the hardware on the way down.
  • This is a brief, not a build. A full detailed document with schematics-level diagrams follows when we prioritize it. For now: does this direction excite you, and what's the hold-up window we'd actually have to work with?
