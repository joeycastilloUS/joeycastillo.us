PLAN — AWAITING APPROVAL

pi_run runs the dianoia

Make the interpreter read + execute the dianoetic triple (.pi · .si · .sm) for the Argus NPS-triage scenario. Sized from Fable5's ~d (cap 98bb32eb, argus eb42282). Owner: jc.

Intent

The dianoetic triple is authored but inert — pi_run still hardcodes the words, the jacket still owns the illness fold (the cleanSafe != 2 roster-bug class), and verify_card checks keys, not intent. Until pi_run runs the triple, biRT is a claim in a doc, not a refusal at load. This plan makes the interpreter run the dianoia: intent executes from the file the operator owns, verified before a single unit fires.

Scope

In: pi_run reads/verifies/executes the triple (dia_load, 3-stage dia_verify, words-seal, fold-in-C, config: flow); the illness lane end-to-end off the dianoia; then recovery; drain the two jackets to pass-through; generate nous.sm from the C headers.
Out: prod arming; any rename (pi_run keeps its name); .learned / mind-loading; every other card — this is the reference scenario only.

Approach — Intent · Purpose · What

  • Intent: intent runs from the operator's file, verified before it acts.
  • Purpose: biRT becomes a load-time refusal; the fold moves into pure C (roster bug dies); the jackets shrink to dumb arms.
  • What: a new pirun/dianoia.c/h beside the engine — pirun.c is untouched, this is a delta not a rewrite. dia_load parses the triple into the existing PiPlaybook/PiUnit (grown with why/bind/words/set/res/idem). dia_verify runs three stages before any unit. Words seal by hash into the ledger + a committed .pi.seal. Sibling-.si detection picks the dianoetic path — no .si beside a card → the legacy path runs byte-for-byte, so the working card never breaks. pantheon_fold in pure C folds the panel's raw verdicts against set: panel.models.

Phases

  1. D1 — Load & verify. The triple parses and the 3-stage verify makes drift a refusal.
  2. D2 — Illness lane, proof of life. The lane runs end-to-end off the dianoia with sealed .pi words; a planted why: D99 refuses to load; every trace event carries its why: D#.
  3. D3 — Fold in C + recovery. pantheon_fold takes the fold from the jacket; the recovery lane runs; config: alert.requester flows.
  4. D4 — Drain the jackets + generate the map. Both bridges become pass-through (the audit's end state); nous.sm is generated from headers; the dianoia files become the card's canonical pair.

Constraints (won't bend)

  • pirun.c engine untouched — a delta, never a rewrite.
  • The legacy card path stays byte-for-byte until the dianoetic path is proven (sibling-detection, no flag).
  • No unit runs until all three verify stages pass — biRT is a refusal, not a warning.
  • The fold cutover never leaves a window where nobody, or both, fold the verdict (dual-emit + prefer-raw).
  • C99 for everything we own; the C# jacket is transport only — the whole point.
  • Sandbox until jc arms prod.

Unknowns (named)

  1. The .si↔.sm signature rule. Sig names are roles (email), not ledger keys (alert.guest_email); out-sigs use wildcards (alert.*, *); some out-key counts exceed the sig. Positional arity + type with wildcard coverage is the pick — but the exact rule needs locking, or verify is either too loose to protect or rejects the very files we authored.
  2. The fold cutover is cross-repo and live. Moving the fold from gcp-bridge to pantheon_fold must never gap or double-fold. Dual-emit + prefer-raw is the sequence; the deploy ordering + the multi-line-words-through-JSON payload path size as one lane.
  3. Word bytes to the jacket. The escalation note/subject render via the existing translate_strings, but panel-question ships to the jacket as raw multi-line bytes through JSON — escaping needs a clean, tested path.
  4. The .pi.seal lifecycle. First load seals + commits; who re-seals on an operator-approved .pi edit, and does an unsealed edit hard-refuse.

When To Revisit

  • After D1+D2: if the verify semantics (unknown 1) don't hold — drift slips through, or the authored files get rejected — v2 re-locks the signature rule before D3.
  • When a second card is authored: .sm goes shared/generated across cards; the per-card assumptions get their first real test.
  • If the sandbox shows a fold gap or double-fold during cutover (unknown 2) → v2 the sequence.
