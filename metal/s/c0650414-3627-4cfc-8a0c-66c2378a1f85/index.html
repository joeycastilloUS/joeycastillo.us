Scope in every NPS alert — guest-originated first

Four real detractor alerts were dropped and can never be recovered. This designs the change that stops it.

Paired serial — driver writes, navigator reviews with authority to block. Nothing is built. A prototype was written to test feasibility, was reviewed, and has been reverted; pi_run.c is untouched. What it proved is recorded below as evidence for the design, not as work in progress.

1 · The need

Tickets #730–733 are real guest complaints. Nobody answered them, and nobody ever will.

Guest Relations alerts, created 2026-07-21 04:37–04:44Z. 0 of 4 carry argus_nps_handled twelve hours later. They failed at unit 0, were counted into sweep.errors and swallowed, and have aged out of the sweep window (60 seconds by code default). There is no retry and no alarm. The failure mode is not "delayed" — it is "gone."

One of them reads "My soup had a hair in it." Another, "The food was okay but I got sick afterwards" — a phrase that should have triggered the illness path.

Why they were dropped

scan_alert qualifies a ticket by strstr for five literal strings. The two brands render alerts differently, and all five miss on Guest Relations:

Four distinct differences, not one. Stripping asterisks alone still loses the Store value and all of the feedback text.

2 · Raw user stories

As the operator, every NPS detractor alert gets handled, whichever brand it arrives on and whatever the template looks like.

As the operator, an alert that arrives from the guest directly is the most important one in the queue — that is a person who took the trouble to write to us.

As the operator, when an alert cannot be handled I find out. It does not evaporate.

3 · The shape — and the decision that matters

Parse the comment body. Stop parsing the whole HTTP response.

Today every field read runs strstr across the entire raw JSON blob — which contains the body, and html_body, and the via.source.from sender metadata. That is the actual defect; the markdown is only how it surfaced.

The prototype proved this the hard way. A first cut that simply tolerated bold extracted the feedback for ticket #733 as the single word "Test". Why: the requester's Zendesk profile name is "Guest Feedback Test", which appears in the sender metadata. The alias "Guest Feedback" matched there — thousands of bytes away from the real **Guest Comments** field — and captured the next word.

That is not a markdown bug. It is a whole class: any label can collide with any guest's name, subject line, signature, or the HTML twin of the body. Extract comment 0's body span first, then read fields only within it. That closes the metadata class outright. The remaining in-body class is closed separately, by ordering — see the rule below.

Then, inside the body, read tolerantly

RuleHandles
Match the label bare or bold; step over *, :, spaces**Guest Email**
If the value is empty on that line, take the next non-empty line**Store**\n\n9 - Westlake Village
Accept field aliases, resolved by earliest position in the body, not first alias tried"Guest Feedback" / "Guest Comments"
Within the body, the first occurrence of each label winsfree text that happens to contain a label word

The in-body rule rests on an invariant worth stating out loud: in both live templates the free-text field is always last, so every genuine label precedes any guest-written prose. That is what makes first-occurrence-wins safe. A template that ever places free text above other fields re-opens the collision class — a guest who writes "my Guest Email never got the receipt" would otherwise poison the extraction. Carried into When To Revisit.

The blob is raw JSON, so a line break is the two-character escape \n — never a real newline. Any next-line rule has to step over that pair. The current grab() already stops at \\ for this reason.

How loose is "less strict"?

Your instruction was "pretty much any NPS is scoped in." The first draft of this section argued there was a tension — that looser qualification costs model calls and vault codes, so the email gate should stay. That was a false dichotomy and it under-delivered on the instruction. Qualification and email-extraction can fail separately, at the same zero cost, with different visibility.

The two-stage predicate:

StageTestOn failure
Is this ours?the body contains ## Guest Experience Alert — verbatim in both brands, verified on all five live tickets. (An NPS-Score marker, bare or bold, is an equally good alternate.)silent skip — correctly "not ours"
Can we answer it?a guest email was extractedloud, counted failure — never the silent "not ours" path

This costs nothing. Both tests sit at unit 0, before any model call and before any vault code is claimed — exactly where today's single gate already sits. No code is ever spent on a ticket we cannot answer. The email stays required to answer; it stops being required to see.

That matters because today's failure mode is the silent one. An alert whose template drifts — a renamed field, a new brand, a malformed address — vanishes into "not ours" with no trace. Under the two-stage predicate it lands as a visible failure with a ticket number attached, which is the whole point of "monitor and handle all NPS."

4 · "Especially from guest" — the part this change does NOT fix

Getting them seen is not getting them answered.

The two brands' alerts are structurally different, and it changes what a correct reply even is:

Default brandGuest Relations
Created byAPI, by the NPS systemThe guest, by email
Requesterthe neutral NPS identitythe guest themselves
Alert commentprivatepublic
Correct replya new follow-up ticketa public comment on this ticket

The recovery send posts {guest_email, subject, body, draft_id} — no brand; the alert ticket id survives only inside the draft_id idempotency key, which the bridge does not use to pick a brand or a thread. So a guest who wrote to hello@guestrelationstest.zendesk.com would get a reply from the default brand's address, in a brand-new ticket, while their own ticket sits unanswered. Fixing detection without this means the most critical alerts get the most confusing response.

So this is two changes, and they should be sequenced deliberately:

ChangeDelivers
ABody-scoped tolerant parse (this design) plus a send guard: when the alert's brand is not the default — equivalently, when the requester is not the NPS-system identity — stop after triage. Do not run the recovery send, and mark the ticket distinctly rather than letting argus_nps_handled imply it was answered. The guard is removed when B lands.guest alerts are seen and triaged, and visibly awaiting a correct reply
BCarry the alert's brand_id and requester through to the send; reply as a public comment when the requester is the guestguest alerts are answered correctly

A without the guard is actively worse than today. The alert would be tagged argus_nps_handled, a wrong-brand reply would appear in a brand-new thread, and the guest's own public ticket would sit unanswered while monitoring reports it handled. A silent drop at least leaves the failure visible as an unhandled ticket. That is why the guard is part of change A rather than a caveat attached to it — and why this design does not lean on PIRUN_ARM_SEND being 0 by default. A build flag is not a design.

The illness escalation is unaffected: it posts to an internal lane, recipients come only from the operator-set escalation list, and the guest is never addressed. One caveat for honesty — the public=false on that note is enforced by the bridge jacket, not by pi_run.c itself.

5 · What it costs, and the deploy reality

This is pi_run.c — C99 in the metal substrate, running on a live cadence against real tickets. It is not a console change.

  • Change A is roughly 40 lines: a body-span extractor, a tolerant field read, earliest-match aliases. Provable offline against the real bodies before anything is deployed.
  • The deploy is the risk, not the code. The path is manual, undocumented, and targets live traffic. Unit 0 sits on the path every brand's traffic takes — a regression there breaks the pipeline that currently works.
  • The test must run against the live bodies, not hand-written fixtures. The prototype's fixtures passed while the real ticket #733 failed, precisely because the fixtures omitted the metadata the bug lived in. Any test for this must pull the real bridge response for 728 and 730–733 and assert on that.

Recommendation: do not deploy on demo day. Build it, prove it against all five live tickets, deploy after. The four dropped tickets are already unrecoverable; a fifth hour changes nothing, and a broken unit 0 in front of an audience changes a lot.

Unknowns

  • Whether the four dropped tickets should be manually replayed once the fix lands. They are outside every future sweep window, so nothing will pick them up on its own. A guest with a hair in their soup is still waiting.
  • Whether other brands will introduce further template variants — IT Support and Marketing are active with live support addresses and zero alerts today. The bug class is "any non-default brand."
  • Whether sweep errors should raise something. Today a unit-0 failure is silent by design (it is the "not ours" path), which is exactly why this went unnoticed for half a day.
  • Whether the illness path should treat guest-originated alerts differently — the guest is on the ticket, and the alert comment is public.

When to revisit

Immediately, if any template moves its free-text field above the labelled fields — that breaks the first-occurrence-wins invariant the in-body parse depends on. Immediately too if a fifth brand appears or a template changes — the fix is tolerant, not universal. When change B lands, revisit whether the follow-up-ticket shape should exist at all for guest-originated alerts. And whenever the deploy path stops being a manual scp, because the "don't deploy today" advice is entirely about that.
