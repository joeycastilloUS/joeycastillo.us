S13 first — because the answer is already in the file

A runbook's tags are its fingerprint — but the trace is not free.

You said "leverage our existing search capability, or something like that." The first half is real and better than expected — every runbook already declares the marks it leaves, so we never have to invent a way to identify its footprint:

mendo-nps-detractor-triage.si:38   set: gate.tag       = argus_nps_handled
mendo-nps-detractor-triage.si:65   set: escalation.tag = argus_illness_escalation

D2 makes the gate tag the thing that stops a second run. The escalation tag is declared one level down, in the plan (.si:65, serving D6–D8) — D7 itself never mentions a tag. That earns an asterisk on the fingerprint idea: the gate tag is demand-level truth, the escalation tag is plan-level, and the plan can change without any demand changing.

QuestionAnswer is a search for…
Every alert it claimed — set at the gate, before the illness check, so it includes escalated and aborted runs, not just delivered recoveriesgate.tag
The escalated subsetescalation.tag
Everything it touchedeither tag

The existing search cannot do it, and we should say so before anyone builds against the assumption. The corpus search is a fixed contract — /search /replay /similar /shape /spine (index.html:4674) — and it accepts q, limit, sort, dir, group. There is no tag parameter. It is full-text over a frozen snapshot, so tags a runbook applies at runtime are not in it at any price. A footprint button wired to it would return empty forever.

The receipt is in the intent file. D2 records that this exact approach was already tried here and pulled:

D2  … every later sweep reads that tag straight off the ticket (a direct
    read, not the lagging search index) and bows out. … (Restored
    2026-07-19 as a supportable tag claim — the old guest-search was
    over-broad + eventually-consistent and was withdrawn.)

The team learned that on 2026-07-19 and the file remembered it. That is a better argument for putting truth in the intent file than the free-footprint version would have been.

So S13 costs one small read path, and there are two honest ways to buy it: a bridge endpoint querying live Zendesk by tag (fast, but it inherits D2's eventual-consistency caveat — say so on screen), or staging tags into the next corpus rebuild and adding a tag facet to /search (consistent, but only as fresh as the last rebuild). Not free. Small, and worth it:

Footprint

See the tickets this runbook touched →
Needs the new read path above — the existing corpus search cannot answer this. Until that ships, this control does not appear at all.

Nobody designed a footprint feature — the runbook declared its own marks for a different reason, and the identity half fell out anyway. That is the real win. The retrieval half is ordinary work, and pretending otherwise is how a demo grows a button that goes nowhere.

S12 — generate a runbook from templates

Harder, and worth being precise about what "template" means here, because the console already has a considered position on it.

"Template" in Argus means a Zendesk macro. The Off-Script & Gaps tab replaced a passive macro list on purpose — the retro note is in the source (:4187-4192): a read-only inventory "earned nothing." What it does instead is find where agents hand-wrote a reply instead of using a template, cluster those into macro candidates, and hand you a drafted body. It is deliberately read-only: "Copy drafted macro only copies text; the operator creates it in Zendesk."

That gives S12 two possible sources, and they are not equally good:

SourceWhat you'd getVerdict
Existing Zendesk macrosA runbook whose words are a reply your team already sendsYes — this is what you asked for
Off-Script macro candidatesA runbook built from replies agents wrote because no macro existedBetter later — it turns a gap into automation, but it is a second step

What a macro can and cannot become

This is the honest core of S12. A macro is words plus an action. A runbook is demands plus words. The words map cleanly. The demands do not exist in a macro at all.

Runbook needsFrom a macro?
words — what we sayYes — the macro body, near-verbatim
Tags / priority / assignmentYes — macro actions map to set: values
When it firesNo — a macro is fired by a human choosing it
What it must never doNo — macros have no refusals
Safety demands (the illness floor)No — and this is the whole point

Design consequence: generation produces a draft runbook, deliberately incomplete, with the words filled in and the demands blank and marked as required. It cannot produce a runnable runbook, and the screen must say that plainly rather than implying one more click ships it.

This drafts the words. It cannot draft the rules — when it fires, and what it must never do, are yours to state. The draft will not run until they are.

Why this shape and not a wizard that "just makes it": the demands are the part that keeps a guest who says they got sick from receiving an automated coupon. A generator that invents them would be inventing your safety floor. It gets to write the words; you state the rules.

Naming — settled

Outside: Runbook. Inside: playbook, unchanged.

Operator decision, 2026-07-20. The earlier draft argued this backwards and the correction is worth stating plainly, because the split is the point:

WordWhy
The operator's surface — the tab, the docs, what a manager says out loudRunbookIt is the word an operations team already owns. They are not managing an engine concept; they are managing the procedure their shop runs on.
The runtime — pirun, the C99, PiPlaybookplaybookAlready correct and staying. pirun.h:5: "A .pi playbook is POLICY AS DATA." That is the engine describing what it holds, and no operator ever reads it.

This is not a compromise, it is the right shape. The internal word describes the artifact's nature — policy, as data, loaded and sealed. The external word describes its job — the book your shop runs by. They were never required to be the same word, and forcing them to be would have made one of the two lie.

Consequence for the rename: it touches documents and labels only. Zero C99 changes. The 35 playbook occurrences in the pirun sources stay exactly as they are — which is also why this is safe during a freeze: nothing that executes is being modified.

One collision still to resolve when the external rename fully lands: "runbook" already names a human deploy procedure in be/plans/2026-07-10-1640-runbook-airbyte-philz-deploy-fire-fable5.html. Two meanings, one word — worth a distinguishing prefix on one of them.

Unknowns

  • Whether S12 should read live macros from Zendesk or the sealed corpus. Live is truer; the corpus is already wired and read-only. Not decided.
  • Whether a generated draft is saved anywhere before its demands are written, or lives only on screen until complete. Leaning: on-screen only — an incomplete runbook in the library is a trap.
  • The gate tag is claimed before the illness check, so nearly everything the runbook examines carries it — including runs that escalated or aborted. "Touched" is therefore the honest word; "handled" would not be. Whether you also want the delivered-recovery subset as its own view is open.
  • Whether "touched" should include the follow-up tickets the recovery creates, not just the alert tickets it tagged.

When to revisit

S12 changes shape the moment a generated runbook is expected to run without a human writing demands — if that expectation ever appears, stop and re-read this section, because it is the safety floor being asked to generate itself. S13 changes the moment a runbook stops tagging what it touches; the footprint is free only while the tags are declared. The naming window closes the first time a customer uses the word in their own sentence.
