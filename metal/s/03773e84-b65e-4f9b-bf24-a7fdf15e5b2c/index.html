Two Purcius Send buttons

Testing only. Add two buttons to the Test Bench, next to the Gmail ↗ links, that fire a real email through our Purcius node + mesh into each arm's intake — so Arm B's in-box AI agent gets tripped on one click, no mail client.

Paired ~d — Opus + Fable, reconciled. Right-sized: the architecture is already chosen (Purcius node + mesh), so no relay/Choices ceremony.

1 · Need

The Test Bench already carries a ready NPS-detractor email, but sending it is manual — the Gmail ↗ / mail app ↗ links open a compose from your address and you hit send by hand. The card itself says a hands-off Send button "needs the server-side path." This is that path: one click → Purcius composes and sends a real inbound email, so we can re-run the Arm-B illness test (T1) repeatably instead of hand-typing every time.

2 · Raw user stories

As jc, I want a Send (Purcius) button on the Arm A and Arm B rows, so one click drops a real via:email ticket in that intake without opening Gmail.
As the illness-safety tester, I want a detractor / illness toggle on the send, so each click fires the exact T1 body and mints a fresh ticket — never re-threads onto the last one.

3 · Sourced solution

The DIA argus-email-send.pi/.si already specifies this exact lane (compose → mesh → egress node → SMTP to the recipient MX). Almost everything under it exists:

  • HAVE · comms/skill/mesh (store-and-forward), dns (MX resolve), security/skill/crypt/tls13.h → tls13_connect (client TLS 1.3, AES-256-GCM + X25519, openssl-proven — in main today), memory/store (idempotency), relay (running node)
  • HAVE · the Test Bench UI + the pre-filled detractor body (zTestGmail/zTestMailto, index.html ~7213)
  • NET-NEW · comms/skill/smtp — the one new part: reassemble → DKIM-sign (RSA/Ed25519) → MX-resolve → tls13_connect SMTP :25 deliver. Named for the transport we implement (literal-naming); reserve comms/skill/imap for a future receive lane.
  • NET-NEW · a bridge route POST /zendesk/guest-send, an illness body variant, and the egress node (below)

4 · Naming & shape

The two buttons land on the existing Arm A / Arm B rows of the "Test-support intake" card, right after the two links:

The wire, end to end:

button click
→ POST /zendesk/guest-send {to, subject, body, env} (daily-token gated)
→ route drops a compose-intent onto the mesh (240-byte frags, store-and-forward)
→ the Purcius egress node runs comms/skill/smtp: reassemble → DKIM-sign as argus.net.ai → dns MX-resolve the intake → tls13_connect SMTP :25 to Zendesk's MX
→ lands as a via_id=4 (email) ticket — the only kind that trips Arm B's AI agent

Correctness rules (from the reconcile):

  • Fresh ticket per click. msg.id = hash over (to, subject, body, per-click nonce); the nonce goes into the RFC Message-ID header. Zendesk threads on Message-ID — a stable one would append to the last ticket instead of minting a new one. The mesh-level dedupe on msg.id is only retransmit-safety.
  • Recipient allowlist, not a flag. /zendesk/guest-send hard-codes the two intake addresses as the only permitted to: — a stronger sandbox guard than an env check, three lines. jc fires each send.
  • From identity. Sends come From: one fixed @argus.net.ai test address (the DKIM/SPF domain). The requester on these tickets differs from the old Gmail tests — expected, not a bug.
  • Out of scope: receiving mail, multi-recipient, any production send.
⚠ The buttons are trivial; the send path is the real work. "Send via Purcius node + mesh" needs infra that does not exist yet: (1) the net-new comms/skill/email, (2) DNS auth on argus.net.ai (SPF + DKIM + DMARC TXT — MX not needed for send-only), and (3) an egress node that can send on port 25. GCP blocks :25 permanently — so the nodes Purcius runs on today (GCE) can never be the egress. That node must be a small non-GCP VPS (Hetzner/OVH) with a fixed IP and a PTR record (set at the provider, or Zendesk spam-buckets it). Under the no-relay constraint, that VPS is the floor — there is no smaller path.

4b · Coordination — shared substrate (consume, don't rebuild)

The infra session (webhost / TLS) flagged overlap. Reconciled against main — the honest picture for a send-only lane:

  • Our only real dependency is tls13_connect (client), which is in main today. We initiate the connection to Zendesk's MX; we never listen.
  • The server-side pieces are not ours. tls13_accept, the webhost accept-loop, and the p256 cert signer are all for a future receive lane (IMAP/SMTP listener). Send-only touches none of them — consuming them now would be scope creep into a lane nobody scheduled.
  • The P-256 "not constant-time until Phase 3b" gate does NOT block us. As a TLS client we present no certificate; key exchange is X25519, cipher AES-GCM, and DKIM signs RSA/Ed25519 — there is no P-256 private-key operation on the send path. The gate applies only to a future mail-server cert.
  • VERIFY One honest open item: confirm main's tls13_connect can verify an ECDSA-P-256 server cert (Zendesk's MX may present one). Verify ≠ sign — no timing gate — but if the client only chains RSA today, that's a functional gap to close, not a blocker on 3b.
⚠ One-home discrepancy (Rule 14 / one-project-one-org). The infra note cites security/transport/tls13.c, crypt/p256.c, and comms/skill/webhost — none exist in main or the visible branches as of 2026-07-26; that work is unpushed. Main's real TLS home is security/skill/crypt/, not a new security/transport/. We cite what's real in main and dep on nothing unverified; their pieces must land in the one canonical home before any receive-lane consumes them. Diff against the real tree before writing socket/TLS code.

5 · First Move

Ship the two buttons + the /zendesk/guest-send route now (they queue onto the mesh regardless). Then the one decisive move to a single delivered email:

  1. Provision one :25-capable VPS (non-GCP, fixed IP, PTR set) — the egress node. Shrink for proof #1: run the mesh endpoint + email skill on that same node (bridge → mesh frames → same-node egress). Still genuinely mesh; no multi-node choreography.
  2. Publish SPF + DKIM + DMARC TXT on argus.net.ai (Cloudflare); one SPF record only.
  3. Minimal C99 comms/skill/smtp: reassemble → DKIM-sign → dns MX → tls13_connect STARTTLS :25. Confirm tls13_connect verifies the MX's cert (ECDSA-P-256 or RSA) on the way up.
  4. Fire the Arm B illness button → verify a via_id=4 ticket appears (subject carries the nonce). Check GET /api/v2/suspended_tickets.json before declaring failure — a fresh IP will likely land mail #1 in the suspended queue. Suspended = delivery proven, trigger unproven; fix reputation and resend, don't recover-and-declare-victory.
  5. Bind route.egress in argus-email-send.pi to the node id — that's what earns the seal.
