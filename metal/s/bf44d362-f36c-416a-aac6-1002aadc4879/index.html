Paired inspection — driver Opus + three independent Fable5 navigator passes (audit / red-team / test-inventory), reconciled, no contradictions · project: argus + kastil-systems/nous · r952 · 2026-07-31

Verdict in three lines. (1) The pure-C crypto core is sound — Ed25519 rejects non-canonical S, constant-time compares, fail-closed RNG, correct MAC-before-sig order. Every real weakness is in the C# jacket, the browser gate, or the deployment plane. (2) A handful are exploitable today with no dormant door: the guessable daily data-key on prod writes (R0), unaudited crew self-escalation (R3), the directly-reachable Cloud Run URL (N1), and CORS *.pages.dev+credentialed cookies (N4). (3) Meta-critical: Argus CI runs zero tests — ~235 real security asserts exist but none gate a deploy, so the whole test suite is currently theater.

2. Findings — severity-ranked (R = prior lockdown inspection, N = new this audit)

CRITICAL — exploitable now or one misconfig away

R0 — Guessable daily Bearer on production WRITE endpoints. works today
zrawPass()="yyyymmdd~go" (index.html:4698) is the Authorization: Bearer for 5 services incl. writes: /zendesk/promo-claim :7391, /promo-release :7401, /zendesk/config-apply :8069, /cc-apply :8083, /vertex/correction :3464. Scheme is in committed comments (:3115,:5547). Exploit: compute today's string, POST prod Zendesk mutations with zero login. Fix: retire the daily key — prime-signed Ed25519 wire auth (the purcius-bridge-auth plan, already written), writes first.
R3 — Any crew session can rewrite the crew via POST /settings, and it is UNAUDITED. works with 1 session
A member session is an alternative credential on every gated route (Program.cs:88-90); POST /settings (:690-703) is proxied (_worker.js:11) with no extra authorization and no AUDIT line. Exploit: one allowed login adds @attacker.com to argus_crew_v1 / removes the operator — invisibly. Blue-team's #1 blind spot. Fix: restrict crew-mutating settings to a key: (warrant) session + emit an AUDIT line on every settings write.
N1 — Cloud Run is directly reachable, bypassing the edge. works today
_worker.js:10 hardcodes the public meraki-bridge-…-uw.a.run.app. CORS constrains only browsers. Exploit: a non-browser client hits run.app directly with the daily key (R0) or the empty-token path (R2), bypassing any Cloudflare edge/WAF. Fix: Cloud Run ingress = internal + IAP/edge-only, or an edge-injected shared secret the run.app URL requires.
N4 / CORS — *.pages.dev + AllowCredentials + SameSite=None = credentialed cross-origin. works while victim logged in driver-verified
CORS predicate allows any *.pages.dev host (plus argus.com.ai / joeycastillo.us / the-it-center.com) with .AllowCredentials() (Program.cs:22-28); the cookie is SameSite=None (:264,398). Exploit: stand up a free attacker.pages.dev; a logged-in victim who visits it triggers credentialed fetches to the bridge riding their cookie — read, write, even POST /settings. Fix: drop .pages.dev from the allow-list (pin the exact preview hosts you use), add a CSRF double-submit token on all POST, move to SameSite=Lax with a same-origin session front.
R2 — Empty BRIDGE_TOKEN disables auth for the whole data plane. works if misdeployed
Program.cs:83: || string.IsNullOrEmpty(bridgeToken) → next(). A missing/unset secret opens every /meraki/* incl. writes, silently — no "gate disabled" alert. Fix: unset BRIDGE_TOKEN AND unset AUTH_SESSION_KEY ⇒ 503 all gated routes (fail closed), CRITICAL-log at boot.
CI-GAP — Argus CI runs zero tests. meta-critical
deploy-argus.yml is deploy-only — it runs no web suites and no bridge-tests. ~235 real security asserts exist but execute only on dev boxes / inside the C Docker build. Every "fail-closed" claim below is an untested comment until a test job gates the deploy. Fix: add a CI test job (node web suites + dotnet run --project bridge-tests) that blocks deploy red.

3. Design challenges (architectural, not line-level)

  1. Identity lives in the wrong house. 10/35 meraki-bridge routes are identity/ops; every auth change redeploys the Meraki data routes over a known CI fork. Extract to argus-identity — after logins are green (see the 2026-07-25 inspect).
  2. Two trust models bolted together. A titanium Ed25519+warrant front door beside a yyyymmdd~go screen door on the loading dock. The weakest door defines the posture.
  3. No revocation anywhere. Stateless HMAC sessions; Firestore session/member docs are write-only decoration. Crew changes and de-provisioning don't take effect for ≤12h; the only "log everyone out" is key rotation.
  4. Fail-open defaults contradict the stated "fail-closed everywhere." R1 (client) + R2 (server) open on absence/failure; the key door and Ops routes correctly fail closed — the pattern exists, it just isn't applied to the two oldest gates.
  5. OVERLORD_EMAIL vs mendo identity mismatch. The key door asserts overlord@joeycastillo.us; the intended crew is jcastillo@mendocinofarms.com. Decide what the key door is.
  6. Thin OIDC trust as a permanent state. "v2 hardening" is the live path. Safe only because the exchange is server-side today; anything that fronts/caches token exchange makes R4 exploitable.
  7. Cross-repo / edge-plane trust. Bridge directly reachable (N1); blind proxy (N5); Host-derived redirect (N6); key-ceremony page without SRI/signed-deploy proof (N7). The air-gap story is only as strong as the integrity of the page that asserts it.
  8. Multi-instance statelessness the core assumes isn't guaranteed by the host. The pure-C skill is stateless + monotonic-clock; Cloud Run's multi-instance, per-uptime reality breaks both the TTL and the per-instance burn table (N2). Correct in isolation, violated by the substrate.

  1. Recon (home): diff shipped index.html for endpoints/bases/zrawPass; hit /version, /auth/key/status, /ops/doors (posture booleans).
