Dynamic membership from signed DNS TXT · closed output schema · staleness lives in the app layer · companion to ~d v2

THE LAW (step 4) — why dynamic input is still leak-proof

Membership is dynamic; the output schema is closed. Discovered fields enter named local variables, never a forwardable blob. addr and pubkey are consumed only as a probe target and a verify key — no output field is ever assigned from them. A new attribute requires a code change to the projection, never a discovered field auto-appearing. String fields (region, transport) are validated against a word-allowlist before emit — a bad node can lie in a number but can’t smuggle an address through one.

Sense on / off (green + red path)

  • On: node boots → announces signed TXT → within TTL+requery it’s discovered, verified, probed → appears. No recompile.
  • Off: node stops announcing → TTL 300 expires → drops from discovery → recently_departed[], then gone.
  • never-seen = absent · went-away = present, reachable:false · departed = in recently_departed[].

Two upstream must-solves (yellow flags)

  • Relay re-announce. Relays announce _relay at boot only, TTL 300 → a live relay would flap out. Add dns_announce_self() to periodic_refresh() first (Rule 11, flow up).
  • Probe protocol. Confirm relays serve plain HTTP /status on :8080 in-VPC (vs wire-TLS) — one peer curl (Rule 13).
