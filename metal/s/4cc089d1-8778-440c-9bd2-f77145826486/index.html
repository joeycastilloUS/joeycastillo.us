~d — pi_run firmware tracelog

A firmware trace of a .pi as biRT executes it — the logic-analyzer view of the punch card, cycle by cycle, hop by hop. Every claim below was verified against the source: pirun.c (548 lines), pirun.h (138), pirun_host.c (95), store.h (171), and the 13-unit card mendo-app-survey-autoresponse.pi (v6). No guessing.

1 · Need

The trace already exists. Nobody can see it. Every state change in a pirun run is written to the IDS ledger as a JSON event on run:<id>:trace:<seq> (trace_ev, pirun.c 65–83), and pirun_trace_json (529–548) already serves it with a since_seq cursor. But the only view today is the P1 host's printf of RUN codes — 14 lines of step N → RUNNING. The in: reads, the out: writes, the gate decisions, the hop each skill takes through the layers — all recorded, none rendered.

pirun is firmware and the .pi is its punch card: one pirun_advance() call is one instruction cycle — FETCH (cursor→unit) · DECODE (find_skill) · READ (in: keys ← ledger) · EXECUTE (SkillFn) · WRITE (out: keys → ledger) · GATE · ADVANCE. The ledger is the memory bus; every operand fetch and result store is DMA on run:<id>* subjects. What's missing is the logic analyzer: the view that shows each cycle with its operands, its bus traffic, and the layer it hopped through. That view is the pi_run tracelog.

2 · Raw User Stories

  • "I want fable5 ~d a pi_run tracelog now."
  • "Essentially a firmware trace as the pi is executed."
  • "I want a complete diagram of the code layers and hops.. break down precisely read the code no guessing."

Decoded: (1) as operator, when a run walks the card I want to see every cycle — which unit, which skill, what it read, what it wrote, where it hopped — so I can trust the run without re-reading C. (2) As operator, I want the layers-and-hops map so a trace line is instantly locatable in the architecture. (3) As Argus, I want the trace to be the audit surface — "we are firmware / we are the motherboard" made visible.

Code-verified corrections to the brief

  • The event vocabulary is 19, not 13. Besides start, run, out, done, slice-end, gated, pass, exit, held, step-hold, fail, fail-hold, fail-continue, pirun_verb (pirun.c 441–527) emits verb-hold, verb-abort, verb-continue, verb-rerun, verb-add, verb-edit. Operator verbs are trace events too — the tracelog must render the operator lane, not just the machine lane.
  • Trace timestamps are whole unix seconds ((long)time(NULL), pirun.c 80). Per-cycle elapsed-ms cannot be derived from today's events; it is a genuine ADD field, not a derive.
  • A flow run of the 13-unit card emits exactly 44 events: 1 start + 10 non-exit units × 3 (run/out/done) + 3 exit-gate units × 4 (run/out/pass/done) + 1 final done "all units walked" from the 14th advance call (cursor ≥ n_units, pirun.c 278–281).
  • Linking detail for the view tool: find_skill references extern PIRUN_SKILLS[], so any binary linking pirun.c — even a read-only trace viewer — must define the table. The viewer defines const SkillEntry PIRUN_SKILLS[] = {{NULL,NULL}};.
  • Minor: the in:-key resolve reads into char v[8] (pirun.c 308) — it is a presence check, values are re-read by the skill. The trace's run event detail is the slot if set, else the skill (line 337–338).

4 · Naming

Literal names for what things are:

  • pi_run tracelog — the artifact: the rendered firmware trace of one run.
  • pirun_trace — the view tool (C99). File: src/sdk/nous/action/skill/pirun/pirun_trace.c, next to the executor it renders.
  • cycle — one pirun_advance() call. bus / DMA — the IDS ledger and its ids_* ops. hop — a layer crossing (L2→L3→L4→L5, or L4→L6). No cute names, no "flight recorder", no "black box".

5.3 Anatomy of one tracelog line

The renderer joins three sources per line: the trace event (emitted), the card (derived via pirun_load), and a static skill→hop map (derived). Three fields are genuinely absent today and are the only candidates to ADD.

FieldSourceStatus
seq, ts, unit, ev, detailthe trace event JSON (trace_ev)emitted today
cycle # (= step index), skill, slot, gate, fail, in: keys, out: keysjoin unit name → PiPlaybook (pirun_load of the same card)derived

5.5 Choices (the real forks)

  • Derive in the renderer vs add fields to trace_ev → derive first. Cycle #, skill/slot/gate, in/out keys, hop, RUN code, and cost are all reconstructable from event + card + data plane. Deriving keeps trace_ev's emit minimal (it runs inside every cycle) and ships the tracelog with zero executor change. The only field that cannot be derived is elapsed-ms (ts is whole seconds) — when the timing question actually gets asked, add one "ms" field to the trace_ev JSON (additive; old events render with ms=?). Not in the First Move.
  • Live-tail vs post-run replay → both, replay first. pirun_trace_json(since_seq, &next_seq) is already a tail cursor. The First Move ships replay (read seq 0→end, print); a -f follow flag is the same call in a poll loop — the caller's poll loop is the clock, same as the executor itself.

6 · First Move

pirun_trace.c — a C99 view tool beside the executor: src/sdk/nous/action/skill/pirun/pirun_trace.c. Reads a real run's ledger and prints the firmware trace above. Builds on the P1 host that already runs; touches no executor code.

  1. pirun_trace <card.pi> <store.ids> <run_id> [-f] — pirun_load the card (the join), ids_open the store, pirun_trace_json from seq 0.
  2. Per event: parse the flat JSON (the json_pair walker pattern in pirun.c 411–439 is the prior art), join unit→PiPlaybook for cycle/skill/slot/gate/in/out, map skill→hop tag, map ev→RUN code, enrich out-values and cost via pirun_get. Print one cycle block per the anatomy in 5.4.
  3. Define const SkillEntry PIRUN_SKILLS[] = {{NULL,NULL}}; in the tool — required to link pirun.c's extern (find_skill), never called by a viewer.
  4. Build mirrors pirun_host.c's line: gcc -std=c99 -O2 -I../../memory/skill/store pirun.c pirun_trace.c store.c index.c hash.c scope.c journal.c -o pirun_trace -lm.
  5. Prove: run pirun_host on the mendo card, then pirun_trace against the same store + run_id — expect the 44-event trace, byte-stable across two runs (the determinism contract, now visible).

Later slices (not now): the -f live tail; an HTML tracelog artifact per run (metal-live pattern); the "ms" field in trace_ev; the mesh-prime host serving the same trace over the wire.
