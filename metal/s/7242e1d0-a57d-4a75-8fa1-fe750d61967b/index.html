Correction 1 — v1 put the button where the server can never appear

/meraki/wireless drops every wired client by construction — bridge/Program.cs:989-991: 
// A client with a switch port is WIRED -- not on Wi-Fi, even if it carries a
// residual ssid. Don't bucket it as Wi-Fi.
if (!string.IsNullOrEmpty(c.Switchport)) continue;
So a button in the SSIDs pane would answer for iPads and never once for the machine actually asked about. The kitchen server appears in exactly one place: the portmap client cell (Program.cs:580-583, rendered by the switch table at index.html:1531-1581).

Position: the port row is the primary surface. Keep the SSID-row button too — same endpoint, near-zero marginal cost, and it serves Windows Wi-Fi clients. Both tables live in the same Network tab, so "Network SSIDs view" still gets you there.

Correction 2 — the join key breaks for a wired host

v1 joined our client MAC to an SM device with sm/devices?wifiMacs=<mac>. The navigator verified the complete filter set against Meraki's published docs: wifiMacs, serials, ids, uuids, systemTypes, scope.

There is no ethernet-MAC filter and no IP filter. A server with no Wi-Fi radio has no wifiMac to match, and serials means the SM-reported hardware serial, which a Meraki client row does not carry. For a wired host there is no deterministic server-side join at all.

The fix: fetch the SM network's device list unfiltered — one page covers any restaurant fleet — with fields=ip,name,lastConnected,hasDesktopAgent, and match client-side on IP. A kitchen system server is static-IP by definition, and our roster op-targets already encode named devices at fixed IPs (index.html:1119). Name-match is corroborating evidence, never the key.

GET /meraki/host-firewall?network=&mac=&ip=
  1. try wifiMacs=<mac>        -> wireless case, unchanged from v1
  2. else fetch list, match ip -> wired case
  -> { state, fireWallName, lastConnected, matchedBy:"wifiMac"|"ip" }

matchedBy is not decoration. An IP join is honest-but-heuristic, so the UI must say how it knows — same dashed-border law Drift already ships: solid = evidenced, dashed = inferred.

Also correcting v1: it listed fwName in the sm/devices?fields= set as if it meant firewall name. That is unverified and may mean firmware name. The verified firewall field is securityCenters.fireWallName. Treat fwName as decoration until proven. Navigator's catch.

Access-policy naming

accessPolicyType is a documented enum: Open · Custom access policy · MAC allow list · Sticky MAC allow list. Three of the four are self-naming and cover the screenshot exactly (Open).

Only Custom access policy needs more — the meaningful name lives in GET /networks/{net}/switch/accessPolicies, keyed by accessPolicyNumber. Position: project the number, render Custom access policy #3, and do not fetch the policy list at all. A kitchen access port on a template-stamped restaurant network is Open or a MAC list; building name resolution for a policy type we have never observed in this org is speculative plumbing. When a #N actually renders in production, that is the signal to add the one-call resolve (Rule 7).

Drift interaction

Once projected, accessPolicyType + accessPolicyNumber join the switchports fingerprint. They are intended config, human-changed, low-churn — exactly fingerprint material, and nowhere near the excluded observed-state class.

What that catches that we miss today: the kitchen port silently flipping Sticky MAC allow list → Open — the lockdown quietly removed — or access → trunk, a VLAN-hopping vector on the highest-value port in the store. Today SW-PORTSEC only counts policies network-wide at audit time. Drift would name the port and the moment.

Read-only guardrails — and the blast radius

The temptation here is structural, not hypothetical. The new ACCESS POLICY cell will sit directly beside VLAN cells that already carry write pencils (vlanedit, index.html:1571-1572), backed by a live write path: POST /meraki/port-vlan (Program.cs:859) can re-VLAN this exact port today when the set-vlan lab feature is on. woprGated intercepts it and RequireWritable gates server-side — but the machinery exists, and it is one "just add a policy dropdown" away from writable.

Blast radius, named so nobody has to learn it the hard way: re-VLANing or policy-flipping the kitchen server's port takes POS and KDS down mid-service. And a MAC-allow-list write that omits the server's own MAC is a lockout that survives a reboot.

Guardrails held:

  • TYPE and ACCESS POLICY cells render with no data-target, no button class — nothing the delegated click handlers can find.
  • No new PUT fields. port-vlan's rollback switch (Program.cs:842-849) stays ignorant of type and accessPolicy*, so a future write attempt has no rollback path and fails loudly in review rather than quietly in production.
  • Read-only is not a phase here. For this port it is the posture.
