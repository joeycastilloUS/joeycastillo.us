Ship pirun to the mesh

~d + ~p + ~e · seat the .pi executor in the running NOUS prime, once — so the mesh reads and executes ANY .pi card against the ~45 skills already seated there · this is a deploy to a LIVE production mesh · design only, nothing touched yet

~dDESIGN

Need

The prime already carries ~45 seated skills in g_action_table. The .pi cards already exist (recover-guest.pi v4 parses clean: 13 units, rc=0). The ONE gap: nothing in the mesh can read a card. pirun — the executor — is vendored in metal only, not in the canonical mesh source. Ship it once and the doctrine holds forever after: we never ship skills again; we ship .pi. Every future card runs in the mesh with the card waiting out there ahead of us.

Raw User Stories

  • "The point is to NEVER ship skills — 45 already exist and run in the prime. We ship .pi."
  • "~b do it ship pi-run to the mesh"
  • "~d~p~e again with fable5."

Sourced Solution

Nothing invented — every part exists and gets wired:

  • pirun (C:\metal\src\sdk\nous\action\skill\pirun\pirun.c/.h) — pure C99, libc only. Step runtime: walks one unit per pirun_advance(), all state in the IDS run ledger (crash-safe, holds nothing between calls), gates auto/hold/exit/fire honored, fail abort/hold/continue honored. Parse-verified against recover-guest.pi v4.
  • The prime's g_action_table — the ~45 already-seated skills (understand, reason, restate, http, wire, vault, fanout, judge, store, ingest, conditions, …). This is the MUSCLE. pirun is only the READER.
  • nous IDS — already inside the prime; pirun's ledger (run:<id> subjects) is just triples in the store the prime already runs.
  • MESH_DEPLOY_AND_VERIFY.md (C:\a-d-d\nous\, canonical kastil-systems/a-d-d/nous) — the operational truth: on-node build via intelligence/tool/prime-server/startup.sh, build tree /tmp/nous, live binary /opt/nous/prime (systemd prime.service), full-source tar sync (msys /c/... paths), backup-first, restart + MainPID check.
  • The relay (relay.3-nous.net, builds off-node) — OUT of scope unless the chosen ingest path requires its /ingest HTTP route.

Naming

Literal, no themes. The executor stays pirun. The one new file is the adapter: pirun_skills_prime.c — it defines PIRUN_SKILLS[] as thin shims that resolve each unit's skill name against g_action_table and dispatch. The prime-side verbs are named for what they do: pi.seal (accept + store a sealed card), pi.start (create a run), pi.advance (the poll clock), pi.status / pi.trace (read the run). Exact spelling bends to the prime's existing verb convention once its real source is read (P1/P2).

  • pirun is additive. No existing skill is touched; no new skills are written. A unit whose skill isn't resolvable ends the run as a clean slice-end — honest by design.
  • The shim honors pirun's contract (SkillFn: read in: via pirun_get, dispatch, write out: via pirun_put, rc 0/nonzero). One generic shim + a name map beats 45 hand-written entries.
  • The ingest→run path is UNDESIGNED — candidate lanes: (a) a new prime HTTP handler on :8080, (b) the relay's /ingest route delegating a wire verb, (c) a prime wire verb. The decision is LOCKED in P2 after the prime's real source is read — choosing before seeing g_action_table's dispatch shape would be a guess.
  • Fire stays disarmed. pirun's fire gate stops AWAIT_FIRE in the mesh exactly as it does locally. Prod arming is jc's, not this ship's.

First Move

SSH the prime node (…us-west4…las-vegas) and read what's actually there: ls /tmp/nous, find g_action_table and startup.sh's compile list. Everything downstream keys off that one look.

Escape Routes (live prod mesh — reversal is mandatory)

  • The restore — cp -a /opt/nous/prime /opt/nous/prime.bak BEFORE install; reversal is cp -a .bak back + systemctl restart prime + MainPID check. Total exposure window is one restart.
  • Build-failure safety — startup.sh is set -e-gated: a bad compile never touches the live binary. The new binary also boots standalone (loads store + roster) as a pre-restart sanity check.
  • Additive surface — pirun files + handlers only; zero edits to seated skills. Worst case with no .pi submitted: the prime behaves exactly as today.
  • Relay untouched — unless P2 picks lane (b), the relay (currently hung per the deploy doc) is not on this ship's path at all.

~pPLAN

Intent

Seat pirun in the canonical prime — once — so a sealed .pi can reach the prime, start a run, and advance against the seated skills; prove it with recover-guest.pi v4 walking in the mesh to its honest stop (slice-end, hold, or AWAIT_FIRE). After this ship, shipping a new capability = writing a card, never code.

Scope

  • In: locate prime source; prove node access; pirun + shim + ingest/start/advance/status handlers into the canonical tree; on-node build + install + restart; one verified in-mesh run.
  • Out: new skills (hard NO — the point), relay changes (unless P2's lane requires its /ingest), prod arming of any fire gate, Zendesk writes, the host trigger plumbing (webhook/sweep — that's the recover-guest ship, not this one).

Approach

Preflight resolves the three honest unknowns BEFORE any code moves (source location, node access, ingest path). Then one additive integration, one full-source sync, one backup-gated restart, one same-plane proof run. Rule 13 governs every verify: same plane (on-node), right protocol (:8080 HTTP vs :8443 wire — a curl 000 on a wire port is NOT down), process + journalctl + uptime, DNS names not guessed IPs, cause named with evidence or "unknown."

Unknowns

  • Where the prime source truly lives — /tmp/nous on the node is the best lead but is documented as a stale partial snapshot; the authoritative tree may be elsewhere. P1 answers it.
  • Node access — wrong project or missing IAM is a real possibility; it is THE gate.
  • Skill-name parity — the card says zread / claim_code / vertex_panel / corpus_match / reply_send; the prime's table may not carry those names (bridge-side skills). Expected and fine: slice-end is the honest answer — but P2 must confirm which of the card's 8 skill names actually resolve, so P5's expected stop is predicted BEFORE the run.
  • The advance clock — whether the prime has a natural poll loop to host pirun_advance() or needs a minimal timer. P2 decides from the real source.
  • PIRUN_UNITS_MAX=32 / key caps — fine for recover-guest (13 units); a future giant card may hit the caps. Not this ship's problem; noted for the revisit trigger.

When To Revisit

  • P1 fails to reach the node → this plan pauses; the deliverable becomes the access blocker (project/IAM), not a workaround.
  • P2 discovers the prime's dispatch shape can't back the generic shim (e.g. skills aren't name-addressable) → v2 of this design before P3.
  • The first REAL card run (recover-guest end-to-end with bridge skills) → that's the next ship, and it will teach us what the ingest lane got wrong.
  • A card exceeds 32 units / key caps, or two cards need to run concurrently → pirun v2 sizing pass.
