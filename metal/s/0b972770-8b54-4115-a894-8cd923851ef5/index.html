The design in one line. A Baseline per network — the blessed config, stored as canonical JSON plus a hash — swept on a cheap change-feed-gated tick inside meraki-bridge, diffed against live, surfaced as a Drift tab of before→after items you empty by clicking Accept, which re-blesses. Read-only to Meraki, deterministic, no model, $0 per cycle.

Both passes independently disagreed with one word in the ask — see §0.

0. One disagreement with the ask, surfaced before anything else

You said: "I want to detect drift when any network changes."

Taken literally, "any change" includes what the Network tab shows in its right-hand columns — STATUS, IP ADDRESS, MAC ADDRESS, LAST SEEN. Those are observed state. Ports connect and disconnect, DHCP leases rotate, laptops roam, PoE draw wobbles. On a 24-hour client window across five restaurant networks that is a firehose, and a drift list that cries every hour is a drift list you stop reading by Thursday.

Both the driver and the navigator reached this conclusion independently, without coordinating. The recommendation is to scope Drift to intended configuration — VLAN, allowed VLANs, PoE enable, port enable, port name, device name, SSID name/enable, template binding, firewall rules — and leave observed state to Watch, which already owns exactly that and is already live.

This also draws a clean boundary: Watch answers "is it up?" Drift answers "is it the same?" Two verbs, two tabs, no overlap.

If you do want state-change alerting too, that's a Watch threshold item, not a Drift item — say the word and it gets boarded there.

1. Need

Five production restaurant networks, all bound to one firewall template, and nothing in the system remembers what they looked like yesterday. Argus can already see the live fabric; it cannot compare. Meraki keeps a change ledger, but that ledger provably misses roughly one config change in four or five, carries no state, and never records presence changes at all — a device appearing, a MAC moving. The audit checks posture against policy at a point in time; the Watch rail checks live metrics against thresholds. Neither remembers.

The need is memory: a blessed prior state per network, a cheap periodic compare, and a one-click "yes, that was me" that moves the blessing forward. The product is a short list of unaccepted changes that a human can empty.

2. Raw user stories

As the operator, I want to know when a switch port's VLAN, name, enabled state, or allowed-VLAN list changes on any of my five networks, so a mis-patched POS port is caught before the store calls me.
As the operator, I want to see before→after for the exact field that changed, so I'm not eyeballing two Meraki screens side by side.
As the operator, I want to click Accept when the change was mine, so the alarm stops and the new state becomes the blessed one.
As the operator, I want to know whether the change came through the API or someone clicking in the Meraki dashboard, so I know who to ask.
As the operator, I want drift caught even when Meraki's change log missed it, because it provably misses one in four or five.
As the operator, I want a template change caught once at the template, not as five identical alarms on five networks.
As the operator, I want this to cost $0 per cycle and involve no model, because Watch already proved that's possible.

5. Shape

Where the engine lives: inside meraki-bridge

Not a new argus-drift service (what DR1 says). Not the gcp-bridge Watch rail.

The bridge already holds the Meraki API key, the Firestore binding, the typed records — including SwitchPort.Enabled, which /meraki/portmap drops at Program.cs:577 — and the audit's raw-fetch helpers. It is the one place Meraki rate-limit budget can be accounted. A separate service duplicates the org key (secret sprawl) and turns every sweep into HTTP hops through the very service that would have done the work. The gcp-bridge rail is out because its source is unreadable from this box; coupling to it would be coupling blind.

This does not contradict one-service-per-source — it obeys it. Drift over Meraki is Meraki functionality, so it belongs in the Meraki jacket. IDENTITY-EXTRACT wants to remove non-Meraki things (auth, ops) from meraki-bridge; adding a Meraki capability is the architecture working, not eroding. And when drift later spans other sources, the right topology is drift-per-source inside each jacket, not one central drift service. That is why DR1's argus-drift skeleton was the wrong cut, and why it sat unbuilt for seven weeks.

Parts

  1. Fingerprint builder — new file bridge/Drift.cs. Per subject, fetch and canonicalize: 
    net          name, configTemplateId
devices      [{serial, model, name, mac}]            sorted by serial
switchports  per switch: [{portId, name, enabled, type,
                           vlan, allowedVlans, poeEnabled}]
             sorted numerically by portId
             -- read from SwitchPortsAsync (HAS enabled),
                NEVER from portmap (drops it)
ssids        [{number, name, enabled}]               sorted by number
l3           full appliance/firewall/l3FirewallRules array,
             ORDER-PRESERVING, full content
    Canonical form: stable key order, nulls dropped, sorted where order is non-semantic, canonVer:1 stamped into every document. sha256 per section, plus a composite.
  2. Excluded from the fingerprint — this is the alert-fatigue answer: port status, poeDraw, clients[], lastSeen, uplink state. All observed, none intended. They stay history-only.
  3. Change-feed gate — one /meraki/changes call per subject per tick (networkId filter, timespan since drift_cursor.lastTs). Zero entries and last full sweep < 24h ago → skip. Entries or floor exceeded → full sweep + hash compare. This is cadence's ChangeGate in spirit, and it is what makes the tick nearly free.
  4. Diff engine — per section: hashes equal → clean. Else structural diff of the normalized JSON → [{path, before, after}], appended to drift_events, drift_state flipped with Watch's flip-only changedAt.
  5. Attribution — only when drift is found, one /meraki/apirequests cross-reference at the change timestamp ±60s → via: api | dashboard | unknown. One extra call, never on a clean sweep. Worth v1 because "who did this" is always the second question.
  6. Routes in meraki-bridge: 
    POST /drift/run      key-authed tick, optional ?network=
GET  /drift/state    open, console polls (Watch precedent)
GET  /drift/events?network=
POST /drift/accept   session-authed; writes FIRESTORE ONLY, never Meraki
    Baseline auto-locks on the first clean sweep — the 2026-06-10 locked decision, kept.
  7. Firestore — drift_baseline/{subjectId}, drift_state/{subjectId}, drift_events/{subjectId}/events, drift_cursor/{subjectId}. subjectId is a networkId or a configTemplateId.
  8. Tick — Cloud Scheduler */15 → POST /drift/run. Fifteen minutes, not Watch's five: config-drift latency is bounded by the feed anyway, and 15min × (5 networks + 1 template) × 1 gate call ≈ 576 calls/day — noise against Meraki's org budget even before headroom is measured.
  9. Surface — a new Drift tab in APPS.meraki.tabs, copying the Watch tab shape (45s poll of /drift/state, 15-minute staleness banner, per-network verdict, expandable before→after, Accept button). Plus a drift badge on the Network tab's per-network header — that's 3 pts of glue, after the tab exists.
  10. The template is a first-class subject. "1 PRODUCTION - Global Firewall MX67 MX64" gets its own baseline. A template change ripples to all five networks; catching it once at the source beats five correlated alarms. Navigator's idea — the driver's design missed it entirely.

Drift vs the audit

Orthogonal axes. The audit's OVR-* compares network vs template — point-in-time posture. Drift compares now vs baseline — continuity. Keep them separate. Fingerprinting the full, order-preserving L3 rule array makes OVR-L3's count-only check obsolete in practice, but don't touch audit code in v1.

Out of scope

Any Meraki write. Alert channels (Slack/email — after the tab exists). Wireless auth-mode fields. Non-Mendo orgs. A C99 differ. Sovereign-IDS storage.

6. First Move

Add POST /drift/run?network=<id> and GET /drift/state to meraki-bridge — switchports section only, one network (023-Sacramento). Sweep → canonicalize → sha256 → write drift_baseline/L_x + drift_state/L_x → deploy.

Proof: a third party hits the deployed Cloud Run /drift/state and sees {network, section:"switchports", hash, lockedAt, status:"clean"} — externally verifiable per Rule 10. Then flip one lab port's name in Meraki and watch status go to drift on the next run, with the before→after in drift_events.

That one route pair exercises the entire load-bearing loop — fetch → canon → hash → Firestore → open read — and nothing else.

7. Choices + consequences

  1. Engine in meraki-bridge / new argus-drift service / Watch rail. → meraki-bridge. 2nd-order: the bridge grows another responsibility and it is already carrying audit, portmap, and action plans. 3rd-order: when drift spans other sources, drift-per-source in each jacket is the correct topology anyway — which is precisely why DR1's central service was the wrong cut.
  2. Config-only fingerprint / literal "any change." → config-only. 2nd-order: a change the operator wanted to see reflected in state is still caught, because enabled is config. 3rd-order: if he genuinely wants state alerting, Watch is its home. Surfaced in §0.
  3. 15-min gated tick + 24h re-hash floor / 5-min full sweep. → gated. 2nd-order: worst-case latency for an unlogged change is 24h — acceptable, because the logged 75-80% land within 15 minutes and the floor is a knob in a drift_policy doc.
  4. Diff logic in the C# jacket / C99 now. → jacket for v1, flagged honestly. Canonicalization is Meraki-shape work and jacket-legitimate; a generic differ is "code we own" and belongs in C99 eventually. Storing normalized JSON and not just hashes means a future C99 differ can replay history without re-sweeping. Navigator raised this tension; the driver hadn't.

8. Escape routes

  • Engine placement → routes are namespaced /drift/* and the collections are self-contained. Lifting to a standalone service later is a redeploy plus a scheduler retarget, zero data migration. Reversible.
  • Accept granularity → finer granularity is additive; the baseline stores full normalized JSON, so a field-merge is a new code path with no schema change. Reversible.
  • Tick and floor → a cron field and a policy doc. Trivially reversible.
  • ⚠ Canonicalization rules — semi-irreversible. Changing the canonical form invalidates every stored hash and screams false drift fleet-wide. Mitigation baked in from day one: canonVer in every document; a version bump triggers a silent re-baseline, never a drift verdict. This is the one choice that must be close to right before the first baseline locks. Navigator's catch — the sharpest risk in the design, and the driver's pass had no answer for it.
  • ⚠ Firestore 1MB document limit. A large network's switchports JSON in one document courts it. Five small networks are safe today; if a subject ever trips it, sections split into a subcollection — a schema change with migration. Flagged, not solved. Navigator's catch.

⚠ ONE SPLIT UNRESOLVED — operator's call.

Accept granularity.

Navigator: per-section. Accept blesses the whole switchports section at once. Simpler, matches binary severity, and is mitigated by re-sweeping live at click time so you see exactly what you're about to bless — plus the drift_events ledger is append-only, so nothing is ever lost.

Driver: per-entity (per port, per device). Accepting port 7's VLAN change should not silently bless port 12's change that arrived in the same window. The navigator's own consequence analysis concedes this exact hole and calls the live re-sweep a mitigation rather than a fix.

Driver's recommendation: per-entity. It is one extra key in the diff loop, it makes each drift item independently acceptable, and it removes the only footgun in an otherwise fail-safe design. Navigator owns the reconcile verdict per Rule 1 and picked per-section — so this does not resolve silently. Your call. Either way NDD4 is where it lands, and §8 confirms the choice is reversible.
