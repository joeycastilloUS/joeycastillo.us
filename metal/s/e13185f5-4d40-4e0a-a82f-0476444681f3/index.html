Board Liveness — Green / Amber / Red

~d · argus · Konductor Rollout Board · fixes the regression from cf4a828 (2026-09-03)

1. The need

Operator: “why is this not updating.. these sites are done being upgraded switch wise” — the board says a store is dead when it is merely closed.

Technical: since cf4a828, st='live' at :1147 requires Meraki client Online, which is a ≤2-minute traffic flag. A present-but-quiet Konductor device (measured lastSeen 34–44 min at a closed store) falls to notlive, so unacc climbs, solid goes false, and the quad reads 1/12 live · NOT SOLID.

2. Raw user stories

  • At 1am, across the room, I can tell a closed store from a broken store without reading a word.
  • A device someone unplugged, or that hung, still turns red — inside an hour or two, not never.
  • A device that has never checked in is never green; the board says gap, not guess.
  • The number in the corner means “devices accounted for”, and Solid means “nothing is wrong”.

  • clientCount remains unread.

The one thing most likely to make this wrong in a week

IDLE_MAX_MIN=90 is measured on one night. It is validated on the present side — 99 of 119 fleet records sit at 15–60 min and zero exceed 60, so 90 carries 30 minutes of headroom. It is not validated on the dropped side: there is no genuinely-dropped Konductor device in tonight’s data to test against. The mechanism is confirmed — Meraki queries clients with timespan=86400 and legacy records were observed ageing to 292 min rather than vanishing — but the threshold itself is untested against a real drop.

A device class with a longer quiet gap (a printer with no keepalive, a long DHCP lease) will flip red at 3am and look like a drop. The “last seen” line on amber rows exists so that gets tuned with evidence.

Second-order: Date.now() minus a cached portmap’s lastSeen includes cache age, which only pushes toward red — conservative, but a stale bridge read will look like a site going quiet.
