Design — ai-metal.net as a Test Post Office

A token-correlated email capture inbox for the NPS-recovery test loop. Every test mints a random token; the guest address is <token>@ai-metal.net; whatever the sandbox sends comes home to that token, captured, pull-verifiable, and eyeballable. One token threads the whole loop.

“I want to use ai-metal.net as a post-office for our testing.. so we will receive automated responses to the email you sent from. each test will use a random different id or token.. make this easy on us.” — jc, 2026-07-15

1. Need

The sandbox recovery-loop design (2026-07-14) sketched the email leg — a single guest@ai-metal.net address, an email-capture worker, Workers KV, a pull. But a single fixed address collapses the moment two tests run: message two lands on the same key as message one, and “which test got which email” becomes archaeology. jc named the fix: each test gets its own random token. The token is the correlation key — the fake alert carries it in as guest_email = <token>@ai-metal.net, and the recovery email (plus any bounce or auto-response) comes home under the same token. What’s missing is the post office itself: routing enabled on the zone, a catch-all so any token-address delivers, capture filed by token, and the “easy” part — mint a token in one call, fetch by token in one call, and an inbox page for human eyes. Without it, every test is a hand-built one-off; with it, a hundred tests can run without ever colliding, and the receipt for each one is a single lookup.

2. Raw User Stories

  • As jc, I want each test to mint a fresh random token in one call — getting back the token and its <token>@ai-metal.net address — so no two tests ever share a mailbox.
  • As jc, I want anything mailed to any token-address on ai-metal.net captured automatically and filed by token — recovery reply, bounce, auto-response, all of it — so the receipt is complete, not just the happy path.
  • As the test harness, I want to fetch “what did test <token> receive” in one pull call (Rule 13: the dev box takes no inbound), so the verify-loop can byte-match the captured body against the expected Zora reply.
  • As jc, I want a status check — pending or received — so the harness can poll cheaply while mail is in flight.
  • As jc, I want a post-office inbox page on ai-metal.net listing tokens and their captured mail, so I can eyeball a run without curling anything.
  • As jc, I want the option of a copy forwarded to my real inbox, so my own eyes stay in the loop — without that forward being the system of record.
  • As jc, I want all of this reversible and none of it touching cap-URL serving — ai-metal.net keeps its day job.

One token, whole loop: the fake alert carries it in, the recovery email carries it home, the receipt is one lookup. The token also becomes the pirun run’s ticket label (sandbox ticket tagged argus_sim_<token>, run ledger seeds sim.token), so the IDS trace, the Zendesk ticket, and the captured mail all answer to the same key.

Part 1 — Token scheme

  • Format: 12 characters, lowercase base32 alphabet a-z2-7 (RFC 4648, lowercased). 60 bits of OS-CSPRNG entropy (RandomNumberGenerator in the jacket). Example: k7m2p9q4x6t3.
  • Why this shape: url-safe (rides in query strings and cap-style paths untouched), email-local-part-safe (no dots, no plus-tricks to strip), case-insensitivity-safe (mail relays may fold case; an all-lowercase alphabet is immune), short enough to read aloud, long enough that collisions are a non-event.
  • Minted where: the post office — cloudflare-bridge POST /email/mint. The lane rolls the token, writes the placeholder t:<token> to KV via the CF REST API (value pending, metadata {minted_at, note?}), and returns {token, address, status:"pending"}. Minting at the post office is what makes status meaningful: a token the post office knows about but has no mail for is pending; an unknown token is an error, not a silent empty.
  • Embedded how: the token is the entire local-part — <token>@ai-metal.net — delivered by the catch-all, recovered by message.to.split("@")[0]. It is also the run’s label: the IN generator passes it as guest_email and tags the sandbox ticket argus_sim_<token>; pirun seeds it into the run ledger as sim.token.

Part 2 — Cloudflare Email Routing setup (one-time, gated, reversible)

POST /cloudflare/email-route — a new gated write lane on cloudflare-bridge, modeled on /cloudflare/dns and stricter: the ai-metal.net zone id is hard-pinned in-process (the DNS lane validates inputs but takes any zoneId; this lane takes none — there is exactly one post office). Same caller-gate middleware, capture-before reads, [AUDIT] lines. It performs, idempotently:

  1. Enable Email Routing on the zone — CF plants the MX + SPF records itself. Safety: MX ≠ A/CNAME; the Pages custom-domain records that serve cap-URLs are untouched. https://ai-metal.net/s/<cap>/ keeps returning 200 before, during, and after.
  2. Catch-all rule — *@ai-metal.net → action worker: email-capture. Catch-all (not per-address rules) is what makes tokens free: no write per test, ever.
  3. Optional destination address for jc’s real inbox — CF emails jc a verification link (the one human click). Once verified, the worker’s optional forward has a legal target.

The email-capture worker itself (script + EMAIL_CAPTURE KV binding + postoffice.ai-metal.net custom domain) is deployed once via the CF API from the checked-in source (argus/postoffice/email-capture.js) — a one-time provisioning step in First Move, not a permanent lane.

Part 3 — The Email Worker: a thin dumb pipe (the whole thing)

The CF edge runs JavaScript only — so this is JS, held to jacket discipline: zero decisions, zero parsing beyond a split, raw MIME straight to KV. Headers the Email Worker API hands over for free (from, to, subject) ride as KV metadata so the inbox page can list without reading bodies; no MIME body parsing happens on the edge — decode (quoted-printable etc.) is C99’s job in email-match, where it already lives.

// email-capture — ai-metal.net post office. Thin dumb pipe: raw MIME → KV. Zero logic.
export default {
  async email(message, env) {
    const token = message.to.split("@")[0].toLowerCase();
    const raw = await new Response(message.raw).arrayBuffer();
    await env.EMAIL_CAPTURE.put(`m:${token}:${Date.now()}`, raw, {
      metadata: { from: message.from, to: message.to,
                  subject: message.headers.get("subject") || "",
                  ts: Date.now(), size: raw.byteLength } });
    if (env.FORWARD_TO) await message.forward(env.FORWARD_TO);   // optional human copy
  },
  async fetch(request, env) { /* Part 5: the inbox page — read-only render of KV */ }
};

Bounces and auto-responses addressed to a token-address land through the same catch-all and file under the same token — the receipt is complete by construction. Messages to unknown local-parts still capture (a m: key with no t: mint record) — the inbox page flags them as strays instead of dropping evidence.

Part 4 — The read path: PULL, by token (Rule 13)

The dev box takes no inbound — so nothing ever pushes to it. All reads go through the C# jacket speaking the CF KV REST API (accounts/{account}/storage/kv/namespaces/{ns}/… — list-by-prefix + get-value + get-metadata), on the existing CloudflareClient. The worker never grows an API surface for machines; its only fetch() duty is the human inbox page.

LaneDoesReturns
GET /email/status?token=KV list, prefix m:<token>: (keys only — cheap){token, status: "pending"|"received", count, latest_ts} — 404 unknown-token if never minted
GET /email/get?token=KV list + get each value{token, messages: [{from, to, subject, ts, size, rawBase64}]} — raw MIME, untouched

verify-loop.pi’s pull-capture unit polls /email/status with backoff (mail is not instant), then /email/get, and hands rawBase64 to the C99 email-match skill — decode quoted-printable, strip transport headers, byte-compare against the expected Zora reply, assert the claimed IMSORRYTEST code appears exactly once. Green is an exit code, not an opinion.

Part 5 — “Make it easy”: the three calls + the counter window

    "subject":"We're Sorry — From Your Friends at Mendocino Farms",

The inbox page — https://postoffice.ai-metal.net/?key=<INBOX_KEY>, served by email-capture’s fetch() on a worker custom domain (subdomain — deliberately NOT a _worker.js on the ai-metal-net Pages project, which would put edge code in front of cap-URL serving). Read-only render of KV, gated by a single shared key held as a worker secret: a table of tokens (newest first) — token · status pill (pending / received / stray) · count · from · subject · received-at — each row expanding to the raw message. Be dark style. Eyeballing a run is: open the page, find your token, read the mail.

Part 6 — Worked example: token k7m2p9q4x6t3, all the way around

  1. POST /email/mint → k7m2p9q4x6t3 / k7m2p9q4x6t3@ai-metal.net. KV: t:k7m2p9q4x6t3 = pending.
  2. IN: /zendesk/alert-create raises “Guest Alert – Detractor” in sandbox mendocinofarms1781637851, guest_email = k7m2p9q4x6t3@ai-metal.net, tag argus_sim_k7m2p9q4x6t3.
  3. CARD: recover-guest.pi under pirun — scan → understand → claim IMSORRYTEST-… → compose Zora reply → AWAIT_FIRE → jc fires. Run ledger carries sim.token = k7m2p9q4x6t3.
  4. Sandbox Zendesk emails the guest. The catch-all delivers to email-capture; KV gains m:k7m2p9q4x6t3:1768520000000 = raw MIME; jc’s inbox gets the optional copy.
  5. verify-loop.pi: poll /email/status?token=k7m2p9q4x6t3 → received; /email/get → raw; C99 email-match byte-verifies skeleton + slots + code-appears-once. GREEN.
  6. jc opens postoffice.ai-metal.net, sees the row, reads the mail. Same token everywhere: ticket tag, run ledger, KV keys, inbox row.

Out of scope: prod anything (sandbox-only, per the 2026-07-14 design’s arm discipline); retention/cleanup policy beyond KV TTL (set expirationTtl ~30 days on m: keys so the post office self-empties); DKIM/SPF alignment for sending from ai-metal.net (the post office only receives); multi-zone post offices.

6. First Move

Stand up the post office and prove it with one letter: build the four bridge lanes (/email/mint, /email/status, /email/get, /cloudflare/email-route) + the ~20-line email-capture worker; run the route-setup once (jc clicks the one verification link); then — before any Zendesk is involved — mint a token, send a plain email to <token>@ai-metal.net from any mail account, and watch /email/status flip pending → received and /email/get return the exact bytes. That single round-trip proves routing, catch-all, worker, KV, and both pull lanes with zero moving parts from the rest of the loop. The sandbox recovery run is then just a different sender.

Into the plan: the four lanes on cloudflare-bridge (in-process bodies, pinned zone id, audit lines), argus/postoffice/email-capture.js + one-time deploy (KV binding, custom domain, INBOX_KEY + optional FORWARD_TO secrets), the inbox page render in fetch(), verify-loop.pi’s pull-capture switched to token inputs, and the smoke test above as a TLT check.
