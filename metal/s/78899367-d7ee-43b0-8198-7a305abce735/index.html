Manifold / Chat Interact — the plan

Joey.AI over everything in the rollout, built story by story. Source design: 2026-09-09-design-chat-interact.html + data-flow diagram. The Manifold is its own C99 service (Bus + source slots on a content-addressed cache); the panel is the AI-Pantheon (api.3-nous.net). This plan sequences the build around the operator’s own words.

Plan — Awaiting Approval

Intent (the why)

The operator watches the rollout live in Argus, but the answer to any real question — “does the Meraki port match the playbook and the install verdict?” — is scattered across ~10 streams and three screens. Intent: make every piece of rollout data something you can select and ask Joey.AI about, with the AI back-and-forth kept off the ops feed. Ship the thinnest live slice first (chat only), then widen one source at a time — each new source is one slot + one pin, zero Manifold change.

The user stories (drives everything below)

US-1 — “For every single chat event including Joey.AI I want the ability to use Joey.AI to do some action to it. I can chat to Joey.AI about the exact message including images if they exist.”
US-2 — “I can select multiple messages to scope things.”
US-3 — “I see all my interactions with Joey.AI — my internal back-and-forth — on the right. The middle is the actual context of what I selected.”
US-4 — “Move the chat to the left; no need to show the 4 site quadrants.”
US-5 — “When I say Joey.AI I mean the top two Gemini, the same technical way we use Gemini from the inventory OCR stuff. Very simple interaction for now.”
US-6 — “I want scoped into this all of what we have data-wise — inventory, decomm and install, the Toast info, all of what Argus Meraki can do, and all of Airtable. Essentially everything in this system I should be able to use Gemini to interact with.”
US-7 (derived) — As the operator I don’t want to re-pay the metered panel for the same question over unchanged data, and I don’t want a dead source to break the ask.

Approach (the how)

Build the Manifold outside every bridge — airtable is a source, its bridge is only the C# jacket for that API; the Manifold sits above all jackets and reads through them (and straight from the Firestore caches). Normalize is not new code — it’s existing a-d-d C99 skills.
POST /joeyai/ask { scope:[{source,id}…], prompt, thread } → Manifold.gather: Bus → slot[source].fetch(ids) cache chat_gather/{source}__{id} hit? serve : normalize (read+hash) & store → scopeHash → chat_answers/{scopeHash} hit? serve $0 : → fanout → POST api.3-nous.net (gemini-2.5-pro + gemini-2.5-flash + judge) → { answer, sourceRefs[], cost, turnId } // cached by scopeHash, appended to thread
C99 skills reused (kastil-systems/a-d-d/nous): read (extract, the core) · http (slot fetch) · hash (image dedupe + keys) · fanout (the panel ask) · summarize (disagree → show both). One gap → new photo skill for image bytes.

Constraints (what we won’t bend)

  • The Manifold is ours → C99. Bridges stay C# only because they jacket a foreign API. The Manifold is not inside airtable-bridge or any bridge — it is its own service above all jackets.
  • Read + reason only. No writes back to any source in this cut. No auto-actions.
  • The panel is always the AI-Pantheon via api.3-nous.net (fanout+judge) — never a direct Gemini SDK call.
  • Cache keys are SHA-256 content-addressed so the store re-plumbs onto the C99 nous memory store later — a re-plumb, not a re-key. No per-instance in-memory TTL at the normalize layer.
  • Best-effort gather: a dead/slow source omits itself; it never fails the ask.
  • Secrets by env name only, never Secret-Manager-pulled at runtime, never committed.
  • Identifiers that carry PII (guest emails/phones in chat) are hashed before anything persists (the ingest rule).

Unknowns (named, not hidden)

  • Panel latency at multi-source scope. One chat message is fast; 30 mixed items + images may push the panel call long enough to need streaming or a progress state. Unmeasured.
  • Image payload ceiling. How many/how large images can ride one api.3-nous.net call before cost or timeout bites — drives whether photo must downscale aggressively.
  • contentHash freshness for live sources. Meraki/chat move fast; is riding their existing freshness signal enough, or does the item cache need a short floor? Decide with real traffic.
  • Thread model at scale. Per operator+scope is fine for one operator; multi-operator + very long threads may need pagination/pruning.
  • Auth surface of the new service. Session-gated like the board — but a brand-new Cloud Run service needs its own allow-list/ingress decision confirmed.

When To Revisit (the v2 trigger)

  • After P3 ships and the operator runs the first real cross-source question — the answer quality tells us whether normalize is rich enough or slots need more context.
  • When the panel-answer cache hit-rate + cost meter come back from real use — if savings are thin, re-key or widen what’s cached.
  • The moment anyone asks for a write-back / action (“flag this”, “draft the reply”) — that breaks the read-only constraint and demands a v2 with an approval gate.
  • If a source’s bridge can’t answer what a slot needs — flows up to the design before code (Rule 12).
