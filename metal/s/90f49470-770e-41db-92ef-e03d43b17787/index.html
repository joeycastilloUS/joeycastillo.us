"Why did it happen" — the honest answer

You asked for user / API / external factors, and — critically — "if we can't tell why, state as such." That second clause is the harder requirement and it drives the whole treatment.

We have exactly two evidence sources: Meraki's configurationChanges (what changed, old→new, which admin) and apiRequests (every API call: admin, method, path, sourceIp, userAgent, 31-day hard cap). Cross-referencing them at the change timestamp ±60s yields five honest categories and no more:

BadgeMeansHow we knowClass
ARGUSWe did it — an Argus write path API-request entry whose userAgent is our own bridge, plus our own audit lineDirect — solid
APIAnother API client did it API-request entry ±60s, userAgent is not ours. We show admin, sourceIp, userAgent.Direct — solid
DASHBOARDA person clicked in Meraki Change-log entry with no matching API request. Dashboard actions never appear in the API log — absence is the signal.Inferred — dashed
EXTERNALSomething outside every channel we watch The hash moved but Meraki's change feed has no row at all. Consistent with a template push side-effect, a Meraki support action, or an out-of-band edit.Inferred — dashed
UNKNOWNWe know what changed. We cannot say who. Change-log entry exists but the change predates the 31-day API-request window, so API-vs-dashboard is no longer resolvableNone, and it says so

Your three words map exactly: "user" → DASHBOARD, "api" → API and ARGUS, "external factors" → EXTERNAL. UNKNOWN is the fifth, and it is the one you specifically asked for.

Confidence is encoded structurally, not just in the wording — one rule, everywhere: solid border = direct evidence. Dashed border + the word "inferred" = a conclusion.

That means DASHBOARD is always dashed too, not just UNKNOWN — because "a human clicked it" is a conclusion drawn from a missing row in the API log, not from a record of a person. Rendering that as confidently as an API call with a source IP would be exactly the dishonesty you asked us to avoid. This was the navigator's catch; the driver's first pass only dashed UNKNOWN.
UNKNOWN must read as honest, not broken. Four rules:
  1. Dashed border, neutral slate. Not red — it is not an error. Not grey-dead — it is not a missing field. It is a legitimate verdict with its own identity.
  2. It gets the same evidence line as a known attribution — the evidence is the absence, written out. Never a blank cell. "Meraki's change feed has no record; that feed misses ~20-25% of changes; the backstop sweep caught it anyway." or "API-request log only covers 31 days and this change predates the window." A broken UI hides what it doesn't know; an honest one itemises it.
  3. It is filterable and countable. An unexplained chip in the summary row. If that number climbs, that is itself the signal — somebody is changing things outside every channel we can see.
  4. Attribution is resolved once, at detection, and stored immutably in drift_events — never re-derived at render time. Otherwise a change attributed correctly today silently becomes UNKNOWN on day 32 when the API window rolls past it. With detection-time resolution, "window expired" only ever applies to backfilled archaeology, and a badge never changes under your feet. Navigator's catch — an engine contract, and the driver's design missed it entirely.

Template ripple is a grouping problem, not an attribution one

The driver's first pass gave template ripple its own TEMPLATE badge, which produced two cards for one act. The navigator's rule is better and is what the mockup now does: a template change that fans out to five bound networks renders as one event on the template subject with a fan-out line naming the affected networks. One change happened, so it is one event — and accepting it accepts the ripple. The template is a first-class drift subject precisely so the stream can say "1 change" when 1 change happened.

Rendering before→after by shape

Three shapes, three treatments. Getting the third one wrong would be a real bug:

  • Scalar (VLAN 100 → 20): old struck through and dimmed, arrow, new in green.
  • List (allowed VLANs): set diff — + added, − removed, unchanged dimmed. Order is not meaningful, so don't imply it is.
  • Ordered array (L3 firewall rules): numbered rows with explicit move indicators (#3 → #1). Firewall rule order is semantic — a reorder with no content change still changes what the firewall does. Never render this as a set.

1. Intent

Drift is a trust surface: its job is to be believed when it says something changed, and believed when it says nothing did. It is a new tab inside a shipped, dense operations console, so the `~laf` axes are constrained more by the existing product than by taste. The six resolve to serious, dense, abstract, bold, responsive, restrained. The top two traits are dense and serious. The one real contradiction — dense wants to pack, bold hierarchy wants whitespace to separate — resolves the way the console already resolves it: hierarchy comes from colour and weight, never from added whitespace. A 4px left border does the work eight pixels of padding would have.

2. System rules

Colour — strategy, anchored to the console's live values

Inherited verbatim from web/app/index.html :root. The mockup does not introduce a single new base colour:

--bg #0a0a0a   --surface #141414   --line #262626   --accent #6FC3DF
--text #e8e8e8   --dim #888   --ok #7CFFB2   --warn #ffce85   --bad #ff6b6b

Temperature: cool neutral base, single cyan accent, warm only for warning. Relationships: one accent and never two — cyan means "interactive or identifying," never "good." Good is --ok. Contrast: body text #e8e8e8 on #0a0a0a is ~17:1; --dim #888 on surface is ~5.2:1, which holds AA for the 11.5–12.5px metadata it carries. Nothing meaningful is ever encoded in colour alone — every badge carries a word.

One new sub-palette, and only one: the five attribution badges. Each derives from an existing console hue — green from --ok, cyan from --accent, amber from --warn, violet from the existing .lvl-org purple #d6a3ff, slate net-new for UNKNOWN.

Spacing

Base unit 4px. Scale 2/4/6/8/10/12/14/18/26. Card padding 10px 14px — the Watch card's exact value, kept so Drift and Watch cards sit at identical rhythm when you flip between tabs. Card gap 8px. Section gap 12px.

Typography

System stack, no web fonts (hard constraint — no CDN): -apple-system, 'Segoe UI', Helvetica, Arial, sans-serif. Monospace Consolas, monospace for every machine value: MACs, field paths, old/new values, hashes. That distinction is load-bearing — if it's a value the machine read, it's monospace; if it's prose we wrote, it's the sans stack.

Scale: 10px uppercase micro-label · 11px badge · 11.5px metadata · 12.5px body · 13.5px card title · 1.05rem pane heading. Weights 600/700/800 only — no light weights, they disappear at these sizes on this background. Line-height 1.5 body, 1.1 titles.

Density

Target: 8–10 drift cards visible per viewport collapsed, plus the density strip and the chip row, without scrolling on a 900px-tall window. Collapsed card height ~40px. Padding-to-content ratio stays under 1:3. The strip compresses 30 days × 5 networks into ~90px of vertical space.

Depth

Flat, with one exception. No shadows on cards, no gradients, no texture — elevation is communicated by border and surface value only (#141414 card on #0a0a0a page, #262626 hairline). The single exception is the dropdown menu, which the console already gives box-shadow:0 12px 30px rgba(0,0,0,.6), because a floating layer genuinely needs to read as floating. Depth is information, not decoration.

3. Component behaviour

Buttons

Three tiers. Primary — none in this tab; Drift never has a "do the thing" button, because it never writes to Meraki. Secondary (.acceptbtn, .ref): transparent fill, 1px #2a343b border, 5px/13px padding, 6px radius, hover promotes border and text to accent. Ghost: no border until hover, for tertiary actions like "view in Meraki."

Accept is two-step and the second step is red. First click arms it — the label changes to "Re-baseline — confirm" and the button turns to the --bad family. It re-blesses state; it deserves the same friction as a delete, without a modal (modals in a dense console are a tax).

Cards

#141414 surface, 1px #262626 border, 4px left border carrying severity, 8px radius, 10px 14px padding. Collapsed by default — the collapsed row must carry enough to triage without expanding: what changed, which network, when, and why. Expanding reveals evidence then diff, in that order. Evidence before diff is deliberate: you ask "who did this" before "what exactly."

Tables

The diff table is the only table. Row height 4px vertical padding, no zebra striping (the console doesn't stripe), 1px #1c1c1c row rule. Header 10px uppercase, letter-spacing .08em, --dim. Values monospace. Columns: field, was, now — and for ordered arrays, a fourth position column.

Navigation

Fixed left sidebar, 172–188px, already built. Drift takes the fifth slot, after Audit — last, because it is the newest, and the existing order is muscle memory. Active state background:#1d2a31; color:accent; border:rgba(111,195,223,.35), unchanged from the shipped rule. The count badge is the only sidebar element allowed to carry the --bad family, and only when the count is non-zero. Deep links follow the existing three-segment scheme: #meraki/drift/<eventId> — same shape the Runbooks tab already uses, so a drift item is shareable by URL.

4. Interaction

Transitions

120–150ms, no exceptions. The console's shipped values are .12s for colour and background, .15s for the chevron rotate. Drift adds nothing slower. What animates: disclosure chevron rotation, hover colour, chip active state. What must never animate: the arrival of a drift item. No slide-in, no fade, no pulse. A new critical item appearing with motion trains you to watch for motion, and motion you learn to see is motion you learn to ignore. It appears; the count changes; that is all.

Feedback

  • Hover — border and text promote to accent. Never a background jump on cards; only on nav items.
  • Focus — outline:2px solid #6FC3DF; outline-offset:2px, the console's existing :focus-visible rule. Every control is keyboard-reachable; the disclosure row is a real button.
  • Loading — the existing .spin; the pane keeps prior data visible while refetching, so a refresh never blanks the screen.
  • Error — the Watch error bar (#2a1414 / #6b2b2b / #ffb4b4) with an inline Retry, falling back to last-known state labelled as last-known.
  • Poll cadence — 60s, not Watch's 45s. The engine ticks every 15 minutes; polling faster than that buys nothing but churn. The poll diff-checks before re-rendering, and never collapses an expanded card. Re-rendering under the operator's cursor mid-read is energetic, not responsive. Navigator's catch — the driver's pass would have shipped that bug.
  • Stale — amber bar at >35 minutes since last sweep (two missed ticks plus a 5-minute margin). The bar composes above everything, including the empty state — the clean card and the stale banner render together, so a stalled sweep can never look like a clean network. That inversion is the single most important feedback rule in the tab.

Two splits, neither resolved silently:

1. The density strip — driver's, and the navigator argues against it

Driver: keep the 30-day × 5-network tick strip. You asked for "drift timelines" plural, and burst-pattern-at-a-glance is something a chronological stream structurally cannot show — you can see at once that Culver City has been quiet for three weeks and Davis lit up twice today. It costs ~90px.

Navigator: drop it. At five subjects those are "mostly-empty ribbons 95% of the time," they cap out around eight networks, nothing in the shipped console scrolls sideways, and every chronological precedent in the product is a vertical stack. The subject filter chip is the per-network timeline when you want one.

Both are right about different things. The strip is in the mockup so you can judge it with your eyes. The navigator's scaling objection is the real one: it works at 5 networks and breaks at 20. If Argus stays Mendo-only it earns its keep; if it goes multi-tenant it has to go.

2. Arrival animation

Driver: a new drift item must never animate in. Motion you learn to watch for is motion you learn to ignore.
Navigator: use the console's existing one-shot fcflash pulse (:153) — it already ships, it does not loop, and consistency with the product beats a private rule.
Navigator's consistency argument wins on Rule-1 precedence and is adopted, but the driver's concern is on the record: if the flash ever starts firing often enough to be background noise, it should go.

Still open from the ~d, and this mockup takes a position on it: Accept granularity. The mockup shows per-entity — Accept sits on the individual card, so accepting port 7 does not bless port 11. That is the driver's position. The navigator's ~d verdict was per-section. Both agree Accept must live inside the expanded drill-down — you should not be able to bless a change you have not looked at. Your call.

Open questions neither pass could close

  • Can we identify our own bridge in apiRequests? The ARGUS-vs-API split needs a stable marker — our userAgent, or the admin identity of the bridge's key. If Meraki reports a generic UA, ARGUS attribution has to come from correlating our own audit log instead. Unverified.
  • Clock skew between the two logs. The ±60s window assumes configurationChanges.ts and apiRequests.ts share a clock. If skew is worse, DASHBOARD-by-absence gets noisier — though the dashed "inferred" treatment already covers us honestly.
  • How template pushes actually appear in the feed — one template-level row, N network-level rows, or nothing. Determines whether fan-out grouping can be read from the feed or must be inferred from simultaneous same-hash drift across bound subjects.
  • Sidebar position. Placed fifth because the existing order is muscle memory. Argument for second: it is the tab you want first each morning. Cheap to move.
  • History depth. 30 days shown, matching the attribution horizon. Meraki's change log holds 365, but everything past 31 days reads UNKNOWN — true, and useless. Past ~200 events the stream needs a "load older" cut; drift_events supports cursoring.
