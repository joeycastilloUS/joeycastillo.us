DIA Spec — how to generate a card

Everything a session needs to write a Salesforce DIA that pi_run will load without refusing it. Grammar, the per-demand allow/ignore/options contract, and the checks that fail you.

This is the spec, not an example to copy blindly. Every rule below is what the C parser and dia_verify actually enforce — matched against dia.c, not from memory.

0 · What you produce

A DIA card is a cortex of three files that share a base name:

FileIsWho writes it
<card>.piTHE DEMAND and THE WORDS — what must happen and what we say. Human/operator intent.You generate this.
<card>.siTHE PLAN — the units that enact each demand, each bound to one C micro-op.You generate this.
nous.smTHE SKILLS catalog — the C micro-ops available, with their in/out signatures.You already have this. You bind to it; you do not write it.

The two you generate must agree with each other and with the .sm, or the card is refused at load. That agreement — called biRT — is the whole point of Section 4.

Naming: the three files sit in one directory and share the base name exactly (e.g. sfdc-lead-triage.pi / .si, alongside nous.sm).

1 · The .pi — demand and words

Header lines, then sections opened by exact tokens. The parser opens a section only on these literal starts: demand:   words <name>:   config:   and the header card:. owner: and env: are frontmatter, not section tokens (see the note below the example).

# sfdc-lead-triage.pi   ·   PURE INTENT   ·   owner: jc   ·   env: sandbox
card:   sfdc-lead-triage
owner:  jc
env:    sandbox

# ---- THE DEMAND -----------------------------------------------------------
demand:

  D1   Every inbound lead is read and understood before it is routed or scored.

  D2   A lead already carrying our handled marker is skipped — we have processed it.

  D3   Score the lead's fit from its own fields, never from an enriched guess.

     allow:  score.model = vertex/gemini-2.5-pro, vertex/gemini-2.5-flash
     allow:  score.model requires="BYOK — data leaves the Google boundary" =
             byok/gpt-5.5, byok/o3
     owner:  score.model = it

  D4   Route a qualified lead to the owning team; leave an unqualified one for nurture.

     allow:  route.threshold = 60, 70, 80
     owner:  route.threshold = ops

  D5   Never write to a lead flagged Do-Not-Contact.

     ignore: lead.status = do_not_contact
     ignore: lead.region = EU  until=2026-09-01

# ---- THE WORDS  (what we say; sealed by hash at load) ---------------------
words route-note:
  | Lead {lead_id} scored {score} — routing to {team}.
  | Basis: {reason}

# ---- CONFIG  (declared values pi_run hands to the jackets) ----------------
config:
  crm.system:  salesforce  "SFDC prod org"   # D1

The rules the parser actually applies

  • A demand line starts with D then a digit (D1, D2…). Any indented line under it that does not start D<digit> is continuation of that demand — including the allow:, ignore:, owner: lines.
  • A words block is words <name>: followed by pipe-prefixed lines (  | text). The | prefix is stripped; {placeholders} are filled at run time from ledger keys.
  • config lines are key: value "label" # D#. These are values pi_run hands to the C jackets — and the trailing # D# comment is load-bearing: it is how a config line realizes a demand (Section 4, coverage-down). A demand satisfied by a fixed config value, not a unit, cites itself in that comment. The same is true of a header line like env: sandbox # D14.

owner: and env: are not section tokens — the parser only opens sections on demand:, config:, words , and the header card:. env: is read as frontmatter; a top-level owner: is ignored by the runtime. Do not expect a section to start on them.

Keep each demand tight. The runtime holds a demand's full text — the D# line, its continuation, and its allow/ignore/owner lines — in a fixed 512-byte buffer. Past that it truncates silently. The reference card's D4 allow list alone exceeds 512 bytes. Write demands as one or two sentences and let the allow lists be the structured part.

Indentation is structural. Every allow/ignore/owner line must be indented under its demand. An unindented, non-token line inside demand: ends the section — and every indented demand line after it is silently dropped. One stray flush-left line can quietly delete half your demands.

2 · The allow / ignore / options contract — per D#

This is the part the operator asked for by name: every demand carries its allows, its ignores, and the options that are configurable under it. Statements indent under the demand they belong to.

StatementMeansShape
allow: KEY = a, b, cthe permitted value set for a setting this demand governscomma list
allow: KEY requires="…" = …a gated subset — permitted only with a human step; the requires= text is the reason, shown verbatimattribute + comma list
ignore: KEY = VALUEan intake skip — do not act when this matchesexact value
ignore: KEY = VALUE until=YYYY-MM-DDa dated skip — inert after the datevalue + until
owner: KEY = ops | itwho may change it — see the honesty box: no code reads this line todayone role

The “options” for a demand ARE its declared settings: each allow: key is a configurable option and its comma list is the choices. A demand with no allow: declares nothing configurable — fixed behaviour. That is a valid, common case; do not invent options a demand does not have.

Be precise about what reads these lines today. Most of it, nothing does — yet.

To pi_run these are demand-continuation text, full stop — it parses none of them into structured data. And the app layer reads far less than you would expect:

StatementRead by, today
allow: models = …The Argus bake, but only this one key — a regex matches allow: models and nothing else. An allow: score.model or allow: route.threshold is read by no code at all right now.
ignore: …Nothing. Not implemented anywhere.
owner: KEY = …Nothing. Edit rights are a hardcoded map in the Argus bake (bake-runbooks.py); a per-demand owner: line is not read. To grant edit rights for a new card, that map is updated — not this line.

Write them anyway, correctly and completely — they are the versioned, human-owned contract the operator and the tooling will grow into, and the design intent is that a card declares its own options. But do not tell anyone the runtime enforces them, and do not write a demand that depends on it. In particular: keep each .si set: value inside its demand's allow: set yourself — nothing cross-checks it for you.

3 · The .si — the plan

Opens with plan:; each unit opens with - unit: NAME why: D#. Fields are one per line.

plan:

# The run starts with exactly ONE key in the ledger: `ticket`. It is the only seed.
# The first unit MUST read [ticket]; everything else is produced by an earlier out:.
- unit: read_lead            why: D1
  skill: sfread   slot: inbound-lead
  bind: http.read_lead              # PLACEHOLDER — must exist in YOUR nous.sm, marked pub
  in:  [ticket]                     # the seed — a bare Salesforce card still starts from `ticket`
  out: [lead.id, lead.fields, lead.status, lead.region]
  gate: auto     fail: abort

- unit: gate_handled         why: D2
  skill: sfread   slot: already-handled
  bind: http.tag_claim
  in:  [ticket]
  out: [handled.already:bool]
  set: gate.tag = argus_lead_handled
  gate: exit     fail: abort         # exit ends the run when out[0] is "true"

- unit: score_lead           why: D3
  skill: ai-panel   slot: fit-score
  bind: http.score_panel
  in:  [lead.fields]                 # produced by read_lead above — valid key-flow
  out: [score:int, score.reason]
  set: score.model = vertex/gemini-2.5-pro    # keep inside D3's allow set YOURSELF

- unit: route_lead           why: D4,D5
  skill: sfwrite   slot: assign-owner
  bind: http.route_lead
  in:  [score, lead.status]          # both produced earlier
  out: [routed.team]
  words: route-note
  set: route.threshold = 70
  idem: route-{env}-{lead.id}        # never route the same lead twice
  gate: auto     fail: abort
FieldRule
why: D#[,D#…]which demand(s) this unit realizes. Required. Every D# named must exist in the .pi.
bind:the C micro-op. Must be in nous.sm and marked pub.
in: / out:ledger keys, optionally typed (:int :bool :float). Every in: key must be produced by an earlier unit — except the one seed, ticket, which the run supplies. There are no other root inputs; the first unit reads [ticket].
idem:an idempotency key (e.g. route-{env}-{lead.id}) — the mechanism that stops a re-run repeating a side effect. Use it on any unit that writes or sends.
res:names a resource file the unit reads (a vault, a template store). Optional.
set:a policy value pi_run injects into the ledger (e.g. the model, the threshold, the tag).
words:names a words block in the .pi. Required if the bind's signature expects words.
gate:auto (proceed), exit (end the run when the unit's first out key is "true"), hold, fire.
fail:abort (stop the run), hold, continue. On error, what the run does.

4 · biRT — the checks that refuse your card

dia_verify runs at load and refuses the whole card on the first failure. These are the actual messages; satisfy every one or the card never runs:

If you…REFUSE
write a unit with no bind:unit has no bind
bind a micro-op not in nous.smbinds '…' — not in .sm
bind one that is not pubbinds '…' which is priv, not pub
list a different number of out: keys than the .sm signature declareswrites N out keys but its .sm out-sig arity is M
bind a words-taking op with no words:…in-sig names 'words' but declares no words: — it would silently run the jacket's baked copy
write a unit with no why:cites no why: — unauthorized mechanism
cite a why:D# that is not a real demandcites why:D# — not a demand (dangling)
name a words: block not present in the .pispeaks words '…' — not in .pi
read an in: key nothing earlier producesreads in:… — no earlier unit produces it (broken key-flow)
leave a demand with no unit and no config realizing itdemand D# is unrealized

The two directions to check yourself before you hand it over:

  • Coverage-up: every unit's why: points at a demand that exists. No unit acts without a demand authorizing it.
  • Coverage-down: every demand is realized by at least one unit (or a config line). No demand is written and then ignored.

A card that passes both, binds only real pub skills, and has clean key-flow will load.

5 · The seal

On first load, pi_run writes <card>.pi.seal — a hash of each words block (words only; not demands, not config, not the allow lists). After that, any change to a words block is refused until the seal is regenerated (rm the seal and reload). You do not write the seal — the runtime does, trust-on-first-use. Just know that editing a words block later requires re-sealing.

6 · Generation checklist

  1. Confirm you have nous.sm and can read every skill's name, visibility (pub), and in/out signature. Bind only to what is in it.
  2. Write the .pi: card/owner/env, then demand: with each D# one or two sentences, its allow:/ignore:/owner: lines, the words blocks, the config.
  3. Write the .si: one unit per mechanism, each why:-cited, each bind: a real pub skill, in:/out: keys typed, set: values inside their demand's allow: set, words: where the signature needs it.
  4. Self-check biRT both directions (Section 4). Trace key-flow: every in: comes from an earlier out: or a root input.
  5. Keep each demand under the 512-byte line. Keep .si set: inside .pi allow:.
  6. Do not claim the runtime enforces allow/ignore — it is app-layer intent today.

What this spec deliberately does not cover

  • The C skills themselves — you have the .sm; writing new micro-ops is a substrate change, out of scope for generating a card. Every bind:, skill: and slot: name in the Salesforce example above is a placeholder — a wrong bind: is refused loudly at load, but a wrong skill:/slot: is not checked and will persist silently. Substitute all of them from your real nous.sm.
  • Deploy — getting the three files onto a running prime is a separate, manual step.
  • Runtime enforcement of allow/ignore/options — not built; declare them as intent, honestly.
