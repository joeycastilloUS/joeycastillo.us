Phase 1 proves the routing with zero change to what any guest receives. Only then does anyone new get an email.

User stories

PHASE 1 The plumbing — nothing a guest sees changes

S1

As the operator, a detractor still gets exactly the email they get today — same words, same code, same sweep cadence — even though the work now runs across two cards instead of one.

S2

As the operator, anyone who mentions being unwell still reaches a human, whatever they scored.

S3

As the operator, a guest is answered once. Never twice, never by two cards.

S4

As the operator, if a band goes unanswered I find out — a green number never means "handled" when nobody was written to.

PHASE 2 The two new bands

S5

As the operator, a guest who scores 9 or 10 gets a thank-you written for what they actually said, and a $10 code.

S6

As the operator, a guest who scores 7 or 8 gets asked what we could do better, and a $20 code to come try again.

S7

As the operator, a written reply never promises something we cannot honour and never discusses illness or safety — that conversation belongs to a person.

S8

As the operator, if the models fail or take too long, the guest still gets a proper message — never silence, never half a sentence.

PHASE 3 Finish

S9

As the operator, each band draws its own coupon value, and if one denomination runs out we hold that band and keep serving the others rather than quietly handing out the wrong amount.

S10

As the operator, I can open one card and know everything that happens to one kind of guest.

The plan

Phase 1 is not scaffolding. It is a live correctness fix.

Sandbox tickets #696 and #699 carry "NPS Score 10 / 10" and are tagged argus_nps_handled. Promoters are already arriving and already entering the detractor path — nothing in the card gates by band, and the alert lane stamps "Detractor" into the subject for any score.

So the earlier framing was backwards. The risk is not "Phase 2 may be inert if promoters never arrive." It is that promoters arrive today and take the apology path. Phase 1's band decision is what stops that, and it stops it whether or not Phase 2 ever ships — an unrouted band holds rather than falling through to "We're Sorry."

And Phase 1 has an exact-answer test.

Split today's card into entry + detractor and route between them — but change nothing about what a detractor receives. If the plumbing is right, the output is byte-identical to today. That is a test with an exact expected answer, run against real tickets, before a single new guest is ever emailed.

Nothing in Phase 2 can be trusted until Phase 1 produces an identical email.

61 points.

You called this a minor tweak. The scores and the dollar amounts are minor — that part is items 1.1 and 3.1. The rest is what it costs to let a model write to a guest and to route between cards on a runtime that does neither today. Two new micro-ops, three dispatcher changes, four cards, and a recompile-and-redeploy to both seats.

Pin the baseline before starting

Two designs from earlier today — the intake rework and the #735 inspect — both propose changing the send path for Guest Relations tickets (reply on the alert ticket instead of creating a follow-up). If either lands mid-Phase-1, "what a detractor receives today" moves and the exact-answer test is chasing a baseline that is still shifting.

Pick one order and hold it: freeze the intake work until 1.6 is green, or land the intake work first and re-baseline against it. Running them concurrently is the one sequencing mistake that would waste Phase 1 entirely.

Riskiest item

1.3 — the second hop. Everything else is additive; this changes a guard that today protects against unbounded fan-out, in the one code path every ticket crosses. Get the depth counter wrong on an error return and either the guard stops protecting, or dispatch stops working for every band at once.

De-risk: 1.6 is the answer — the identical-output test exercises the new hop on every real detractor before any new band exists. If a detractor's email changes by one byte, the hop is wrong and nothing else ships.

Unknowns

  • Whether the form emits non-detractor alerts. Promoters demonstrably reach Zendesk by other means (#696, #699), and the alert lane accepts any score — so Phase 2 is testable regardless. Item 2.0 settles the form question in two minutes.
  • Whether one generative micro-op serves both bands or needs variants.
  • What the generate lane costs. The bridge source is local and readable — this should be a firm number before Phase 2 starts, not an estimate.
  • Whether each dispatched card needs its own addressing row on the primes — node-local, not knowable from the repos.
  • Whether the live vault claim honours denominations; the local store does.

When to revisit

After 1.6 — if the identical-output test does not go green quickly, the second hop is harder than estimated and Phase 1 should be re-cut rather than pushed. Before 2.1, on the delivery question above. And when the card deploy becomes a script, because 1.7 and every later change get cheaper and the standing sync cost drops.
