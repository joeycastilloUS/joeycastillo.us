Design — DIA hit count

Per item, per DIA, a count of how many times that DIA has acted on it. The DIA reads its own count and decides. That's it.

1. Need

Many DIAs and automations will land on the same work item (one Zendesk ticket: NPS recovery, a classifier, CSAT, escalation…). Today mendo-nps decides "did I already do this?" by searching Zendesk for any prior "Follow Up" requester:<guest_email>. Two things wrong:

  • Keyed on the guest, forever — once a guest is ever recovered, every future alert for them is dropped. A returning guest's new complaint gets swallowed.
  • Blind to which DIA acted — the gate can't tell its own prior work from another automation's, so idempotency can't be per-DIA.

2. Raw User Stories

  • As a DIA, I want to know how many times I have hit this item, so I decide whether to act again.
  • As a DIA author, I want to decide for myself what a nonzero count means — skip (dedup) or act anyway.
  • As an operator, I want to see, on the item, which DIAs hit it and how often.

3. Sourced Solution

It's mostly here already — finish it, don't invent.

SourceWhat we use
nous / .siThe .pi card: name is the DIA-id. The .si already has idem: keys. pi_run already reads/writes the ticket via the jacket.
mendo-npsgate_handled (retire the guest search) and the Ref: id-{ticket} line shipped today.
OutsideAn idempotency counter — the oldest trick there is.

Approach: On the item, keep a small count per DIA: <dia-id> = <hits>. The bump is the claim: a DIA bumps before acting, and the jacket's count-bump returns created (true only for the run that won the bump). A dedup DIA acts iff created==true; always-on DIAs ignore created and just let the count climb (audit). This closes the sweep race — runs launched 15s apart (an illness-panel triage runs longer than the cadence) can both read hits==0, but only one wins the bump. pi_run stays blind — DIA-id from the card, the count read/bumped on the item via the jacket.

4. Naming

ThingNameWhy
Whose countdia-idThe .pi card: name. Already unique; nothing new invented.
The numberhitsHow many times this DIA has acted on this item.
The mark on the itemdia:<dia-id>=<hits>A tag/field on the Zendesk ticket. One per DIA that touched it.

Collision: "tag" is a literal Zendesk term — the count is carried as a tag; the idea is a hit count, not a "tag" scheme.

5. Shape

  • The count — on the item, one small value per DIA: dia:mendo-nps-detractor-triage=1.
  • Read — the DIA reads its own count off the item it already has in hand (no extra search, no guest lookup, no index lag).
  • Claim by bumping — a dedup DIA bumps first; the jacket returns created (true iff this run won). Act iff created. Always-on DIAs skip the check and bump as audit.
  • Blind runtime — pi_run gets the DIA-id from the card; the jacket reads/bumps the count on the ticket (Zendesk update with safe_update — a 409 is a lost race → created:false).

Accepted trades (KISS, not gaps to fix):

  • Same incident, two alert tickets (survey re-fire, or webhook + sweep both minting a ticket) → two recoveries. The count is per-item; cross-item is out of scope. The old guest-key masked this by over-blocking; we accept the rare double over dropping every returning guest.
  • Bump lands, act then fails → count says 1 with nothing sent. send is fail: hold, so it surfaces to an operator, not a silent drop. Double-coupon is the worse failure; this is the right side.
  • Always-on concurrent bumps may lose a count (last-write). It's audit, not a gate — acceptable.
  • Claim-then-act is at-most-once — win the claim (created:true), then die before sending, and the count says handled with nothing sent. For a dedup follow-up that's the right failure (silent miss beats a double-coupon; send is fail:hold so it surfaces). A chosen trade, not a surprise.

Out of scope: cross-item counts, expiry/decay, retro-marking old tickets, the doculink/DIA viewer (separate line).

Build-time verify (not a design fork): confirm Zendesk preserves :/= in tag text; if it normalizes them, spell the mark with underscores or use a ticket field — same op, different spelling.

6. First Move

Retire mendo-nps's guest search. The gate bumps dia:mendo-nps-detractor-triage on the source ticket and reads back created; the run acts iff created==true; then compose → send. If a returning guest with a new ticket now gets a recovery, the same ticket re-swept dedups, and two near-simultaneous sweeps of one fresh ticket send exactly once — done.

Into the plan: a hits read/bump helper in pi_run (DIA-id from card); jacket count-read / count-bump ops; then it's the default idempotency for every DIA.
