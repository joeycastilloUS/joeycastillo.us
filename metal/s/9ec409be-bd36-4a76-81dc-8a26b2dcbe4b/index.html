Airtable write-back — the corrected serial

Phase 1: edit an entered value in the review console → Firestore receipt → the customer's Airtable base. Text only; photos are a later board.

~d PAIRED · Opus driver / Fable navigator, concurrent independent passes, reconciled. Navigator owned the verdict. Three splits surfaced inline below — none resolved silently.

1 · Need

An installer types a serial into a Jotform. It lands in Airtable. The reviewer opens kreview, sees the photo next to the typed value, and the AI-read says they disagree — the human fat-fingered a character. Right now the reviewer can mark it FAIL and that is all he can do. Fixing the actual value means leaving the console, opening Airtable, finding the row, and editing it by hand — with no record of who changed what or why. So the correction either doesn't happen, or it happens invisibly. The need is not "write to Airtable." The need is: fix it where you found it, and leave a receipt.

2 · Raw user stories

As the reviewer, I want to correct the entered serial on the row I'm already looking at, so the MISMATCH clears for the right reason instead of me marking FAIL and moving on.
As the operator, I want every correction to carry before, after, who and when, so when the customer asks "who changed this" there is an answer that isn't "someone, in Airtable, sometime."
As the customer, I want the base to end up holding the right serial, so the downstream reports and the asset register aren't wrong.
As the operator, I never want a correction to post a card into ext-mendo-c1techs. A typo fix is not an incident.
As the reviewer, I want to see the corrected value immediately — not in sixty seconds when the cron catches up.

5 · Shape

5.1 The Rule 12 first move — architecture before code

ARCHITECTURE.md:78-81 declares the read-only invariant and says writes stay "explicit, allow-listed, capture-before + audited … production stays un-writable." That sentence is Meraki-shaped — it assumes a lab/prod split. Airtable has none: the base is production. And there is no §ISource section for airtable-bridge at all (only incidental mentions at :350, :695) — the largest bridge in the repo is undocumented. So this isn't amending a spec, it's writing the missing one plus a narrow exception.

Proposed as a new §15. Per Rule 11 this is a proposal — the operator approves before a line lands in ARCHITECTURE.md, and no code ships first.

§15. airtable-bridge is a source — and carries the ONE production-write exception.

airtable-bridge/ is an ISource under §3: curated catalog (bases, base-schema, records, record), GET-only in the API Browser, no arbitrary passthrough. Firestore is ours and writable. Until this section, Airtable was not.

Exception. The operator may correct an entered text value on a Konductor Inventory or Decommission record from the review console, and that correction propagates to the customer's base. This is §3's gated path applied to a source whose whole base is production, so the gate is per field, not per network: (1) allow-list — an explicit server-side list of (table, field) pairs: the typed-serial text fields of Inventory and Decommission on the one rollout base, never widened by schema discovery. (2) capture-before — the prior value is read from atb_cache and recorded before any write. (3) audited — every attempt is an atb_edit document (before, after, who = session email, when, state). A machine-token caller cannot edit. (4) fail-closed — unknown field, unresolvable field id, wrong field type, missing PAT write scope, kill-switch unset → refused, nothing written. Field identity is the Airtable field ID resolved from base-schema, never the display name; typecast is always false. The write is synchronous and single-record. Airtable's own revision history attributes the change to the PAT identity; atb_edit is the operator-level audit and is the record of truth for who.

Out of this exception: attachments/photos (a further amendment), any other table, any bulk or scripted write, any write from the API Browser.

Four code comments are law-shaped and must not outlive the amendment — each gets one line reading "read-only except §15": Program.cs:6-11, Program.cs:1121, Airtable.cs:6-12, AirtableSource.cs:5-9.

5.2 The receipt — atb_edit

One document per attempt, append-only. AtbReview is one-doc-per-slot and overwrites — the wrong shape for an audit, so we don't copy it here.

atb_edit/{recordId}|{fieldId}|{unixMs}
  tableId, recordId, field (display name), fieldId
  before:    string|null     captured from atb_cache before the write
  after:     string
  by:        email           argus_session payload, never "token"
  at:        Timestamp       server
  state:     "pending" | "applied" | "failed"
  appliedAt: Timestamp?
  error:     string?         Airtable status + body on failure

Keying the doc id on fieldId instead of the field name makes the id pure-ASCII and slash-free, so the percent-encoding dance in AtbReview.DocId (AtbReview.cs:24-25) simply doesn't arise. The display name lives in the body; the read path queries by body fields and never parses the id.

Three states, one writer. The same request handler advances all of them: write pending → PATCH → applied or failed. A pending that never resolves means a crash mid-PATCH — it is visible (query state == pending older than 60s), and that visibility is exactly why the receipt is written first. No worker resolves it; the operator re-saves, and PATCH is idempotent by value.

5.3 Propagation — synchronous

PATCH inside the POST: after the pending doc, before the response. See Choices below for why this beats a queue.

The 60-second cron overwrite is solved by write-through, not by a queue: Airtable's PATCH response is the full updated record, so we persist it straight into atb_cache/{tableId}/records/{recordId} using the SyncRecordAsync persist shape (AtbCache.cs:166-173) minus the GET — we already hold the record. The cache holds the new value before the response returns; the cron's next pass fetches the same value from Airtable, so there is no optimistic-UI reversal, just one fingerprint change and one epoch bump.

5.4 The gate — RequireAirtableWrite

No lab analog exists, so the allow-list key is (tableId, field name), and the base is pinned to reviewSyncBase (Program.cs:123) — never caller-supplied. Five checks; any miss returns 403 with a one-sentence detail in the meraki style (bridge/Program.cs:1176) and nothing reaches Airtable.

  1. Kill-switch. ATB_WRITE env var; unset or short = closed, mirroring the cronToken.Length >= 24 discipline at Program.cs:365-369. Rollback is --update-env-vars, no rebuild.
  2. Scope. hasWriteScope from the startup whoami probe. Absent data.records:write → refuse. We do not take the token's capability on faith at runtime.
  3. Who. by must be an email from argus_session (Program.cs:989-992). A BRIDGE_TOKEN-only caller resolves to "token" and is refused — an audit without a human isn't one.
  4. Allow-list. Static AtbEditable: the serial text fields from KR_INV_ROWS + KR_INV_ROWS_X (index.html:10153-10184) and the KR_DEC_GROUPS + _X serials (:10233-10254) — 39 names, copied verbatim with the typos intact ("Mircrotouch", "Salad OLO Screen"). Not the photo fields. Not schema-driven: the schema says what can be written, the list says what may. The web copy and bridge copy will drift one day, and drift fails closed (403) — the safe direction. Changing the list is a commit; git is its audit.
  5. Type. The name resolves to a fld… id in base-schema and the type is singleLineText or multilineText. Anything else → 403 field-type.

Plus bounds on after: trimmed, ≤200 chars, no control characters (the ReviewSet validation shape, Program.cs:967-985). We deliberately do not apply krBadSerial server-side — the operator may legitimately set N/A.

5.5 Field identity

Resolve (tableId, fieldName) → (fieldId, type) from meta/bases/{baseId}/tables (the existing catalog entry, AirtableSource.cs:21). Cache in per-instance memory; populate on first miss; invalidate on a miss for an allow-listed name, or on a PATCH 422 naming an unknown field — refetch once, retry once, then fail. Nothing in Firestore, no pre-warm at boot.

Body: { "fields": { "<fieldId>": "<after>" }, "typecast": false }. Airtable accepts field IDs as keys, and the response comes back name-keyed unless returnFieldsByFieldId is set — we want name-keyed, because the cache and the entire kreview render key by name.

Why typecast: false: with true, Airtable coerces values and will create select options or link records to make a write fit. A serial edit must never mutate the customer's schema. false turns a wrong-shape value into a 422 we surface, rather than a silent side-effect on their base.

5.6 Blast-radius containment — structural, not a flag

Both passes traced every ShouldFire independently and agreed: no Slack lane keys on a field value.

LaneTriggerReachable by an edit?
AtbFailNotify.ShouldFire :34-37verdict=="fail" && prev!="fail", fires only inside ReviewSetNo — different handler
ShouldFireReleased :83-87verdict-only, same laneNo
ShouldFireSubmitted :199-213record id + createdTime + markerNo — an edit changes neither
ShouldFireReceived :296-316same marker discipline, already markedNo
AtbNetFlip :20-60Meraki flip timestampsNo — not an Airtable field

Containment therefore needs no suppression flag, only three disciplines: (a) the edit route is its own handler with no AtbFailNotify/AtbMilestoneNotify reference; (b) the write-through uses the single-record persist, which has no collect hook and so no milestone lane (SyncAsync's collect param is where those fire, AtbCache.cs:112); (c) phase-1 law: an edit posts nothing to Slack, period.

⚠ The trap. It is tempting to clear the slot's verdict on edit, since the PASS/FAIL was judged against the old value. Don't. Clearing a FAIL resets prevVerdict, so the operator's next FAIL on that slot re-fires a fail card into ext-mendo-c1techs — the one way an edit can reach Slack is by trying to be tidy. Phase 1 does not touch atb_review from the edit route. The MATCH/MISMATCH badge recomputes from the OCR read anyway; re-reviewing stays the operator's call.

5.7 Read-after-write

PATCH response record → persist to the cache doc → return in the POST response → client splices into KR[listKey] by id and re-renders, which is exactly the existing krSyncRecord path (index.html:10505-10510). Truth on screen in one round trip. No extra GET — the PATCH response is already the record.

Other open boards converge within 60s for free: the cron fingerprints Airtable's new value against lastFp, bumps atbEpoch, and their 10s poll re-reads. An optional Interlocked.Increment(ref atbEpoch) in the edit route cuts that to ~10s — harmless, worth including, not required.

5.8 CORS — not a prerequisite

This reverses what the inspect said. The console never reaches the bridge cross-origin: web/_worker.js:33 mounts /atb → the Cloud Run service and forwards same-origin so the cookie rides automatically (:24-27), and every kreview call is a bare fetch("/atb/…") (index.html:11244). No absolute airtable-bridge URL appears in the console at all. The CORS policy at Program.cs:18-32 is not exercised on the phase-1 path.

The *.pages.dev + AllowCredentials hole (board.md:189) stays real and stays a Kaizen item. The right-sized guard for this one route: reject any request whose Origin host isn't ours. The worker forwards headers verbatim (_worker.js:69), so Origin survives the hop. Five lines, route-local, no change to shared middleware — and preview deploys on *.pages.dev correctly can't edit.

5.9 Explicitly out of scope

  • Photos / attachments. Different host (content.airtable.com), needs fieldId, 5 MB cap against 2-12 MB originals, and a new attachment id that orphans every atb_ocr / atb_review / GCS-mirror key. Its own board.
  • Any table beyond Inventory and Decommission. Any field beyond the 39 serials.
  • Bulk or scripted writes. Batch PATCH. Writes from the API Browser.
  • A revert button, a history panel, a global CORS fix.

6 · Choices + consequences

Synchronous PATCH vs. Firestore-as-queue + worker

Picked: synchronous. Write the receipt first, PATCH in the same request, resolve the receipt, respond.

SynchronousQueue + worker
Load~1 request per operator click, against 5 req/s/base. Two orders of magnitude of headroom.Solves a throughput problem we do not have.
TruthOne place: the base, with a receipt beside it.Two places — queue doc vs. base — that can disagree.
Surface areaOne route.A drain lane needs its own narrow door (another CRON_TOKEN), retry policy, poison handling.
UXClick → spinner → the row shows Airtable's returned value or a named error.The UI still has to learn the outcome later, so you build the notification path too.

2nd-order: sync keeps the failure in the operator's hands while he is still looking at the row — he retypes and re-saves. Async defers the failure to a moment when nobody is watching. 3rd-order: a queue invites batching, batching invites bulk edits, bulk edits are how a typo-fix feature becomes a data-migration tool nobody gated for.

The operator's phrasing — "save to firestore as an auditable change and then ultimately update in airtable" — is a sequence, not a demand for asynchrony. Auditable means write the receipt first. Synchronous means resolve it in the same breath.

8 · First move

One route, one field, one record, end to end.

  1. Startup probe. GET meta/whoami, log the scopes, set hasWriteScope. Surface it on the gated /sources — not on the unauthenticated /version.
  2. The route. POST /atb/edit {tableId: inv, recordId, field: "Windows Ingest Device Serial Number", after} → pending doc → schema resolve → PATCH → applied → cache persist → {ok, edit, record}.
  3. The allow-list ships complete at 39 names (it's a constant, there's no reason to ship a partial one) but the test exercises one field.

Guinea pig: the textbox_sample0 ghost row that ShouldFireReceived already knows to ignore (AtbMilestoneNotify.cs:293) — a Jotform test record in the real base with no site attached, so a mistake is invisible to the customer.

The test that proves it:

  • Unit — AtbEditable.Allowed(tableId, field) over a fixture asserting all 39 names pass and that every photo field plus "Site" is refused.
  • Unit — the pure state planner (before/after, the three transitions) with no web host, Gate.cs-style.
  • Live — curl with the operator cookie against the ghost row: /atb/read?id=record shows after; the atb_edit doc reads applied with a real email in by; both Slack channels show nothing; a second identical POST yields a second applied doc with the base unchanged (idempotent by value); a POST naming a photo field returns 403 with only a failed receipt and the base untouched.

Into the plan (not written here — that's ~p/~e): the §15 amendment commit; AtbEdit.cs + route + gate; the AtbEditable constant; the schema resolver; the inline-edit affordance in krCompareFrag; the route-local Origin guard; the two unit suites; the live ghost-row proof. Photos are a separate board. The CORS fix and the argus_session expiry stay Kaizen, re-ranked.

9 · Unknowns

  • PAT scopes. Operator asserts write is available; unverifiable from code. The whoami probe settles it in step 0 and gates on it thereafter.
  • Field types of the 39 serials. Assumed singleLineText; "Salad OLO Screen" is suspicious. The type check turns a wrong assumption into a 403, not a bad write.
  • Jotform clobber. Jotform created these records. If a resubmission overwrites our corrected field, our receipt says applied while the base drifts back. Not answerable from this repo.
  • Attribution. Airtable's own revision history will name the PAT owner, not the reviewer. The receipt is the real who; the customer should be told that once.
  • The console's real origin set for the route-local guard (ARCHITECTURE.md:22 lists argus.com.ai; confirm the deployed hostname).
  • Whether PATCH-by-fieldId returns createdTime. It should; if it doesn't, persist via the SyncRecordAsync GET path instead.

10 · When to revisit

  • Operator asks for the photo → phase 2, its own design.
  • A pending doc orphans more than once → add a stale-pending sweep to the existing cron pass. Still no worker.
  • Jotform clobber observed → the cron must detect cache value ≠ latest applied after and flag it.
  • Edits exceed ~1/s, or anyone wants bulk → then batch + queue, and not before.
  • A second customer base → the base pin and allow-list become config, and meraki's Settings-doc pattern becomes worth porting.
  • argus_session gains an expiry (board.md:187) → the edit gate should require a fresh session, not merely a valid one.

11 · Pair reconcile — the splits

Split 1 — CORS. Driver called CORS a hard blocker in the inspect and said fix it before the first write route. Navigator found _worker.js:33: the path is same-origin, CORS isn't exercised. Navigator right, driver wrong; verified independently before adopting. Resolution: route-local Origin guard, global CORS stays Kaizen.

Split 2 — read-after-write. Driver proposed calling SyncRecordAsync after the PATCH. Navigator pointed out the PATCH response is the record, so the GET half is waste. Navigator right. We use the persist half only.
