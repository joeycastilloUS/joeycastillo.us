Meraki Provider Upgrade — who did what, time & cost

One build, four model tiers, paired per Rule 1. The regression: refresh clicks returned cached data. The fix: a proper provider — an interactive force-lane, a rate governor, parallel builds. Below is exactly how each model contributed, with wall-clock time and token cost.

What shipped

P0 — Force-read the fix you feel — manual refresh sends ?force=1; the bridge bypasses the TTL (with a per-key 10s floor) so your click always fetches live Meraki data. Auto/board polling stays cached. min=max=1 kills the two-instance split-brain.
P1 — Rate governor stay within limits — token bucket (~5 req/s, burst 10) + concurrency cap on every Meraki call; BuildPortmap/BuildVerify parallelized under it (sub-second builds, deterministic output order).
P2 — Honest asOf show real age — the app stamps the server's real asOf ("as of Ns ago") instead of your local clock.

Why the pair earned its cost
Fable (build) wrote clean code that compiled with zero warnings — and would have shipped the headline feature silently dead. The force path called RefreshAsync, whose inner TTL re-check re-imposed the exact freshness gate the force meant to bypass; with the warmer keeping the cache fresh, every "force" would have returned cache. Fable (navigator) traced it and called FAIL. Opus wrote the freshSince fix, Haiku confirmed the recompile. That's the reconcile doing its job: two brains caught what one would have shipped.
