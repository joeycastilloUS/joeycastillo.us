What was actually wrong

The Inventory section was a hardcoded 16-row device spec and Decommission a hardcoded 3-group spec, duplicated verbatim into the phone search page. 465 California St has a back kitchen with full Bread Start/Finish and Salad Start/Finish, so Airtable grew 23 Station 2 columns on its Inventory record and 10 on its Decommission record. Worse than invisible: krReviewTally measures “complete / released” against the same fixed list the renderer walks. And the 12 second-kitchen photos were already being OCR’d and billed — krRecAttIds walks every attachment on a record — while krAttStats counted only the listed fields. The cost meter was under-reporting real spend, not saving it.

The fix: the spec got smarter, not longer

Appending the rows globally would have given the other 91 sites eight phantom slots each and ~728 phantom findings. Instead the spec became record-aware.
// Airtable omits an empty column from a record, so column presence IS the layout signal.
function krInvRowsFor(rec){
  var f=rec.fields||{};
  var extra=KR_INV_ROWS_X.filter(function(r){ return f[r[1]]!==undefined||f[r[2]]!==undefined; });
  return extra.length?KR_INV_ROWS.concat(extra):KR_INV_ROWS;
}
No per-site config, no allow-list to maintain, and a third kitchen needs another entry in an array rather than new render code. Fourteen call sites were rewired to it — findings, duplicates, exceptions, review scope, read-state, cost meter, SN index, both views, the audit-stamp lookup — and the same resolver shipped into search.html so the serials are findable on a phone.

Field names are verbatim, and the asymmetries are real

  • The Bread Station 2 scanner photo field carries 10". The Salad one does not.
  • Salad Station 2 OLO Screen has no Serial Number suffix — the same quirk the base Salad group has.
A typo in any of these renders an empty slot that reads as a missing device, which is why every name is asserted against the live record.

The field we deliberately did not trust

Decommission carries Kitchen Layout on 91 of 92 records — Bread,Salad,Expo on 86, Bread,Expo on 4. It is the obvious signal for “which stations does this site have”, and using it would have been wrong.
Site 21’s value is the free text 21 - 465 Location, not a station list. Reading that field to decide what to render would have hidden the exact kitchen this change exists to surface. The record’s own columns decide; the field renders as evidence beside them.

The blocker the navigator stopped

My first cut memoised the resolvers by record id. The navigator refused it, and was right:
The page re-fetches records under the same id. krReadAllStores swaps the whole list; krSyncRecord splices one in. A crew submitting the second kitchen at 9pm, then the operator hitting Refresh — the normal flow — would have kept the cached 16-row spec, leaving the site releasable with a kitchen unreviewed. That is the exact defect this change exists to kill, resurrected by an optimisation worth sixteen property lookups.
Caches deleted, not invalidated. T7a/b/c mutate a record under the same id and assert the spec re-resolves. It also caught that my first N/A-exclusion test was vacuous — I had asserted it against a site with zero findings, so it proved nothing and my commit note claiming otherwise was false. Rewritten to break a slot deliberately (0 → 1 finding) and assert N/A removes exactly it.

What I broke, and fixed

I blanked SHARE_KEY in production for about two minutes, on an install night. Every sign-in-free crew link on the airtable-bridge — the rollout board included — returned 401.
I read cloudbuild.yaml before a rebase pulled in a commit that added - --update-env-vars=SHARE_KEY=${_SHARE_KEY} with _SHARE_KEY: '', then deployed from that stale reading. The config’s own comment called the empty default “stats lane closed, message still ships”. It is not: it overwrites the live capability token with empty.

Restored the same value deliberately: a-d-d/share-links.md is explicit that minting a new key instantly expires every link already in a crew’s hands. Then fixed the trap so omission cannot do it again — SHARE_KEY now rides --set-secrets from Secret Manager (ARGUS_SHARE_KEY) beside the other five, and the substitution is deleted. It also joins --remove-env-vars next to BRIDGE_TOKEN, because Cloud Run refuses to convert an env var from literal to secret ref in place — which failed my first attempt at the fix.
The first fix attempt reported success and had not worked. The background task exited 0 — that was the wrapper’s status, not the build’s. The build had failed. I caught it only by checking the revision list and finding no new revision. Every claim in this report is verified against live state for that reason.
