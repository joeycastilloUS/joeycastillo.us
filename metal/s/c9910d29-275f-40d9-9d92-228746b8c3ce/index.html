Why #735's guest got nothing

The parser fix worked. The reply was composed and Zendesk fired a notification. It was never delivered, and the reason is one line of platform behaviour.

Paired. Read-only — nothing changed. Scoped to #735, the shape production will actually see.

The cause

Zendesk never emails the author of the comment it is notifying about.

On the recovery ticket the public comment's author_id was the guest — who is also the requester. The trigger fired, the Notification event is in the audit, the recipient list names the guest. Zendesk simply does not send someone mail about their own comment.

It is platform behaviour, not a rule anyone wrote. The trigger that fired — "Support Happy - Initial Comment Email" — has no “current user is not requester” condition. And the audit's performer was an admin, yet delivery was still suppressed. So the suppression keys on who authored the comment, not on who performed the update. Authenticating as an admin is not enough; the comment itself must be authored by someone other than the recipient.

What #735 gets right, and it is the whole opportunity

Brendan's JotForm emails the alert as the guest:

FROM  joey.castillo@acmedev.com   ("Joey Castillo")
TO    hello@guestrelationstest.zendesk.com  ("Guest Relations Test Brand")

So on #735 the guest is already the requester, on the right brand, in a thread they can reply to. There is no need to create a second ticket to reach them — and creating one is what broke it. Post the recovery as a public, agent-authored comment on #735 and stop making a second ticket.

The trap that would have burned us a second time

#735 has no group, and every notify trigger in this account is group-scoped.

ticket 735   group_id = None

trigger "Guest Relations - Notify Requester ... When Public Comment Is Added"
  ALL  update_type        is  Change
  ALL  comment_is_public  is  true
  ALL  group_id           is  50360136527764     <-- cannot match a null group
  ALL  custom_fields_...  is  false
  ALL  current_tags  not_includes  hubspot_nps_survey

The group is null because the auto-assign trigger only matches the production Guest Relations address, not the sandbox hello@guestrelationstest.zendesk.com.

So a correctly-authored public comment on #735 today would still send nothing — and this time with no Notification event recorded at all, so it would look like nothing even tried. The fix must set the group in the same call.

The exposure to fix in the same breath

The Guest Relations notify template quotes prior public comments into the outbound email. The alert comment on #735 is public. So the recovery mail would carry the raw alert back to the guest:

On ..., Joey Castillo Wrote:
## Guest Experience Alert
**NPS Score** 3 / 10
**Guest Email** joey.castillo@acmedev.com ...

Their own data, with literal markdown asterisks, quoted beneath the apology. The same template also contains a malformed Liquid conditional that renders unpredictably. Making the alert comment private is mandatory, not polish.

A demand now contradicts reality

D13 says the alert ticket's requester is a neutral NPS-system identity — for privacy, and to prevent notification loops. On the JotForm path the requester IS the guest, and that is precisely what makes replying on the alert ticket possible.

The old assumption was "you cannot reply to a guest on the alert ticket." It is now inverted. D13 needs amending, or someone will helpfully restore the neutral requester and silently break this whole path. The comment in pi_run.c describing the follow-up-ticket mechanism is now false too.

Three things upstream in JotForm

  • The guest is copied on their own alert. original_recipients lists the guest as well as the Zendesk address, so they receive the raw internal template from themselves. If they reply-all it has no Zendesk headers and opens a brand-new ticket. Notification recipients should be the Zendesk address only.
  • JotForm spoofs the From as the guest. That fails SPF/DKIM alignment for the guest's domain. acmedev.com passed here; a real guest on a domain publishing DMARC p=reject can be suspended or spam-binned — Argus would never see the alert and the guest is never recovered. Worth one test from a yahoo or gmail address before production.
