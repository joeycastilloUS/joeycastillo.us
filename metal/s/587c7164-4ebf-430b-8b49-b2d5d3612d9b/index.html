Argus Access Control Confidential

Director brief · kASTIL Systems / Argus · v0 · r1022 · paired Opus + Fable5
Four of five Argus production services will hand their data to anyone presenting a password computed from today’s date. The fifth opens to a shared password that sits in readable configuration on four of them. All five are openable. Verified by live probe from an ordinary machine on 2026-08-01. Behind those doors sit a customer’s production support system, a second customer’s case corpus, and our own cloud account APIs. The fix is sequenced and mostly already funded — 59 of 73 points are on existing boards. The first three points close the worst of it today with configuration alone.

Argus reaches its data through five independent services. Each was given its own front-door check. One of those checks accepts a password computed from the calendar — the current date followed by a fixed suffix. It is not a secret; it is a formula, and it is written in our own source.

Live probe, run twice from an ordinary machine outside our infrastructure. HTTP 200 means the door opened and data came back:

These returned real payloads, not empty responses — between roughly half a kilobyte and five kilobytes of live content. Tomorrow’s date works as well as today’s, so the window is not bounded by the day.

The fifth service is not closed. meraki-bridge performs an exact credential comparison, so it rejects the computed password — but it accepts the shared console password, and that value is stored as readable configuration on four of the five services. Anyone who reaches one of the four open doors can read the credential that opens the fifth. Every one of the five is openable; four of them by a password anyone can compute from the calendar.

Same intent, five different implementations, and the weakest one is copied four times. That is the whole story in a sentence.

Additionally, on the customer support service
The write path is switched on, and both its access tokens are stored as readable configuration values rather than managed secrets. Whether the write path is reachable with the date formula alone is unconfirmed — that service’s source is not on the machine used for this review, and we will not claim it either way without reading the gate. It is the first thing to check, and the reason the write switch should go off now rather than after.

What we verified, and what we did not

This brief separates the two deliberately. Everything in the table above was probed directly, twice, by two independent reviewers — not inferred from documentation.

  • Verified: read access on four services with the computed password; real payloads returned; the exposure is not time-limited to a single day; the fifth service rejects the computed password but accepts the shared one, which is stored readable on four services.
  • Verified: customer sign-in via Google now works end to end in production, confirmed in the audit log — including a correct rejection of an unauthorised address. That is the foundation the fix builds on.
  • Not yet asked: whether anyone outside our own automation has used these doors. Request logs have not been reviewed for third-party access. Until that review lands we cannot say the exposure was unexploited, and no customer-notification decision should be made on the basis of this brief. This outranks every decision listed below. It needs an owner and a date today.
  • Not verified: whether the write path on the support service is reachable with the computed password alone.
  • Not verified: whether any automated job besides our own sweep holds the formula. If one does, retiring it needs a coordinated cutover.
  • Not verified: whether the proposed first-party routing can carry the heaviest data reads within our current edge budget. This is the one assumption that could change the shape of the fix.
Correction, on the record
An earlier pass in this session reported one of these four services as “already broken, not a regression.” That was wrong. It was never broken — it was open, and the first pass had simply never tested it with the date formula. The second reviewer caught it and the result was re-verified independently before this brief was written. The pairing requirement is what surfaced it.

How it happened

No single mistake. Argus accumulated five overlapping ways for a human to authenticate as it grew from one data source to five, and nobody retired the old ones when a better one arrived:

  • A shared console password, which doubles as a machine token and sits in readable configuration on three services.
  • The date formula, added as a convenience for a rolling data surface.
  • A real signed session — the correct mechanism — which only one of the five services actually honours.
  • Per-source tokens for one remaining service.
  • A break-glass hardware key door.

The growth pattern is ordinary and the outcome is predictable: each new service copied whichever check was nearest to hand. The date formula was the easiest to copy.

Three structural findings worth director attention
Any site on a free public hosting domain can call us as you. Our services accept credentialed browser requests from an entire shared hosting domain that anyone can publish to. A page there, opened by a signed-in operator, can read the same data the operator can. This needs no password at all — it is an independent route to the same information, and it survives every fix aimed at the passwords.

Sessions do not expire. The twelve-hour lifetime we believed we had is enforced only by the browser, which the holder controls. A copied session value stays valid indefinitely. Revoking access today means rotating a key that logs everyone out — we have no per-user revocation.

The break-glass door bypasses the access list. It is configured to a legacy address of our own that we deliberately removed from the approved list last month, and it does not consult that list. Break-glass should stay independent — one that depends on a possibly-broken list is not break-glass — but it should not point at an identity we have already retired, and every use should raise an alarm.

The fix

One session. First party. Fails closed.

Today the console talks to five services at five different addresses, so the signed session cannot travel to four of them — which is precisely why they invented their own checks. The correction is to stop them being separate addresses. Every service moves behind the single Argus address; the session then travels automatically; the browser never carries a password again.

The edge routes and nothing more. Each service still makes its own trust decision, using the same verification the working service already runs in production — this is largely copying three lines into four more places, not new invention. It is our existing Trust pattern applied unmodified, and the pattern’s two named failure modes are exactly the shortcuts available here: putting a master key on the edge, or letting the edge grow logic. We take neither.

Humans authenticate with a session and never a token. Machines authenticate with a signed request and never a session. The two classes stop being confusable, which is what allowed one credential to serve both roles and end up in readable configuration.

This is not new scope. Fifty-nine of seventy-three points already sit on approved boards from prior reviews. What was missing was the ordering and the dependencies between them — two of which the boards record backwards:

  • Locking the services to internal traffic is impossible before Phase 1, because the console still calls them directly today.
  • Rotating the session key must come after sessions can expire. Until then, rotation is the only revocation we have, and spending it early leaves us with nothing.

One item on the boards should be dropped, not scheduled: a code-reorganisation task carrying thirteen points of its own (unrelated to the contested figure in Decision 2). It closes no doors, and its two substantive pieces — the routing change and the proof that services can validate a shared session — are produced as by-products of Phase 1 regardless. It is the right instinct spent on the wrong target.

Decisions required

Before any of the three below
Name an owner and a date for the access-log review — whether anyone outside our own automation used these doors. Nothing else on this page can be sequenced honestly until that answer exists, and a customer-notification decision depends on it entirely.
1. Authorise Phase 0 now?
Turn the write path off, move readable tokens into managed secrets, delete dead credentials. Three points, configuration only, minutes to execute. Writes are operator-initiated, so nothing routine stops working.
Recommendation: yes, immediately. It does not close the read exposure — that needs Phase 1 — but it removes the armed write path from behind a public gate.
2. Settle the machine-authentication estimate
Three numbers exist for the same work: the board says 8 points, the standing plan says 18, this review prices it at 13. The reviewers deliberately did not choose.
This is a scheduling decision, not a technical one. It sits in Phase 3 and blocks nothing earlier — but the 73-point total is provisional until it is settled. Needed by the time Phase 2 closes.
3. Approve the architecture amendment
Three statements in the Argus architecture specification are now false: that the shared token is also the console password; that each service holds exactly one vendor secret (one value is on four of them); and that each is a read-only proxy — the support service has its write path switched on. That third one is the same fact driving Phase 0 and Decision 1. Proposed: correct all three, and add a new section recording the access model above.
Architecture is human-owned by policy; it is not amended without approval. Until it is, the console change removing the password box stays parked — specification moves before code, deliberately.

The part that is already right

This brief is a finding, not a failure report. The reason the exposure is now fixable on a funded, sequenced path is that the destination finally exists.

Shipped and verified today
Google sign-in works end to end in production, restricted to a single named identity, with a fail-closed access list that correctly rejected an unauthorised address on its first real attempt. The console’s password box is removed and reviewed. The identity we need to consolidate onto now exists — which is what makes the rest of this affordable rather than theoretical. Six weeks ago there was nothing to consolidate onto.

The exposure described here is not new; it has been accumulating since the second data source shipped. What is new is that we can now see all of it at once, and that there is finally a correct destination to move to.
