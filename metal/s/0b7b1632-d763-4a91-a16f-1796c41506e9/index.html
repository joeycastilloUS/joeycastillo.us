~i — Identity is in the wrong house

Paired inspection (two blind passes, reconciled) · driver Opus + navigator Fable5 · project: argus · r917 · trigger: operator — "meraki-bridge seems like the wrong place"

Verdict: the operator's instinct is right — the console's entire human-identity surface lives inside meraki-bridge, a service named for network switches. It should be extracted to a dedicated argus-identity service. But not now: get both logins working first (Google + Overlord), then extract. Migrating an auth flow that has never once authenticated anyone — across the one deploy pipeline the architecture doc flags as forked — is two unknowns in one incident. Working logins are the regression test that makes the move safe. The _worker.js proxy is the seam that makes the extraction flag-day-free and makes today's login work non-throwaway.

What it is — the smell, quantified

meraki-bridge (bridge/meraki-bridge.csproj) has 35 routes. Only 22 are Meraki. 10 are identity/ops — ~30% of a "Meraki" service is the console's identity substrate:

Identity/ops routeConcern
/auth/{p}/login, /auth/{p}/callback, /auth/me, /auth/logoutOIDC member federation (Google)
/auth/key/status, /auth/key/challenge, /auth/key/verifyEd25519 Overlord key door
GET/POST /settingscarries the crew allow-list (who may sign in)
/ops/doorsthe just-built Argus Ops surface

Why it's the wrong house

1. It violates the architecture's own law. ARCHITECTURE.md canon: one Cloud Run service per source — own secret, own IAM, own deploy. The fleet honors it: gcp-bridge=Vertex/cost, zendesk-bridge=Zendesk, slack-bridge, cloudflare-bridge, airbyte-bridge. Identity is not a source — it's the substrate every source's gate depends on. It has no business inside the Meraki box.
2. The deploy coupling is real and we felt it. Twice this session we rebuilt + redeployed the Meraki service purely to change auth (removing the Slack door; adding /ops/doors) — each redeploy putting the 22 Meraki data routes at risk for an identity change. And every auth deploy rides meraki-bridge's known CI fork (canonical acmedevUS/meraki-bridge vs the working bridge/ copy, flagged in ARCHITECTURE.md).
3. The crypto is already pure-C. The Ed25519 identity core is a pure-C sidecar (bridge/identity-skill); the C# is only a thin OIDC/session/crew jacket. A dedicated identity service is the natural seam to let the jacket shrink and the Purcius-native core grow — consistent with the Language Boundary law (C# only for foreign-API jackets; OIDC is the only foreign API here).

The non-conflation (important)

This is not the purcius-bridge-auth plan (2026-07-20). That plan is a different auth: it replaces the guessable daily key (yyyymmdd~go) with prime-signed Ed25519 wire auth between machines and the data bridges — the R0 data-plane / machine-to-machine fix. It says nothing about the human/member identity surface. So there is no existing approved plan to extract human auth from meraki-bridge — this ~i is a new call. Keep the two "Purcius auth" threads separate: machine wire-auth (purcius-bridge-auth / R0) vs human identity home (this).

Where it should live

A dedicated service named argus-identity (navigator's naming call, reconciled):

  • Not identity-bridge — in this fleet -bridge means "foreign-API jacket for a source." Identity is substrate, not a source.
  • Not purcius-identity — invites conflation with the machine-plane purcius-bridge-auth plan above.
  • Stays C# OIDC jacket + C sidecar today; it is the seam to go pure-Purcius later (jacket shrinks, sidecar grows).

Sequencing — the load-bearing call

Logins first. Extract second. Firm (both passes). The counter-argument — "extract first so you don't wire Google creds into a service you're about to gut" — dies on the worker seam: _worker.js makes /auth/* first-party at the console domain (argus.com.ai), so the Google OAuth redirect URI points at the console's path, not the run.app service. Wiring the creds today is preserved across the extraction by design — nothing done for login-day is wasted. Meanwhile, extracting an auth flow that has never authenticated anyone means debugging OIDC + Overlord + a service migration at once. Working logins are the regression test. It also honors the operator's own gate literally: "nothing changes until I can log in."

Migration — flag-day-free (do it after login-day)

  1. Both logins green on the current meraki-bridge (the baseline / regression test).
  2. Scaffold argus-identity: move /auth/*, /ops/*, /settings + the key sidecar. Bind the shared state: argus-session-secret (authSessionKey), Firestore db argus (settings/members/sessions), providers.json, BRIDGE_TOKEN.
  3. Deploy alongside; smoke /auth + /ops/doors directly at its run.app URL.
  4. Worker flip: replace the single BRIDGE const in _worker.js with a per-path target map; route /auth, /ops, /settings → argus-identity. (Note: /ops is not in today's PROXY list — add it.)
  5. Verify sessions minted by argus-identity validate on the Meraki data routes (shared authSessionKey + sessions-doc shape). This is the step most likely to break.
  6. Gut identity from meraki-bridge, one redeploy, and reconcile the CI fork.

Risks

  • Biggest risk of doing it NOW: splitting an auth flow that has never authenticated anyone, across the one deploy pipeline the architecture doc flags as forked. → Sequence it after login-day.
  • Most likely break during migration: cross-service session validation — meraki-bridge rejecting a cookie minted by argus-identity (key or session-doc-shape drift). Mitigate: identical AUTH_SESSION_KEY + identical SessionSign payload shape, verified in step 5 before the worker flip.
  • CI fork on meraki-bridge (canonical repo vs working copy) should be reconciled as part of step 6, not carried into the new service.

Recommendation / first move

Do nothing structural yet. First move is still login-day: wire the Google OAuth creds (operator creates client) + build the Overlord warrant signer, prove both logins from the operator's machine. Then the first structural move is step 2 above — scaffold argus-identity and stand it up alongside, worker-flip last. Board it as its own IDENTITY-EXTRACT board, blocked on login-day.
