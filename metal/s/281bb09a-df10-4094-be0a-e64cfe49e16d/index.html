Zendesk NPS-Detractor Automation — Drill-Down + Complexity Assessment

One production workflow: auto-recover NPS detractors with a food-illness safety gate. Every figure below is verbatim from the live configuration. Click a block to see its steps; click a step for the exact trigger conditions. Each card is plain-terms first, then a bulleted technical spec.
Zendesk can run this natively. At this depth it takes:
  • 7 custom triggers (33 conditions, 12 actions), 2 authenticated webhooks, 2 hardcoded custom fields, 1 group, a 9-tag free-text state machine.
  • 4 setup steps with no API on any stack.
  • No config-as-code, no versioning, no diff, no rollback, no master on/off.
  • 3 steps with no native path — the only reason custom code exists.

OUR CODE /promo-fulfill — re-check illness, mint code, write it back
Plain termsMake one $10 code for this ticket and write it on the ticket. Zendesk can't compute a secret-keyed code, so our service does it and writes it back.
webhook → illness re-check (live tags) → derive HMAC code → PUT SorryCodes + internal note └─ fail → 502 → Zendesk retries
Technical — flow
  • Guards: 503 until PROMO_SECRET seeded; env-required (prod 403); GET ticket; LaneGuard

  • HMAC-SHA256(PROMO_SECRET, env + ":" + ticket_id) → MENDO-XXXXXXXX

  • Same ticket = same code forever; two tickets can't share one; env keeps arm A / arm B distinct
  • Secrets: PROMO_SECRET · BRIDGE_TOKEN · ZENDESK_SANDBOX_B_TOKEN

Correctness of "never auto-reply to a guest reporting illness," "exactly one $10 code per ticket," and "never touch the other arm's tickets" is spread across seven trigger records, one external service, and nine untyped strings. No single place defines or validates any of it: no config-as-code, no versioning, no diff, no staging promotion, no rollback, no test harness, no master switch. Changes are made live.

Manual setup: 7 steps, 4 with no API on any stack

  1. Create + train the custom food-illness Topic (Intelligent triage) — no create API.
  2. Enable Copilot intelligent triage (the add-on) — Admin-Center only.
  3. Configure the AI agent + its auto-reply trigger — no config API.
  4. Build the promo custom-action + tone personalization — Admin-Center only. (Legacy of the pre-Option-A design; the deterministic lane retired this in favour of the S5a trigger → service path.)
  5. Provision the escalation group before the triggers that reference it (our tooling 409s a dangling reference; the raw API would misroute).
  6. Create + authenticate the 2 webhooks with bearer tokens.
  7. Seed 3 secrets: BRIDGE_TOKEN, PROMO_SECRET, ZENDESK_SANDBOX_B_TOKEN.

Nine standing hazards

HazardWhat actually bites
Object orderingGroup must exist before the triggers that assign it, or (raw API) a dangling id silently misroutes.
Position-ordered re-run loopZendesk re-runs the whole trigger list after any fire. Correctness needs you to hold that loop in your head — and nothing warns you when a reorder changes intermediate tag states.
Async classification racesThree safeguards exist only because the classifier lands after create (T4 present-gate, T6 no-Create, service illness re-check). Miss one and a sick guest can get a coupon.
Marker-on-fireEvery once-only guarantee is a tag set at fire time, not success. The only retries are two deliberate 502-webhook paths (promo-fulfill and nps-cc's failed-PUT); nps-cc's resolution miss never retries.
Tag clobberA single-ticket PUT replaces the whole tag list — the service never touches tags on the code write, or it could erase a concurrently-landed illness tag.
Scattered arm state8 independent flags, no master arm; re-apply needs special logic in two paths just to not silently disarm a live trigger.
Whole-record editsAdding one condition to the vendor trigger means re-PUTting its entire definition; a sloppy edit deletes its actions.
Silent stalenessDelete the Topic and the S2 trigger stays armed against a value that no longer exists — undetectable natively. Our /intent-status "stale" probe exists only because the platform has none.
No test / diff / rollbackNo native preview, staging diff, rollback, or environment promotion. Live only.

What has no native path — the code that cannot be removed on any Zendesk

Limit 1 — trigger webhooks are one-way.
  • A trigger can call out but can never use the response.
  • "Compute a value, put it on the ticket" is natively impossible — an external service must write it back.
  • That write re-enters the trigger engine as a new update (the loop the once-markers break).
  • ZIS can consume a response, but a ZIS flow is itself hand-authored code with no secret store or crypto — it relocates the code, doesn't remove it.
Limit 2 — no compute or secret primitive.
  • Triggers can't hash, hold a secret, or query a table.
  • Coupon mint: HMAC(secret, env:ticket) → unforgeable without the key, identical per ticket, never shared.
  • DO resolution: parse the store, look it up in an external map, CC the DO + store inbox — data lives outside Zendesk, and the native CC action takes only a fixed user id, not a data-driven recipient.
Limit 3 — no create/config API for the AI layer.
  • Custom Topics and the AI agent + its reply trigger are permanently manual.
  • That's why the semantic detector ships as a placeholder with a whole pin-and-validate code lane built around the hole.
Bottom line. Zendesk can be configured to do this — at this depth it is a hand-built, unversioned distributed system behind a helpdesk UI, and three steps can only exist as external code.
