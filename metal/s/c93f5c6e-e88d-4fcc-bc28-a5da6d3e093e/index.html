Navigator's catch. The driver's plan would have built the whole tab against unreachable routes.

1. Intent

Argus already answers two questions: "is it up?" (Watch) and "is it configured sanely?" (Audit, point-in-time). Nobody answers "what changed in the intended config, when, and who did it?" — and nobody can from the Meraki dashboard alone, because its own change feed provably misses roughly one config change in four or five.

Drift gives Argus memory. A blessed baseline per subject, a cheap gated compare, and a short list of unaccepted changes an operator can empty — each carrying an honest answer to "why did this happen," including an honest "we don't know." It turns two live-but-unconsumed bridge routes into a product surface, and it retires DR1–DR8 (39 pts, seven weeks, zero built) with a shape that fits the codebase.

2. Scope

In

  • bridge/Drift.cs — canonicalisation of five sections (net, devices, switchports, ssids, l3), sha256 per section, canonVer:1, change-feed gate + 24h re-hash floor, structural diff, attribution resolver.
  • Firestore in the existing named DB argus: drift_baseline/{subjectId}, drift_state/{subjectId}, drift_events/{subjectId}/events, drift_cursor/{subjectId}. Subjects = 5 networks + the bound config template.
  • Routes: POST /drift/run (key-authed, Scheduler-only) · GET /meraki/drift/state (open) · GET /meraki/drift/events?network= · POST /meraki/drift/accept (session-authed, Firestore-only).
  • Cloud Scheduler */15 straight to meraki-bridge run.app.
  • The Drift tab exactly as approved in the ~laf.
  • CI fork reconcile — first item, gates every deploy.
  • SwitchPort.Enabled projection into /meraki/portmap — off the critical path, included so the Network tab agrees with what Drift reports.

Out — explicitly

  • Any Meraki write. Accept writes Firestore only. The read-only law holds.
  • Observed state — port status, poeDraw, clients, lastSeen, uplink. Watch owns it.
  • Alert channels (Slack/email/Signal). After the tab earns trust, not before.
  • Historical backfill. Baseline auto-locks on first clean sweep; history starts at t0.
  • Multi-tenant / non-Mendo orgs. appliance/vlans, fixedIp, group policies.
  • A C99 differ. Retiring the audit's OVR-* checks.
  • bridge-tests CI enforcement — that is an open 8-pt SECURITY-HARDENING item. Don't smuggle it in here; run the suite by hand per item and say so.

3. Approach

One tick, five steps, all deterministic and model-free:

Cloud Scheduler */15
  -> POST /drift/run  (key-authed)
       1. GATE      one org-wide /meraki/changes since drift_cursor covers ALL subjects
                    open a subject if it has feed entries OR its last full sweep > 24h
       2. SWEEP     gated-open subjects only; read INTENDED config from the Meraki
                    client directly -- SwitchPortsAsync (has Enabled), DevicesAsync,
                    NetworkAsync, WirelessSsidsAsync, raw L3 rules
       3. PRINT     canonical JSON -> sha256 per section, canonVer:1
       4. DIFF      vs drift_baseline; on mismatch, structural diff -> [{path,before,after}]
       5. EMIT      append drift_events with attribution RESOLVED NOW and stored immutably;
                    update drift_state (flip-only changedAt)
  -> GET /meraki/drift/state | /events   (console, first-party through the worker)

Two findings that shaped this plan

ARGUS attribution is direct evidence, not inference. bridge/Meraki.cs:31 sets UserAgent.ParseAdd("meraki-bridge/0 (acmedev)"). Since apiRequests returns userAgent, any entry carrying that string is provably us — no guessing. And every Meraki write path (name, device-name, port-vlan, port-poe, template, remediate-apply/rollback) already emits an AUDIT line to Cloud Logging as a second corroborating source. Both the ~laf driver and navigator had listed "can we identify our own bridge?" as an open unknown. Closed, with evidence. Driver's find.
The rate-limit worry dissolves — because of the config-only decision. Excluding observed state means the sweep never calls ClientsAsync or SwitchPortStatusesAsync — which is precisely what drove portmap's N+2 fan-out. A full sweep is ~5-7 calls per network, ≈33 for all six subjects. A gated tick is 1-2. Even a pathological day where every one of the 96 ticks opens the gate lands near 3,200 calls against a ~10 req/s org budget. Safe by orders of magnitude; no new guard beyond keeping the sweep sequential (no Task.WhenAll) and relying on the client's existing 429 retry (Meraki.cs:50-58). Both passes computed this independently and agreed.

4. Phases

Phase 1 — Engine core + external proof. CI fork neutralised first, then canonicalisers, the gate, /drift/run, /meraki/drift/state, and the baseline/state Firestore model. Deployed. Exit: a third party GETs the state route and sees real sha256 fingerprints and timestamps for six subjects. This ships before events, before attribution, before any UI — and it could deploy this week.
Phase 2 — Production tick + events + attribution. Scheduler */15; diff → drift_events; the attribution resolver; the template subject. Exit: timestamps advance unattended, and a hand-made lab change appears as an attributed event within 15 minutes.
Phase 3 — The Drift tab, read-only. Route coverage, tab registration, cards, density strip, shape-aware before→after, deep link. Exit: the operator sees the Phase-2 event in the console at argus.com.ai.
Phase 4 — Accept + polish. /meraki/drift/accept + woprGated, the two-step inline accept, the non-destructive poll, the stale banner, the portmap projection fix. Exit: the list can be emptied.

Real dependency edges vs false ones

Real: CI reconcile → any deploy · canonicalisers → everything · events writer → the UI · session auth → accept (already live in Auth.cs, no new auth work).

False: the UI does not wait on attribution correctness — an unresolved event renders honestly as UNKNOWN. The template subject does not block the five networks, because baselines lock per subject.

One ordering constraint that is easy to miss. Attribution is resolved at detection and stored immutably. If the */15 scheduler goes live before the resolver exists, every event detected in the gap is permanently second-class. Within Phase 2, the resolver lands before the Scheduler job is enabled — or the job stays paused until it does. Driver's catch; the navigator's board ordered the Scheduler item first.

Why the gate is Phase 1 and not Phase 5: DR1–DR8 put the change-feed gate fifth. The gate is not a feature bolted on for cheapness — it is the tick's control flow. Retrofitting it rewrites the sweep loop.

5. Constraints

  • Read-only to Meraki, forever. Accept writes Firestore only.
  • Tier-0. Deterministic classify, no model anywhere in the loop, $0/cycle.
  • Attribution immutable at detection. Solid border only for direct API evidence; everything inferred says "inferred."
  • canonVer in every document from day one. A bump triggers a silent re-baseline, never a drift verdict.
  • Fibonacci 3 or 5 only; boards 13–21 points; every item a verify loop.
  • No new root CSS variables. The tab uses only shipped console values.
  • Nothing deploys to meraki-bridge until the CI fork item closes.
  • Rule 10: every phase ends externally verifiable from a machine that is not the dev box.
Language-law tension, named not glossed. The canonicaliser and differ are logic we own, written in C#. Justification: the design correctly locked engine-in-bridge — the Meraki client, the Firestore binding, and auth all live there, and a separate service was DR1's mistake. Mitigation: the canonicalisation rules are pinned as data (golden files), so a future C99/nous port replays them byte-for-byte, and the stored normalised JSON lets a new differ replay history without re-sweeping. A conscious exception, not drift into "C# because convenient."

6. Unknowns

  1. Config-template surface shape. Templates have no devices; they have switch profiles (configTemplates/{id}/switch/profiles + per-profile ports). The audit's GetTpl path proves template L3 works, but the profile-ports shape versus SwitchPort is unverified, and a profile is keyed differently from a serial. This is the likeliest estimate-breaker.
  2. Does a Cloud Build push trigger on the stale acmedevUS/meraki-bridge actually exist? Unknowable from this repo — needs gcloud builds triggers list. The plan assumes yes until proven otherwise, because the downside is rolling live auth back six weeks.
  3. Timestamp skew between configurationChanges.ts and apiRequests.ts. The ±60s window assumes a shared clock and second precision. The tolerance constant can only be tuned against live data.
  4. Change-feed truncation. /meraki/changes is single-page, no cursor, 1000 cap. A window with >1000 changes silently truncates. Mitigated by 15-minute windows plus the 24h floor; residual risk accepted.
  5. Firestore 1MB ceiling against the template's real L3 rule count — unknown until the first template sweep.
  6. Scheduler auth provisioning. The drift tick needs a key header on a new job hitting run.app directly. The Watch tick goes through gcp-bridge, whose source is not on this box, so there is no in-repo precedent to copy.
  7. Whether cadence's ChangeGate.ShouldHash is reachable for a verbatim lift, or gets re-implemented from its recorded semantics (feed hit + 24h floor). Either fits the estimate.

7. When To Revisit

  • Hard v2 trigger: the first real drift whose section diff cannot be expressed by the three shape renderers — or the first canonicalisation false positive on a no-op Meraki representation change (e.g. allowedVlans as "1-1000" one day and enumerated the next). Bump canonVer, revise the canonicaliser spec.
  • Product v2 trigger: the operator accepts more than three events in one section in a week — that is real usage data re-opening the per-section vs per-entity question (§8).
  • Trust trigger: the unexplained count trends up instead of staying rare. That means our attribution model is wrong, not the network.
  • Scale trigger: subjects past ~15 networks, event volume past ~200, or the change feed ever hits the 1000 cap. The density strip and the un-paged stream both break there.
  • Milestone check-in: after Phase 2 runs unattended for 7 days, hand-compare drift events against the Meraki dashboard change log once. That measures the 20-25% miss-rate claim on our own org rather than trusting a number from a June inspect.

The open question — and the driver has changed position.

Accept granularity was left to you in the ~d and the approved mockup shows per-entity. The navigator now costs the alternative properly, and the argument is better than the driver's was:

Per-section is a hash swap — copy the observed section hash into the baseline, done, provably correct. Per-entity requires merging accepted entities into the baseline's canonical section JSON and recomputing a hash that must then not re-flag the accepted entity while still flagging its unaccepted neighbours. That is partial-baseline mutation, roughly +5 engine points, and a new class of canonicalisation bug — in v1, before anyone has accepted anything even once.

The driver's original objection was that accepting port 7 shouldn't silently bless port 11. That objection largely dissolves on inspection: Accept lives only inside the expanded drill-down, which shows the whole section diff — you cannot bless what you have not been shown.

Reconciled recommendation: ship per-section in v1, with per-entity as a costed v2 story triggered by real cherry-picking behaviour. The mockup's per-entity affordance moves up to the section header. This is your call and the estimate assumes per-section — say the word and it changes.
