Auto-CC the District Operator / Store — three technical approaches

Zendesk NPS-detractor response CC · off-the-shelf options · diagrams + facts · sources inline · 2026-07-23

The requirement

On every response to an NPS-detractor ticket, add two parties as CC: the District Operator (DO) who owns the store, and the store inbox. The store is written in the ticket body (e.g. "12-SM"). The correct DO for a store is not stored in Zendesk.

Facts that constrain the options

No Add-CC trigger actionZendesk trigger/automation actions include "Add follower" but no "Add CC." Source.
Follower = agents onlyThe follower action takes a static agent user. Non-agent emails submitted as followers are removed. Source.
API accepts CC by emailPUT /api/v2/tickets/{id} with email_ccs:[{user_email, action:"put"}]. If the email has no user, a user is created. Source.
Lookup fields, actionsCustom-object lookup relationship fields are usable in trigger conditions and notification actions, not in ticket-membership actions. Source.
email_ccs limitsMax 48 email CCs per ticket; a CC change in the same API update as an internal note is ignored; the field requires "CCs and followers" enabled in settings. Source.
Store→DO sourceNot present in Zendesk (verified live: no ticket field, group membership, or object links a store to a DO). The mapping exists in Mendo operational systems.
Observed current behaviorIn 25 recent NPS-detractor tickets, the DO was added as CC + follower by the inbound email's CC header (audit via.channel = email), not by a trigger or agent. Argus Escalations tab.

Approach A — Organization field + webhook + trigger

Store the CC email(s) on an organization custom field; one trigger calls a webhook that PUTs the ticket's email_ccs. Documented method: Jason Riddell, "Adding CC and Followers — The Scalable Way."

Approach B — Custom object + lookup + webhook

Model stores as a Zendesk custom object with a lookup field to the DO user; a webhook dereferences the lookup and PUTs email_ccs. Zendesk custom objects docs.

Approach C — iPaaS (Zapier / Make) + spreadsheet

A no-code automation platform reads the ticket, looks the store up in a spreadsheet, and PUTs email_ccs via a raw API-request step. Zapier Zendesk + Code + Sheets.

Common element across all three

SharedThe CC is added via PUT /tickets/{id} email_ccs in all three; native trigger actions cannot add a CC.
SharedThe store→DO map is loaded into a datastore (org field / custom object / spreadsheet); it originates from Mendo operational data, not Zendesk.
Marketplace appsThe purpose-built app "Carbon Copier" (CC from a field) was removed from the marketplace after Zendesk deprecated its HTTP targets. Source. SweetHawk's documentation for adding a CC directs to a webhook + trigger. Source.

Current state at Mendo (observed)

Escalation todayIn the 25 most recent NPS-detractor tickets sampled, the DO was added as CC + follower via the inbound email's CC header (audit via.channel = email). No trigger, automation, or agent added it.
ImplicationA store→DO resolution is already occurring in the system that generates the NPS survey email. Scope of this sample: 25 tickets.
