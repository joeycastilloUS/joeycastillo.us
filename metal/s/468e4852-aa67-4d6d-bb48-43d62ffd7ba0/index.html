Pure. The bridge holds no secret.

Purcius bridge auth — the prime lane. Asymmetric, done right, once.
~D · ~p · ~e · paired: Opus design + three Fable red-team rounds · v3 PURE (supersedes v2 symmetric — operator: "I want pure")
SCOPE — Purcius production only. pi_run on both primes, the 6 lanes, the 15s sweep, and the coupled gcp-bridge twin. Browser callers are out. The date string yyyyMMdd~go — forgeable by anyone who knows the format — dies.

1 · The pure shape

The only secret is pi_run's private key, on the trusted prime, generated there, never transmitted. The bridge holds only public keys — it can verify, it can never mint, and a leak of everything it stores is a non-event. No shared secret, no mint-capable key on the most-exposed box, nothing to rotate-in-flight. This is the structural fix the symmetric cap could only quarantine: asymmetry moves the trust to where the trust already is.

Ed25519 (RFC 8032 PureEdDSA), per-prime keypairs, key-id in header, signing a domain-separated request-bound canonical. pi_run signs; the bridge verifies with a public key. That's it.

2 · Vendor Monocypher — and this is pure

"Roll our own / no frameworks" means zero-dep, auditable, bare-metal, no black box, no package manager. It does not mean personally typing field arithmetic over GF(2²⁵⁵−19). The AES and SHA already in crypt.c are transcriptions of FIPS reference algorithms — nobody invented AES. Vendoring a reference Ed25519 into a source file we compile is the same discipline.

Why not hand-roll — the one fact that settles it: Ed25519's foot-guns do not appear in test vectors. A variable-time scalar-mult leaks the private scalar bit-by-bit via timing and passes every RFC 8032 KAT green. Your suite goes green while you leak the key. Field-carry bugs verify sometimes. Verify-side cofactor/malleability (must enforce S < L, canonical encodings, reject small-subgroup points) is exactly what shipped broken in cryptographer-written libraries. The substrate already knows where the line is — crypt.c ships SHA-512 tagged "required internally by Ed25519." The hash half is already ours and correct; the missing piece is the curve arithmetic — precisely the part you must not write by hand.

  • Pick Monocypher (CC0/BSD-2, ~1 file, no allocations, constant-time, Wycheproof-clean, enforces S < L + canonical encodings = strict RFC 8032 verify). TweetNaCl is smaller but frozen and uses cofactored verify — weaker on the exact edge cases, and our verify runs on a public bridge.
  • Own it as source: src/sdk/nous/security/skill/crypt/ed25519.c beside crypt.c — vendored, not pasted-in; header pins upstream version + commit + file SHA256. Add RFC 8032 §7.1 KATs + a Wycheproof EdDSA subset to security/tests/ so our build is provably correct and a future bump can't silently regress.

3 · What gets signed (the one change Fable insisted on)

The crypto is only ever as strong as what it commits to. The breach that lands isn't a key ceremony slip — it's a signature that commits to too little: a "read" sig retargeted as a "write," a zendesk sig crossed to gcp, a swapped body. So bind the full request, mirroring cap.c's proven NUL-separated shape:

signed = "purcius-bridge-v1" \0          domain separation — no cross-protocol reuse
         audience \0                       "zendesk-bridge" | "gcp-bridge" — no cross-bridge replay
         verb \0 tenant \0 ticket \0
         sha256( method | rawpath+query | body )   32 bytes — the exact action, incl. query
         ts(8, little-endian)              matches cap.c ts8 encoding
         nonce(16)
         key_id \0                         binds the claimed signer — can't be relabeled

Header X-Metal-Key: hk-01 | vegas-01 selects the pubkey; key-id is also inside the signed bytes. Per-prime keypairs give attribution (which prime signed) + independent revocation (retire one prime, leave the other).

4 · The C# bridge — P/Invoke the one verify

The bridge verifies with the same ed25519.c pi_run signs with — compile ed25519.so, ship it in the Cloud Run container, 10-line [DllImport]. One implementation, zero cross-language drift (the failure you're avoiding: C-sign produces a signature .NET-verify rejects, found in prod during the sweep). It's less code than a NuGet dep and fits the existing C#-jacket pattern.

  • Marshaling (these bite): canonical is NUL-bearing → pass byte[]+length, never char*; build with explicit byte copies, never string concat; ts little-endian (BinaryPrimitives, not host-endian); hash the raw received bytes before ASP.NET re-serializes; length-check sig=64, pubkey=32.
  • Cross-language KAT in CI (required): a committed {seed, canonical-inputs, expected-sig} fixture from the C signer, asserted green by C# on every deploy, plus a known-bad corpus (flipped bit, S ≥ L, wrong audience) that MUST reject.

5 · Replay — pure doesn't fix it; idempotency does

Signatures are stateless; replay is a state question. The nonce ring is process-local BSS (auth.c:18); Cloud Run overlaps revisions on deploy + wipes it on restart, so a captured in-window request can replay against a fresh instance (--max-instances=1 narrows, doesn't close).

  • Nonce ring stays as the cheap same-instance first line.
  • ts window ±30s (tighter than cap.c's 60s — NTP-synced, survives cold-start + TLS on the sweep).
  • Durable per-ticket idempotency on every mutating verb, at the Zendesk system-of-record — the only control that survives instance churn. Mostly already there (recovery-send idempotent on draft_id, tag-claim reads-then-merges). Reads are naturally idempotent.
  • Pure bonus: requests are now attributable per key-id, so the idempotency key can include the signer — double-execution across HK+Vegas on the same ticket becomes detectable, which the shared daily key never allowed.

6 · Key custody — the clean win

  • Private seed on the prime: /var/nous/keys/<key-id>.ed25519, mode 0400, dir 0700, service-user owned (mirrors cap.root). Generated with crypt_fill_random (/dev/urandom). RLIMIT_CORE=0, mlock the seed page, MADV_DONTDUMP, volatile-scrub after deriving the keypair and before any fork. Never logged, never in a telemetry field.
  • Public keys committed to the repo (security/.../pubkeys/hk-01.pub, vegas-01.pub, status active|retired) — they're public, versioned, code-reviewed. Bridge bakes them into the image / loads at boot. No secret on the bridge, ever.
  • Rotation = publish new pubkey + retire old key-id. New keypair on the prime → commit hk-02.pub → bridge accepts hk-01+hk-02 → cut pi_run to hk-02 → retire hk-01. No secret in flight.
Caveat worth naming. Pubkey-in-repo moves the trust root to "who can land a signed commit + trigger deploy." Acceptable only because signed commits + the pre-commit hook are already Project-DoD canon (P4/P5). That commit-signing gate is now load-bearing for auth — don't let it weaken.

7 · Migration — telemetry-gated, per-audience independent

Phase 0 — Additive + see it. Bridge accepts daily key AND a valid signature. Log auth_method=sig|daily, key_id, ts_skew_ms — never the signature. The daily-key sweep never notices.
Gate: telemetry live; baseline 100% daily.
Phase 1 — Land the primitive. Vendor ed25519.c + KATs; build the shared canonical + the native ed25519.so + P/Invoke verify + cross-language KAT green in CI. Generate per-prime keypairs, commit pubkeys.
Gate: a prime's authenticated pre-flight 200 probe on a read endpoint returns auth_method=sig, while daily still works.
Phase 2 — Lower-traffic bridge first. Audience-binding makes the two bridges independently migratable — cut over the lower-traffic bridge first to derisk marshaling without risking the sweep. HK signer → Vegas signer, watch telemetry.
Gate: zero daily on that bridge, a full cycle.
Phase 3 — The sweep-critical bridge. Now zendesk-bridge: HK first, bake a UTC-midnight cycle, then Vegas. Pre-flight probe before any mutating traffic depends on it.
Gate: both primes on sig, zero daily, a full day.
Phase 4 — Retire + fail CLOSED. Delete the daily branch (Config.cs AcceptsBearer) and rip daily_key() from pi_run at all 5 sites (142/195/215/233/405) + pirun_bench.c. Refuse all without a valid signature.
Done = a forged yyyyMMdd~go is rejected by both services, verified from outside.

9 · First move

Two things start in parallel, neither touches the sweep: Phase 0 (bridge additive + telemetry — changes nothing live) and Phase 1's load-bearing build — vendor ed25519.c, stand up the shared canonical + native verify + the cross-language KAT. Everything after is gated on a green KAT and a 200 probe. The sweep's auth doesn't move until Phase 2, lower-traffic bridge first.

Worst residual · the honest floor

Pure collapses the whole attack surface onto "compromise HK or Vegas." Once there, the attacker signs requests that are legitimate — real key, real signature. Attribution names the prime and revocation cuts it, but between breach and detection they have correctly-signed access. Crypto can't help a secret doing its job for the wrong hands — so the prime's own integrity (and the commit-signing gate, §6) is the real perimeter now. That's the right place for it to be.
