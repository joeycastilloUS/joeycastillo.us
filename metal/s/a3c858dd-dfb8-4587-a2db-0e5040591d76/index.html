The server re-reads the doc as gate authority (Program.cs:673-682) rather than trusting the client — which is the shape the triage config needs anyway. This is the shortest honest persistence path, and it is already deployed.

Three things that will bite, named now

1. The manager cannot get in — and the workaround overshares

Console auth is a shared operator password (PW = BRIDGE_TOKEN, sent as a bearer on every call, :815) plus a hand-kept Crew allow-list (bridge/Auth.cs:79-111). Handing the Mendo support manager that password hands him all six apps and every tab — Meraki, Salesforce, GCP cost, the lot.

“Sign in with Zendesk” was designed for exactly this (be/designs/2026-07-08-2151-design-zendesk-user-login-fable5.html, identity key zendesk:<subdomain>:<userid>, role ∈ {agent, admin}, fail-closed) and is unbuilt — bridge/providers.json holds only slack and google. Its own DoD closes “awaiting operator call on policy pick.” That call is still open.

2. Porting the HTML alone ships a lie

The tab renders real values and real allowed sets, but nothing writes. Today that is honest because the file is visibly a dev tool. Inside the console it becomes a surface that looks editable to a manager and silently isn't — strictly worse than the current state. The applier (validate → write .pi → deploy sandbox) is the actual build, and the safety argument in the manager-console proposal depends entirely on it existing.

Second-order: the config is currently a build-time snapshot baked from the .pi at publish. In the console it must read the intent live, or it will drift silently the first time the .pi changes.

3. Two hazards each pass caught alone

  • Driver only: be/tools/bridge-postman.html embeds a Firestore API key in client-side source (the comment thread). Contained while it is a local tool; it becomes real exposure the moment that content is hosted in the console. Strip the comment engine on port.
  • Navigator only: bridge/ is a working copy forked from canonical acmedevUS/meraki-bridge (ARCHITECTURE.md:29-34). Any /settings change must reconcile upstream first or it gets clobbered by CI.

Neither pass caught both. That is the reconcile earning its keep.

What I'd do first

Don't port the tab yet. The cheap half (three edits, one file) is not the risky half. Land the applier against the /settings seam first — then the tab is a thin render over something that actually works, and it can go in behind the operator password while the Zendesk login question stays open. That also answers “who gets to change what” server-side, where it belongs, instead of with a disabled attribute the browser controls.
