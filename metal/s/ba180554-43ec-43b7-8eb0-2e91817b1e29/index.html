What shipped

A ticket browser in the Argus Test Bench. Choose an arm, press Load tickets, and the pane lists that environment's tickets — id, created time, status, subject, via-channel, tags — with paging and a live count. Two lanes: newest first (Zendesk search, hard-capped at 1000 results and labelled as such) and everything, by ticket id (uncapped walk). Every call is a GET through the bridge's declared read catalog; nothing in this feature can write.

Three truth bugs found and fixed

1 — Mixed denominators

The header printed “N of 61,522” while paging search results, which report 435,641. Zendesk archives closed tickets after ~120 days: they leave tickets.json but stay in the search index. Two different universes under one number. Each lane now carries its own denominator and names which universe it counted.

2 — Arm A and Arm B returned identical lists (operator-caught)

Selecting sandbox A vs sandbox B showed Arm A's tickets both times. Not a UI bug — a false premise. Both env slots resolve to the same Zendesk account (mendocinofarms1781637851, confirmed via /version slots). The arms are two brands inside it, so filtering by environment filters by nothing. The split now runs on brand_id, the only axis that separates them.

The signal was in the pre-ship verification — both arms returned count 673 and the same top ticket #755 — and it shipped anyway. Recorded rather than smoothed over.

3 — Arm B would have rendered empty

The by-id lane decided “end of list” from the brand-filtered batch length. Arm B holds 1 ticket in ~194, so page 1 filters to zero and the walk stopped immediately — showing an empty arm rather than a short one, the exact failure the brand fix existed to end. Paging now uses the pre-filter count.

Navigator verdict — PASS-WITH-NOTES

Fable reviewed the diff serially (Rule 1: driver writes, navigator reviews) and verified the fixes in the working tree rather than trusting the commit messages. Confirmed: no cross-arm leak path; brand ids sit well under 253 so the string coercion is exact; all four lane/denominator combinations are honest; every attacker-influenced field is escaped; /read cannot write in any environment. Both non-blocking findings were applied before this report:

  • Busy-guard gap — zTktLoad reset state and awaited the count unguarded, so a double-click fired a duplicate request. Guard now spans the await.
  • Param hardening — {brand}/{page} are digits-only. URL-encoding already blocked traversal, but inside a search-query template a %20 is a term separator. Verified live: brand=...%20status:open → 400.
  • esc() contract — documented that it escapes & < > but not quotes, so a future attribute interpolation of a guest-authored subject can't become an injection.
