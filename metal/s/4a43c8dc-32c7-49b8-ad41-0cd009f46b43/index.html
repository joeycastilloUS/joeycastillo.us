Argus Salesforce: where we are, what we built, what's next

One session. Four tabs shipped, a case-pattern engine running against 42,402 sealed cases, two bugs found and one of them fixed but not deployed.

Status · every number measured live · 2026-07-27

Where we are in one line: Salesforce went from a read-only viewer to a working corpus console with a case-pattern engine, built almost entirely out of parts that already existed. 1,578 of 42,402 cases now match a known support pattern. The ceiling on that number is not the matcher — it is that we cannot read the email threads, and a search bug we have now fixed in source but cannot deploy.

1. What shipped

LIVEShapeFive distribution charts over the whole sealed store — case type, status, origin, priority, and Reason. Reuses the Zendesk chart component and an endpoint the query service had been serving all along that nothing called. No new backend.
LIVELoad DataLive corpus stamp plus a sync check counting the live org against the sealed store. Currently +163 cases, +87 comments, raw 403 hours old. Before this, that number only existed if someone measured it by hand.
LIVECase PatternsThe sealed corpus matched against the 10-entry Case Pattern Library. Deterministic literal-signal matching, no model, zero tokens. 1,578 cases matched, 69 to more than one pattern, ground truth 4 of 6.
FIXEDWrong-key bugEvery Salesforce data call was sending the console login password as its bearer to services that gate on the daily passphrase. Logged out it worked; logged in it failed. Raw IDS had it too and hid it by falling back to a stale bundled copy.

Ground truth = can each pattern find the real case its own author already proved. Six patterns cite a case number; four are found.

The rule that decides everything

Signals are written from each pattern's SYMPTOM, never its ROOT CAUSE. We hold the case subject and description — the opening message and nothing after it. "Publisher paused", "Print on Held", "drive mapped to the wrong letter" are conclusions, reached later in the reply thread. They do not appear in our corpus at all. What does appear is "we are not receiving the full orders" and "wont print".
We could have tuned terms until all six known cases lit up. That is scoring against the answer key, and it would have produced a better-looking number that meant nothing. The rule is principled and the score is whatever it is.

Working this out produced the most useful finding of the session, and it was arrived at independently on our own data: the symptom is in the case, the cause is in the thread. A separate tool working the same OneDine data reached the same conclusion from the other direction. Two independent routes, one answer.

3. What we found along the way

BUGSilent truncationThe store's search counted matches past ~2,000 distinct strings but stopped collecting them — returning a confident, complete-looking answer built from a fraction of the data. It costs us 2 of our 6 ground-truth cases. Both misses are on patterns whose signals hit that ceiling.
BUGWrong credentialConsole login password sent as the API bearer once an operator signed in. Fixed and live.
BUGSilent deploy gapThe pattern data file shipped as a 404 fallback with a 200 status while the build reported green. Caught by fetching the deployed URL rather than trusting the build. Fixed.

4. The blocker — said plainly

The truncation fix is written and committed. It is not deployed, and I could not deploy it.

Rebuilding the query service requires the exact library snapshot the running image was built from in July. It is not on this machine. The current copy is a different generation with an incompatible interface, and the build fails immediately on it.

This is bigger than one bug. The same missing snapshot blocks the stager port — the single item that would unlock ranked search, similar-case matching, pattern spines and rebuild together. Both need the same thing.

What would unblock it: the library revision used for the 2026-07-09 build — a tag, a machine, or an archived copy. With that in hand, both the fix and the keystone are unblocked.

Not attempted: rewriting the service against the current interface. That touches every endpoint including one that works today, it was not asked for, and guessing at it to avoid saying "blocked" would be the wrong trade.

5. The ceiling on all of this

Two things cap what the pattern engine can do, and neither is the engine:

  1. We cannot read the email threads. 87% of cases arrive by email, and we hold 0.39 comments per case. The diagnosis lives in the replies. The tool working the same data reads those threads on 100% of its cases — in the same org, with a different credential. That is an access grant, not an engineering problem, and it is the largest single lever available.
  2. The truncation ceiling, above. Fixed in source, waiting on the snapshot.

Everything else — ranked search, similar-case retrieval, pattern spines, corpus rebuild — sits behind the stager port, which is a field-map of an engine already running in production on a corpus ten times larger.

6. What's next, in order

  1. NEEDS YOUFind the July library snapshot. Unblocks the truncation fix and the stager port in one move. Nothing downstream moves without it.
  2. NEEDS YOUEmail access grant. Match our integration to the permission set already granted to the other tool in the same org. Turns pattern matching from symptom-only into cause-capable.
  3. THENPort the stager. Ranked search, matching, spines, rebuild — all four fall out of the one port.
  4. THENLifecycle handlers, which turn the Rebuild card into working buttons.
  5. THENThread cleaning, using a recipe already verified elsewhere, once the grant lands.

Still open and not engineering: whether to consolidate our index with the other team's before both get built, and one privacy standard covering both stores rather than the stricter review landing on the smaller one.
