Refresh-Align-Warmer — quads refresh when the warm pass is DONE

Design (~d), grounded in ~i of web/board/index.html, bridge/Program.cs, bridge/MerakiCache.cs, and the live Cloud Scheduler jobs (verified via gcloud, us-west1). Investigate + design only — no code changes in this artifact.

0 · ~i — what actually happens today (verified)

Board pull cadence (web/board/index.html)

  • boot() arms setTimeout(tickClock, nextBoundaryDelay()) (line 898). nextBoundaryDelay() (line 722) targets the next wall-clock 15-second boundary (Date.now()%15000).
  • tickClock() (line 724) fires exactly ON :00/:15/:30/:45 and refreshes one quad per tick — doRefresh(SITES[whichSlot()%SITES.length]), slot from whichSlot() (line 723: :00→0 :15→1 :30→2 :45→3). With a 4-site day, each quad refreshes once per 60s, pinned to a fixed slot.
  • doRefresh → bgRefresh(num) (line 695): plain (no-force) GET /meraki/portmap + /meraki/wireless; stamps qd.asOf from the portmap response only (line 712).
  • Force lane: manual ↻ = refreshSite (line 864) → loadSiteForce (line 842) with &force=1 on all three reads — bypasses TTL server-side, 10s floor (MerakiCache.ForceFloorSec, MerakiCache.cs:28).

Warm pass (bridge/Program.cs + MerakiCache.cs)

  • In-process loop (Program.cs:1490–1504) sleeps to the exact UTC :00/:30 second boundary then runs WarmActiveOnce() (1480–1489): sequential foreach over ActiveNetworks() × 3 kinds (portmap / wireless / verify), each awaited.
  • Cloud Scheduler backstop, verified live: meraki-warm-0s (* * * * * → POST /meraki/refresh-active?after=0) and meraki-warm-30s (* * * * * → ?after=30), both ENABLED, targeting meraki-bridge-d5vc4tye3a-uw.a.run.app. Handler at 1505–1516 clamps after 0..55, sleeps, then runs the same WarmActiveOnce().
  • TTL 30s default (MERAKI_CACHE_TTL, Program.cs:60–61). Each key's asOf = the instant its own Meraki fetch completed (MerakiCache.cs:95–96) — the pass is not atomic; completion trails the :00/:30 trigger by the fan-out duration (seconds, growing with active-network count).
  • FOUND IN ~i Skip-if-fresh alternation: WarmAsync (MerakiCache.cs:73–77) refetches only if age ≥ TTL. A key stamped at boundary+f seconds has age 30−f < 30 at the next boundary → skipped, refreshed the boundary after. Any key whose fetch takes >0s effectively warms every 60s, on alternating boundaries. A "warm pass completed" therefore does NOT mean "every key refreshed this pass."

The mismatch

wall clock :00 :15 :30 :45 :00 warmer █ pass (0..f s) ─┘ █ pass ─┘ █ pass board slot 0 ▲ reads AT :00 — races the pass; cache still Fresh(30−f) → serves the PREVIOUS snapshot; won't re-read for 60s board slot 1 ▲ :15 — ~15s post-warm (ok-ish, off-phase) board slot 2 ▲ :30 — same race as slot 0 board slot 3 ▲ :45 — off-phase
  • Race at :00/:30: quads in slots 0 and 2 pull at the exact instant the warmer starts. GetAsync finds the previous entry still Fresh (age ≈ 30−f) and serves the OLD snapshot; the new data lands seconds later, and that quad won't look again for 60s. Worst case a quad renders data ~90s behind Meraki reality just before its next tick.
  • Half-updated composite: bgRefresh reads portmap + wireless back-to-back mid-fan-out — portmap can be post-warm while wireless is pre-warm for the same network. The quad's shown asOf (portmap only) hides this.
  • Open-loop phase: the board's 15s metronome and the warmer's 30s metronome are aligned to the same wall clock but neither knows when the other finished. Nothing today says "the cache is now the freshest it will be for 30s — read it."

1 · Need

  • Every quad should render the freshest warmed cache — read right after a warm pass completes, never mid-pass, never racing it, never a full slot-rotation behind it.
  • The board must not guess the warm completion time (fan-out duration varies with active-network count and Meraki latency); the bridge knows when it finished and should say so.
  • Zero extra Meraki load (cache-hit reads only), and the manual ↻ force lane stays exactly as it is.

2 · Raw user stories

  • As the rollout operator watching four quads on install night, when the :30 warm lands I want all four quads to show that data seconds later — not one quad now and the last one 45 seconds from now.
  • As the operator, I never want to see a quad's asOf sit ~60–90s old while I know the warmer ran twice since — the board should track the warmer, not its own metronome.
  • As the operator, when I hit ↻ on a quad I still get a true force-read from Meraki, immediately, regardless of warm phase.
  • As the bridge owner, I don't want 100 shared-link viewers turning "refresh after warm" into 100× Meraki traffic — post-warm reads must all be cache hits.

4 · Choices — the three options, weighed

a · Phase-align (:03/:33)b · Server signals readiness (warmEpoch)c · asOf-compare
MechanismClient shifts its metronome +3s past :00/:30Bridge stamps pass completion; board polls the stamp, re-pulls quads only when it advancesBoard compares quad asOf to a published "latest warm asOf," pulls when newer
Fixes the :00/:30 raceOnly if the pass finishes in <3s — open-loop guess; a slow pass (many nets, slow Meraki) still gets read mid-fan-outYes — by definition; the signal IS completionYes, but needs the server to publish the value → it IS option b's endpoint plus a client guard
Half-updated compositeStill possible on slow passesEliminated — reads start only after the pass endsEliminated only with b's signal present
Self-correcting on long/failed warmNo — fires blind at :03/:33 regardlessYes — epoch doesn't advance, board doesn't churn; stall detector falls backSame as b (it rides b's signal)
Extra loadNone1 tiny in-memory GET / ~5s / viewer + all-quad cache-hit reads per epoch (zero Meraki)Same as b
ComplexityTrivial (client-only, ~2 lines)Small (≈15 lines bridge, ≈20 lines board)b + extra per-key bookkeeping that fights the skip-if-fresh alternation (a skipped key keeps its old asOf legitimately → false "stale" verdicts)
Recommendation: option b — server signals readiness. The bridge is the only party that knows when the fan-out finished; everything else is a guess. (a) is a bet that every pass beats 3 seconds — it loses exactly on the busy nights the board matters most, and it can't know a pass failed. (c) collapses into b once you ask "compared to what?", and its per-key asOf comparison misfires against the skip-if-fresh alternation found in ~i (a key legitimately skipped this pass keeps an old asOf — that is not staleness). Gate on the pass epoch, not per-key stamps: one monotonic token, one comparison. Post-epoch re-pulls are all L1 cache hits, so even 100 shared-link viewers add zero Meraki load — the exact property the cache was built for (MerakiCache.cs:8–11).

5 · Literal naming

  • warmEpoch — ms-epoch instant the last WarmActiveOnce() completed. One value, monotonic, per instance.
  • lastPassMs — duration of that pass (telemetry; answers the "how long does the fan-out really take" unknown for free).
  • GET /meraki/warm-status — the readiness endpoint: {warmEpoch, lastPassMs, active, ttl}.
  • Board: _warmSeen (last epoch acted on) · pollWarmStatus() (the ~5s poll) · refreshAllQuads() (staggered doRefresh sweep). No cute names — each says what it is.

6 · Shape

Bridge (C# — the Meraki jacket, per the language boundary)

  • WarmActiveOnce() tail: record sw.ElapsedMilliseconds → lastPassMs, then warmEpoch = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds(). Volatile/long — no locking needed for a monotonic stamp read.
  • app.MapGet("/meraki/warm-status", ...): returns the two stamps + mcache.ActiveNetworks().Count + mcache.TtlSec. No Meraki call, no cache mutation. warmEpoch=0 before the first pass (cold instance) — board treats 0 as "no signal yet."

Board (vanilla JS)

  • pollWarmStatus() every ~5s (day view only): fetch /meraki/warm-status; if warmEpoch > _warmSeen → _warmSeen = warmEpoch; refreshAllQuads() — doRefresh per visible quad, staggered ~300ms apart to keep the existing top-down touch-sweep feel. All reads are post-pass cache hits.
  • Fallback (deploy-order + failure safe): if warm-status 404s/fails, or the epoch hasn't advanced in > 90s (3 missed passes), revert to today's tickClock 15s slot rotation until the signal returns. The board never goes dead because the bridge is old, restarting, or wedged.
  • Force lane untouched: ↻ still calls loadSiteForce (force=1, 10s server floor). A force result also updates the quad's paint; the next epoch sweep simply reads the (now even fresher) cache. No interaction to special-case.
  • Cadence change, stated honestly: each quad goes from 1 read/60s (fixed slot) to ~1 read/30s (every epoch) — 2× the HTTP GETs, 0× extra Meraki (all L1 hits). The quads also now refresh together, which is the point: one coherent snapshot per pass.

8 · Unknowns + when to revisit (Rule 7 — this plan is a v1 hypothesis)

  • Real fan-out duration. Unknown distribution of pass length on 4–8-network install nights. lastPassMs measures it from day one. Revisit if passes routinely exceed ~25s (epoch starts colliding with the next boundary → consider parallelizing the warm fan-out).
  • Instance count. warmEpoch is in-memory, per Cloud Run instance — same documented scope as the cache itself (MerakiCache.cs:13–16). Fine at min-instances=1. Revisit the moment the bridge scales past one instance: epoch (and cache) move to the shared layer together, or the signal becomes SSE.
  • Skip-if-fresh alternation. Left as-is here (a key skipped this pass is ≤60s old — within tolerance, and the epoch gate is orthogonal to it). Revisit if operators notice per-quad asOf alternating 30/60s and care: the fix is a small slack margin in WarmAsync's freshness check (refetch at age ≥ TTL−pass-duration), a bridge-only change.
  • Poll interval vs. viewer count. ~5s × N shared-link viewers of an in-memory endpoint is assumed negligible. Revisit only if bridge CPU says otherwise; then either lengthen the poll or switch to SSE/long-poll.
