D5 — Auto-CC the District Operator + store inbox: three designs

Given the store→DO map is available (Google Sheets / Firestore / Airtable) · Zendesk AI arm (arm B) · paired Opus + Fable, reconciled · 2026-07-23

Demand

D5: every response to an NPS-detractor ticket CCs the correct District Operator (DO) who owns the store, and the store inbox, automatically.

Facts that constrain the design

CC mechanismZendesk has no native "Add CC" trigger action. A CC is applied via PUT /api/v2/tickets/{id} with email_ccs:[{user_email, action:"put"}]. Source.
Every responseemail_ccs is ticket-level state. Set once at create; Zendesk notifies all CCs on every subsequent public comment. Internal notes do not notify CCs.
Write authorityOnly the bridge holds the Zendesk write token. In all three designs the bridge makes the PUT.
Store locationThe store is written in the ticket body, not a field. It is parsed and normalized (NpsResolver.NormStore()).
Firestore already wiredThe bridge already reads the argus Firestore DB (us-west4) with ADC, no key (NpsComments.cs). Adding a collection needs no new auth.
Auto-create by emailA PUT email_ccs with an email that has no user creates a user. A wrong/typo'd email would CC a new stranger.
48-CC capMax 48 email CCs per ticket; this design adds ≤2 and dedupes.

The four atoms

Every design is the same four parts. The designs differ only on MAP and TRIGGER.

Design 1 — Trigger Iron

Map in Firestore; a brand-scoped Zendesk trigger fires the bridge at ticket-create.

Design 2 — Ops Ledger

Same runtime as Design 1. The map's edit surface is a Google Sheet, synced into Firestore; the hot path reads Firestore only.

Design 3 — Agent's Hand

Map in Firestore; the AI agent's custom action calls the bridge (same lane as the promo code).

Recommendation (reconciled)

A/B nowDesign 1. Firestore is already in the bridge; the trigger is brand-scoped to arm B; one seed script imports the map. D5 says "every," and a create-time trigger delivers every.
ProductionDesign 2 — Design 1's runtime unchanged, Sheet added as the ops edit surface. Additive, no rework.
Airtable vs SheetsSheets, on this stack: shareable with the service account (no stored key). Airtable requires a PAT secret in Cloud Run + an external SaaS dependency for the same editability. Choose Airtable only if the map already lives there.

Map shape

Recommended: store → { do_email, store_inbox_email } direct. Enumerating a DO group to pick "the" email is a guess (groups can hold admins/backups); the map is authoritative on the email, and the 17-group registry validates that the named person is a real DO. Per doc: {store_norm, store_label, store_code, do_email, do_person, store_inbox_email, updated_by, ts}.

Fail-closed policy

Unresolved storeStore unparsed, ambiguous, or unmapped → no CC PUT. Tag the ticket nps-cc-unresolved, log it. Never nearest-match, never default-DO.
Import validationMap rows validated at write time: DO person must match the 17-group registry; emails must pass a domain allowlist (@mendocinofarms.com) or existing-user check. This fences the auto-create-a-stranger risk.
Sync safety (Design 2)A bad Sheet row is rejected; the last-good Firestore map stays live. A bad edit cannot blank the map.
Visible silenceUnresolved tickets are queryable by tag; Argus audits the count.

A/B validity note

Arm A (Argus) meets D5 inside its own composer as it writes each reply. Arm B under Design 1 meets it via create-time infrastructure. The mechanisms differ; the measurable outcome is identical (correct CCs present on every public response, verified by Argus reading email_ccs back). If mechanism parity is required instead of outcome parity, that is Design 3 — which trades away the "every" guarantee. Operator decision.

Open operator decisions

1Does the map carry store_inbox_email explicitly, or must it be derived? D5 requires the store inbox; the map must carry it.
2Map shape sign-off: store → {do_email, store_inbox_email} direct (recommended) vs store → group → members.
3Edit surface for production: Sheets (recommended) vs Airtable.
4A/B: outcome parity (Design 1) vs mechanism parity (Design 3).
5The upstream system currently CCs DOs via inbound email headers on some tickets. Dedupe handles overlap. Retire the upstream path eventually, or leave it?

First move

Seed script: map → Firestore store_do_map with import-time validation. Then the /nps/cc endpoint (resolver seam + PUT). Then the brand-scoped trigger. Verify end-to-end on one test detractor ticket with Argus reading email_ccs back before wiring the A/B.

Method

Paired per kernel Rule 1: two independent designs, reconciled. Both converged on Firestore + bridge + trigger as the primary. One driver design (an iPaaS live-read of the map) was superseded by the navigator's sync-to-Firestore form, which keeps the map's datastore off the hot path.
