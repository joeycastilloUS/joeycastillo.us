Fix the serial where you found it

Plan + estimate — correcting a typed serial number from the review screen, with a receipt, into the customer's list.

Plan — awaiting approval

⚠ Nothing below starts until you approve §15. The house rule today says this system never writes to the customer's list. Changing that is your decision, not an implementation detail. The exact wording is drafted in the design; Phase 0 is you reading it and saying yes or redlining it. Every other item is blocked on that.

Intent

When the person checking install photos sees a serial number was typed wrong, they should be able to correct it on the spot — and the correction should land in the customer's master list carrying a receipt that says what it was, what it is now, who changed it and when. Today the only two options are "mark it failed and move on" or "go fix it by hand somewhere else, silently." This delivers the narrowest useful version: typed serial numbers only, one at a time, from the review screen, behind a switch you can flip off in seconds.

What you're getting, in plain words

1. As the person checking the install photos, I want to fix a wrongly typed serial number right where I spot it — so I don't have to go hunting in another program and hope I remember to come back.Phase 3

2. As the person checking the photos, when the computer has already read the right number off the picture, I want to accept its reading with one tap instead of retyping twelve characters — so a fix takes two seconds and I can't fat-finger it a second time.Phase 3

3. As the person checking the photos, I want the fix to stick immediately and the red "doesn't match" mark to clear if the numbers now agree — so I know it worked and can move to the next one.Phases 2 and 3

4. As the person checking the photos, if a fix can't be saved I want to be told plainly why, with what I typed still sitting there — so I'm not guessing, and I'm not typing it all again.Phases 2 and 3

5. As the owner, I want every correction to keep a receipt — what it said before, what it says now, who did it, when — so when a customer asks "who changed this?", the answer isn't "someone, at some point."Phase 1

6. As the customer, I want my master list to end up holding the right serial number — so my records match what's actually sitting on the counter in the store.Phases 1 and 2

7. As one of the crew who gets alerts on my phone, I never want a spelling fix to ring like an emergency. Fixing a typo should be completely silent.Phases 1 and 2 — proven on the practice row

8. As the owner, I want only the serial-number boxes to be changeable. Not photos, not dates, not the customer's store names, and never a hundred at once.Phase 1

9. As the owner, I want one switch that turns this whole ability off in seconds, without anybody rebuilding anything.Phase 1, flipped in Phase 2

10. As the owner, I want the very first attempt to happen on a practice entry that no customer can see — so if we get it wrong, nobody's real data is touched.Phase 2

11. As the owner, I want no machine or script to be able to make these changes — only a signed-in person, by name. A receipt with no human on it isn't a receipt.Phase 1

12. As the person checking the photos, fixing the number should not quietly erase the pass or fail I already gave it. I'll look again and judge it myself; the fix shouldn't decide for me.Phase 1

13. As the owner, I want the house rules updated and approved by me before a single line of this gets built — so our promise that we never write to a customer's list gets changed on purpose, not by accident.Phase 0

Scope

In: the §15 amendment (approval-gated); one route POST /atb/edit; the 39-name allow-list; the five-check gate including the ATB_WRITE kill-switch and the startup scope probe; the atb_edit receipt (pending / applied / failed, one writer); synchronous update by field ID with typecast:false; write-through of the response into the cache; a route-local origin guard; the inline-edit affordance in the entered cell per the locked look-and-feel; the practice-row proof asserting both Slack channels stay silent; your first real correction as the production Done.

Out: photos and attachments (own board); any table beyond Inventory and Decommission; any field beyond the 39; bulk or scripted edits; edits from the API Browser; a revert button; a history panel or an "list all edits" endpoint; the global CORS fix (stays Kaizen); session expiry (stays Kaizen); a stale-receipt sweeper; Jotform-clobber detection.

Approach

The design already made every decision, so this is sequencing, not re-arguing. The order is the one the law requires: amend the architecture, build the server side as one route with its tests riding inside each item, deploy it switched off and open the switch only after a proof on the practice row, then put the affordance on screen and have you make one real correction.

One contract is pinned up front so the bridge and the console can be built in parallel without waiting on each other:

POST /atb/edit  →  { ok, edit: { before, after, by, at, state, error? }, record }

      `record` in exactly the shape krSyncRecord already splices
      (web/app/index.html:10505-10510)

Constraints

  • The read-only law holds until §15 is approved. No write-capable code merges or deploys before Phase 0 exits.
  • The switch unset means closed. Deploy closed; open only after the practice-row proof.
  • An edit posts nothing to Slack — structurally, by keeping it out of the review handler, and the proof asserts it.
  • The edit route never touches the pass/fail record. Clearing a verdict is the one way an edit could fire a card at the customer's channel.
  • Practice row before any real row.
  • Text fields only, the 39 names only, the base pinned server-side, field IDs never names, no type coercion.
  • No new service, no new port, no change to the edge worker — it already forwards these requests.
  • No photos.

Unknowns

  • The token's permissions. You've said it can write; that isn't checkable from the code. The startup probe answers it at first boot, and the gate refuses if the answer is no.
  • The field types of all 39. "Salad OLO Screen" and its Station 2 twin are suspicious. A wrong type becomes a refusal rather than a bad write — but it also means those rows can't be fixed in phase 1.
  • Jotform overwriting us. Jotform created these records. If a resubmission lands on a field we corrected, our receipt says applied while the list has quietly drifted back. Not answerable from this repo — this is the one I'd most like your read on.
  • The update response shape. Whether it returns everything we need to refresh the cache. If not, we fall back to a re-read — small cost, code already exists.
  • Whether a redeploy preserves the switch. The build config removes two other env vars explicitly; confirm on the first redeploy after the flip.
  • The real hostname set for the origin guard.

When to revisit

  • You ask for the photo → its own design and board.
  • A receipt gets stuck on "pending" more than once → a sweep inside the existing scheduled pass. Still no worker.
  • Jotform clobber actually observed → the scheduled pass detects the drift and flags it.
  • You ask "who edited this?" after a page reload → the footnote graduates from session-memory to a small lookup. Not a history panel.
  • Any of the 39 refuses on type in real use → the allow-list gains a per-name type map.
  • Edits exceed about one a second, or anyone wants bulk → batching, and not before.
  • A second customer base → the pinned base and allow-list become configuration.
  • Phase 3 overruns → split the drawing from the wiring, and fix the known refresh-latch bug first.
