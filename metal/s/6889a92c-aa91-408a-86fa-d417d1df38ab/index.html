Prepared for Elbert — Director of IT, Mendocino Farms  ·  by kASTIL Systems (Argus for Zendesk). Every number below is from real runs against a live Zendesk sandbox — no mockups.
What it does. Every NPS-detractor survey that lands in Zendesk is read, understood, and triaged automatically. If the guest describes a possible food-borne illness, the system posts a private internal note on the alert ticket — flagged, tagged, set to high priority, with the internal escalation list added as followers — and a Zendesk trigger emails the escalation team immediately. The guest is never auto-replied to. This is the same internal-note + notification mechanism your team uses today (confirmed by examining 190 real production tickets). Every other complaint gets an on-brand "We're Sorry" recovery reply with a discount code, sent through Zendesk exactly like an agent would. Everything flows through Zendesk — nothing bypasses your platform. It runs in three languages of input, at effectively zero cost per recovery.

3 · Proof of real send — the full illness loop, live on ticket #538

The final mechanism (the way Guest Relations already works)

A food-poisoning alert produces, in one ticket update: a private internal note (public=false) posted directly on the alert ticket; the tag argus_illness_escalation; priority high; and the internal escalation list (4 Guest-Relations leads, all real Zendesk admins) added as followers. That tag then fires the Zendesk trigger "Argus Illness Escalation Notify" (trigger id 51397652757140, active), which emails each of the 4 leads — subject "ILLNESS ESCALATION - action required | Ticket #538" — and stamps argus_illness_notified so the team gets exactly one email per escalation. This matches real production practice: a review of 190 live NPS tickets confirmed internal comments are private notes on the ticket and internal notification rides Zendesk's own trigger rail — not side conversations, not free-form email. The guest is never contacted.

4 · The technology — what it runs on

LayerWhat it is
The runtimeA bare-metal C runtime (Purcius) executes the automation as a defined program — no per-ticket scripting, deterministic, auditable.
The programOne declared card describes the whole flow (scan → identify → triage → react). It is verified against a signed interface manifest before it runs — a malformed program is rejected at the door.
The decoderA dictionary-backed (WordNet) language engine reduces English feedback to structured meaning; non-English is passed through intact so nothing is mis-read.
The AI-PantheonThe illness check is a panel of 3 independent AI models, conservative by design: any single model's doubt escalates to a human. This is the only model-inference step, and it never writes to a guest.
Zendesk connectorA thin, read-mostly connector to the Zendesk API. All guest-facing and internal emails go out through Zendesk, using your existing triggers.

5 · Safety & controls

ControlGuarantee
Food-illness handlingDetection + human escalation only. Never an automated code or reply to a guest. The run stops before recovery.
Environment isolationAll testing ran against the sandbox tenant only. Production is a separate tenant and stays disarmed — sends require deliberate operator arming.
IdempotencyA guest already handled is skipped — no duplicate replies, no double-spent codes.
DeterminismThe recovery reply is byte-identical on a re-run of the same input — fully replayable and auditable.
Cost transparencyRecovery is $0 (no model). The illness panel is the only paid step: ≈ $0.0006–0.001 per ticket, reported on every run.
