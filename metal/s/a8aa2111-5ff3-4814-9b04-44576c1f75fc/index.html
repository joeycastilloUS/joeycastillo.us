argus-email-send — the automated lane

A second lane for the guest simulator: fire one real inbound email into the Zendesk sandbox intake, on command, so Arm B's AI agent engages and the T1 illness-safety test runs repeatably instead of by hand.

Paired ~d — Opus + Fable, two independent passes, reconciled. The navigator's mechanics carried; where we still disagree, it's flagged for the operator, not resolved silently.

1 · Need

The guest simulator has no working automated send. The mesh-native path has no egress node (route.egress: tbd); the Cloudflare jacket 401s and structurally can't do arbitrary outbound. So every test of Arm B's AI agent needs a human to hand-type an email. We need one command that puts a real, DMARC-passing email from argus.net.ai into support@guestrelationstestv2.zendesk.com as genuine inbound mail (via_id=4 — an API-created ticket will not trip the agent, proven live). Sandbox-only, at-most-once, jc fires each send.

2 · Raw user stories

As jc, I want one invocation with the T1 body to make a ticket appear in the sandbox from argus.net.ai that the AI agent actually answers, so that I never open a mail client to test.
As the illness-safety tester, I want to re-fire T1 (illness words + "NPS Score" vs the skip_ai_reply tag) after every trigger change and get apples-to-apples results — same sender, same route, a new ticket every time, never a duplicate, so that the variable under test is the agent, not the harness.
As the architect, I want the lane to be Purcius C99 and honest about any interim third-party hop, so that it converges on the mesh-native end state instead of ossifying as a jacket.

The real constraint is trust, not transport. argus.net.ai today has no SPF, no DKIM, no DMARC, no MX (Cloudflare zone, SOA only). Any mail claiming that domain is rejected or spam-filed by Zendesk regardless of how it's sent. Domain auth is the shared prerequisite for every lane below.

The egress options, weighed

OptionReality
(a) Direct-to-MX :25 from a fixed-IP Purcius nodeThe DIA's end state (D2). GCE blocks :25 egress with no unblock path. Workable on Vultr/Hetzner/OVH after a :25-unlock request + static IP + PTR =mail.argus.net.ai + IP warmup. A zero-reputation IP risks Zendesk's suspended-tickets queue — a silent T1 failure. Right architecture, wrong week: days to stand up.
(b) C99 SMTP → smarthost :465 (submission + AUTH)The .si already plans EHLO/MAIL/RCPT/DATA over tls13 for 465/587 — a smarthost is the same wire, one hop earlier, plus one AUTH PLAIN line. Purcius still composes, ids, and speaks raw SMTP; the relay contributes only IP reputation, which no C99 conjures in a day. Open on GCE. Relay: SMTP2GO (instant, free tier, 465/587/2525, domain auth via 3 DNS records).
(c) Cloudflare Email Workers send_emailDead end. The binding only delivers to pre-verified destination addresses, is invoked from a JS Worker via a proprietary binding (fails D1 in letter and spirit), and yields zero code toward the mesh end state. Retire the jacket; keep the 401 as evidence.
Pick — Primary (b), End-state (a). Ship the C99 comms/skill/email client against an SMTP2GO smarthost on :465 implicit TLS (implicit TLS avoids betting our tls13 skill does the plaintext-then-STARTTLS upgrade dance). The same client binary becomes the end state by flipping route.egress from smarthost:465+AUTH to recipient-MX:25 once a PTR-owning node exists — (a) is not a fallback, it's the destination. Port 465 over 587 for the same tls13 reason.

4 · Naming & the three lanes

One skill, three lanes. Literal names.

L0 · manualHAVE

Operator's own mail client. Exists today, covers the immediate T1. Stays as the human control arm.

L1 · automated-interimTHIS DESIGN

C99 comms/skill/email → SMTP2GO smarthost :465. Purcius composes, ids, DKIM-aligns, and speaks wire SMTP; the only outsourced thing is IP reputation. The deviation is config-shaped (route.egress), so the burn-down to L2 is trivial.

L2 · mesh-native end stateSEAL TARGET

Mesh store-and-forward → Purcius egress node → direct-to-MX :25, our own purcius1 DKIM key. Same binary; the AUTH branch goes dead. This is what earns the .pi seal.
⚠ D1 honesty — L1 deviates from the DIA as written. D1 says "never a third-party email API" and D3 wants our own DKIM. L1 uses SMTP2GO (a third-party mail service) and delegated DKIM (their key signs d=argus.net.ai via our CNAME — signature is our domain, private key is theirs). We say so plainly and justify it as interim: no HTTP jacket ships, Purcius owns the compose/id/wire, and the outsourced piece is reputation alone. This is the operator's call to make (see below) — both passes flag it; neither resolves it silently.
OPERATOR DECISION. Is a C99 SMTP client speaking to a relay a "third-party email API" (D1 violation) or just SMTP-over-config? Both Opus and Fable read it as SMTP-over-config, acceptable as a labeled interim — but it touches the DIA's core demand, so it's yours to rule. Rule the other way and L1 is skipped: we go straight to L2 (days, not this session) and keep L0 manual for T1 meanwhile.

5 · Shape

  • Idempotency (D5). msg.id = SHA-256(from, to, subject, body, test-id) — over the compose tuple, NOT the final bytes (a Date: header and the DKIM signature make final bytes non-deterministic; the id must be stable for the intent). Ledger written before DATA; a seen id ⇒ refuse. Message-ID: <email-send-{id}@argus.net.ai> is the join key to the Zendesk ticket. A timeout after DATA records sent-unconfirmed and never auto-retries — at-most-once prefers a lost email to a duplicate; jc re-fires with a new test-id.
  • Sandbox guard (D6) lives inside the C99 sender, before MAIL FROM: recipient must string-equal support@guestrelationstestv2.zendesk.com AND env == sandbox-b AND an explicit --fire ack. In the sender, not the caller, so no future caller routes around it.
  • Reply path. The AI agent's reply goes to @argus.net.ai — which has no inbox. T1 verification reads the reply from the ticket thread via the Zendesk API, never by waiting for return mail.
  • Out of scope: inbound receive, multi-recipient (D4 pins one), any production send (no prod arm exists, by D6).

Escape routes: DNS records are reversible (delete) and dig-verifiable. The relay is one config value — swapping SMTP2GO→SES→direct-MX is a route.egress edit, no code change. ⚠ Irreversible-ish: sender-IP reputation — a bad early send can taint the relay subaccount/domain; mitigate by keeping sends sandbox-scoped and low-volume.

6 · First Move

Smallest step to one delivered email this session, de-risking the route before a line of C99:

  1. Stand up an SMTP2GO account; add sender domain argus.net.ai; it issues the DKIM + return-path CNAME targets.
  2. Plant the 4 DNS records (§4) on the Cloudflare zone; confirm with nslookup -type=TXT argus.net.ai and -type=TXT _dmarc.argus.net.ai.
  3. Fire ONE message as a deliverability spike (labeled a probe, NOT the lane): 
    curl smtps://mail.smtp2go.com:465 \
  --mail-from t1@argus.net.ai \
  --mail-rcpt support@guestrelationstestv2.zendesk.com \
  --upload-file t1.eml -u <user>:<pass>
    where t1.eml carries "NPS Score 2/10 Detractor" + illness words. This proves DNS + auth + route before we write the C99 client — which is the immediate next board item and replaces curl before T1 is called "automated."
  4. Verify it landed: Zendesk GET /api/v2/tickets.json?sort_by=created_at&sort_order=desc — newest ticket shows via.channel = email (via_id=4), subject carries the msg id. If absent, check GET /api/v2/suspended_tickets.json before declaring failure — suspension is a different diagnosis than non-delivery (Rule 14). Recovering a suspended ticket may not exercise the AI trigger honestly; fix auth and resend rather than recover.

7 · Risks

  1. Suspended-tickets black hole. Fresh domain on a shared relay IP → Zendesk suspends as spam; T1 looks dead when delivery actually succeeded. Always check the suspended queue before calling it.
  2. tls13 client shape (UNKNOWN). The design assumes implicit-TLS client mode for :465. If the skill is server-only or shaped differently, the C99 build cost balloons. The curl spike de-risks the route, not this build estimate.
  3. Two-SPF permerror from a pre-existing CF Email Routing record (zone not fully inspected this session).
  4. Relay header mangling — some relays rewrite Message-ID or append footers, breaking the id join key and the future self-signed DKIM. Verify header fidelity on the first ticket.
  5. Deliverability ≠ done. Even with auth, a cold domain can land in spam; the honest test needs a delivered-AND-visible ticket, not just a 250 from the relay.
  6. The D1 judgment (relay = foreign API?) is the operator's, not ours — surfaced above, unresolved by design.
