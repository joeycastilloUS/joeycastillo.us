Build it their recommended way or the A/B is unfair to them.

The backtest question — the honest answer is no, not the way you do it

Argus's screen is CALLABLE over the API, on any text. Zendesk's screen is a side effect INSIDE the platform, only at ticket-create. That difference is the whole answer.

You batch history because the detector runs offline on arbitrary text — pull every past ticket, open or closed, run each through the screen, score it. The deterministic layers replay exactly; the two-model panel carries a “today's models” caveat, stated up front. Zendesk cannot replay at all, and documents that it cannot:

“Intelligent triage does not analyze tickets retroactively. Only tickets created after intelligent triage is turned on are processed for predictions.” — Zendesk help

The one backtest Zendesk actually allows — re-inject, and its price

Because triage predicts at ticket create (and, if dynamic detection is on, updates on later end-user replies — but never on historical or closed tickets), the sole path is to re-create each historical ticket as a NEW ticket in a sandbox and let triage classify it on the way in. This is exactly what the post tool we already built does — so it is reachable. But it is a forward-simulation, not a replay, and the caveats are real:

StepHow
1 · Pull the corpus + ground truthIncremental Export API (tickets + comment_events sideload). Fully supported, ~10 req/min — the same pipeline Argus already uses.
2 · Stand up the illness topicCreate the custom “food-illness” topic in the sandbox and activate it. It only classifies tickets created after activation.
3 · Re-inject each past ticketPOST /api/v2/tickets, on behalf of an end user, with a public comment — the post tool. NOT the Ticket Import API, which is explicitly excluded from triage.
4 · Read back the predictionThe intent/topic field via the ticket-fields API. Predicted-illness vs your known-illness label = recall & precision.

Why it is not a clean replay — state this next to any number it produces:

  • It scores today's model on yesterday's tickets. The model is a moving target (Zendesk retrains and suggests new topics weekly); it can never reproduce “what triage would have said at the time,” and a long run can straddle a model update.
  • Custom topics are account-specific and personalized. A sandbox is a separate account, so the topic is a fresh model — no documented guarantee it behaves like the prod one would.
  • Whether Intelligent Triage even runs in a sandbox account is not documented — confirm empirically before trusting a single number.
  • Rate limits are not the obstacle — the account-wide API budget is 200–2500 requests/min by plan tier (creation and read-back share it), which clears thousands of tickets in hours. The obstacle is that the thing being measured is a re-injected copy, not the original event.

And the AI agent's hold-back cannot be backtested at all. Its illness route is a live conversational behavior. Zendesk ships only an interactive “test AI agent” widget — no batch replay, no offline simulator. Measuring its hold-back recall over history would mean hand-feeding tickets one conversation at a time. So a backtest can score the triage classifier (approximately); it can never score the agent's actual reply decision.

What this means for the A/B

You wanted parity: backtest both illness screens over prod history and compare recall. You can do that for Argus exactly. You can only approximate it for Zendesk's classifier, and not at all for its AI agent's reply behavior.

The fair, honest experiment is therefore two-sided and asymmetric on purpose:

  • Argus: batch-run over all prod tickets offline, open or closed — the deterministic layers replay exactly; the two-model panel carries the same “today's models” caveat, stated up front. Yields a recall number the re-inject path cannot.
  • Zendesk triage: re-inject the same corpus into the sandbox via the post tool, read back the topic prediction, report recall with the “today's model, re-injected copy, sandbox” asterisks attached. Never present it as equivalent to Argus's replay — it is a forward simulation.
  • Zendesk AI agent: not backtestable. Its behavior can only be observed on live sandbox traffic going forward — which is the A/B itself, once the agent exists on v2.

The finding is itself a result: that Argus can backtest its illness screen over the entire history — and prove its reply-gate is fail-closed by construction — while Zendesk structurally cannot replay at all is not a footnote; for a food-safety hold-back, it is arguably the headline.

Honest scorecard — today

Argus wins today

  • Illness gate is fail-closed by construction (two-model unanimity + escalate-on-doubt)
  • Guest reply is deterministic, human-authored, $0 — no model writes a guest word
  • One-time coupon claimed atomically in-flow
  • Screen is callable offline — history replayable in principle (Zendesk cannot at all)

Zendesk wins today

  • Multilingual understanding (~150 languages) — Argus's deterministic reader is English-only
  • Live re-evaluation of an active, souring ticket
  • Shipped per-action human-review UI (Copilot) — Argus's is not built
  • Every operational dimension: scale, uptime, support/SLA, compliance, reporting, ecosystem

The frame, stated plainly: Argus is not a Zendesk replacement — it runs on top of Zendesk. Its honest pitch is narrow and sharp: on this one recovery use case, the safety floor is fail-closed, the guest path is deterministic and $0, and history is replayable — three things Zendesk structurally cannot offer. Everything broad and operational still favors Zendesk today, and the Argus edge is sandbox-proven, not production-proven. Biggest gaps to close before this is gold: (1) non-English coverage, (2) run the full-history backtest (pending), (3) ship the per-reply human-review loop, (4) earn production exposure.
