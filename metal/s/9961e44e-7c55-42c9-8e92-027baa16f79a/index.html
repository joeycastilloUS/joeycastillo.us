Manifold / Chat Interact — the plan (lean)

Joey.AI over the rollout — the smallest thing that delivers the operator’s stories. The Manifold is its own C99 service (Bus + source slots); the panel is the AI-Pantheon (api.3-nous.net). “Very simple interaction for now.”

Plan — Awaiting Approval
Lean pass (Fable drive · Opus reconcile): cut 6 phases / 102 pts → 3 phases / 51 pts. Caches, the photo skill, and 3 of ~10 source slots deferred to v2 (see When To Revisit). No operator-stated story was cut.

Intent (the why)

The answer to any real rollout question — “does the Meraki port match the playbook and the install verdict?” — is scattered across screens. Make every piece of rollout data something you can select and ask Joey.AI about, with the AI back-and-forth kept off the ops feed. Ship the smallest live slice, learn, widen one source at a time. Each new source is one slot + one pin, zero Manifold change — so deferring sources costs nothing.

The user stories (drives everything)

US-1 — “For every chat event I want to use Joey.AI to do something with it. I can chat to Joey.AI about the exact message including images if they exist.”
US-2 — “I can select multiple messages to scope things.”
US-3 — “I see my back-and-forth with Joey.AI on the right. The middle is the actual context of what I selected.”
US-4 — “Move the chat to the left; drop the 4 site quadrants.”
US-5 — “Joey.AI = the top two Gemini, the same way we use Gemini in the OCR stuff. Very simple interaction for now.”
US-6 — “Eventually scope all of it — inventory, decomm, install, Toast, Meraki, Airtable, playbook, board.” (“eventually” — v1 proves it with 3 sources)

Approach (the how)

Build the Manifold outside every bridge — airtable is a source, its bridge is only the C# jacket; the Manifold sits above all jackets and reads through them. Normalize is not new code — existing a-d-d C99 skills.
POST /joeyai/ask { scope:[{source,id}…], prompt, thread } → Manifold.gather: Bus → slot[source].fetch(ids) → normalize (read+hash) // a dead/slow source omits itself — never fails the ask → fanout → POST api.3-nous.net (gemini-2.5-pro + gemini-2.5-flash + judge) → { answer, sourceRefs[], cost } // cost shown; thread keeps refs, not raw context
C99 skills reused (a-d-d/nous): read (extract) · http (slot fetch) · hash (keys) · fanout (the panel ask) · summarize (disagree → show both). Nothing new built in v1.

Constraints (what we won’t bend)

  • The Manifold is ours → C99, its own service — not inside airtable-bridge or any bridge (a bridge is a single-source C# jacket).
  • Read + reason only. No writes back to any source in v1.
  • The panel is always the AI-Pantheon via api.3-nous.net — never a direct Gemini SDK call.
  • The meraki slot reads warm/cached bridge data only — never triggers a live Meraki call (be kind to the API).
  • The thread stores refs ({source,id}) + answers, never raw source content — this is what keeps PII out of v1 without a hashing pass.
  • Chat-image pass-through is size-capped; an oversized image is omitted with a note (and is the trigger for the v2 photo skill).
  • Best-effort gather: a dead/slow source omits itself; it never fails the ask.
  • Secrets by env name only; never Secret-Manager-pulled at runtime; never committed.

Unknowns (named, not hidden)

  • Panel latency at multi-source scope. One chat message is fast; a mix of items + images may need a progress state. Unmeasured.
  • Image payload ceiling. How large a chat image can ride one api.3-nous.net call before cost/timeout bites — the size cap is a guess until measured.
  • Real panel spend. With no answer cache in v1, cost-per-ask is visible but unbounded — the number itself tells us if/when the cache is worth building.
  • Auth surface of the new service. Session-gated like the board — but a brand-new Cloud Run service needs its own ingress/allow-list decision confirmed.

When To Revisit (explicit v2 triggers)

  • Cache layer (normalized-item + panel-answer, SHA-256 keyed) — when week-1 panel spend hurts. Design already keys by content hash, so it’s a re-plumb, not a re-key.
  • photo C99 skill + ocr/photos slot — the first oversized-image omit, or the first request to scope OCR/serials.
  • Remaining slots (toast · airtable · board/journal) — one slot + one pin each, the moment the operator asks for that source.
  • Use-case chips / write-back / actions — when “very simple” graduates; write-back demands an approval gate (breaks the read-only constraint).
  • After P3 ships and the operator runs the first real cross-source question — answer quality tells us whether normalize is rich enough.

Definition of Done (plan-level)

  • A-D-D verified — matches the approved design (Manifold as own C99 service, panel via api.3-nous.net).
  • All 6 stories mapped: v1 delivers US-1–5 fully and US-6 with 3 proof sources; the rest are named v2 triggers.
  • Sections present: Intent · Scope · Approach · Phases · Constraints · Unknowns · When To Revisit.
