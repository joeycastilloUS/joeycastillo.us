What was updated

The Network tab port grid could read a port’s admin state but never change it. Port 8 in the operator’s screenshot shows STATUS Disabled with no way to bring it back up. Now every port row carries one button in that same cell: Disable when the port is up, Enable when it is admin-down.
  • bridge — POST /meraki/port-enabled, mirroring /meraki/port-poe line for line: RequireWritable(network,"set-enabled"), Gate.TryParseTarget, capture-before-write, GET-after, CloudLog AUDIT line.
  • web — a new Enable / Disable Port Lab Feature (set-enabled), the .porttog button, and doPortEnabled(). CSS shares the existing .poetog rules — no new style invented.
The one bug this change could have had. STATUS reads "Disabled" for an admin-down port — but it also carries Connected and Disconnected, so it is an observed field, not a config field. Keying the toggle off that string would have made a merely unplugged port offer to “Enable” something already enabled. The button keys off p.enabled (config), which the bridge has shipped in the portmap payload since Board PORT-POSTURE. That distinction is what the test below exists to prove.

The blast radius, stated plainly

Admin-down is sharper than the PoE toggle beside it. Cutting PoE de-powers what the port feeds; admin-down kills the link itself — a terminal, a printer, an uplink goes dark until someone re-enables it. Two independent gates stand in front of it: the set-enabled Lab Feature UI-side, and the bridge’s RequireWritable server-side, which admits only lab/test-named networks or ones on the Allowed list. The feature key has no list of its own, so it inherits the global Allowed list rather than inventing a wider door.

What this ~u found on the way — and fixed

The live bridge was running code that existed in no commit and no branch. Revision meraki-bridge-00106-v26, deployed 2026-09-02 06:53Z via gcloud run deploy --source ., reported SWSTAT1 at /version while bridge/Program.cs on main still said FIND1 r1320. SWSTAT1 appeared nowhere in the repo and in no remote branch. Deploying this change from the repo would have silently reverted switch-down alerting.
Recovered byte-exact from the source archive named in the revision’s own run.googleapis.com/build-source-location annotation, committed as af4526f before the port work went out. Program.cs was the only file that differed from HEAD; every other bridge source matched. The build stamp now chains PEN1 · SWSTAT1 · FIND1 · CHG2, and all four were verified present on the live /version after deploy — the proof that nothing was lost.
What SWSTAT1 does: portmap devices[] and switches[] now carry Meraki device status (online/offline/alerting/dormant) from organizations/{org}/devices/statuses, so the board can raise a switch-DOWN alert. Switchport statuses are last-known and stay connected after a switch stops checking in, so they cannot carry that signal.
Why it was caught at all: a build-stamp baseline taken by hand before deploying. Nothing in the pipeline enforces source == deployed. Mercury L2 presence could not warn either — presence.exe is Device-Guard-blocked on this box. Both are now Kaizen items.
