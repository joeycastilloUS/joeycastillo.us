What It Is

Intent — expose Purcius mesh health on a stable public URL without leaking any internal topology. Purpose — an inverted Hollow Edge: probe inward from in‑VPC, publish outward as a static, allowlist‑projected contract. What — a C99 node process (status_bridge) on bridge-los-angeles that probes each mesh node, projects the result into a fixed publishable struct (a field not in the struct cannot leak), and emits mesh.json + index.html. A separate push step ships those to Cloudflare Pages; the node serves no public port. Public face: status.purcius.net (page) + /mesh.json (machine contract). Per Rule 5 that .net surface is correct (platform/machine contract).

Stack

  • Core: C99, _GNU_SOURCE + raw BSD sockets, non-blocking connect + select timeout. Roll-your-own clean — no curl/popen/posix_spawn/system, no comms/skill/http dependency. Self-contained (gcc status_bridge.c -o status_bridge, no nous DEPS needed).
  • Output: writes both mesh.json and index.html to outdir (argv[1], default .). JSON: as_of, nodes[]{name,role,region,state} (+ relay-up {uptime,sessions,peers,transport}), mesh{nodes_up,nodes_total,primes_connected,health}. HTML is a static Be-styled shell that fetches mesh.json client-side and re-renders every 60s.
  • Push path (reuse, proven): cloudflare-bridge (the sanctioned C# vendor jacket) on Cloud Run acmedev-platform-hq/us-west1. Endpoints /cloudflare/pages-deploy, /pages-deploy-site, /pages-add-domain. Auth: BRIDGE_TOKEN or daily <yyyyMMdd>~go passphrase. CF key CLOUDFLARE_API_TOKEN (server-side). Live-proven today: every ai-metal.net/s/<token> and the ai-doculink.net custom-domain bind ran through it. CF account 7c605ea0….

Patterns Found

  • Allowlist projection (verified, not asserted): the ip field is in the Node struct but no emit statement references it — provable by reading the JSON build (only name/role/region/state[+relay counts] are written). Genuine allowlist, not a blocklist filter. This is the whole security thesis and it holds in code.
  • Relay contract MATCHES: relay_server.c handle_status() serves GET /status emitting {role,sessions,peers,uptime,transport,region,identity}. The bridge parses uptime/sessions/peers (ints) + transport/region (strings) — all five names match; identity is correctly NOT projected out.
  • Deploy template exists: metal/src/sdk/nous/action/skill/pirun/build-enact.sh is the proven “C99-on-prime” pattern to mirror (BUILD_DIR=/opt/nous/build, find -type d → -I harvest, gcc -std=gnu99 -O2 -w -D_GNU_SOURCE, DISARMED-by-default). status_bridge needs no DEPS list — simpler.

Open Questions — the two that could make the build silently wrong

RISK 1 (highest) — relay probe protocol: HTTP vs wire-over-TLS on :8080.
The committed code probes relays with plain HTTP/1.0 GET /status on :8080. Pass A read relay_server.c and found a matching plain-HTTP /status handler — so it likely works. But Rule 13 warns the relay speaks wire-over-TLS and returns 000 to plain HTTP, and the design prose says “wire_request / wire-native.” If :8080 is the wire-TLS port and /status is served elsewhere, every relay shows down. Resolve by one live in-VPC smoke (curl :8080/status from a peer node) before trusting the probe. Do not conclude from this dev box (home-router high-port block — Rule 13).
RISK 2 — Cloudflare Pages allow-list does not contain a Purcius project.
cloudflare-bridge Program.cs:42 hardcodes {argus-app, argus-net, ai-metal-net} and rejects any other project with 400 project-not-allowed. There is no purcius/status-purcius project anywhere. Plan of record (from the design): deploy mesh.json+index.html to the already-allow-listed ai-metal-net project, then pages-add-domain?project=ai-metal-net&domain=status.purcius.net — the exact path that already bound ai-doculink.net. Requires purcius.net to be a zone in CF account 7c605ea0… (design asserts “confirmed in-account 2026-07-18”; edge-confirmed same 104.21.x edge as ai-metal.net; account-membership itself unverifiable from outside — confirm in the CF dashboard). Alternative: add a dedicated project to the CLOUDFLARE_BRIDGE_PAGES_ALLOW env var (one-env change, no code deploy).

Secondary gaps (expected — the “fan-out” half)

  • Binary runs ONCE, no loop. The “every 60s push” must be an external systemd timer / cron on the node. The 60s in the HTML is only the browser’s client re-fetch.
  • No code posts to the cloudflare-bridge. status_bridge.c writes local files only — the push step is 100% unwritten.
  • No build recipe, no test. Design promised tests-ahead (IP/pubkey-in → neither-out; timeout → state:"down"). Write build-status.sh + the test.
  • Field shortfall vs design: code omits last_seen, stale, regions, prime facts/sources. Decide: ship lean-as-coded or grow to the design’s must-haves.
  • GCP project for bridge/relay nodes is not in the repos (cloudflare-bridge is in acmedev-platform-hq, a different node). Get it from live gcloud/operator.
  • Baked IPs are single-sourced (only in status_bridge.c) — no mesh.json/mesh.sealed to cross-check. Validate against live VPC.
  • Minor: design diagram says relay-hong-kong-b; code says relay-hong-kong. Reconcile the real public role-name. HTTP body buffer capped at 4KB (fine for ~200-byte relay JSON); JSON parse is naive substring pluck (brittle but OK for trusted flat JSON).

Build order for the pair (smallest real path to 200)

  1. Confirm RISK 1 from in-VPC: curl http://10.168.0.2:8080/status on a peer. Green → probe is correct. Red → switch the probe to wire_request before anything else.
  2. Write build-status.sh (mirror build-enact; simpler, no DEPS) + a status_bridge_test.c proving the allowlist. Build on the node, run once, eyeball mesh.json for zero addresses.
  3. Write the push step: POST index.html (+ mesh.json) to cloudflare-bridge /cloudflare/pages-deploy-site, project ai-metal-net. Add a systemd timer (60s).
  4. Bind the domain: pages-add-domain?project=ai-metal-net&domain=status.purcius.net. Verify dig status.purcius.net resolves + curl https://status.purcius.net/mesh.json = 200 with clean fields. That is Done (Rule 9).
