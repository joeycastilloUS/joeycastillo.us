How Internal Comments Are Really Made on Prod NPS Tickets

Read-only forensics against live production Zendesk (mendocinofarms tenant) via zendesk-bridge. 190 unique NPS tickets pulled: 100 “Follow Up On Your Mendo Feedback” + 80 “Guest Alert – Detractor” (plus 10 alert-family overlap in the first sweep). Every comment on every ticket inspected: public, via.channel, via.source, author_id, ticket email_cc_ids/collaborator_ids/follower_ids. Staff and guest names redacted per Rule 8.

2 · The three real mechanisms (evidence, not guesses)

A — API tool note (“Recovered by Shredder”) — 10 tickets, the most common.
via.channel=api, public=false, body is exactly Recovered by Shredder. Authors are real Guest Relations agents (one author id resolves as assignee on 10,184 tickets, another on 1,138 — only agents can be assignees). A recovery tool posts a private audit note on the ticket through the API under the agent’s identity. Examples: tickets 440806, 435485, 429999, 428581, 423532.
B — CC’d staff replying by email → Zendesk auto-converts to internal note — 7 tickets.
The Guest Relations agent sends the public recovery reply to the guest with field management on email_ccs (store manager, ops leadership). When one of those CC’d staff members hits reply-all from their inbox, Zendesk ingests the email into the ticket as a comment with via.channel=email and marks it public=false (comment metadata shows trusted:false, flags [15,2]). This is Zendesk’s documented CCs-and-followers rule: replies from CC’d staff become internal notes; replies from the CC’d guest (end user) stay public — both behaviors observed on the same ticket (454047). Smoking gun on 454047: a staff member’s user id sits in the ticket’s email_cc_ids, their reply-all landed as public=false with internal store addresses in via.source.from.original_recipients, and the guest’s next public reply thanks that person by first name. Examples: tickets 454047, 448850, 443210, 441745, 450763, 444462.
C — Agent-typed internal note in the agent UI — 6 comments.
via.channel=web, public=false, author is a Guest Relations agent. Bodies are short agent-to-agent working notes: Dupe (tickets 455091, 435800), an order number (385745), and a four-message internal dialogue on alert ticket 437895 where an ops leader’s email replies (mechanism B) interleave with the agent’s web notes.

3 · Verdict on the hypothesis

jc was right that the internal comment is not “a CC.” No internal comment is created by the CC mechanism, and none is a side conversation (0 in 190 tickets). Every internal comment is an internal note on the same ticket — posted via API (tool), via ingestion of a CC’d staff email reply, or typed in the agent UI. CCs are heavily used (63/100 follow-ups, 47/80 alerts carry email_cc_ids) but only as the transport that loops field management into the guest-facing reply — their responses then land as internal notes. No group reassignment observed either: all 190 tickets sit in the same Guest Relations group.

4 · Implication for illness_escalate

Match prod practice: post an internal note (public=false) on the alert ticket via the API — exactly the pattern the existing machine partner (“Shredder”) already uses and agents already read. Not a side conversation (never used here), not a CC (that is the guest-facing loop-in channel, and an illness escalation must not ride a guest-visible reply), not a group reassign (single-group shop). If field management must additionally be pulled in, the prod-native follow-up is the CC on the eventual public recovery reply — but the escalation artifact itself is the private API note.
