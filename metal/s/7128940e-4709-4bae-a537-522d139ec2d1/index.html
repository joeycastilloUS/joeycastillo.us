~p~e — Status Bridge, full dyno

Plan + estimate · paired (planner + estimator, reconciled) · from design 1127 (v2) · project: argus / Purcius substrate

AWAITING APPROVAL. Boards are laid in board.md as Ready but not pulled. The build runs in-VPC on the Linux mesh nodes — the other pair’s plane. This artifact is their build sheet. Note: a concurrent session advanced argus r707→r709 mid-authoring — rebase before building.

Intent

Make the status bridge sense the mesh instead of memorizing it. Turn a node on and it appears on status.purcius.net within minutes; turn it off and it’s sensed gone — with no recompile, exactly like the relay fabric. Discover membership from the mesh’s own operator-signed DNS TXT, emit raw observations, and let the app layer decide what “not seen” means — all while keeping the leak-proof guarantee strictly intact under now-untrusted input.

Scope

In: replace the baked NODES[] with DNS-TXT discovery + the operator-Ed25519 verify gate; the closed-schema projection; seen_cache + observation emit; verdict-field removal; the build recipe + 60s push + status.purcius.net bind. The one upstream relay fix that discovery depends on.
Out: per-prime direct probing (primes stay relay-counted); a human-readable public-name protocol (named as Kaizen); any change to the cloudflare-bridge itself (reused as-is, project ai-metal-net already allow-listed).

Approach

Reuse, then close. The dynamic mechanism already exists — lift dns_discover_primes() into dns_discover_relays() (retarget _relay.3-nous.net, role=='r', same Ed25519 gate). The security work is not adding a guard but separating dynamic input from a closed output schema: discovered fields land in named locals, the publish struct is filled field-by-field from an allowlist, and addr/pubkey are structurally never assigned to output. Then the DIA-DRAIN split: the bridge emits facts, the app owns the verdict. Ship the smallest slice that renders one discovered, verified, address-free record live before fanning out.

Phases (Rule 11 order: flow up first)

  1. Phase UP — the relay, upstream (in-VPC only). The bridge cannot trust a relay roster until relays keep their _relay record alive. Fix dns_announce_self() into periodic_refresh() (re-announce < 300s TTL), and confirm by peer-node curl that relays serve plain HTTP /status on :8080 in-VPC (Rule 13). Everything downstream blocks on this.
  2. Phase CORE — the bridge read side. The First Move + fan-out: dns_discover_relays() + verify gate → kill NODES[], wire the per-cycle roster → closed-schema projection (id=hash, per-string allowlist, no addr/pubkey out) → seen_cache + observation emit + recently_departed[] → strip verdict fields to counts + discovery{}. Tests-ahead at each step; the keystone test is address-in→address-never-out and bad-sig→dropped.
  3. Phase PUSH — build, schedule, go live (in-VPC + external proof). build-status.sh (mirror build-enact.sh, Linux) → systemd 60s timer POSTing to cloudflare-bridge /pages-deploy-site (ai-metal-net) → pages-add-domain status.purcius.net → Rule 9 proof: dig resolves + curl https://status.purcius.net/mesh.json = 200, address-free.

Week-one interim slice — 18 pts. SBDYN-UP fully (8) + the two CORE keystones: dns_discover_relays with the verify gate (5) + the closed-schema projection (5). That is the design’s own First Move — one discovered, verified relay renders with an id and no address anywhere in the JSON, bad-sig dropped. Constraints

  • C99 only for everything we own; the bridge + relay build and run on the Linux mesh nodes in-VPC, never the Windows dev box.
  • Tests-ahead (Rule 7): each item is a verify loop; the allowlist and bad-sig tests gate the projection.
  • Done = production, externally verifiable (Rule 9): status.purcius.net/mesh.json = 200 with address-free fields from a third-party vantage.
  • Rule 13 vantage: the two UP items are peer-node work; a dev-box curl proves nothing.
  • cloudflare-bridge reused unchanged; ai-metal-net already allow-listed; purcius.net already in the CF account.

Unknowns (named, not hidden)

  • Probe protocol. Does :8080 serve plain HTTP /status in-VPC, or is it wire-over-TLS? The v1 code assumes HTTP; the design prose says wire-native. SBDYN-UP item 2 resolves it — and if it’s wire, the probe step in CORE grows (swap to wire_request). This is the single biggest sizing risk.
  • Public name. Nothing baked means the page shows an opaque id until the signed-name Kaizen lands. Acceptable for v1; confirm the operator is fine with hashes first.
  • Cloudflare account membership. Design asserts purcius.net is in account 7c605ea0…; edge-confirmed but not dashboard-confirmed from outside. pages-add-domain fails if it’s a different account.
  • Relay identity carries region but not a name in /status/TXT — the projection must source region from the signed record or a word-allowlist, not free text.

When To Revisit (the signal that triggers a v2 of this plan)

  • SBDYN-UP item 2 shows relays speak wire-over-TLS on :8080 → re-plan the probe step (CORE grows; the estimate moves).
  • The mesh outgrows a handful of nodes → DNS-TXT discovery gets slow/impractical → revisit toward a signed gossip/registry read (the design’s named escape route).
  • pages-add-domain status.purcius.net is rejected (account mismatch) → re-plan the surface (fallback purcius.net/status/ path, per the design).
  • The operator rejects opaque ids on the page → the signed-name Kaizen is pulled forward into v1 scope.
