~dDESIGN

Need

Detractor Guest Experience Alerts land in Zendesk and wait on a human. The recovery reply is already a fixed house artifact (the "Digital I'm Sorry" macro, Tyler's voice, an IMSORRY code) — it should fire itself, deterministically, at $0, the moment a clean detractor appears. Same input → same output, always. Illness never gets a reply. That is the whole need.

Raw User Stories

  • "This Guest Experience Alert NPS-detractor event is the first event we key from to then auto-reply to the guest. Generate this auto response and post it to zendesk and zd sends the email and it looks handled."
  • "we just quite simply need scan, identify, react all based on defined .pi"
  • "I want .pi and i want it deterministic and i want it now."

Sourced Solution

Nothing invented — every part exists and gets wired:

  • pirun (src/sdk/nous/action/skill/pirun) — the .pi step runtime. Policy as data: the card's protocol[] drives everything; the run ledger (nous IDS) carries all state; crash-safe, one unit per advance.
  • nous understand / reason / restate — pure C99, 28 invariant operators, cannot hallucinate. IDENTIFY rules, classification, name/audit reasoning, byte-verbatim skeleton assembly.
  • zendesk-bridge (C# jacket) — zread (alert fetch, handled-check, guest name) + reply_send (FollowUpTicket write, the proven lane: new ticket, requester = guest, PUBLIC comment → ZD emails the guest — receipt: guest Lara on #456251).
  • gcp-bridge Firestore vault (standalone GCP, never Firebase) — claim_code: atomic, idempotent IMSORRY claim, synced from the brand's Sheet.
  • corpus / IDS (deatomizer) — corpus_match: closest past real reply, shown as the MATCH beside the .pi output. Display only; .pi stays authoritative.
  • vertex_panel — the gang of three: 3 Vertex models, panel, agreement-gated. Bounded to one job: the empathy sentence when the deterministic map misses. The only non-$0 line.

Naming

Literal, no themes: card recover-guest.pi; units scan_alert, gate_illness, gate_not_detractor, gate_handled, classify, resolve_name, claim_code, empathy_map, empathy_panel, compose, corpus_match, send, audit; skills zread, understand, reason, restate, claim_code, vertex_panel, corpus_match, reply_send. Every name says exactly what it does.

Shape — the protocol[] and where determinism is enforced

 1  scan_alert          zread          alert fields -> ledger                    auto/abort
 2  gate_illness        understand     HARD LAW: illness -> exit (escalate only) exit/abort
 3  gate_not_detractor  understand     nps<=6 + event rule, else exit            exit/abort
 4  gate_handled        zread          follow-up exists -> exit (idempotency)    exit/abort
 5  classify            understand     complaint -> fixed category set           auto/abort
 6  resolve_name        zread          ZD profile -> local-part -> "there"       auto/hold
 7  claim_code          claim_code     atomic vault claim; empty -> HOLD         auto/hold
 8  empathy_map         restate        fixed category->dialect map (Tyler)       auto/abort
 9  empathy_panel       vertex_panel   BOUNDED fallback; $0 passthrough on hit   auto/continue
10  compose             restate        byte-verbatim skeleton + slots            auto/abort
11  corpus_match        corpus_match   MATCH view, never blocks                  auto/continue
12  send                reply_send     sandbox auto (Q2) — PROD flips to fire    auto/hold
13  audit               reason         react record + run.cost_usd               auto/continue

Determinism is enforced at three points. (1) IDENTIFY = pure rules over understand()'s 28 invariant operators — units 2–4 are exit gates, no inference. (2) REACT assembly = fixed byte-verbatim skeleton + slots read straight from the alert (units 6, 7, 10). (3) The empathy is chosen deterministically by the category→dialect map (unit 8); the 3-Vertex panel (unit 9) exists only behind a map miss, and its 3-way agreement gate makes even that path effectively deterministic — disagreement falls back to the safe generic empathy, never a coin flip. Data-flow law: everything moves through the run ledger; operator edits are authoritative.

First Move

Build the C99 pirun host: register PIRUN_SKILLS[] with the three nous skills plus stubs, load recover-guest.pi, run a real alert to slice-end, and read the ledger trace. Everything after that is filling in skills.

Escape Routes

  • Illness — exit gate, host escalates to the manager lane. No draft, no code, ever.
  • Vault empty — claim_code fails to hold; operator refills; never invent a code.
  • Panel disagreement / Vertex outage — safe generic empathy, fail: continue; the send still goes.
  • Webhook drop — the 15-minute sweep reconciles; gate_handled makes the overlap idempotent.
  • Prod — the send unit flips gate: auto → gate: fire: runtime stops AWAIT_FIRE, armed, visible, DISARMED. Only jc arms prod.

~pPLAN

Intent

Make recover-guest.pi v4 actually run end-to-end in the brand sandbox: dual-trigger scan, deterministic identify + react, auto-respond (Q2), cost reported, MATCH shown.

Scope

In: the pirun host, the eight skills in the card, the category→empathy map, the determinism replay test, sandbox send. Out: prod arming (jc only), Q6 (deferred), any UI beyond the MATCH side-by-side view.

  • Never Firebase — Firestore via standalone GCP only.
  • Illness = detection/escalation only. Hard law, unit 2, exit gate.
  • Sandbox only (mendocinofarms1781637851); prod send is a disarmed fire gate; jc arms.
  • Deterministic > clever. Same input → same output is the acceptance test, not a nice-to-have.

  • Map coverage: what fraction of real feedback classifies into a clean category (drives how often the panel fires).

  • $10 vs $20 selection policy — vault-driven today; jc may want a severity rule.

After the first sandbox week of real alerts: if map-miss rate > 20%, expand the map (drive the panel toward $0); if panel disagreement > 10%, revisit the panel prompt or widen the generic; when jc says "arm prod", flip send to gate: fire and hand him the trigger.
