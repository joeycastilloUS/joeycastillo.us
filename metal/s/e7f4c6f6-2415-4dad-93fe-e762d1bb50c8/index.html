Argus AI Config pane — plan + estimate

Build the zaiconfig pane that enacts the Zendesk DIA from Argus. 23 points, six shippable phases, read loop before any write.

Paired — two independent ~p~e passes, reconciled. Two findings changed the plan: the recipient_addresses + groups Catalog reads already exist (first move is console-only, no bridge change), and ConfigCatalog is a new reversibility class, not a WriteCatalog extension (4 of 5 pushable knobs are creates; rollback-of-a-create ≠ restore-prior).

Intent

One Argus pane rendering every DIA D1–D6 knob as Desired / Live / Lane — push the API-pushable five through zendesk-bridge with capture+rollback, guide+verify the four Admin-Center-only AI knobs. jc never logs into Zendesk to configure, verify, arm, or disarm.

Scope

In: zaiconfig tab in web/app/index.html; ConfigCatalog.cs + GET /config/state + POST /config/apply in zendesk-bridge; drift render; manual-lane deep links + verify; arm switch; the .si bind flips.  Out: browser-automation jacket for the 4 AI knobs (separate later ~d); prod arming beyond the double-gate; any non-mendo DIA generalization.

Approach

Ship the read loop before any write exists (the design’s second-order risk: push without read = silent divergence). Console work is pattern-copy from the zdfacts pane (tab wiring touches ~5 registration points; zfLoad/zdOne/zdAll is the env-aware read template; ZF_AB, ZD_DEEP, the “Admin Center” honesty cell all reused). Bridge work is a new declared-config class beside WriteCatalog, pure builders unit-tested in the existing harness, endpoints reusing the triple write gate. Trap: the WOPR debug intercept matches mutating paths by name — config/apply must be added or writes bypass the hold panel.

Estimate — critical path & risk

Critical path: P1 → P2 → P3 → P5 (arm toggles a trigger P3 creates). P4 runs parallel after P2. Assumptions: 1pt ≈ a focused half-day; sandbox creds seeded (env=sandbox isolation exists); the triple write gate + cloudbuild deploy reused untouched; no auth work. Riskiest phase: P3 — if the create-rollback class needs its own board review, 8 → 13. P4’s verify-by-behavior sampling is second.

Unknowns (named — Rule 7)

  • U-CREATE-ROLLBACK — does the house permit DELETE in a rollback, or is rollback deactivate-only (orphaning created objects)? WriteCatalog forbids DELETE for its class; ConfigCatalog must decide.
  • U-NPS-ADDRESS — can nps@ be fully created by API (native address), or does verification force it into the manual lane? Moves a D1 knob across lanes if so.
  • U-VERIFY-SIGNAL — what read actually proves “agent published” and “tone = short/informal”? account/settings may not expose AI state; the sampled-ticket heuristic is undefined.
  • U-DESIRED-SOURCE — the .pi config: values get duplicated into C# constants; nothing polices drift between the DIA file and ConfigCatalog. Accepted for v1.
  • U-SEAL — who re-seals when the .si bind lines flip in P6.

When to revisit (v2 signal)

The first time jc asks to set (not verify) one of the 4 manual knobs from Argus, or drift on a manual knob recurs twice → the browser-automation jacket ~d. Second signal: a second brand/DIA wants this pane → generalize ConfigCatalog from mendo-hardcoded constants to catalog-per-DIA.

The single biggest 2×-maker

P4’s verify loop depends on Zendesk-side state no code can create.

“Green only when a live read or an answered ticket proves the click” requires the sandbox AI agent to be actually live end-to-end — AI agents-Advanced enabled, nps@ receiving, agent published, replying. Those are the very manual knobs being verified: a circular dependency on operator clicks + Zendesk SKU/sandbox behavior, not on any repo. If the sandbox agent isn’t answering mail, P4 can’t close its gate and the schedule doubles. De-risk: do the prereq + respond manual clicks (with P1’s drift pane watching) during P2/P3 development, not after.
