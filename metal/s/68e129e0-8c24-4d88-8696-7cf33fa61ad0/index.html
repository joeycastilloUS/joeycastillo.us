Argus AI Config pane — enact the Zendesk DIA, no admin login

One Argus pane: pick the brand, set every DIA demand, push what has an API, guide+verify what doesn’t. You never log into Zendesk to configure, verify, arm, or disarm.

Paired — two independent designs, reconciled. Supersedes the manual steps + directions in the DIA. From your doculink comment: “~d an enhancement to Argus where we configure all we need — select the sandbox, change configs from there. Don’t make me login to Zendesk and read documents.”

The crux — what Argus can push vs what Zendesk gives no API for

Zendesk sells no public API for AI-agent configuration. So “configure everything from Argus” is partially impossible today — and the pane must not pretend otherwise.

API-pushable: support addresses, triggers, groups, tags, brand read — the ticketing scaffolding, via the zendesk-bridge write lane (capture + rollback). Admin-Center-only: the four AI-agent knobs (tone, custom action, procedure text, agent publish) — Zendesk’s AI-agent API is runtime-only. For those, Argus deep-links to the exact page and verifies by reading it back / sampling an answered ticket — no doc-reading, one click, confirmed.

Need

One pane in Argus where jc picks the brand (Guest Relations Test / GR Test v2), sees every D1–D6 knob of mendo-zendesk-ai-config as Desired vs Live vs Lane, pushes every API-pushable knob through the bridge, and gets a guided Admin-Center link + read-back verify for the four Zendesk sells no API for — and never logs into Zendesk to configure, verify, arm, or disarm.

User stories

  • “I open Argus, pick GR Test v2, and see every DIA demand as a row: what it should be, what Zendesk actually says it is, and whether they match — no Zendesk tab.”
  • “I click Apply and the nps@ address, the CC trigger, the illness trigger, and the escalation group exist ten seconds later, response IDs shown.”
  • “The rows Argus can’t push don’t lie — they say Admin Center, link me to the exact page, and go green only when a live read (or an answered ticket) proves the click.”
  • “Arm is a switch in Argus: off = the Received-at trigger is inactive, no guest can be touched; prior state captured for rollback. I arm prod, nobody else.”
  • “Change my mind on tone or the CC list — I change it here; drift between the DIA and the live instance shows red, never silently.”

Sourced — reuse / build / split

  • Reuse: the DIA (.pi config: = desired state; .si units = the row list, each with its D#); the Argus console tab machinery + the ZF_AB brand pair already in web/app/index.html; the zdfacts “Admin Center” honesty cell + ZD_DEEP deep links; the zendesk-bridge env=sandbox isolation + the WriteCatalog capture/rollback write lane.
  • Build: the pane; a bridge declared-config write class (server-side bodies built from DIA values, never caller JSON — same law as WriteCatalog); read entries for recipient_addresses + groups; the drift check (desired vs live read).
  • Split: pushable = D1-address, D1-gate, D3-trigger+group+tag, D5, D6-toggle. Manual-with-verify = D1-publish, D2-action, D3-procedure, D4-tone.

Naming

  • Pane/tab: zaiconfig, label “AI Config” (joins the z* family).
  • Bridge: GET /config/state?env=sandbox&brand=<id> (live reads, drift vs the DIA computed server-side) · POST /config/apply?env=sandbox&unit=<unit>. Unit names = the .si’s own: prereq respond promo_code illness_escalate tone cc_response arm. Class: ConfigCatalog.cs.
  • Objects pushed (literal): triggers argus: nps@ AI gate / argus: illness skip_ai_reply / argus: CC DO/Store; group NPS Escalation (human); tag skip_ai_reply.
  • No shadow store: desired = the .pi config: block; actual = live Zendesk reads; the pane renders the diff. Manual-knob acknowledgments append to mendo-zendesk-ai-config.sm.add.

Shape

Top: brand picker (the ZF_AB pair; env=sandbox pinned). Middle: seven rows, one per .si unit, three columns — Desired (from the .pi) / Live (from /config/state) / Lane. Lane = an [Apply via bridge] button (pushable units; response IDs + rollback capture rendered inline) OR an amber Admin Center chip + deep link to the exact dashboard page + a [Verify] button (re-read, or sample the brand’s latest AI-answered ticket). Bottom: the D6 arm switch — reversible active toggle on the gate trigger, prior state captured, prod arming double-gated on jc. Every apply/verify writes an audit line.

First move

Read-only, zero writes: add the zaiconfig tab + the seven-row pane rendering Desired-vs-Live from existing reads (brands, triggers) plus two one-line Catalog.cs entries (recipient_addresses, groups). That alone answers “is the sandbox configured per the DIA?” without a Zendesk login, proves the drift loop, and de-risks the apply lane before ConfigCatalog.cs lands.

Risk

No AI-agent config API — the sharp one. Persona/tone, generative procedures, custom actions, and agent publish live only in the AI agents-Advanced dashboard. So four DIA knobs stay guided clicks; Argus links + read/behavior-verifies them, but cannot set them. The only path to closing them from Argus is a browser-automation jacket (Playwright driving the dashboard with jc’s creds) — brittle, session/2FA-entangled; a separate later ~d, not smuggled into this one. Second-order: the push lane is one-directional until the drift-read lands — push without the read loop and a manual Zendesk edit silently diverges from the DIA. That is why the first move is the read.
