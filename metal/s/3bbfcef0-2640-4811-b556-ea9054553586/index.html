NPS Detractor Triage · Use Case 1 — for the Mendocino Farms IT Project Team
This is the whole brain of the system — its Pure Intent. Fifteen plain demands the machine must obey, enforced on every single run. No hidden logic; if the intent below and the running code ever disagree, it refuses to run. Below are the fifteen demands, in order, as the file states them.
D1 — Every NPS-detractor alert is read and understood before anyone answers anything.
D2 — If this alert ticket already carries our handled-tag, stop — we have been here. The first run to reach an alert tags the ticket itself; every later sweep reads that tag straight off the ticket and bows out. Per-ticket, so a returning guest’s new ticket is always fresh.
D3 — Read the guest’s feedback in their own words, in any language. Never translate or flatten it before the illness check.
D4 — Check every alert for a possible food-borne illness. The check is a panel of two models — vertex-gemini and vertex-gemini-pro.
D5 — Recovery runs ONLY if BOTH models say safe. Any flag, any error, any silence counts as illness. Doubt escalates — a human minute is cheap; a missed illness reply is unforgivable.
D6 — Illness never reaches the guest: no reply, no code, no Zora. A human owns it and the run ends.
D7 — Escalate an illness by posting a PRIVATE note on the alert ticket AND reaching the escalation list through the ticket’s Zendesk side-conversation (never a direct mailer — D15). Mark it urgent. Tell them what the guest said and what the models saw.
D8 — One escalation per alert, ever. Re-runs never re-send.
D9 — A non-illness detractor gets the deterministic “We’re Sorry” recovery, at zero cost: name what went wrong, claim one real code, send the Zora reply. Same feedback in, same reply out, always.
D10 — The empathy line mirrors what the guest complained about. If we can’t place the complaint, use a safe generic line. No model ever writes a word a guest will read.
D11 — One code per guest, claimed atomically from the vault, spent once. If the vault is empty, hold and ask to refill — never invent a code.
D12 — Send the recovery as a public follow-up so Zendesk emails the guest. Idempotent — never double-send, never double-spend.
D13 — The alert ticket’s requester is a neutral NPS-system identity — never the guest, never an agent. So no one is falsely notified, and the guest is never contacted on the illness path.
D14 — Sandbox until jc arms prod. jc is final approval.
D15 — Every message to a person goes through Zendesk — never direct. The guest hears from us only as a Zendesk follow-up (D12); staff only as a Zendesk private note / side-conversation (D7). No direct email, no SMS, no back-channel. Zendesk is the one auditable channel; nothing speaks to a human around it.

NPS Detractor Triage — proven live

An unhappy guest (an NPS detractor) comes in. The system reads their words, checks for a possible food-borne illness, and takes the right action automatically — all through Zendesk, in the sandbox. This tab shows real output from it — the results, then how it works. For the full set of rules it follows, open The Intent (.pi); to fire your own test, open Generate NPS.

How it works — two branches, one rule: when in doubt, protect the guest

Every detractor is read in the guest's own words, in any language, never translated first. Two models — vertex‑gemini and vertex‑gemini‑pro — check for a food‑borne illness. Recovery runs only if BOTH say safe. Any flag, any error, any silence counts as illness — a human minute is cheap; a missed illness reply is not.

⚠ Illness path

Escalate to a human: a private note on the ticket + a Zendesk side‑conversation to the team, marked urgent. One escalation per alert, ever — re‑runs never re‑send. The guest hears nothing.

✓ Recovery path

An empathy line that mirrors the actual complaint, one real code claimed from the vault (never invented), and the Zora follow‑up email. Idempotent — never double‑sends, never double‑spends.

Everything runs through Zendesk — the one auditable channel; nothing emails or texts a human around it. The alert's requester is a neutral “NPS Alert System” identity, so no guest is ever falsely notified. It stays in the sandbox until Joey arms production — he is final approval.

How to test it, and what to expect

Open the Generate NPS tab (you hit the button). Put your own email in guest_email so a recovery reaches you. Allow ~30–60s (a sweep runs every 15s). Nothing here touches a real guest — it's the sandbox.

  1. See the recovery path: fire a normal complaint — e.g. feedback “the app kept crashing and my order arrived cold and late.” → within a minute you get a “Follow Up On Your Mendo Feedback” email from Zora with a $10 code (like ③).
  2. See the illness path: fire a complaint that names a symptom — e.g. “the food made me sick” or “I think I got food poisoning.” → the guest gets nothing; instead the ILLNESS ESCALATION email lands with the team (you're on the list) and the ticket shows the private note + side‑conversation (like ①②).
  3. Watch the ticket: every fire creates a sandbox Zendesk ticket — open it to see the alert note, the illness verdict (if any), and the escalation trail.
  4. Try the edge: a sarcastic line like “this food is sickening to look at” is an idiom, not a symptom — fire it and watch it be treated as a normal detractor, not an illness.

Escalations go to the team list (jcastillo@mendocinofarms.com + enghiem@). Recovery coupons go to whatever guest_email you post. Codes come from a test vault (TESTCODE…).
