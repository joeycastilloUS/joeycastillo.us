OneDine Case Data: where we are, where it comes from, what's blocked

Read-only ingestion of OneDine Salesforce cases for root-cause mining and a case-pattern knowledge base

Status brief · every number below was measured live on 2026-07-26 · nothing is estimated

1. Where we are

The full OneDine case history has been pulled once, sealed into an immutable local store, and is being served read-only to the Argus console. Salesforce is not touched again after the pull — every downstream question is answered from our own copy. That copy is live and queryable today.

Cases42,402complete history, not a recent window
Case comments16,385the only correspondence we currently have — see §5
Facts (triples)634,907every field of every record, preserved verbatim
Pulled2026-07-1000:00 UTC, in 182 API calls total
Methodadaptive created-date windows — query a span, split it if it hits the page cap, recurse. Completeness is guaranteed regardless of case density.
Rate impact182 calls against a ~100,000/day allowance, paced at 0.35 s. Effectively zero load on the org.
What this buys: the corpus can be re-derived, re-indexed, re-analyzed as many times as we like at zero cost and zero risk to OneDine — no re-querying, no rate pressure, no chance of a runaway integration. The only time we go back to Salesforce is to fetch what's new.

The target is measurable. "No Solution" plus "Resolved itself" is 3,852 cases — 9% of everything — where a root cause was never established. That is the number a pattern KB exists to move, and it can be reported on every rebuild.

Fields that look useful and aren't — worth knowing before anyone builds on them.

IsEscalatedFalse on all 42,402 records. The field is unused in this org. Real escalation shows up in Status instead: Tier 2 (208), Development (92), Vendor (5).
PriorityLevel 2 on 33,128 of 42,402 (78%) — effectively a default, not a signal. Level 3 (7,498), Level 4 (983), Level 1 (792).
Status = Merged8,128 cases (19%) are merged duplicates. Only 8 of them carry a ParentId, so what each was merged into is not recoverable from the fields we can see. See ask 4.

5. The gaps — what's blocked

The correspondence is not in the corpus. 87% of cases arrive by email, but the entire org holds only 16,472 case comments — 0.39 per case. The actual email threads live in Salesforce's EmailMessage object, and every query against it fails: the simplest valid request, SELECT Id FROM EmailMessage LIMIT 1, returns HTTP 400. That is the response Salesforce gives when the object isn't visible to the integration user.
Consequence: today we can mine case subjects and descriptions, but not the back-and-forth where the diagnosis actually happens. For root-cause mining, that is the difference between reading the title of a book and reading the book.

Same result, same likely cause, for two more:

EmailMessageBLOCKEDthe email correspondence — the priority ask
Account · Case.AccountIdBLOCKEDno way to attribute a case to a customer or site
Contact · Case.ContactIdBLOCKEDno way to attribute a case to a person

Confirmed field by field: OwnerId, SuppliedEmail, SuppliedName and Origin all return normally on the same query shape — only AccountId and ContactId fail. So this is specific access, not a broken query.

And three objects that are already readable and simply not being pulled yet — no permission needed, just a decision:

CaseHistory79,960READY field-level change trail — 21,318 owner changes, 11,530 status changes. This is how a case moved through Tier 2 / Development, not just where it ended. Nearly double the case count in rows.
Task3,819READY activity records linked to cases
Attachment465READY metadata (screenshots, logs referenced by cases)

Likewise OwnerId, SuppliedEmail and SuppliedName are readable today and are not yet in our pull — adding them gives agent attribution and requester identity for the 87% email population without needing Contact access at all.

6. The asks

Four for whoever administers the OneDine org; the rest is our work.

  1. Grant read on EmailMessage to the integration user. This is the one that changes the product. Everything about root-cause mining and case-pattern matching depends on the conversation, and the conversation is in there.
  2. Grant read on Account / Case.AccountId (and Contact / ContactId if it's not sensitive). Without it we cannot say "this problem hits these customers" or "this site generates 40% of the Tier 2 load" — only "this problem exists."
  3. Confirm we may pull CaseHistory, Task and Attachment metadata. They're already readable; we want the nod before roughly doubling what we hold.
  4. Where does the merge link live? 8,128 cases sit at Status = Merged with no parent pointer we can see. If a custom field records what each was merged into, that's 8,128 human-verified "these are the same problem" pairs — a free, hand-labeled validation set for the matcher. If it isn't recorded anywhere, we'd like to know that too, so we stop looking.

A fifth, informational: are Priority and IsEscalated deliberately unused, or unused by accident? We won't build on them either way — but if they're supposed to carry signal, that's a process finding worth surfacing.

7. What we build, in order

  1. Refresh path. Incremental pull from the stored cursor, a rebuild that re-derives the whole store locally, and an explicit promote step so a new corpus only goes live when someone chooses it. Plus two counters — how far behind we are, and whether we hold everything the source has. The equivalent already runs in production on a support corpus 10× this size.
  2. Search that ranks. Current search finds matches but doesn't rank them, and truncates silently past a couple of thousand matches. The ranked, indexed version is a port of code already running.
  3. The pattern KB. With email threads in hand: cluster by root cause using Reason as the seed labels, match new cases against the clusters, and report against the 3,852 unexplained cases as the scoreboard.
  4. Beyond support. The same corpus already answers questions nobody is asking it yet — 3,817 data requests (a self-service gap with receipts), 2,745 questions (the documentation backlog, clustered into the docs that don't exist), 802 field bugs, 449 feature requests ranked by real demand.
One honesty note for any coverage claim. Notification cases (6,892) and phone cases (5,385) together are 12,277 — 29% of the corpus — and carry little or no minable text; a phone case body is call metadata, not conversation. Any KB coverage number should be stated against the ~30,000 cases that actually contain language, not against 42,402.

8. How to verify any of this

Every figure here came from one of two places, both repeatable by a third party with the same credentials:

  • Live org — read-only SOQL counts through the bridge (SELECT COUNT() FROM Case, and the field-by-field access probes in §5).
  • Our sealed copy — the query service's own status and facet endpoints, which read the store and never touch Salesforce.

Nothing in this document is inferred from code comments or prior documentation. Where the documentation and the running system disagreed, the running system won.
