One line. Every NPS reacts.

The DIA and pi_run you have today. One added line, five strings shortened, one fallback label. Nothing else moves.

Tested against both real sandbox bodies before writing this. Paired.

The change

In grab() — pi_run.c:208:

static void grab(const char*blob,const char*marker,char*out,int cap){ out[0]='\0';
    const char*p=strstr(blob,marker); if(!p)return; p+=strlen(marker);
    while(*p=='*'||*p==':'||*p==' ') p++;          /* skip label decoration */
    int n=0; while(*p&&n<cap-1&&*p!='\\'&&*p!='"'&&*p!='\n'&&*p!='\r'){ out[n++]=*p++; }
    out[n]='\0';
    while(n>0&&(out[n-1]==' '||out[n-1]=='*')) out[--n]='\0'; }

Then drop the trailing space from the five markers — "NPS Score " becomes "NPS Score", and so on — and add one fallback for the feedback field, whose name differs upstream:

grab(resp,"Guest Comments",feed,sizeof feed);
if(!feed[0]) grab(resp,"Guest Feedback",feed,sizeof feed);

Order matters, and getting it backwards is a real bug. The first draft tried Guest Feedback first. On live ticket 733 that matches the requester's profile name — "name":"Guest Feedback Test" in the response metadata — and returns "Test". Non-empty, so the fallback never fires and the guest's actual words are lost. Guest Comments first is correct on all five live tickets: the default-brand blob contains no such string, so it falls through cleanly.

Two added lines, one modified line, five shortened strings. The gate itself does not change. Unit 0 keeps its shape.

Every stored field on the default-brand path is byte-identical. That is the thing Mendo HD is exercising, and this change cannot move it. One nuance for accuracy: the raw NPS grab loses a trailing * to the new strip ("2 / 10 — **Detractor" vs "…Detractor**"), but the caller keeps only the leading digits, so alert.nps is "2" either way.

The one thing it does not fix

Store stays empty on the Guest Relations format, because the value sits on the line after the label. The code already handles an empty field — it writes "?" — so the alert still processes end to end.

Leaving it. Store is a display field; it decides nothing. Chasing it means teaching the reader to cross line breaks, and a reader that walks to the next line will happily grab the next label when a field is legitimately blank. That is a bigger change and a worse failure mode than a "?".

What this is and isn't

  • Is: every NPS alert that reaches Zendesk now reacts, whatever brand, whichever of the two templates it arrives in.
  • Isn't: the recovery reply still goes out on the default brand. Separate change, already designed, not required for "react to every NPS."
  • Isn't: a general-purpose tolerant parser. It skips decoration and knows one extra field name. That is the whole of it.

Test before deploy

The first proof ran against fixtures — and the fixtures flattered it, omitting the via.source.from metadata where the 733 collision lives. The navigator then ran the same extraction against the real bridge response (ZBRIDGE/read?entry=ticket-comments, the exact endpoint http_read_alert uses) for 728 and 730–733 and found it. That is now the standard for this change: real blobs, five of five, or it does not ship.
