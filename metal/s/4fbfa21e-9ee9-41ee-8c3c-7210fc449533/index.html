~i — Argus Login Lockdown

Paired inspection (two blind passes, reconciled) · driver Opus / navigator Fable5 · project: argus (acmedevUS) · r881

Verdict in one line: Argus opens four login doors today; you want two. Closing the login plane is a small, clean change — delete one provider row, set the crew to a single exact email, rotate one key. But the login plane is not the whole building: the console's data lanes (five services, including write endpoints) authenticate with a guessable, comment-documented daily Bearer — yyyymmdd~go. Weld the front door shut and the loading dock still opens with today's date.

What It Is

Intent — the operator wants Argus login locked to exactly two doors: the operator passcode in use today, and Google restricted to a single identity, jcastillo@mendocinofarms.com. Every other way in must be closed. Purpose — reduce the console's authenticated surface to the smallest defensible shape before it carries live customer data. What — the auth core is the C# meraki-bridge jacket (multi-auth OIDC + Overlord key seam), fronted first-party by a Cloudflare Worker (web/_worker.js) so the argus_session cookie is same-origin. Access control is a server-side Crew Allow-list. Login proves who; the crew decides what.

The Lockdown — gap → target

1. Kill Slack. Delete the slack object from bridge/providers.json. Routes are data-driven (providers.TryGetValue → 404 on miss, Program.cs:203,219), so that one deletion closes the door server-side. Caveat (navigator): the table is read once at container startup from AppContext.BaseDirectory Program.cs:192-193 — the edit does nothing until redeploy. Then remove the loginSlack button + handler (index.html:548,8396) and fix "Slack / Google" copy (:603-604,1095). Verify Done: live GET /auth/slack/login → 404.
2. Lock Google to you. Set the crew to exactly ["jcastillo@mendocinofarms.com"] — the exact email, never @mendocinofarms.com. Confirmed both halves: the exact form admits that one identity; the domain form admits any Google account on that domain (Auth.cs:105-106). Editable from the console Crew tab; stored in Firestore settings.
3. Keep the operator password. Untouched. (But see R1/R2 — today it only actually authenticates the Meraki tabs.)
4. Rotate AUTH_SESSION_KEY during the change. Sessions are HMAC-validated only; the Firestore sessions doc is written but never read back (Program.cs:90,270). Tightening the crew does not evict already-signed-in Slack/Google members — their cookie rides up to 12h (MaxAge, :264). Rotating the key kills every live session immediately.

The one most likely to leave a hole

R0 — the data plane is wide open with a guessable key. The console's data calls use zrawPass() = UTC yyyymmdd + "~go" (index.html:4694) as the Bearer for five services — zendesk-raw, zendesk-bridge, gcp-bridge, onedine-raw R2, ZREC. It is not read-only: write lanes ride the same key — /zendesk/promo-claim, /promo-release (:7208,:7218), /zendesk/config-apply (:7652), /zendesk/sync-object (:8881), /vertex/correction (:3483). The scheme is even documented in a committed comment (:3111). Anyone who knows the pattern reaches these with zero login. Locking the four doors does not touch this. Recommend folding a data-plane key fix into the same lockdown.

Login-plane risks

R1 — the operator-password gate fails open. Any non-401 failure of loadNetworks() sets bridgeDown=true and opens the console anyway, password unverified (index.html:8377-8390). The Zendesk/GCP/corpus tabs never use PW at all — only zrawPass(). So door A really only authenticates the Meraki tabs.
R2 — BRIDGE_TOKEN fails open. If the env var is empty, the middleware skips auth entirely for all data routes (Program.cs:83, IsNullOrEmpty(bridgeToken) → next()). A missing secret = no gate, not a locked gate.
R3 — any crew member can edit the crew. A member session is an alternative credential to BRIDGE_TOKEN on all gated routes (Program.cs:88-90), which includes POST /settings (proxied, _worker.js:11). One allowed login can invite anyone — self-escalation. Contained with a one-email crew, but it is the mechanism to watch.
R4 — OIDC id_token trust is thin. Confirmed absent in the callback (Program.cs:216-266, Auth.cs:51-71): (a) no JWT signature verification — DecodeJwtPayload base64-decodes the payload only ("v2 hardening" per the file's own note); (b) no aud/client_id check; (c) no email_verified check; (d) the nonce is signed into the state cookie but never compared to the id_token nonce (:223-224). Trust anchor is the server-side code exchange with client_secret over TLS, so exploitation needs more than a forged token — but for "all the way big time," add aud + email_verified at minimum.
R5 — the key door bypasses the crew entirely. /auth/key/verify never calls EmailAllowed; it mints a session directly with OVERLORD_EMAIL defaulting to overlord@joeycastillo.us (Program.cs:353-365). If the sidecar + PURCIUS_OPERATOR_PUB are configured, a warranted device is a crew-exempt door — which is exactly why Decision 1 must be explicit.

Cosmetic: the Slack button is unconditional client-side (index.html:548); after server removal it stays visible and a click just 404s until the UI edit ships.

Open Questions — decisions that change the build

Decision 1 — the Overlord/Purcius key (door D). Keep it or kill it? It is your own crypto key-login, not the passcode, and it bypasses the crew (R5). "Keep only passcode + Google" reads as kill / prove-503, but it is your key — explicit yes/no needed.
Decision 2 — harden Google, or just restrict it? Restrict-only = the crew edit alone. Hardened = also add aud + email_verified (+ optional JWKS signature + nonce check) per R4.
Decision 3 — fix the data-plane key (R0) in this pass? Recommended yes — it is the real hole. Replace yyyymmdd~go with a real per-session/served credential across the five services (writes first).
