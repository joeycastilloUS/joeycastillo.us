Where both passes agreed — the real constraints

1. The wire cannot carry a card. One verb, and it is not “install.”

enact_server.c:21   #define ENACT_VERB "enact"
                    /* the ONE generic plumbing verb -- never a business word */

Relay verbs are auth / register / verify-register / reset-totp / verify-reset / enact / status. The enact frame carries {tenant, ref} only, and the tenant comes from the capability, so the frame cannot even name a card. There is no verb that writes, installs, or transfers anything.

2. No write path for a .pi exists. Anywhere.

A sweep of fopen(...,"w") across the whole substrate finds three runtime writes: the seal, the coupon-vault slot claim, and debug dumps. No script in either repo pushes a card to a node. The C# bridges have zero .pi awareness. Cards are placed by a human with scp.

Confirmed by omission: the repo card was edited 2026-07-20 (389d608, the D4 allow-list), after the last documented copy to the primes on 07-19. The primes are running the older card right now, and nothing detected that.

3. The seal is not an approval gate against a program

dia.c:327-332   if (!sf) { FILE *w = fopen(seal_path,"w"); ... }   /* trust-on-first-use */
dia.c:338       REFUSE: words '%s' hash %08x != sealed %08x -- reseal to approve
dia.h:48-49     "guards accidental edits, not an adversary who can also write the .seal"

There is no reseal tool. “Reseal” is rm <card>.pi.seal and re-run. So an applier that writes cards is the new approval authority — whatever it can write ships without a human ever seeing it.

And the seal covers only the words blocks. Demand text, config values and the D4 allow-lists are not hashed. An update flow that edits demand prose passes biRT silently.

4. “Add a DIA” can mean “recompile the substrate”

Dispatch is a hardcoded if-chain of 14 (skill, slot) string pairs in pi_run.c. A new card that recombines existing micro-ops is fine. A new card needing any novel capability requires new C compiled onto the primes. This is the biggest architectural question and it sits upstream of any UI.

5. The console is honest; the draft is a dead end

runbook-from-macros.js is a pure function that always returns demands: [], runnable: false, draft: true. Its own header says a generator that invented demands “would be inventing the safety floor.” The draft lives in RBG.draft in memory and dies on refresh. Nothing claims to write; nothing writes. The macro read is real and live through the bridge.

The one thing I will flag despite “ignore security”

Do not teach the wire to accept a card.

This is not a security-ceremony objection, so it is worth thirty seconds. The mesh's entire safety property today is that the wire can only run pre-installed, sealed intent — one verb, capability-gated, relay drops everything else. An install verb turns every reachable relay and prime port on a public 34.x address into remote intent injection — and the injected intent commands real guest email, spends the coupon vault, and escalates to staff, in a loop, every fifteen seconds.

The alternative costs nothing and is strictly easier: push from the operator's side over ssh/scp. The trust stays where your keys already are, and the wire keeps its one-verb guarantee. Ignoring auth on a console demo is survivable; a write verb on a public IP is a different category.

Shortest real path

Update an existing DIA — mostly a deploy problem

  1. Take the staged dial change against the repo card.
  2. Validate by actually running dia_load_pi + dia_verify — dia.c is self-contained and compiles standalone. Not a reimplementation of the rules.
  3. Rewrite the .pi, reseal, commit.
  4. scp card + seal (+ .si/.sm if changed) to both primes. This mechanizes the exact manual step that was skipped this week — and closes the live drift.

Add a new DIA — same pipeline, plus registration

Add the tenants.tsv row and a trigger, and constrain it to cards that bind only existing micro-ops, enforced by running dia_verify against the real nous.sm before any copy. That constraint is the difference between adding a DIA and silently shipping a card that exits 5 on every fire.

Riskiest thing

The reseal step. The seal is the operator-approval boundary and it is trust-on-first-use. Any applier that writes cards and seals them together becomes the approval authority. If this gets built, its write-scope should be the narrowest thing in the system: dial values first, words only behind an explicit human confirm, demands never — and remember the seal does not cover demands or config at all, so “biRT will catch it” is false for exactly those fields.
