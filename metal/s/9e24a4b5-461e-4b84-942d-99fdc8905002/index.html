Plan — DIA hit count

Plan — Awaiting Approval

Implement the design (design/dia-hit-count): per item, per DIA, a hit count; bump is the claim. Retire mendo-nps's guest-keyed dedup.

Intent

Replace mendo-nps gate_handled (searches Zendesk for any prior "Follow Up" requester:<guest> — keyed on the guest forever, blind to which DIA acted) with a per-item per-DIA hit count the DIA owns. Ship it as the default idempotency primitive every DIA can lean on, with mendo-nps as the first consumer.

Scope

In:

  • Jacket ops: count-bump (atomic claim, returns created) + count-read on a ticket.
  • nous.sm binds for the two ops; a pi_run hits helper (DIA-id from the card).
  • A declared dedup: mark | none policy in the .si + biRT check.
  • Rewire the mendo-nps gate to bump-then-act-on-created; retire the guest search.
  • Prove live: returning guest, re-sweep, and two near-simultaneous sweeps send exactly once.

Out: cross-item dedup, count expiry/decay, retro-marking historical tickets, the doculink/DIA viewer, and rolling this onto DIAs beyond mendo (generalization follows once mendo proves it).

Approach

Bottom-up: land the durable atomic counter first (it's the load-bearing bit), then the blind runtime plumbing, then the intent, then prove and retire the old gate.

  • Counter as claim — the jacket owns an atomic per-DIA increment on the ticket that reports whether this caller won the bump (created). Everything else keys off that boolean.
  • Runtime stays blind — pi_run passes the DIA-id (from the .pi card:) and reads back created; it never knows Zendesk.
  • Intent declares the meaning — dedup: mark acts iff created; dedup: none ignores it. Missing = biRT refusal.

Constraints

  • KISS — it's a counter. No policy engine, no framework, no versioned-scheme ceremony beyond what a counter needs.
  • Language Boundary — the atomic increment + vendor storage live in the C# jacket; pi_run stays C99 business-blind.
  • The bump is the claim — act only after winning the bump; never read-then-act (the sweep race is real).
  • Sandbox until armed — jc arms prod.

Unknowns

  • Storage primitive. Zendesk tags are a set (increment = remove-old + add-new, not atomic) and may normalize :/=. A per-DIA custom ticket field or a checkbox-audit may be the better home for an atomic counter. Resolve in Phase 1 by testing both.
  • Atomic-claim mechanism. Does Zendesk safe_update + a stale updated_stamp reliably 409 so exactly one concurrent bump wins? Needs a real two-writer test, not an assumption.
  • What counts as a "hit." Bump at the gate (before we know if we'll send) marks an illness-exit ticket as hit=1 with no recovery — is that correct (we did act: escalated) or should the bump sit at send? Define "act" per unit before wiring Phase 3.

When To Revisit

  • After mendo proves it live (first consumer) and before a second DIA adopts it — the storage primitive and the "what is a hit" semantics may need adjustment once a DIA with different act-semantics uses the same counter.
  • If Phase 1 finds Zendesk can't give an atomic claim on any primitive — fall back to keeping the claim in the bridge (a small keyed ledger) and revisit the "mark lives on the item" choice.
