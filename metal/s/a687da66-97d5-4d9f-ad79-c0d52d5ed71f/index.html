Deterministic REACT — understand() + translate_strings(), data-driven

~d design · mendo-app-survey-autoresponse.pi v10 · the classify → empathy_map → empathy_fallback → compose units · replaces the rejected hardcoded-classifier plan

Corrections against the real code (verified, not trusted):
  1. restate() is NOT in understand.h. That header defines only understand(), understand_atomize(), understand_dice(). The restate(const Fact*, int, const Store*, …) signature exists only as a-d-d spec canon (a-d-d/nous/intelligence/skill/understand/CLAUDE.md § Interface) — it is not built in the metal SDK. The only compiled restate is a static round-trip helper inside understand/atoms.c, private to that test tool.
  2. The BUILT inverse of understand() is the translate skill — src/sdk/nous/action/skill/translate/translate.h: int translate_strings(Ids *store, const char *dialect, const char *vars[][2], int nvars, char *out, int out_size). It queries the triple store for (dialect, "template", ?) and fills {name} placeholders. Per a-d-d action canon: translate is "restate() generalized." The card keeps saying skill: restate (intent); the ONE map binds it to translate.translate_strings (the seated muscle). skill_map.tsv's current restate.restate rows point at a micro-op that does not exist in the container — they must be corrected.
  3. Canon already ruled out dice for classify. RESOLVER.md: understand complaint-category → understand.understand (decode only, NOT atomize/dice). So classify matches decoded atoms exactly against a data signature table — no similarity scoring. understand_dice stays reserved for corpus_match, exactly as the map already says.
  4. suppress_close is a no-op against the v10 template. The byte-verbatim Zora body closes "Best, / Zora" — there is no closing guest name to suppress. compose carries slots.suppress_close through untouched; the mechanism (a {close_name} var that renders empty when suppressed) activates only if a future operator-approved template variant adds a personalized close. The bytes of the canonical template never change.

1 · Need

Four REACT units must turn alert.feedback into the real Zora reply.body — deterministic, $0, no LLM — without baking intelligence or intent into the host C. The rejected plan hardcoded a keyword table, an empathy struct array, and template literals into container_dispatch. That violates the a-d-d action principle ("capabilities are not hard-coded — they are dialects") and the IoC contract (RESOLVER.md: the card names, the map binds, the container provides). Everything that varies per deployment — the category set, the category→empathy map, the Zora template — is DATA, like skill_map.tsv itself.

2 · Raw User Stories

  • As the operator, I edit a text file to add a complaint category or fix an empathy clause — no recompile, no C change, and I can read exactly what the machine will say.
  • As the operator, the reply body is byte-identical for the same feedback, every run, provably — the template bytes are MY bytes.
  • As pirun, I stay skill-agnostic: classify/empathy/compose resolve through the same skill_map.tsv as every other unit.
  • As the offline Vertex loop (card Q3), I author a NEW map row (a category signature + its clause) as a data-file diff the operator approves — never touching a guest reply live.
  • As an auditor, a map miss is visible in the ledger (empathy.source=none) and the guest still gets the fixed safe-generic clause.

3 · Sourced Solution

Everything below reuses muscle that exists today. Nothing new is invented; one map file is corrected and four data files are born.

SourceWhat it provides
understand.h — understand()Deterministic decode: UTF-8 text → WireTriple atoms {word, role, fn}. Lowercased tokens, 7 roles, 28 structure fns, closed vocabulary. Cannot hallucinate. THE classifier engine — it tokenizes and normalizes so "app" never matches inside "happy" the way strstr would.
translate.h — translate_strings()The built "restate() generalized": store-resident (dialect, "template", ?) + {name} placeholder fill. THE render engine for empathy clauses and the Zora body.
store.h — ids_insert()Loads each slot's data file into the ledger as a dialect triple, so translate_strings can see it. The ledger is already open in the host.
RESOLVER.md + skill_map.tsvThe ONE map: (card.skill, card.slot) → container.micro_op. The card never changes; only map rows and data files do.
The card (v10 header)The byte-verbatim Zora template, the canonical app empathy clause, the safe-generic clause, the draft_id convention. These bytes seed the data files verbatim.
pirun.hThe data-flow law: micro-ops read in: via pirun_get, write out: via pirun_put. Unchanged.

5.3 The thin C micro-ops (no intelligence in the container)

At host start, load_slots() (mirrors the existing load_map(), ~25 lines) reads the slots/ files and inserts dialect triples into the open ledger: (zora-template, template, <file bytes>), (zora-subject, template, …), (safe-generic-empathy, template, …), and one (category-empathy:<cat>, template, <clause>) per tsv row. Then four dispatch branches:

classify   (~40 lines)  understand(alert.feedback, atoms, …)          [the seated decoder]
                        keep content atoms (ENTITY/ACTION/PROPERTY roles)
                        score each complaint-category.tsv row: distinct
                        signature words present among atom words
                        best>0 -> complaint.category=cat, map_hit=true
                        else   -> complaint.category="", map_hit=false

empathy_map (~12 lines) translate_strings(L, "category-empathy:"+category, NULL, 0)
                        hit  -> empathy.text=clause, empathy.source=map
                        miss -> empathy.text="",     empathy.source=none

empathy_fallback (~10)  source==map  -> empathy.final = empathy.text
                        source==none -> empathy.final =
                                        translate_strings(L,"safe-generic-empathy",NULL,0)
                        empathy.cost_usd = "0.00"   (always; the branch is protocol
                        logic, the clause is data)

compose    (~15 lines)  vars = {name, empathy, amount, code} from the ledger
                        reply.body    = translate_strings(L, "zora-template", vars, 4)
                        reply.subject = translate_strings(L, "zora-subject", NULL, 0)
                        reply.draft_id = "recovery-<env>-<ticket>"  (sprintf; env
                        from host config)
                        suppress_close: carried through, no byte effect on the
                        v10 template (see Corrections #4)

Zero keyword literals, zero empathy strings, zero template bytes in C. The only strings the container knows are ledger key names (the card's contract, same as the existing real units) and the slot-derived file paths.

Choices — the real fork

restate() renders empathy/template vs pure data-fill?

Honest answer: they are the same operation at different degrees, and translate_strings() IS deterministic data-fill — seated as a skill. Per unit:

  • classify genuinely needs understand(). Tokenization, lowercasing, role classification, and the closed vocabulary are real machinery a keyword strstr cannot fake (substring false-positives, no normalization, no role filter). The intelligence lives in the decoder + the signature DATA, not in C. understand() earns its place.
  • compose is exactly translate_strings' job — store-resident dialect template + placeholder fill is its literal spec. Earns its place.
  • empathy_map is a degenerate template call (0 vars) — and that's fine. The alternative (a bespoke tsv-lookup in C) is MORE container code and a second data path, not less. Routing the clause through (category-empathy:<cat>, template, ?) keeps ONE render engine, one loader, and the clause bytes in the store where the operator can inspect them. The card's skill: restate stays truthful: "say it the Zora way" — the map decides how.
  • empathy_fallback is honestly NOT restate at all — it is a two-way branch on empathy.source (protocol logic, thin C) whose fallback CLAUSE is data fetched via the same engine. Naming that plainly beats pretending the branch is intelligence.

So: no unit gets a hardcoded table, and no unit gets ceremony — the one place restate would have been ceremony (the fallback branch) is declared protocol logic instead.

Escape Routes

  • Nothing here is irreversible. All four surfaces are reloadable data files + one map edit; the card is untouched at v10.
  • If translate_strings proves too narrow (conditional sections, a personalized close), the a-d-d-spec restate(Fact*, …) / full translate() grammar engine is the upgrade seam — swap the map row's micro_op, card and data files unchanged.
  • If exact atom-match misclassifies in practice, the map row can rebind classify to a dice-scored micro-op — but that changes the RESOLVER resource ruling (decode-only) and needs jc's approval first. Misses are cheap today: source=none → safe generic → offline authoring grows the signature file.

First Move

Create slots/ with the two canon-seeded files that unblock the whole chain — zora-template.txt (byte-copied from the card header) and category-empathy.tsv (the one canonical app row) — then correct the three restate.restate map rows to translate.translate_strings and wire load_slots() + the compose branch first. compose is the highest-value unit (it produces reply.body), it exercises loader + store + translate_strings end-to-end, and its output is byte-checkable against the card header in one diff. classify follows (understand() + signature file), then the two ten-line empathy branches.
