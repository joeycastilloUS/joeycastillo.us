Feasibility verdict — read this first

Only-if. Meraki can answer "is Windows Firewall enabled on this device?" only if that device is enrolled in Meraki Systems Manager with the desktop agent installed. Without SM, no Meraki-native path sees host firewall state, and the only honest button is one that says so.

There is no Systems Manager anywhere in this repo — not in the bridge, not in the console, not in the ISource catalog. So whether Mendo licenses it, and whether the ingest boxes are enrolled, is an open question. The First Move below answers it with production evidence before a single line of UI is built.
If SM is present, the answer is a first-class documented field — not an inference. The navigator verified this against Meraki's published API docs rather than reasoning from memory: 
GET /networks/{networkId}/sm/devices/{deviceId}/securityCenters
  -> isFireWallEnabled     bool    "device has a Firewall enabled"
     hasFireWallInstalled  bool
     fireWallName          string  (Defender, or a third-party product)
     hasAntiVirus / antiVirusName / isDiskEncrypted

GET /networks/{networkId}/sm/devices?wifiMacs=<mac>&fields=fwName,hasDesktopAgent,lastConnected
That wifiMacs= filter is the load-bearing detail: it joins a MAC we already show in the SSIDs view to an SM device record. Without it there'd be no way to get from a client row to a host.

Inference, labelled as such: the data comes from Windows Security Center via the SM agent, so it reflects whatever firewall product Windows registers, as of the agent's last check-in. It is last-reported state, never live state.
Two paths are closed, and both passes closed them independently.
  • Everything else Meraki-native: no. Group policy, adaptive policy, L3/L7 rules, Umbrella, and the client Os fingerprint are network-side enforcement or passive fingerprinting. The Os field says "Windows 10" — it says nothing about Defender. Presenting a fingerprint as posture would be fabrication.
  • Active port-probing (445/139/3389, RST-vs-drop): no, twice. Not reachable — the bridge runs on Cloud Run; the clients sit on 10.100.9.x behind the MX NAT, and Cloud Run egress cannot route there without a connector we do not have. Not advisable even if it could — Argus is read-only by contract, probing is active traffic into a live restaurant network, and RST-vs-drop is unreliable evidence anyway: AP client isolation, Windows profile rules and MX policy all mimic "firewalled". Rule 14 in product form — a probe from the wrong vantage returns a confident wrong answer.

1. Need

You need to know whether specific Windows clients — the ones you call the Ingest devices — are safely postured, per device, from the console you already have open. The named instrument is Windows Firewall; the need underneath it is "prove these boxes aren't exposed" without walking someone at a store through Control Panel.

Open question: "Ingest devices" appears nowhere in this repo — the only ingest hits are the nous corpus pipeline, unrelated. It is live-network vocabulary for a device class the code has never modelled. The design keys off the per-client row, so the exact name doesn't block the build, but naming the checks concretely needs your answer.

2. Raw user stories

As the operator, I want a button on a client row in the SSIDs view that answers "is Windows Firewall on?", so I can check an ingest box without phoning the store.
As the operator, I want the button to say "can't tell — not enrolled" when Meraki can't see the host, so I never act on a fabricated answer.
As the operator, I want the answer stamped with when the device last reported, so I know how stale it is.
As the operator, I want the device's network-side exposure next to the host answer, so "safe" doesn't hinge on one setting on one box.

5. Shape

Bridge — one read-only route (C# jacket; Meraki is the foreign API, so this is jacket-legitimate)

GET /meraki/host-firewall?mac=<mac>
  1. org networks -> keep productTypes contains "systemsManager"
  2. sm/devices?wifiMacs=<mac>&fields=fwName,hasDesktopAgent,lastConnected
  3. hit? -> sm/devices/{id}/securityCenters

  -> { state:"enabled"|"disabled", fireWallName, lastConnected }
  -> { state:"unknown", reason:"no-sm-network"|"not-enrolled"|"no-agent-report" }

No writes. Not woprGated (nothing to gate). Degrades on MerakiException the same way the audit already does.

Console — the button lives on the client row

Rendered next to the rename pencil in the SSID sections, only when the row's Os fingerprint says Windows. Critical distinction: the fingerprint chooses whether the button appears, never what the answer is. Three result states, rendered inline:

FIREWALL ON  Defender · reported 14m ago

FIREWALL OFF  reported 3h ago

CAN'T TELL  Not enrolled in Systems Manager — Meraki has no visibility into this host. Plus one line naming what would make it answerable.

The dashed border on "can't tell" is the same law Drift ships: solid = evidenced, dashed = we are telling you what we don't know.

Out of scope

SM enrolment itself. Any remediation or toggling of a host firewall — that's a write to a machine we do not manage. Probing. AV / disk-encryption columns (the same endpoint offers them; later, if the button earns its keep). Non-Windows clients.

6. First Move

One catalog line and one click. No route, no UI, no deploy risk beyond a bridge rebuild. 
new("sm-networks", "SM networks (org)",
    $"organizations/{orgId}/networks?productTypes[]=systemsManager", Array.Empty<string>()),
Deploy, then open it from the API Browser tab that already ships.

Empty array ⇒ the org has no Systems Manager, the button's only honest state today is "can't tell", and the real conversation becomes "do we enrol the ingest boxes, or posture them network-side?" — settled with production evidence rather than argument.

Non-empty ⇒ build the route. Either way you learn the deciding fact for the cost of one line.

Choices + consequences

  1. Ship the button with "can't tell" as a first-class state (pick) vs. wait for SM enrolment. Consequence: it lands now, tells the truth now, and becomes the standing argument for enrolment. Waiting ships nothing and leaves you phoning stores.
  2. SM securityCenters (pick) vs. active probing (rejected — unreachable, unreliable, and it breaks the read-only contract) vs. OS-fingerprint inference (rejected — that is fabrication wearing a badge).
  3. Ship the literal button AND the better instrument together (pick). See below — the ask points at the host, but the durable answer is network-side. Both passes reached this independently.
The instrument question — my recommendation, stated plainly.

You asked how to read the host firewall. That's a reasonable thing to want, and there are real reasons for it (compliance evidence, troubleshooting a specific box). But if the goal is "these ingest devices are safe," the host firewall is the weaker instrument — it depends on a setting on a machine you don't manage, reported by an agent that may not exist.

Meraki's strong lever is network-side: put the ingest devices on a dedicated VLAN with a group policy that denies lateral movement and restricts egress to only what ingest needs. Then their exposure does not depend on whether someone left Defender off. And that posture is continuously verifiable with machinery you already own — the audit's WIFI-* and SW-PORTSEC checks read it today, and Drift would tell you the moment it changed.

So: the result popover carries the device's network-side exposure line (VLAN, applied policy, SSID isolation) right next to the host answer — the better instrument visible exactly where the question gets asked.

What the button must NOT claim

  • Never render enabled/disabled for a non-enrolled device. No defaulting, no "probably", no inferring from the OS fingerprint.
  • Never present last-reported state as live state. Always stamp lastConnected.
  • Never say "this device is safe." It answers exactly one question, about one setting, at one reported moment.
  • Never imply Meraki "checked the device" — Meraki relayed what the SM agent last said.
