Port Identity Resolver

Who is on this POS switch port? — Konductor wins, Toast fills the gap, nothing is guessed.
Two Fable designers, independent. Opus reconciled. One real disagreement, ruled below.
Meraki says where and whether. Toast says who. Konductor says who it is becoming.
The ladder says which voice speaks. Crossing those wires is the one fatal bug in this design.

The flow

Port-first, not roster-first — the operator’s refinement

“you can do it by looking up whats on the pos switch first.. then reverse lookup in toast”

This is the correct direction and it is sharper than either design had it. You never iterate the Toast roster. You iterate the ports, take the MAC each one reports, and reverse-look-up that single MAC in tindex.

for each port on the POS switch:        <-- the switch is the spine
    mac = port.mac                      <-- network truth, observed now
    kindex[mac] ? KONDUCTOR             <-- reverse lookup
    tindex[mac] ? TOAST                 <-- reverse lookup
    else STRANGER

What this buys, for free:

1The ledger problem disappears. Toast never purges decommissioned devices — one is 402 days silent — and raw counts overstate the live fleet ~3×. Iterating ports means a dead record is never reached: it is not on a port, so it never comes up. No staleness filter needed for identity at all. That settles the A-vs-B disagreement below by making it moot on the main path.
2The board only ever renders what physically exists. Every row starts from a lit port. Nothing can appear on screen that is not plugged in somewhere.
3It is O(ports), not O(roster). ~24 ports per site instead of a 20-row ledger cross-product, per refresh, per site.
4No extra Toast settings required. device-info already returns the MAC on both POS and PRINTER records — the only thing the reverse lookup needs. Nothing new to catalogue on the bridge.

The Toast roster is still fetched once per cycle to build tindex, and it still feeds the exception pass in the other direction — “Toast claims a device we never see on any port” — but that is a side channel to the issue strip, never a source of port rows.

The transition — 2am, tech at the rack

00:29  POS-7 · [T] Bread Printer · PoE On
00:31  POS-7 · Bread Printer · unplugged 00:31  ← ghost hold, 10 min
00:33  POS-7 · Bread Start? · new device booting…  ← pulsing
00:34  POS-7 · [K] Bread Start ✓ · PoE On⚡  ← locked

Three rules make the handoff legible:

1Never flash to EMPTY mid-swap. The ghost hold keeps what left on screen, so the operator can confirm the right thing was unplugged.
2CANDIDATE looks like a question; KONDUCTOR looks like an answer. The pulse stops the instant kindex confirms the MAC.
3Every confirmation appends one ticker line — POS-7 · Bread Printer → Bread Start · 00:34 — and ticks the rollout %. The ticker is the narrative; the port table is the truth.

Wrong port is not an error. Konductor is matched by MAC, so a device plugged into POS-9 still shows KONDUCTOR there, carrying an amber expected POS-7 chip, while POS-7 stays CANDIDATE. A working device beats tidy paperwork — the discrepancy is visible, not blocking.

Where the designers disagreed

Should Toast staleness gate identity?

Designer A: filter tindex to devices synced within 14 days. Older entries become “ghosts”, excluded from naming a port, kept only for diagnostics.

Designer B: do not filter. “If a MAC is physically lit on a port, Meraki has just proven the device is alive; a 402-day-old lastSyncedAt doesn’t make it less plugged in.” Staleness gates only the disagreement pass.

Verdict — B. Both designs declare that Toast staleness must never imply a device is down. A’s identity filter commits exactly that error one layer deeper: it would blank the name of a device Meraki can see on the wire right now. Staleness is a statement about Toast’s sync log, not about the cable. It belongs in the exception pass, where it decides whether an absence is worth reporting — and nowhere else.

Learn MACs back into the Konductor record?

A proposes learning an observed MAC back into the plan so later refreshes match by MAC even if the cable moves. B keeps Konductor MAC-only and holds the port at CANDIDATE until the feed confirms.

Verdict — B, with A’s idea deferred. Learn-back is genuinely useful but it writes inferred identity into the plan, and A itself notes it must never fire on a multi-MAC port. CANDIDATE is honest and costs nothing. Revisit learn-back once the resolver has run a real install night.

  name contains "terminal"  ← minus serial-auto-named
1The subnets already separate them. Konductor is 10.90.100.x; the five production sites’ Toast devices are all 10.100.9.x. Precedence still matters, but collisions will be rare in production — and common in the lab, where a Toast Flex was observed on 10.90.100.199.
2The board’s printers are Konductor’s, not Toast’s. Bread Printer, Salad Printer, Expo Printer, Digital Expo Printer in DEFAULT_MAP are Konductor units at 10.90.100.7x. Toast’s printers are a different set entirely (Terminal 1 RP, Register 1…). Say so on screen or the two get conflated.
3MAC is already in hand. note() captures c.mac today — the board just indexes by IP. A MAC index is buildable from data already being pulled. No new Meraki calls.
4The migration: add a MAC index beside the IP index, resolve Konductor by MAC-or-IP during changeover, and retire DEFAULT_MAP’s IP keys once every device has been seen once by MAC. IP keying is DHCP-fragile; that is a latent bug independent of this work.

Failure modes

failurebehaviour
Toast unreachableLast-good tindex + fetch stamp: toast roster as of 23:58. Ports keep resolving; Toast names go stale-but-present, never blank. Never render “no Toast devices” from a failed fetch.
Meraki staleBanner network data Xm old; rows freeze with age shown. Suppress MISSING-K — you cannot declare a device missing from a switch you cannot see.
Feed silent, device pluggedStays CANDIDATE indefinitely. Honest. MISSING-K fires only when the window lapses.
Same MAC, two portsDUP. Fresher lastSeen keeps identity; do not oscillate names between refreshes.
Device swapped mid-installRECENT-VACANT on the old port, new claim on the new, ticker line Bread Start moved POS-7 → POS-9. The delta log catches it for free.
Toast MAC unparseableRoster-visible, join-ineligible. Count it: N unjoinable Toast records. Silent drops are the sin this replaces.
One missed pollRequire two consecutive misses before MISSING/ISSUE fires. Install night is full of 30-second unplugs.

What not to build

×Any online/offline badge derived from lastSyncedAt. It is an event marker, not a heartbeat — the healthy reference site runs 24–36h stale all day. Up/down is Meraki’s, full stop.
×Toast-staleness badges on port rows. A port row shows Meraki liveness only.
×Name or hostname regex matching, ever again. Cashier 1 vs Terminal 1 vs Terminal 1 RP vs Terminal 1 Receipt Printer is exactly why MAC is the only key. Names are display payload, never join input.
×Compare-time MAC formatting. One NormMac at ingest; join tables never contain a colon or an uppercase hex digit.
×Cross-vendor knowledge in a bridge. No Toast lookup from meraki-bridge, ever. Correlation lives in the console.
×Purging or curating Toast’s ledger. The 3× overstatement is Toast’s problem. We filter at the exception gate; we do not tidy their data.
