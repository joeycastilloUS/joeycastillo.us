Meraki Bridge — from single cache to proper provider

Why refresh clicks return nothing today, and the two-lane design that gives you a real live refresh while keeping ~100 boards from ever flooding the Meraki API.

Current one funnel — a click gets the same cache as the background poll

Manual refresh, board polling, and the warmer all share ONE cached read path. Within the 30s TTL the warmer has already filled the cache — so your click returns byte-identical JSON. Two instances each keep their own cache, so it also jumps around.

  • ① No force path. A human click hits the same GetAsync as the poll → returns the ≤30s snapshot → “nothing changed.”
  • ② Split-brain. 2 instances, each its own cache + warmer → clicks bounce between snapshots → “works sometimes.”
  • ③ Staleness hidden. Cache-buster makes it look live; the app shows your clock as “as of,” not the data’s real age.
  • ④ No limiter. Sequential fan-out + no token bucket → slow cold builds and latent 429 risk under load.

Proper provider two lanes, one governed pipe

Shared reads stay cached (protect Meraki). Interactive clicks take a force lane that bypasses the TTL but is itself floored per-network. One instance = one cache/warmer. Everything meters through a single token bucket, so nothing floods the API.
