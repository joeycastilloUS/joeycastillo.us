Multi-Site Pulse Management

Idea-stage design · built with Norman Campbell (Pulse Suite author) · fable-only, no reconcile pair · design only — no code. Argus becomes the enterprise consumer of Pulse Suite hardware-health telemetry across an operator's many physical sites. NOT multi-tenant read-only pure C99 / zero C#

1 · Need

A restaurant/hospitality operator runs POS fleets across many physical sites. Norman's Pulse Suite (18 projects, pure C, "verify effects not return codes" — Status Report Ver 1.6, 22 Aug 2026) already measures the truth per terminal: package power, every core temp, every drive temp at one row per second, GFLOPS, watts avg/peak, throttle-visible speed bars, NVMe wear-out with an honest range. Proven on real hardware: a 10-minute run = 599 rows tracking 3 drives at once — including a Silicon Power SATA drive running 69°C against a Kingston NVMe at 56°C, and a stick that reports no temp at all (blank column, not a wrong number).

What nobody has: one screen showing every site. The 69°C drive is only visible if you happen to be standing at that machine. The Pulse Suite's fleet dashboard (Pulse-Health 0.2.1, Track C) is deliberately built last, on field-proven sources — and its common record format is deliberately undefined until then. Meanwhile the operator's terminals cook, wear out, and throttle during service, silently, one site at a time.

The need in one line: the operator sees hardware health for all sites, all terminals, all devices, in Argus, read-only, before a drive dies during a Friday dinner rush — without forcing Norman to define the record format he has deliberately deferred.

2 · Raw user stories

  • "Show me every site on one screen — green, warn, or critical. I'll drill from there."
  • "That SATA drive at 69°C — I want to know before the terminal dies mid-service, not after."
  • "Which terminals across the whole fleet have drives crossing their wear-out estimate?"
  • "A terminal throttled through all of lunch. Show me the throttle history from the speed-bar data."
  • "Which sites are still on the old printer driver? What firmware is on every Pulse-Link dongle?"
  • "One stick reports no temperature. Show me a blank — an honest blank — never a made-up number."
  • "I don't want anyone able to touch a terminal from this console. Watch, never reach in."
  • Norman: "The record format is undefined on purpose until Track C. Don't force a schema on my suite to feed your dashboard."
  • Norman: "Telemetry is one-way, observe-only. Nothing instruments the payment path. Monitoring fails independently — a dead monitor never takes a terminal down."

3 · Sourced solution (reuse first — every piece cited)

Argus already holds the doctrine Pulse deferred

The crux of this design is one sentence: Pulse's deliberately-undefined common record format is not a blocker — it's exactly the problem Argus §7 was built to answer. Don't invent a schema. Import each health record ONCE into a RAW sealed nous TripleStore and atomize it into triples (site, terminal serial, device, metric, value, timestamp), then derive the site/terminal/device views deterministically with the decoder (understand()). When Norman lands Track C and defines the real format, only the decoder changes — the sealed raw rebuilds every derived view byte-identically. Format deferral and fleet visibility stop being in tension.

What is genuinely new (built, not reused)

  • pulse-ingest — a C99 Cloud Run service that receives pushed records (the first receive-shaped source; everything until now proxied a pull API).
  • The atomizer — the understand()-backed decoder that turns a Pulse record (per-test row or per-second CSV) into RAW-IDS triples.
  • The Fleet Health tab in web/ — rollup + drill views over the derived stores.

5 · Shape (MVP + explicit out-of-scope)

MVP

Data path: Pulse records → pulse-ingest → RAW IDS (append-only, sealed) → derived Site / Terminal / Device / Flags views → Fleet Health tab.
  • pulse-ingest — C99 Cloud Run service, mirrors §3 topology (own repo, own IAM, own deploy, one secret). Accepts HTTPS POST of Pulse records — per-test result rows AND the second-by-second CSV — authenticated by per-site token. Append-only writer into the RAW IDS; provenance per batch: site + terminal serial + cursor + wall-clock + row count (§11 metering law mirrored). Exposes /catalog + /read for the frontend, same as every source.
  • Atomizer — understand()-backed decoder: each record row becomes triples (site, terminal, device, metric, value, timestamp). Whatever shape Norman's records take now or after Track C, the raw is sealed as received; only the decoder tracks the format.
  • Derived views —
    • Site rollup: worst-of over terminals → green/warn/critical per site.
    • Terminal view: drive temps over time, NVMe wear-out estimate (with its honest range), throttle history reconstructed from per-test speed-bar data, package power avg/peak, peripheral/driver + firmware inventory (OPOS family + VCD2x20 + Pulse-Link fw).
    • Device view: one drive / package / peripheral across its whole history.
    • Flags view: threshold-derived — drive temp warn/critical (the 69°C SATA case is the calibration point), wear-out estimate crossing, sustained throttle, device not-reporting.
  • Fleet Health tab in web/ — vanilla, plugged via the §3 registry entry { pulse → { baseUrl, scopeToken } }. All sites with rollups → drill to Site Health → drill to Terminal Health. Read-only, every screen.
  • Determinism proof baked in: same sealed raw + same decoder = byte-identical derived views (§7). Full Refresh re-derives the entire fleet.

Explicitly out of scope

  • Multi-tenancy. One operator, their many sites. Locked by operator direction — tenancy is not designed, not stubbed, not "left open."
  • Any control path back to a terminal. Observe-only, one-way, forever. The payment path is never instrumented, never touched. Argus renders; it never reaches in.
  • Defining THE common record format. That is Norman's Track C decision, made when Pulse-Health is built last on field-proven sources. pulse-ingest atomizes whatever record it receives; it does not legislate.
  • Coprocessor / flight-recorder ingest (ESP32-S3 Stage 1/2). Because the suite's law is ONE record format for agent→server AND agent→coprocessor, the flight recorder's decoded records will flow through the same atomizer when ready — nothing here precludes it, nothing here builds it.
  • Mesh store-and-forward transport. Held as the escape route for egress-limited sites (§10 email-DIA precedent). MVP is direct HTTPS POST.
  • Alerting/paging. Flags render in the console. Notification is a later Slot of its own.

6 · First Move (smallest real proof)

One real terminal's real run, visible read-only in Argus.

  1. Norman provides ONE real Pulse-POS-Load-Test second-by-second CSV — the proven 599-row / 3-drive / 10-minute run — plus one Pulse-Link per-unit serial as the terminal identity.
  2. POST it to a stub pulse-ingest that atomizes into a RAW IDS with full provenance (one site, one terminal, one batch).
  3. Derive the Terminal view; render that ONE terminal's drive-temp lines + throttle history in a Fleet Health tab through the existing frontend source registry — no UI-shape changes.

Success is specific: the Silicon Power SATA line visibly hot at 69°C against the Kingston NVMe at 56°C, AND the no-temp stick showing an honest blank not reporting — both read-only in Argus. Then delete the derived store and re-derive from sealed raw: byte-identical (§7 proof).

One terminal proves the seam (§3 registry), the store (§7 RAW→derived), and the decode (§9). Sites and rollups are replication, not invention.

Choices + Consequences

ChoiceTakenConsequence
A · Push-ingest vs pull-proxyPush-ingestPulse agents already emit outbound-only (Norman's one-way law) — pulling would mean opening a listener on every terminal, inverting his architecture and violating fail-independence. Consequence: pulse-ingest is the first receive-shaped Argus source; it must hold per-site auth and rate discipline that pull-proxies never needed. The -bridge naming convention correctly does NOT apply.
B · Invent a Pulse schema vs atomize into RAW IDSRAW IDS (per §7)Inventing a schema now would front-run Norman's deliberate Track C deferral and marry Argus to a format that will change. Atomizing to triples means the sealed raw survives every format revision; only the decoder versions. Consequence: derived views are rebuildable forever; the cost is an atomizer that must honestly represent blanks and ranges, never normalize them away.
C · Transport: direct HTTPS POST vs mesh store-and-forwardHTTPS POST firstSimplest thing that ships; every site with normal egress works day one. Egress-limited sites (locked-down franchise networks) fall back to nous mesh (240-byte fragments, store-and-forward — §10 email-DIA precedent) later, behind the same ingest. Consequence: transport is a swappable front on a stable atomizer; no record is shaped by its carrier.

Escape Routes

  • Per-second atomization too heavy. A 10-minute run is 599 rows × every core + every drive + power — full triple atomization may cost more than it earns at fleet scale. Fallback: store the raw CSV blob keyed by (site, terminal, run) in the sealed store and derive on read. Still import-once, still provenance-backed, fully reversible — atomize later without re-ingesting anything.
  • Record format shifts under us (Track C lands, or an interim change). By design only the decoder changes; sealed raw + new decoder → full re-derive (§7). No migration, no data loss, no coordination cost with Norman beyond the decoder update.
  • Per-site token provisioning drags early. First Move and early pilots may run on a single operator token; per-site tokens become mandatory before the second site goes live. Reversible hardening, not a redesign.
  • Push proves wrong for some environment. Because /catalog+/read and the derived views are transport-blind, a site-local spool that pulse-ingest polls (or mesh, Choice C) can front the same atomizer. The seam holds.
