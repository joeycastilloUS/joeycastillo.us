How refresh works today

Two independent clocks: a server-side cron that keeps a warm cache fresh from the vendor APIs, and a client-side poll that watches a cheap "epoch" counter and only re-pulls when it changes. Viewers never hit Meraki directly.

⚡ The principle: the cron drives the vendor reads (kind to Meraki); the board reads a tiny warm-status epoch every 15s and re-fetches per-site data only when the epoch advances. 1 viewer or 50 viewers → the same refresh load on Meraki.
1 · Server side — the cron keeps the cache warm
Google Cloud Scheduler → bridges (every minute)
meraki-warm-0s + -30s :00 / :30
POST /meraki/refresh-active → pulls the active install networks from the Meraki API into an in-memory warm cache. (:15/:45 cron paused)
→
meraki-bridge warm cache
in-memory, TTL 12s, active-window 1800s. Survives between requests: min-instances=1, CPU always-on. Bumps epoch each pass.
→
Meraki API
portmap · wireless · verify · device status. One retry on 429.
atb-review-sync 60s
POST /atb/review-sync → pulls Inventory/Decomm/Install review changes.
→
airtable-bridge · Firestore cache
content-hashed (SHA-256): bumps atbEpoch ONLY when something actually changed.
→
Airtable + Toast
reviews, serials/OCR · Toast device-info & ghost-printer config.
2 · Client side — the board polls epochs, re-pulls on change
Each open board · timers set in boot()
tickClocks 1s
Display only — clocks & countdowns. Zero network.
pollWarmStatus 15s
GET /meraki/warm-status — one cheap shared read, wall-aligned :00/:15/:30/:45 (all boards synced). On epoch advance → refreshAllQuads() (re-fetch each site from the warm cache).
pollAtbStatus 30s
GET /atb/review-status. On atbEpoch advance → loadStore() + repaint the review badges. (Cron lands ≤1/min, so 30s is plenty.)
checkBuild 60s
GET /version.json. On boardHash change → reload once to pick up a new board deploy.
rollDay 60s
Rolls the share board to the new install day at the 2 PM Pacific business-day boundary.
accept-poll 60s
GET /settings. On change → refreshAllQuads (a device marked "not installed").
🔒 Hidden-tab gate (2026-09-01 outage fix)
Every poll skips while document.hidden. Cloudflare's Workers free plan caps invocations at 100k/day account-wide — a wall of abandoned open tabs blew the cap and knocked out login site-wide. visibilitychange fires a catch-up sweep the instant a tab returns, so nobody sees stale data.
The quad footer shows "as of <cache time> · ↻ 30s" — the timestamp of the warm read it's showing, and the underlying refresh cadence.
3 · Transport — how the read reaches the bridge
Logged-in board
Browser → same-origin → Cloudflare Pages worker → bridge. The argus_session cookie flows first-party; the worker is a hollow edge (injects nothing).
Share-key board ?k=
Browser → bridge run.app directly (CORS-allowed for argus.com.ai). Quota-free — the Pages worker is never invoked; the key is the credential.
In one sentence

A cron warms a 12-second Meraki cache every 30s and a Firestore review cache every 60s; each board polls a cheap epoch (warm-status 15s, atb 30s), re-fetches only when the epoch moves, throttles itself to zero while backgrounded, and shows exactly which cache instant it's displaying — so the wall board, the crews, and the execs all see the same live truth without ever hammering the vendor.
