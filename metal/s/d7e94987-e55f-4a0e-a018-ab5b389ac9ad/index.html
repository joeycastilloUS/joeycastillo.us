Design — Purcius Auto-Sync IDS

The paradigm promises the mesh stays in real-time sync and IDS records replicate. It isn't built. This makes it real — and holds to five laws: forward-only, no racing, no waste, no dup, and it resumes itself through a power cut. The Register (DIA claim/dedup/count) is its first record type. Opus authored; two Fable5 adversarial passes folded in. v3: HRW ownership + a signed roster-record fence (skew is alarmed, not silent), and a deterministic draft_id so effectively-once holds through a mid-send cut — the two claims the model stakes its name on, now bolted down.

The Five Laws

  • 1 · Forward only. Append-only, monotonic. The record never rewinds, never rewrites. "Change" is a new record + a read-time projection (event-sourcing). Time only moves forward.
  • 2 · No racing. Not "race then resolve" — no race exists. Each item has one owner by rendezvous hashing (owner(item)=argmax fnv1a(node∥item)); only its owner writes its claim. And it's fenced: the roster is a signed, epoch-stamped replicated record, every write carries (epoch, claimer), and a peer that receives a claim from a non-owner-under-its-roster alarms the divergence. Ownership plus the fence is "no race exists"; ownership alone is only "no race is visible."
  • 3 · No waste. An item is processed by its owner once — not by every node then de-duped. Work routes to the owner; the others never touch it.
  • 4 · No dup, dedup-protected. The claim is a forward-only append keyed on (dia, item); the store's native exact-triple dedup makes re-apply a no-op; the irreversible act is guarded by a durable intent (Law 5).
  • 5 · Resume through a power cut. Even when the board caps buy a few milliseconds, at some point power is gone mid-act. To the system, power loss is time pausing; on power return, time unpauses and it keeps going from exactly where it stopped — a write-ahead intent + a resume pass drive every incomplete act to completion, forward-only, no dup, no human. It always unfucks itself.

1. Need

Two truths collided. paradigm.md §5: "the mesh remains in real-time sync across the globe… syncing effortlessly once a connection is restored." conventions.md:1511: "IDS records replicate too." A deep inspect of every nous copy found no implementation: store.h has zero node/peer/sync awareness, mesh.c only routes blobs, enact_server runs cards but never applies a remote write, and the only replicate in the tree copies a file to a bucket. Primes hold islanded /var/nous/*.ids.

So every multi-node behavior that needs shared truth has no floor: the DIA claim/dedup, cross-operator .pi collaboration, distributed audit, Tier-0 metering. mendo's double-send didn't reveal a mendo bug — it revealed the paradigm's foundation is a promise, not a substrate. Close it once, at the bottom, to the five laws.

2. Raw User Stories

  • As a node, I want a committed replicated-class write to land on every reachable node, so all nodes hold one record.
  • As a node, I want to own an item's claims alone, so no other node races me for it.
  • As a node, I want a power cut mid-act to resume to completion on reboot, so nothing is lost and nothing is sent twice.
  • As a node, I want to cross-check a peer's record (seal + cap) before I trust it.
  • As an operator, I want the record identical on every node ("same same") and self-healing, with no manual re-arm.

5. Shape

The record-class split (Law 1)

  • Replicated class — its only write API is append; no delete exposed. Append-only by construction → grow-only CRDT → converges with no consensus. Countable records (hit counts) carry a unique event-id subject (a grow-only set can't count identical triples).
  • Local run ledger — pl_set/trace_ev, mutable, local, never replicated. pi_run unchanged.
  • Intents and dones are replicated-class append events (not a mutable state machine): intent and done are two immutable records; "pending" is the read-time projection intent ∧ ¬done. That is event-sourcing — squarely Law 1. Replicating them (not just local) gives a dead owner's successor full information to reconcile. Projection rules, all convergent + order-tolerant: pending = intent-without-done; any done = complete (first-done-wins if two dones carry different sink-refs — a legal outcome when resume produces a second); anti-entropy may deliver done-before-intent, and the projection tolerates it.

Plane 1 — convergence (Laws 1, 4)

  • Append to sync-log (fsync) → broadcast the sealed envelope (the three strings + origin + sync-seq). Durable before the wire.
  • Apply on receive: verify seal+cap → ids_insert(strings). Idempotent; any order converges. Anti-entropy (per-origin high-water on the sync-log) repairs single-hop gaps + reconnects. Real-time is one-hop; beyond one hop is anti-entropy cadence — stated, not oversold.

Plane 2 — the claim: ownership + a fence, not a race (Laws 2, 3)

  • owner(item) = argmax over roster of fnv1a(node ∥ item) (rendezvous/HRW). Only the owner writes the claim. Work routes to the owner (relay/sweep dispatches by owner, or each node processes only what it owns) — once, no waste. The owner's single-threaded enact loop serializes its own claims for free (no lock).
  • The fence (this is what makes it truly race-free, not just usually). The roster is a replicated, epoch-stamped, operator-signed record in the sync-log — so config skew is a sync gap anti-entropy heals, not two divergent files. Every envelope carries (epoch, claimer-id); apply-on-receive checks owner(item, my_roster@epoch) == claimer. Mismatch → the append still lands (forward-only) but raises a divergence alert — v1's reject-if-not-mine reborn as detect-if-not-mine. A silent skew-race becomes an alarmed one; the claim never has to guess.
  • Epoch change (prime joins/leaves): drain pending intents → bump the epoch (operator ceremony, signed) → HRW remaps only the departed node's items. Resume re-checks "do I still own this under the current epoch"; if not, it never blind-sends — it completes only via query-confirm (Plane 3).
  • Owner down = the item holds until the operator removes the prime + bumps the epoch (runbook), at which point the new owner reconciles the dead owner's intents against the sink (Plane 3) — "holds until operator acts," never "unknowable forever." Consistency over availability, deliberately.

Plane 3 — the irreversible act survives a power cut (Law 5)

  • Deterministic key first. draft_id = f(dia, item, epoch) — recomputable by any node on any reboot. There is never a "the key was minted at send time and lost in the cut" window; the intent carries it too: (dia, intent, item, draft_id).
  • Write-ahead intent. Append the intent to the sync-log and fsync. Only then send (using that draft_id). Then append (dia, done, item, draft_id, sink-ref) and fsync. The act waits on local fsync only — never on replication acks (that would rebuild a quorum through the back door).
  • Power loss = time paused; resume = time unpaused. On boot the resume pass (running before the enact loop accepts new work, same single thread) scans for intent with no done and reconciles against the sink by the deterministic draft_id: after a settle-delay (≥ the original request's timeout budget, so a request the dead process launched has resolved), ask the sink "did this land?" → if yes, write done (no re-send); if no, send, then done. Resume is itself crash-safe: same key, same query, so a cut mid-resume just repeats, converging.
  • Honest ceiling — two-generals is relocated, not escaped. Exactly-once delivery in one round is impossible; exactly-once effect is achievable, and this is the standard durable-execution result — but it rests entirely on the sink's guarantee. The requirement is consistently queryable OR idempotent on our key (not merely "a query exists": Zendesk Search is eventually-consistent and would miss in the mid-send window — U5 must verify a consistent read path, e.g. a direct external_id/draft_id lookup, or an idempotency key the vendor enforces). A sink that is neither leaves a residual duplicate window; that lane is declared at-least-once-with-reconcile, not effectively-once. We prove the property per lane, we don't claim it generically.

Out of scope: a general/SQL DB; mutable/LWW replicated records; log compaction (v2); Byzantine tolerance beyond seal-verify; live roster reshuffling (pinned, epoch-bumped by operator).

6. First Move

Two primes, one fact. Build the minimal sync-log (append + fsync, per-origin seq, string-carrying) and its boot replay pass (sync-log → ids_insert); hook a replicated-class commit to append + broadcast the envelope; apply-on-receive (verify → ids_insert(strings)). Prove: a replicated write on HK is queryable on Vegas within a round-trip — and after restart the boot replay restores it, not loses it.

Into the plan: (2) anti-entropy from the sync-log; (3) HRW ownership + the roster-record fence so each item has one verified writer; (4) write-ahead-intent (deterministic draft_id) + resume pass, resume running before the enact loop on the same thread. Proof of Law 5 is a real power cut, not kill -9 (kill -9 leaves the kernel to flush the page cache, so it passes even with fsync unwired) — the ~t plan cuts a VM (or uses dm-flakey) between intent and done and watches reboot finish the act exactly once. (5) port the Register on + delete the vendor already-handled search.

Named Unknowns

  • U1 resolved — nothing fsyncs today; fsync is in the synclog build, not an unknown.
  • U2 mostly resolved — roster is a signed replicated record; epoch change is drain-then-bump (operator ceremony); HRW limits remap to the departed node's items; detect-if-not-mine alarms skew. Remaining: the drain-then-bump runbook detail + how long "owner down = holds" is allowed before the ceremony fires.
  • U3 — which key seals a record for cross-node authorship trust.
  • U4 — log growth/compaction of a never-truncated grow-only sync-log (v2, before real volume).
  • U5 — verify the consistency of the sink's read path per lane, not just its existence: Zendesk Search is eventually-consistent (would miss in the mid-send window); a direct external_id/draft_id lookup is the consistent path to confirm. A sink with neither a consistent read nor a server-enforced idempotency key leaves a residual window — that lane is declared at-least-once-with-reconcile.
  • U6 — dedup identity is fnv1a-64: accidental collision merges distinct facts. Note + accept v1.

What It Obsoletes

  • The vendor "already-handled" search, the C# SentDrafts dict, the Zendesk-tag idea — all routed around a synced store that will now exist.
  • Majority grants / any quorum consensus — deterministic ownership means there's no race to vote on.
  • "At-most-once + a human re-arms it" — replaced by automatic resume-to-completion.
  • It delivers the paradigm's Continuous-Sync clause and Offline-Autonomy clause at once: forward-only, self-healing through a power cut, at Tier-0.
