The DO/Store CC Challenge — three off-the-shelf paths, and why they all end in software

Report for Mendo NPS · D5 "CC the District Operator / Store on every response" · fact-checked + paired (Opus + Fable), every claim sourced · 2026-07-23

The thesis, up front: You can spend a week configuring this entirely inside Zendesk. At the end of that week you will still have written software — a webhook, a script, or a rented app that is itself software. Zendesk cannot do this with configuration alone, and the reason is structural, not a settings oversight. This report proves it, shows where the code hides in each path, and documents the one shelf-bought app that tried — and died.

The task, stated precisely

Every reply to an NPS detractor must automatically CC two parties: the District Operator who owns that store, and the store inbox. The guest wrote about store "12-SM" (Santa Monica); the response must reach whoever runs Santa Monica's district — automatically, on every response.

Why Zendesk can't do it natively — two walls, and they compound

Wall 1 — the dataZendesk knows its stores (a 37-option dropdown) and its DOs (17 agent groups). It does not hold the link between them. "Which DO owns Santa Monica" is operational knowledge that lives in Mendo's ops systems, not in Zendesk. Verified live: no ticket field, no group membership, no object connects a store to its DO.
Wall 2 — the actionThere is no "Add CC" trigger action in Zendesk. It does not exist. The only membership action is "Add follower," which takes a hand-picked static agent — not an end-user, not a field value. Adding an end-user as a CC by rule has been an open, unfulfilled community request for years. So there is no native way to CC anyone by rule, let alone dynamically.
The smoking gun. Zendesk's most advanced relational feature — Custom Objects with lookup relationships — can model store→DO perfectly. But lookup fields work only in conditions and notification actions, never to set ticket membership. So even with a flawless Store object pointing at the right manager, a trigger can email them a side notification (they're not on the guest's thread; their replies fork) but cannot add them as a CC. The relational model exists; the ability to act on it does not. That gap is exactly where every path below inserts software.

The one API fact that makes any solution possible

The blocker is a trigger limit, not an API limit. Per Zendesk's own developer docs, PUT /api/v2/tickets/{id} accepts email_ccs: [{ user_email, action:"put" }] by email address, and — verbatim — "if an email address is specified and the user doesn't exist in the account, a new user is created." Set once at ticket-create and every later public reply fans out automatically. But something must make that call. That something is the software.

Three documented silent-failure modes the blogs gloss over — each one bites only in production:

48-CC capMore than 48 email CCs and the overflow is silently truncated.
Internal-note conflictAn email_ccs change is silently ignored if the same API update also carries an internal note.
Setting gateThe whole field is ignored unless "CCs and followers" is enabled in Admin settings. (Verify this first — one click.)

Path A — Native Zendesk + Webhook (the Jason Riddell pattern)

The reference implementation, verified from source: Jason Riddell, "Zendesk Automation: Adding CC and Followers — The Scalable Way":

  • Two organization custom fields hold the addresses — auto_cc (end-user emails) and auto_follow (agent emails), each a regex-validated comma list.
  • One generic trigger per field fires on ticket-create when the field has a value — not one trigger per store.
  • A webhook does PUT /api/v2/tickets/{{ticket.id}}.json, using Liquid to split the comma list and iterate into email_ccs / followers.

His own gotchas: Zendesk silently strips non-agent emails from auto_follow (followers must be agents — the store inbox can only ride email_ccs); no spaces or trailing commas; sandbox-test first. Where it breaks for us: his key is the organization; ours is the store, which lives in the ticket body — so we add a parse and a store map, i.e. more code. His method needs no new vendor, but the webhook payload is unambiguously a small program written in Liquid, hosted in a trigger.

Path B — Custom Objects + Webhook

The cleanest data model: a Store custom object with a lookup field to the DO user, and a Store lookup on the ticket. A native trigger can then email the DO the lookup points at — genuinely no-code, but that's a side notification: the DO isn't on the guest's thread and their replies fork off. To actually CC them onto the response, a webhook must dereference the lookup and PUT email_ccs. The relational feature carries the map beautifully; it still cannot act on it. Same software, nicer datastore.

Path C — iPaaS Glue (Zapier / Make + spreadsheet)

The most honest about where the map belongs — a spreadsheet the ops team owns. New Zendesk ticket → parse the store → look it up in a Sheet/Airtable → PUT email_ccs. A franchise coordinator can maintain the table. But Zapier's native Zendesk actions don't expose email_ccs, so you drop to a raw "API Request" step "expected to read and utilize the API documentation", usually with a Formatter or Code step to assemble the JSON. The Zap is a program — a lookup, a transform, and a hand-written HTTP body — running on rented, unversioned infrastructure, billed per task.

The shelf is empty — the one app that did this is dead

You cannot simply buy your way out. The one purpose-built marketplace app for CC-from-a-field, Carbon Copier, was removed from the marketplace because Zendesk deprecated the HTTP targets it was built on. The "no-code app" was a rented webhook, and it died of webhook. The surviving vendors don't fill the gap: SweetHawk (~$12–15/agent/mo suite) has no dedicated CC app — their own help article on adding CCs instructs you to build a Zendesk webhook + trigger, i.e. the Riddell pattern. The shelf-bought option isn't just costlier; the one that existed was killed by the exact platform-deprecation risk that makes every rented webhook fragile.

The verdict on the thesis

TRUE — and here is the deepest reason. It is the compounding of two walls. Proximate cause: Zendesk's trigger engine is a condition→static-action rule table with no indirection — actions take literals, not variables; there isn't even an Add-CC action. The instant an action's argument must come from data, you exit to the API, and an API call with a templated payload is software. Deep cause: store→DO is relational routing data Zendesk is not the system of record for — and even once you cache it inside Zendesk, the rule engine cannot consume it to change who's on a ticket. Every path is the same move: put the map in a datastore, write a small program that joins ticket → map → email_ccs. The only real choices are which datastore, and whose runtime the program hides in.

What Argus does differently — and the honest part

Argus is a fourth flavor of the same outcome. It ends in the identical primitive — PUT /tickets/{id} with email_ccs — because that is the only door Zendesk leaves open. It does not escape the thesis; it is the thesis, accepted rather than denied. The defensible differences:

The map is versioned, owned dataNpsResolver holds it as git-diffable, auditable, fail-closed code — unresolved store → null, never a guess. Not an org-field cell, an object record, or a spreadsheet row that fails quietly.
The logic is testable, replayable codeExplicit and unit-tested — not a Liquid string inside a trigger UI or a Zap you can't diff.
$0/mo, no rent, no deprecation cliffNo per-task Zapier bill, no per-agent app. When Zendesk changes an API, you edit a file — you don't wait on a vendor, and you don't get Carbon-Copier'd.

The honest pitch to Brian is not "we avoid writing software while others write it." It's: everyone writes this software. The other three hide it where you can't read, test, or own it — and the one that was sold pre-built is already dead. We write it where you can see it, test it, and run it for $0. That framing survives scrutiny; "ours isn't software" would not.

The part no tool solves — and the real next step

Every path assumes the store→DO table exists. It doesn't yet — not in Zendesk, not anywhere readable. Zendesk, SweetHawk, Zapier, our bridge: all four can only carry the map; none can author it. It is Mendo's operational knowledge (37 stores → 17 DOs). The blocker was never technical. It is a data-sourcing question for Mendo's ops team.
