Three bands, one safety floor

Promoters and passives get a written reply. Detractors keep the deterministic one. The illness check stays above all three.

On "minor": the scores and the dollar amounts are the minor half. Asking the models to write words a guest will read reverses a demand the runbook states outright, and the runtime cannot do it without new compiled code — that half is a substrate change, not a card tweak.

Paired — driver writes, navigator reviews with authority to block. Design only.

~i first — what exists today

Nothing bands by score. alert.nps is captured and carried into the escalation note, but no unit and no line of runtime compares it to anything. The plan is fourteen units in a straight line.

So every alert takes the detractor path regardless of score — a 9/10 would receive the "We're Sorry" apology today. D1 says "Every NPS-detractor alert," which assumed the upstream only ever sent detractors. Brendan's form collects the full 0–10, so that assumption has already expired.

The one structural rule this design turns on

The band split happens after the illness check, never before.

A guest can score 10 and still write "the food was great but I was sick that night." If the band split came first, that guest would get a cheerful thank-you and a coupon, and the illness would never be seen.

scan → gate → understand → ILLNESS CHECK → escalate?  ——→ human, stop
                                          |
                                          +-- safe → BAND SPLIT → 9-10 / 7-8 / 0-6

The illness floor is unconditional and score-blind. Everything else is a branch beneath it.

Two demands say no to this. They have to be amended, not ignored.

DemandSays todayBands 7–10
D10"No model ever writes a word a guest will read."require exactly that
D9"Same feedback in, same reply out, always."are non-deterministic by design

The honest resolution is to scope them, not delete them. Both were written when every reply went to a detractor. Re-scope both to the detractor path, where the stakes that motivated them actually live — a wrong word to an angry guest, or to someone who may be ill, is a liability; a wrong word in a thank-you is a bad sentence.

D1   Every NPS alert is read and understood before anyone answers anything.
D9   A non-illness DETRACTOR (0-6) gets the deterministic "We're Sorry" recovery...
D10  On the detractor path, no model ever writes a word a guest will read.

D12 and D15 survive unchanged provided the generative bands reuse the existing send unit and its idempotency key — then never-double-send and Zendesk-only-channel are inherited rather than re-argued. Say so explicitly in the card.

Do not silently leave D10 as written and branch around it. That is the drift biRT exists to catch, and it would make the card lie about itself.

What the generative bands need that the deterministic one never did

Letting a model write to a guest is a different risk surface. Three things have to be stated as demands, not left to a prompt:

NeedWhy
What it must never sayNo apology it cannot honour, no promise of refund, comp or contact, no admission of fault, no discussion of illness or safety — that topic belongs only to the escalation path.
The code is still the runbook'sThe model writes prose around a code the vault claimed. It never invents, quotes or alters a code. D11's atomic claim is untouched.
A floor if the models failAny error, timeout or refusal falls back to a fixed thank-you or fixed ask — never silence, never a half-written reply. Symmetrical with D5's "doubt escalates."

The coupon becomes a decision, not a constant

Less new work than it looks — someone already pre-plumbed this. The vault already stores mixed $10 and $20 denominations with an amount column, and the claim's declared input already carries the NPS score, which the plan already passes in. What is missing is small: the C claim currently reads only the ticket and takes the first unspent code, denomination-blind. Making it band-aware is a local edit, not a new store.

The question that remains is a policy one: what happens when the $20 shelf is empty but the $10 shelf is not?

D11 already has the right instinct — "if the vault is empty, hold and ask to refill, never invent a code." Extend it per denomination and the answer is principled: hold that band, keep serving the others. Do not substitute a different amount silently.

One card or two?

An earlier design argued that a card whose demands let a model write to guests is a different class of card, not a flag on this one. That still holds — but it argues for one card with three bands, not for splitting.

Everything above the split is shared and safety-critical: the same intake, the same dedup gate, the same illness panel. Duplicating that into a second card duplicates the safety floor, and two copies of a safety floor drift. The class distinction belongs on the reply, which is exactly where the band split puts it.

And structurally, one card is forced, not merely preferred. The sweep dispatches to a single named card, and the score is not known until the alert has already been read — so a two-card split would need band-aware dispatch before the band exists, or a third routing card. Two cards would also race each other on the same ticket's dedup claim.

Consequence for the console: the class badge stops being one value per card and becomes per band — this card is deterministic for detractors and generative for the rest, and the screen must say so rather than picking one label.

A new C micro-op is required. This is answered, not open.

Generated prose cannot reuse what exists, for three independent reasons:

  • The illness panel's declared output is verdicts, detected:bool, conf:float, reason, cost:float — there is no prose field to return prose in.
  • Its C arm hardcodes the verdict parse and the unanimous-safe fold, reducing everything to a boolean. Any prose the panel produced would be discarded on the way out.
  • The deterministic renderer is pure C — no model, no cost. It cannot author.

And dispatch is keyed on hardcoded skill·slot pairs, with nous.sm generated from the C headers and rev-locked to the binary; biRT refuses any bind not in the .sm. So this is a new micro-op, a new .sm row, a recompile onto the primes, and probably a new bridge lane — a substrate change. The estimate must say so rather than pricing a card edit.

Unknowns

  • Whether a 9–10 or 7–8 submission even produces an alert today, or whether the upstream only emits detractors. If only detractors arrive, this design is correct and completely inert until the form starts sending the other bands.
  • Whether the new micro-op can be served by the existing bridge, or needs a new lane there too — the bridge source is not in these repos.
  • Whether the live claim honours denominations. The local vault does; the claim that actually runs is bridge-side, in source not held in these repos.
  • Who approves generated copy before it ships, and whether a sample must be reviewed per band.

When to revisit

The moment a band's coupon economics change — the passive being worth more than the promoter is a bet, and bets get revisited. Also when the first generated reply is read by a human who did not write the prompt; that is the real test of the never-say list. And if the vault ever cannot serve a denomination, because the hold-versus-substitute rule will be exercised for real.
