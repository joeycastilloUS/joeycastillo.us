clarify — the intent-driven control stick

A reusable skill: turn a person's free text into bounded, intent-sourced choices. Ask, don't guess.
~d · paired: Opus + Fable · the answer to "how do I hand my manager a control stick with scoped capabilities"
The idea in one line. The control stick is the intent — the tunable surface of a .pi, filtered to an allowlist. clarify is how a person moves that stick: every question and every option it offers is derived from the intent, so the stick physically cannot push anywhere you haven't allowed. The manager feels like they're chatting freely; they're moving a stick whose range of motion is your intent. Hand it a different .pi + allowlist and the controls re-shape themselves — one skill, every operator's stick.

What it is

The ask-don't-guess front door. Given the allowlist manifest + the person's message, clarify emits exactly one of: a bounded proposal (a specific, in-bounds change) or a bounded question (whose options come entirely from the manifest). It never guesses a material change, and never offers an out-of-scope option. It is read-only — it proposes and asks; deterministic code still does the acting (the interpret/act split holds).

The rule — ask vs propose

Propose iff exactly one op matches, complete and in-bounds. Otherwise ask ONE question that closes the single blocking gap. The proposal is the confirmation (the approve gate lives downstream), so clarify never nags "are you sure?" when only one in-bounds reading exists. Questions exist only when the manifest can't deterministically finish the {op, value}.

One question per turn, aimed at the single blocking gap.

Options carry payloads

Every option embeds its finished {op, value}. Picking an option is a deterministic close — no second model call, nothing to re-interpret, nothing to drift. Only free-entry answers (a typed number, an email, wording) loop back, and those hit the deterministic validator, not the model. Biggest correctness and cost win.

Per-type option rules

  • enum → options = the manifest values verbatim (labels humanized; payload byte-exact). Never add, never omit.
  • number → 3 presets from the bounds (min · current/mid · max) + free entry with the range in the prompt ("or any amount 5–25"). Out-of-bounds input → the nearest bound offered explicitly.
  • email-list → free entry, format-validated, max_items enforced; the question shows the current list + slots left ("2 of 5 used").
  • text (wording) → not enumerable: ask for the wording, show maxlen + a char count, then the proposal echoes the exact text for approval. Opaque value, never interpreted.

Why it's .pi-driven — and safe

  • Manifest at runtime. The allowlist is an input, not baked in. Add set-coupon-expiry to the manifest and clarify asks about expiry on the next turn — zero code change. Point it at any DIA's manifest and the dialogue adapts. This is what makes it a genuine, reusable skill.
  • Least-privilege input. clarify receives the manifest + only the current values of manifest-listed fields — never the full .pi. It cannot offer what it cannot see.
  • Free text is a value, never a command. Wording rides as an opaque, length-capped string — never parsed, never merged into the prompt as instruction, never allowed to name an op. That's the anti-smuggling seam.
  • Enforced twice. The skill derives options from the manifest; the deterministic validator proves them again before apply. A jailbroken skill degrades UX, never safety.
The one invariant. Everything clarify shows or proposes is constructible from the manifest — op in the allowlist, value inside that op's declared type and bounds; free text rides as an opaque, length-capped value that is never interpreted. Not in the manifest → cannot be offered, mentioned, or proposed.

Allow / Ignore — in the grammar

Both live in the .pi grammar — statements indented under their demand line, parsed into the clause. Not a runtime store, not a second surface: declared intent — versioned, sealed, biRT-verified. And they are two different things:

D2: watch Zendesk for new NPS-detractor alerts.
    ignore: email-from = qa-test@mendocinofarms.com   until=2026-08-15
    ignore: store = 05                                until=2026-08-01

D9: offer a "We're Sorry" recovery coupon.
    allow:  amount = 10, 20, 30, 50 $
  • allow: — the permitted value set a demand may use. Permanent intent, no expiry. Fail-closed: a value outside the set is drift → refuse and log, never silently clamp.
  • ignore: — a skip condition at intake (email-from, store, ticket). Mandatory until= — applier defaults +30 days, caps at 90. Expired entries are inert; the engine reads them as absent. Ignores die on their own.
This closes the loop. The allow: statement is where clarify's bounded options come from. The intent declares its own permitted values; the skill reads them and offers exactly those. The .pi doesn't just drive what the DIA does — it drives what the manager can be asked.

Where the check sits — and why illness can't be ignored

The ignore check runs in the intake gate (beside the handled-tag dedup), before any model cost. A match writes ignored.by=D2.ignore.email-from to the ledger and the run exits. There is no ignore hook downstream of the illness check — so an intake ignore filters non-guests (spam, a QA test sender); it can never suppress a detected illness. The escalate unit's existing fail-closed read (empty verdict = escalate) is untouched.

The safety floor — enforced three times, zero prompts.
1 · Manifest: the illness/escalate demands expose no ignore keys — clarify can't propose what isn't listed, and the applier rejects unknown (demand, key) pairs.
2 · biRT: dia_verify gains check 6 — every allow/ignore statement's (D#, key) must exist in the manifest. A hand-edited .pi with ignore: on the escalate demand refuses to run — same fail-closed class as the word-seal.
3 · Engine ordering: ignores are only evaluated by intake-gate units. There is no hook downstream to attach one to.

Four ops, same shape

  • ignore-add {demand, key, value, until}
  • ignore-remove {demand, key, value}
  • allow-set {demand, key, values}
  • list-overrides {} — read-only: current statements with expiry dates and hit counts.

All ride the same propose→approve→apply chain. The manifest enumerates exactly which (demand, key) pairs exist, with type, bounds, and a max-entries cap.

The worst failure, and the guard

An over-broad ignore silently swallowing real detractors past its reason's lifetime — a substring matching every gmail sender, or store 05's "renovation" ignore living forever. Two-part guard, both applier mechanism: exact-match typed values only (manifest types: email, store-enum, ticket-id — no wildcards, no substrings, entry-count cap per key) plus mandatory expiry. Visibility completes it: every ignored run writes to the ledger, and list-overrides shows expiry dates and hit counts.

Note: per-ticket ignore is largely redundant — the handled-tag dedup already lets a manager kill one ticket by tagging it in Zendesk. The value/pattern statements (email-from, store, amount) are the real feature. Audit needs nothing new: who/what/when/why is the approved proposal in the applier's git commit; runtime hits are ledger + telemetry.

Where it lives + the contract

src/sdk/nous/comms/skill/clarify/ — skill.json (contract) + clarify.md (the read-only claude -p prompt with few-shot examples for all five decision states). It is the front half of the interpret step; the C99 applier/validator is untouched.

IN  { "manifest": "<ops-manifest.json>",
      "current":  { "coupon_amount": 10, "coupon_audience": "detractors", ... },   // manifest fields ONLY
      "message":  "<person's free text>",
      "history":  [ ...recent turns... ] }

OUT (exactly one)
  { "kind":"proposal", "op":"set-coupon-amount", "value":25,
    "echo":"Set coupon amount to $25 (current: $10)." }

  { "kind":"question", "reason":"disambiguate|missing-param|out-of-bounds|out-of-scope",
    "text":"Coupon max is $25. Which amount?",
    "options":[ { "label":"$25 (max)", "op":"set-coupon-amount", "value":25 }, ... ],
    "free_entry":{ "type":"number", "min":5, "max":25 } }

Demo-minimum — four turns

  1. "bump the coupon to 20" → straight proposal, no nag. (the premise-setter — it understands)
  2. "make it more generous" → one question: $15 / $20 / $25 (max) / other 5–25 → pick → proposal.
  3. "give them $50" → "Max is $25 — use $25, or another (5–25)?" (the safety beat)
  4. "turn off the survey" → "That's not tunable here. I can adjust: coupon amount, audience, empathy wording, escalation recipients." (the allowlist beat)
  5. "ignore store 5 until Friday" → proposal adds the ignore: line under the recovery demand. Then "ignore the illness alerts" → refused — guarded demand, can't be overridden. (the safety-floor money shot)

Most likely to look dumb on stage: asking on turn 1. A fully-specified command that draws a question kills "it understands" in ten seconds. Mitigation is in the rule (propose-iff-complete; the proposal is the confirmation) and in clarify.md's few-shot — the fully-specified case gets the most examples.
