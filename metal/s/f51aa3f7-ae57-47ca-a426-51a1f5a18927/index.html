Review — Plan A (Argus arm)

Paired review · Opus + Fable ran independent passes, then reconciled · subject: Plan A — Argus arm (Mendo NPS A/B) · 2026-07-23

Verdict

PASS-WITH-NOTES — peer-quality work. Sound as a Plan A execution spec. It overclaims only where it reaches beyond what is true today: the A/B claim and the embedded B config. Four items are blocking before this doc is used to justify the A/B or to arm; the rest is tightening.

What's solid — verified independently

Canon is correctIntake = shared hello@ with the body-content discriminator, no dedicated nps@; brand guestrelationstest #50598728766228; code.source = shared /zendesk/promo-claim for both arms; seals bd557742/aad1c453 and provenance r847/cba487c cited. It tracks the corrected DIA.
Proofs match reality741 → MENDO-D8TP636F, idempotent re-run, 739 (MENDO-CNK3MPJ2) ≠ 741, guest parsed from body — all independently re-verified live from this side. Demonstrated, not asserted.
Safety ordering is rightIllness exits at unit 5, before claim_code at unit 8 — structurally, no code can be minted for an illness case. That ordering is the correct shape.
Blast radius disclosedSandbox not hermetic; armed sends reach a real Mendo inbox (737), a real gmail (739), a bouncing address (741), and real staff on the illness path — with a warn-recipients action. Best section in either arm's docs.
Gaps declaredD5 absent in A, placeholders, $10 hardcode, untag churn, retired-card hazard, prime-vs-Windows. Listed, not buried.

Blocking — fix before claiming the A/B or arming

1 · It is not a fair A/B yet BLOCKING

The doc says the AI layer is "the only variable" because both arms share the code service. That is overstated today. A runs in the shared sandbox against RJ's 8 real samples (#730–741); B is a separate Zendesk sandbox subdomain with zero tickets and no bridge wiring (verified three ways). Corpus differs, environment differs, D5 coverage differs.

Change: add an explicit "A/B validity — preconditions" section: (a) the same 8 tickets replayed byte-identically into B's subdomain, (b) B wired to the same /zendesk/promo-claim, (c) both arms scored on the same D1–D6 rubric over the same corpus. Until all three, say plainly that A is proving its column unilaterally — an A/B does not yet exist.

2 · The embedded card is arm B's, not arm A's BLOCKING

Plan A embeds mendo-zendesk-ai-config.pi as "the Pure-Intent card this plan enacts" — but that card's own header says it configures the Zendesk in-box AI agent (arm B), and it pins env: sandbox mendocinofarms1781637851, brand guestrelationstest (the comment even reads "System A brand"). Meanwhile B is confirmed to live on a separate subdomain. Both arms' docs inherit this knot; neither resolves it.

Change — fix at the canon layer, not in prose: split the card into (i) a shared demand/words card (D1–D6 + the sealed words — common canon both arms serve) and (ii) per-arm config cards. B's config points at B's real subdomain; Plan A should embed the card it actually enacts (mendo-nps-detractor-triage.pi), not B's config. This gates every B step too.

3 · scope.received may be a dead address — verify at source BLOCKING

Fable's probe of the published doc read scope.received as hello@mendoncinofarms.zendesk.com — misspelled ("mendoncinofarms") and missing the sandbox numeric suffix. The committed .pi in argus reads hello@guestrelationstest.zendesk.com. Those do not match, and mail to the former lands nowhere.

Change: eyeball the published doc against the committed card and correct whichever drifted. Flagged as verify-then-fix: one pass read it as literal text, the other pass's fetch redacts addresses and could not confirm.

4 · Name where the arm gate is enforced — and enforce it server-side BLOCKING

PIRUN_ARM_SEND reads like an env var but is described as compile-time (build-enact.sh --arm), and the doc never says where the disarm is actually enforced (C send unit? bridge?). The doc's own "retired-card / harness hazard" — a stale armed build pointed at the wrong card — is precisely the path that turns that ambiguity into a real send.

Change: (a) state the enforcement point explicitly; (b) enforce server-side too — the bridge's /zendesk/recovery-send should refuse unless armed, so no client-side mistake can send; (c) make the retired-card check a hard precondition inside build-enact.sh --arm, not a listed risk. Also: one flag currently arms guest-send and illness-escalation POST together — consider staged arming.

High

5 · "The guest is the requester" is aspirational, not the ticket shape

DIA D1 says the guest is the requester. On the real samples the requester is the NPS system (mendonps@); the guest address lives in the body only (confirmed on #741). A's body-parsing is exactly why A reaches the guest where a native reply would not.

Change: say it outright — it is A's strongest proof point and it is currently implied. Then flow it upward: D1's wording should either match the real ticket shape or be marked as the desired end-state.

6 · Unit 4: pin the model count, and name the Tier-0 exit

"2-model Gemini panel … the ONE model call" is self-contradictory — a 2-model panel is two invocations. For the one unforgivable send the safety claim must be exact. Separately, the mission is LLM/GPU-free Tier-0 at $0; the cost column honestly marks unit 4 "model" but never reconciles the conflict.

Change: call it "the single model stage (two Gemini calls, unanimous-safe fold, fail-closed)", state what happens on model error/timeout (fail-closed to human), and add one line naming the exit path: the sealed illness lexicon (bd557742) + when-in-doubt-escalate is deterministically enforceable in C99 as the primary gate, panel demoted to belt-and-suspenders, then retired. The fail-closed shape today is correct — keep it, name the roadmap.

Notes

"Disarmed" ≠ side-effect-freeDisarmed runs still POST to the live promo-claim endpoint (banking real codes — acceptable, idempotent per ticket) and write argus_nps_handled tags on tickets in the shared sandbox where RJ works. No mail, but shared state mutates. One sentence in blast radius closes it. Also resolve unit 2's ambiguous "writes tag disarmed" — the test plan's untag step implies tags are written while disarmed; say so plainly.
D5 has teeth"Lives only in B" is honest but draw the two consequences: (a) an armed A send without DO/Store CC violates D5 in production — CC must land in A's compose/send before arming; (b) in A/B scoring, D5 is an A-fail until built. It's blocked on resolving DO/Store to real Zendesk user ids — the same dependency Plan B carries, so it's a shared build-todo, not an arm difference.
Automate the untagMake sweep-untag a harness pre-step so a forgotten untag can't silently produce an all-exit run that looks green. That failure mode is quiet and convincing.
$10 hardcodeRemediation as written is fine. Recommend the amount move into the code service so both arms take amount + code from one source — same argument that made the code shared.

Likely an artifact of how the first fetch summarized the page, or a fixed earlier draft. Needs a ten-second eyeball at the source; we are not asserting it either way.
