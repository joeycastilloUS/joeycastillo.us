~d — Argus Ops

Self-administration as a governed feature in the GCP module · paired design (Opus driver + Fable5 navigator, two blind passes, reconciled) · project: argus · r914

One line: take the Argus-admin acts the AI performed by hand this session — set the crew, redeploy a bridge, read service/deploy state — and make them a first-class feature in the GCP module, behind a gate stronger than the normal console session (the Overlord key = Warrant Gate), fully audited. Building this the wrong way would reopen the exact doors this session's lockdown just closed; the gate is therefore the design, not a footnote.
Operator decisions (locked this turn): scope = full self-admin now (view + crew-edit + redeploy + service-mgmt) · gate = Overlord key / door D · actor = operator buttons AND an AI-callable path. Built in verified slices; the AI path ships after the human path proves out.

1. Need

This session the AI administered Argus out-of-band: hand-edited the crew doc (settings/argus, Firestore db argus) via gcloud, hand-fired a Cloud Build redeploy of meraki-bridge, hand-read Cloud Run env wiring and Secret Manager. It worked, but those acts have no home in the product — no gate Argus owns, no audit trail Argus keeps, no surface the operator can repeat without the AI holding his gcloud credentials. And the reason the hand-work happened was a security lockdown whose own inspection (R0–R5) proved the normal console session is too weak to carry these powers. The need: bring self-administration inside Argus — hard-gated, audited, in the GCP module — so "what the AI did by hand" becomes "what the operator (or a warranted AI) invokes, with a warrant," without reopening one closed door.

2. Raw user stories

  • As the operator, I want to see who can get in (crew, live doors, token presence) in one pane, so "who has access right now?" is a glance, not a gcloud-read of Firestore.
  • As the operator, I want to see what's deployed per bridge (live revision, image, deploy time, env/secret names), so "is the providers.json edit live?" is a glance, not gcloud run services describe.
  • As the operator, I want to edit the crew behind a harder gate than my normal session, so one phished crew login can never invite an attacker (closes R3).
  • As the operator, I want to trigger a bridge redeploy from the console with an explicit confirmation, so a config change lands without a terminal.
  • As the operator, I want a warranted AI to be able to invoke the same governed actions, so the assistant can finish a lockdown end-to-end — under the same audit + gate, never a blank credential.
  • As the operator, I want every ops action logged (actor / action / before→after / result) and secret values never shown (names + versions only), so the feature is auditable and can't become an exfiltration surface.

4. Name it true

  • Feature: Argus Ops — the hands, governed. Tab label in the GCP module: Ops.
  • Gate: the Warrant Gate (middleware RequireWarrant) — ops writes require a warranted (Overlord-key) session.
  • meraki-bridge: GET /ops/doors, POST /ops/crew (the only crew write path).
  • gcp-bridge: GET /ops/services, GET /ops/builds, POST /ops/deploy, GET /ops/secrets (metadata only).
  • Audit: Firestore ops_audit + AUDIT log lines. Fleet as data: fleet.json (service → region → cloudbuild source), mirroring providers.json's routes-are-data pattern.

5. Shape — verified slices

Phase A — read-only Ops pane (zero new write surface). Three cards beside Cost/Watch: Doors & Crew (GET /ops/doors: crew from server truth not localStorage, providers loaded, /auth/key/status, token presence); Services (GET /ops/services: revision, image, deploy time, env/secret names — values structurally absent); Builds (GET /ops/builds: last 5 Cloud Build runs). Reads gated by any valid crew session via the worker — never the daily key.
Phase B — two writes, individually warranted. Crew edit (POST /ops/crew replaces argus_crew_v1 only) — and POST /settings loses crew-write power (PreserveCrew flips from preserve to reject), which closes R3. Deploy (POST /ops/deploy {service}) — service must match a fleet.json entry; gcp-bridge submits the checked-in cloudbuild.yaml at pinned HEAD. No caller-supplied build config, ever (a deploy trigger is RCE by design; the only freedom is which fleet member). Both writes: Warrant Gate + typed confirmation + ops_audit + AUDIT line, before/after captured.
Phase C — service mgmt + secret metadata (GET /ops/secrets names/versions; env-name view). Read-only unless the operator later widens scope to env/secret rewiring (Open-Q1).
Phase D — the AI-callable path (ships last). Expose /ops/* to a warranted AI (e.g. via a doculink ~ comment or agent path). The novel/risky piece: how does a non-human present the ed25519 warrant? Needs its own warrant story (a scoped, revocable AI warrant minted by the operator, single-purpose, audited as actor=ai:<warrant-id>) — never the operator's own device key. Designed but gated behind the human path proving out.

6. The Warrant Gate — first-class

Gate optionVerdict
Any crew sessionNo — reopens R3; R0/R1 show the normal plane fails open
ARGUS_ADMIN_TOKEN header per actionEscape route only — a static bearer in browser memory is replayable/phishable
Overlord key session (door D) + per-action confirm + auditChosen (operator-confirmed)
Cloud IAP / Google re-authA fourth identity system; fights the Purcius identity direction

The gate, concretely:

  1. /ops/* never accepts yyyymmdd~go, BRIDGE_TOKEN, or an empty-token fallthrough. Dedicated middleware, fail-closed: unset config ⇒ 503, never open (kills the R2 pattern at birth for this surface).
  2. Reads: valid argus_session (any door), verified server-side, payload parsed.
  3. Writes: session idKey must begin key: — minted by the ed25519 device+warrant door with its single-use challenge burn. A Google-minted session gets 403 "warrant required," which the UI turns into the key-login prompt.
  4. R5 resolved by demotion: door D stops being a general console credential and becomes only the ops credential — its crew-bypass property is now the point (the operator's key, above the crew), confined to /ops/*. Also bind /auth/key/verify to run EmailAllowed on OVERLORD_EMAIL so a stale env can't mint an unknown identity.
  5. Per-action ceremony: typed confirmation client-side; server logs actor (email + idKey + device pubkey prefix), action, before/after, result to ops_audit + CloudLog before returning.
  6. Transport: /ops/* on the worker PROXY list, split-routed (crew→meraki-bridge, GCP ops→gcp-bridge), cookie stays first-party; gcp-bridge gets argus-session-secret verify-only.
  7. Language boundary: C# only where a foreign Google API is jacketed (Cloud Build/Run/Secret Manager REST, Firestore); gate crypto stays in the pure-C sidecar; frontend vanilla JS.

7. First move

GET /ops/doors + the Doors & Crew card. One endpoint in meraki-bridge (the repo we hold), one worker PROXY entry, one card in the GCP module. It forces the load-bearing plumbing into existence — the dedicated ops middleware that rejects the daily key and parses the session payload (:90's discarded out _ becomes real) — while shipping zero write surface. Rule-10 verify: from a non-dev machine, the endpoint 401s with no cookie, 401s with Authorization: Bearer <today>~go, and renders the true crew for a signed-in operator.

Choices / Escape routes / Pure Metal test

Choices: endpoint homes split by ownership (crew ops in meraki-bridge, GCP ops in gcp-bridge) vs. a new ops-bridge service (rejected: third repo/IAM surface, no new isolation). Gate: warrant vs. admin-token vs. IAM (table above). Cookie transport: worker proxy (chosen) vs. CORS-credentialed cross-origin (rejected: widens cookie exposure).

Escape routes: if the identity sidecar isn't deployable in time → interim gate = ARGUS_ADMIN_TOKEN pasted per action, held in a JS closure (never localStorage), same audit, labeled interim. If gcp-bridge reconcile is heavy → Phase A ships Doors & Crew only; Services/Builds render "reconcile pending." If door D is ever killed → gate falls back to ARGUS_ADMIN_TOKEN (weaker, still audited, still never the daily key).

Pure Metal test: every gate decision re-read server-side (no client flag is authority); no secret value crosses to the browser, structurally; fleet + routes are data; deploy runs only checked-in config; deterministic audit (actor, warrant, timestamp, before/after); C# confined to foreign-API jackets.

Open questions for the operator

  1. Ceiling of "do what you want": this design = view state + crew-edit + redeploy + secret/env metadata. Not included: arbitrary gcloud, secret values, IAM edits, env-var rewiring. Widen to env/secret rewiring too? (Recommend: no, at least not in Phase A–C.)
  2. Door D: the earlier lockdown answer was "keep D as break-glass." This design keeps it and repurposes it as the ops gate (ops-only, no longer a general console door). Confirm that's the intended role.
  3. Sequencing vs. the data-plane key (R0): ops reads refuse the daily key regardless, but shipping ops while the data plane still honors yyyymmdd~go is an inconsistent house. Recommend the R0 fix lands with or before Phase B writes.
  4. Deploy fleet scope: meraki-bridge only first, or all five services day one?
  5. The IAM grant + gcp-bridge changes are real privilege expansion on a live service account — explicit go needed before Phase B/C touch gcp-bridge.
