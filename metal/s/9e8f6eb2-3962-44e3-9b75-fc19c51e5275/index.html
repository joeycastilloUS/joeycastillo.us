~i — Network drift detection: the ground

Argus · acmedevUS/argus · v0 · r1014 · 2026-08-01
Operator ask: "detect drift when any network changes."
Paired per Kernel Rule 1 — Opus driver + Fable5 navigator, concurrent independent passes, reconciled in §9. Navigator corrected the driver's central lean; the correction is recorded in full.
Bottom line. Roughly 80% of what drift detection needs already exists in this repo — and none of it is wired together. Meraki emits a 365-day change ledger that a shipped bridge route already proxies and nothing consumes. The scheduler → deterministic-classify → Firestore → open-endpoint → console-tab rail is built and running in production as Watch. Firestore is already bound inside meraki-bridge. The audit already does a sliver of template-drift. What is genuinely missing is small: a stored prior snapshot, a diff, an Accept gesture, and a tab.

But the change feed cannot be the whole answer — the original 2026-06-10 inspect recorded that Meraki logs only ~75-80% of config changes, and presence drift (a device appearing, a MAC moving) never appears in it at all. The design must consume the feed and snapshot.

1. What the Network tab actually pulls

One route: /meraki/portmap (bridge/Program.cs:546), called by fetchPorts() at web/app/index.html:1264. Shape:

{ network, name,
  boundTemplate: { id, name } | null,
  devices:  [ { serial, name, model, mac } ],
  switches: [ { serial, name, ports: [ {
      port, name, vlan, allowedVlans, type, status,
      poeEnabled, poeDraw,
      clients: [ { ip, mac, name, lastSeen, status } ]
  } ] } ] }

Backing records in bridge/Meraki.cs:

SwitchPort(PortId, Name, Enabled, Vlan, Type, AllowedVlans, PoeEnabled)      :12
SwitchPortStatus(PortId, Status, ClientCount, PowerUsageInWh)                :13
NetworkInfo(Id, Name, ConfigTemplateId, IsBound)                             :14
ConfigTemplate(Id, Name)                                                     :15
WirelessSsid(Number, Name, Enabled)                                          :16

Clients come from networks/{id}/clients?timespan=86400 — a 24-hour window (Meraki.cs:177). That window is itself a design constraint: "this MAC disappeared" only means anything within 24h.

portmap drops Enabled. SwitchPort.Enabled is parsed (Meraki.cs:204) but is not projected into the port row (Program.cs:577). A port being administratively disabled — a classic accidental or malicious change — is invisible in the payload the Network tab receives. Navigator's catch: /meraki/verify (:528) does return the raw port records including Enabled, plus device names. So the data is one route away, not one API call away. Driver had the gap; navigator found the existing escape hatch.

2. Meraki already emits a change ledger — and nothing reads it

/meraki/changes (Program.cs:429) proxies organizations/{org}/configurationChanges. Fields the route's own filter proves are present: label, page, oldValue, newValue (:451), plus Meraki's timestamp and admin. Params: timespan default 30d, clamped 1min–365d; perPage ≤ 1000; optional networkId filter (validated L_/N_); optional substring q.

/meraki/apirequests (:465) proxies organizations/{org}/apiRequests, 31-day hard cap. Its own comment calls it the "API vs dashboard-UI oracle": a matching entry means the change was made via API; no entry means someone clicked in the Meraki dashboard.

Neither route has a consumer. grep over web/app/index.html finds zero calls to /meraki/changes or /meraki/apirequests. They shipped as "unbind forensics" and are used ad hoc from the command line. The console calls /meraki/portmap and nothing else for this tab.

Limits that matter: the route is single-page and cursor-less — no pagination, no "since last seen" bookmark. DR5's "cursor" is still real work. And availabilities/changeHistory — the second half of the design's cheap gate — has no bridge route at all (zero matches across bridge/*.cs).

3. The Watch rail is the drift loop, built for a different subject

Board WATCH1, complete 2026-07-07:

Cloud Scheduler (*/5)
  -> POST gcp-bridge /watch/run  (bearer-gated)
       -> read watch.pi  (instruction as data)
       -> call meraki-bridge /meraki/map + /meraki/events
       -> Watch.cs  deterministic classify  (OK / FLAPPING / OFFLINE, no model)
       -> Firestore  watch_state   (changedAt moves only on a flip)
  -> GET /watch/state  (open)
       -> console Watch tab, 45s poll, 15-min staleness banner

Stated cost: $0/cycle, no model. That is Tier-0 in production today.

Reusable: the entire operational skeleton — scheduler tick, .pi instruction-as-data, Firestore state doc with flip-only dedup, open read endpoint, console tab with a staleness cue.

Not reusable: the comparison. Watch compares live metrics against thresholds, not against a stored prior snapshot. There is no fingerprint, no baseline, no before→after. Drift needs a genuinely new diff engine — but it should be a sibling job on the same rail, not a second rail.

Constraint: gcp-bridge source is not in this repo and is not cloned on this box (C:\gcp-bridge does not exist). Everything above comes from be/builds/2026-07-07-1619-report-device-watch-llm-free.html and the console consumer at index.html:9454, not from reading Watch.cs.

4. Persistence already exists inside meraki-bridge

Named Firestore DB argus (Program.cs:54-57). Collections written today: members/{idKey} and sessions/{sid} (auth, :255, :391), and settings/argus — a single shared JSON blob with updatedAt (:685-701). The established pattern is a document of Dictionary<string,object?> via SetAsync, with a server-side re-read as the write-gate authority (:711-724) — the browser is never trusted. A baselines/{network} + drift/{id} pair drops straight into this shape. DR1's "Firestore model" is a collection, not a service.

5. The Save button is not a snapshot

saveMenu(scope) at index.html:9724, engine at :9626. Google Sheets (clipboard TSV + sheets.new), Excel (hand-rolled xlsx zip), JSON, CSV, Printable HTML, PDF. Data is scraped from the rendered DOM (tableData(), :9667) — except the audit tab, which exports the bridge's structured object (:9689). Browser download, no server round-trip, no Firestore write, no history. Pull timestamps live only in an in-memory JS slot (newSlot(), :1253) and die on reload.

No snapshot mechanism exists anywhere in Argus. Save is not a half-built drift feature — but its export engine makes DR8 (drift report export) nearly free.

6. Template-as-baseline: already started, narrower than it looks

The audit computes runOverrides for template-bound networks (Program.cs:1072) and ships four checks (:1264-1306):

CheckComparesDepth
OVR-IDSnetwork IDS/IPS mode vs templateflags only when weaker
OVR-AMPnetwork AMP vs templateflags only when disabled vs enabled
OVR-SPOOFIP spoofing mode vs templateflags only when weaker
OVR-L3L3 firewall vs templaterule COUNT only (:1302) — not content, not order

OVR-L3's own remediation string says "it may be intentional or drift." The code already uses the word. But this is appliance-security only — nothing compares switch ports, VLANs, or SSIDs to a template.

Navigator sharpened this. The driver found the OVR-* block and flagged template-drift as "partly built." The navigator read further and established OVR-L3 is a count comparison — meaning a swap of one rule for another, same count, is invisible. Without that catch the design would have over-credited existing coverage.

The distinction that matters: the audit answers "is this misconfigured against policy?" Drift answers "is this different from yesterday?" They overlap only where policy happens to equal yesterday. Both are wanted; neither subsumes the other.

8. The boards vs the design they came from

DR1–DR8 = 39 pts, 8 boards, zero items Done, zero In Progress, nothing built in seven weeks.

The board contradicts its own design's locked decision. The 2026-06-10 inspect locked six decisions. Decision 6 reads, verbatim: "Cadence — change-feed-driven / near-real-time: poll Meraki's configurationChanges + events + availabilities/changeHistory; do a full re-snapshot only when something actually changed." The design's loop puts GATE first, sweep second.

The estimate then split it into two boards and pushed the change-feed gate into Board 2 — its own sizing note says Board 2 "widens entity coverage, makes it cheap (the change-feed gate)." So DR5 sits blocked behind DR1→DR4, and the cheapness that Decision 6 made structural becomes an optimisation you reach fifth.

That was defensible in June, when the gate had to be built from scratch and value-proof-first was the right call. It is not defensible now: /meraki/changes already ships. The sequencing rationale has expired.

What else in the 2026-06-10 design has gone stale

  1. "The bridge stays a single-purpose read door" is dead. meraki-bridge now has six gated write paths (name, device-name, port-vlan, port-poe, template, remediate ×3) with a settled server-side gate. The argument for a sibling service must be re-made on different grounds (scheduling and diffing are not proxying) — the conclusion may still hold, the reason doesn't. navigator-only catch
  2. DR4/DR8 target /mendo/argus, a retired surface. The product is the console with #meraki/<tab> deep links. Drift should be a tab, like Watch.
  3. DR1's "service skeleton" largely duplicates the Watch rail, built a month after the design.
  4. DR5's bridge half already exists — only the cursor/gate logic remains.
  5. Firestore moved into the bridge itself; the design's "cadence stack in acmedev-platform-hq" framing predates that.
  6. The audit's OVR-* checks landed — a live-vs-template comparison the design didn't have.

Still load-bearing and correct: the baseline-scope split, accept-to-re-baseline, the fingerprint model, binary severity, the First-Move loop, and the nightly full-reconcile backstop.

The navigator corrected the driver's central lean. This is the most important line in the document.

The driver's pass concluded that because Meraki already emits a change log, drift should consume the feed rather than snapshot-and-diff — and framed that as the design pivot.

The navigator went back to the 2026-06-10 inspect and found its Escape Routes section already recorded that Meraki logs only ~75-80% of config changes, which is precisely why the original design mandated a nightly full-reconcile backstop. It further established that the feed has no state: it cannot answer "is the network as it should be right now," it misses a change that was made and reverted inside the window, and presence drift — a device appearing, a MAC moving — never appears in configurationChanges at all.

Verdict: consume-AND-snapshot. The feed is the cheap gate and the evidence enricher (who/when/old→new). The snapshot-diff is the ground truth. The driver's framing would have shipped a detector that silently misses a quarter of config drift and 100% of presence drift. Navigator's position stands.

10. Open questions the design must answer

  • "Any change" invites alert fatigue. Binary severity only works if baseline scope is chosen well. Client MACs on a 24h window will churn constantly. What is baselined vs history-only?
  • Where does the engine live? New argus-drift service (DR1 + one-service-per-source), a second .pi job on the Watch rail, or inside meraki-bridge (which already holds Firestore and the Meraki key)?
  • Does configurationChanges record template-bound settings under the network's id or the template's? Unanswered by the code; it determines whether the per-network filter works.
  • Rate-limit budget for a 5-minute sweep across 5 networks.
  • Is /meraki/apirequests attribution worth v1? It answers "API or someone clicking in the dashboard" — high operator value, 31-day ceiling.
  • Accept: per-item or per-field?
  • Firewall content-diff needs a route that doesn't exist — no bridge route returns raw L3 rules.
