Salesforce has no incremental-events cursor, so freshness and coverage are the same measurement here — one button, two objects. 3. What was deliberately not built

The bake half — Pull new / Rebuild / Go live — is not there, and it is not rendered as greyed-out buttons. A control that cannot act is a lie about the surface. The Rebuild card names what is missing and what to run by hand until it lands.

Nothing else was added. No new tabs beyond the two, no new endpoints, no speculative features. The gap map called for parity; this is parity as far as the existing backend reaches.

5. What we learned after shipping — and what it changed

Hours after this build landed, we read the status page of Tracer — a separate support-triage tool working the same OneDine case data from the opposite end. Reading it against our own board removed work. Nothing on this page's roadmap grew.

What we learnedWhat changed here
Clean, extractable "resolutions" are rare — roughly 5%, and noisy. Support email is conversation (announcements, evidence requests, findings), not a tidy "here's the fix" field. Their example case resolved with "a menu sync has just completed" — a real fix, and nothing a scorer extracts cleanly. SCOPE CUTAn entire resolution-extraction layer was deleted from the plan before it was built. The stager port is now retrieval only: find the similar past cases and let the reader read them.
A retrieval index needs labels, and they didn't have any. USE WHAT'S THEREWe do — the Reason field, 18 human-filled values across all 42,402 cases (§1). Seed the index from it rather than inventing a taxonomy. It also gives a scoreboard: 3,852 cases (9%) closed with no root cause established.
A silent truncation bug dropped the exact records their probe was scoring — the result still looked complete. PROMOTEDOur search has the same class of bug (stops collecting past ~2,000 matches, still returns a complete-looking result). It was last on the list. It is now first — that class has already cost somebody the data they came for.
An invisible-character bypass faked "good" resolutions on their side, caught only in review. It doesn't break a page — it makes a quality number report success it never earned. FOLDED INCharacter normalization is now part of the stager port's scope. One line in the decoder, specified before the metric exists rather than after it lies.
Tracer reads the email thread on 100% of cases (~25k characters each) — in the same Salesforce org where our integration gets a flat refusal on the same object. NOW TRACKEDThe access grant is on the board as a real item instead of a line in a document. It blocks the entire knowledge-base half: 87% of cases arrive by email, and we hold 0.39 comments per case.
Their thread-cleaning recipe is already verified — quote-strip, direction-label, chronological order, filter auto-acknowledgements, dedupe the repeated case description. Measured: five messy messages down to three clean ones. BOARDEDRecorded now, blocked on the access grant — so it gets adopted rather than rediscovered in six weeks. Its known remainder (per-message signature blocks, closure templates, thread tokens) came with it.
The bigger thing. Tracer's next build is a symptom-keyed index over roughly 1–2K cases. That is the same product as ours over 42,402, with a ranking engine already running in production on a sibling corpus ten times larger again. Each side holds what the other is missing: they have the email threads, we have the corpus, the label spine and the engine. Building both means two half-products and two copies of the same customer data. That decision has the shortest fuse on this page — their index is the next thing off their roadmap.

6. What's next — boarded, in this order

  1. Fix the search truncation first — small, and the failure mode is a confident wrong answer.
  2. KEYSTONEPort the stager. The Zendesk bake engine already runs in production on a corpus ten times larger. The Salesforce raw is the same store format, so this is a field-map port, not a rewrite — and it unlocks ranked search, similar-case matching, pattern spines and Rebuild in one move. Now scoped retrieval-only, Reason-seeded, with character normalization. Everything else waits behind it.
  3. The email-access grant — not our code to write, and the largest single lever on the page.
  4. Lifecycle handlers on the bridge, mirroring the Zendesk ones — this is what turns the Rebuild card into buttons.
  5. Store checksum in the version response, so the console can cache computed answers against an immutable store instead of recomputing every visit.
  6. Email-thread cleaning, once the grant lands.

Three items are decisions rather than builds, and none of them are engineering: whether to consolidate the two indexes or build both; one privacy standard covering a 1–2K distilled index and 42,402 sealed full-fidelity cases; and clearing a cached access credential.
