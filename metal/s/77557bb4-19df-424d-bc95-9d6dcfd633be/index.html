This report is its own proof. It was published through the new git-push path, on the code it describes. If you are reading it at its cap-URL, the fix works end to end.

The bug was smaller than the symptom

The board recorded this as “413 Request Entity Too Large — the git-push path works, the helper does not.” True as a symptom, and it sent us looking at payload size. The actual defect is a one-line omission.
The config already said what should happen, in its own words:
"via": "git push to joeycastilloUS/joeycastillo.us -> Cloudflare Pages (git integration).
        NO cloudflare-bridge API token, NO wrangler -- deploy is the push."
But deploy_site() gated on platform and project only. via was read nowhere in the file — grep count zero. Commit 5c2486b on 2026-08-04 rewrote the prose and left the trigger in place. Every publish since has attempted a Cloudflare Direct Upload against a site that GitHub Actions already deploys from git.

What it was actually uploading

_build_files() walked the whole site root with no directory pruning — so the payload included the site repo’s entire .git.

Four failures in one day — 413, WinError 10054, HTTP 500, a >120s hang — are one cause with four faces: a 270 MB body dying at four different points. The going theory that today’s embedded screenshots were to blame is refuted: 104 KB against 270 MB is noise. This failed at any artifact size.
The failure has been protecting the site. The same walk excluded exactly two files — _headers and _redirects — via a startswith("_") filter. So a successful Direct Upload would have replaced the live site with a fileset containing git internals and missing its cache rules and redirects. Every failure of the last month prevented that.

What changed

The mode selector

latchkey.deploy.mode — "git-push" or "direct-upload". Absent means direct-upload, so metal console (whose site root is not a git repo) is byte-identical to before. The mode key is the only selector; the prose via field stays documentation and is still never parsed — config that lies is worse than config that is absent.

The new path

Stage the door copy, commit only that token’s path, push. The push is the deploy. No walk, no reconcile, no upload. Never add -A — the work tree routinely holds other sessions’ stranded door copies, and sweeping those in is the exact accident this replaces. On a non-fast-forward it does one pull --rebase --autostash and re-pushes. On a non-repo site root it refuses loudly rather than falling through to direct-upload, because a fallback there would POST 270 MB.

Two problems removed at the root

Git-push mode skips _reconcile_site_root() entirely. Reconcile exists only because Direct Upload replaces the whole site; under git the repo is the union of every machine’s tokens by construction. That kills both the CRLF stomp of up to 151 unrelated artifacts per publish and the stranded-other-session-copies problem. Staging now also writes LF, matching the site repo’s eol=lf, so the byte-compare stops seeing every door as changed.

Direct-upload hardened anyway

Metal console still depends on it, so both landmines are fixed there too: the walk prunes dot-directories, and _headers/_redirects are no longer excluded. Measured on the argus root: 270.4 MB → 119.6 MB with both files restored.

Retro — ~R

What went well

  • Two independent diagnoses beat one. Both models inspected separately and the results were diffed. The driver’s pass found the via-never-read root cause and the .git inclusion; the navigator’s missed both. A single pass would have shipped a payload-shrinking fix for a config bug.
  • Measuring beat theorising. The screenshot theory was plausible and wrong; one measurement killed it.
  • The rig found what review could not — the dirty-tree rebase refusal only appears when you actually run it against a dirty tree.

What could be better

  • The navigator got the payload number wrong first time by pruning .git in its own measurement — the very thing the bug was about. Measure what the code does, not what you assume it does.
  • A commit was made in the wrong repo mid-ship (a cd that outlived its intent), and a board file’s line endings were flipped, turning a 34-line diff into 5,796. Both caught and corrected before pushing, but both were self-inflicted.
  • Config that lies is worse than no config. The via field described the correct behaviour for a month while the code did the opposite. Prose next to a trigger it does not control is a trap.

What’s next

  • Kaizen — metal console is on the same cliff. Its own deploy root is 1.2x over the cap (531 files, 37.6 MB base64) with no .git to blame, and the dot-dir prune does not rescue it. It is not a git repo, so this mode is unavailable there without making it one. Recorded, not absorbed.
  • Kaizen — the publisher is vendored per-project by copy, with nothing keeping copies in sync. Argus’s was two features behind canonical.
