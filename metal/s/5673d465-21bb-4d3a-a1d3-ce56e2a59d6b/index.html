CASE PATTERNS · METHOD & ACCURACY2026-07-27

How the case classification works — and how accurate it actually is

The full method behind the Case Patterns tab, the audit that was run against it, and the defect the audit found

Method note · written to be checked, not believed · 2026-07-27

Read this first. The audit found a real defect and the numbers moved. The tab showed 1,578 matched cases. After the fix it shows 933 — a 41% reduction. The removed 645 were noise: price-change approval letters, routine ticket correspondence, and in one case a marketing email. Ground truth did not move (4 of 6), which is the evidence that noise came out and signal stayed in.

1. What the classifier actually does

It is a deterministic literal string matcher. There is no model, no embedding, no scoring heuristic, no LLM anywhere in it. Given the same corpus and the same signal list it produces byte-identical output every time. That is deliberate: a classifier you cannot audit is a classifier you cannot trust.

for each pattern (10 of them):
    for each signal term (a literal string, with a weight of 1 or 2):
        ask the store: which distinct strings contain this term, case-insensitively?
        take every fact whose subject / predicate / object is one of those strings
        keep only the facts whose subject is a case
        every such case scores += the signal's weight

    a case MATCHES the pattern when its score reaches 2
        -> one weight-2 signal on its own, OR two weight-1 signals together

Then, separately, the ground-truth check: each library pattern that cites a real case number is asked whether its own signals find that case. That number is not a target to optimise. It is a control.

2. Where the signal terms come from — the one rule

Signals are written from each pattern's SYMPTOM section, never from its ROOT CAUSE.

This is the rule the whole thing hangs on, and it comes from a fact about the data rather than a preference. We hold each case's subject and description — the opening message and nothing after it. The reply thread, where diagnosis happens, is not readable by this integration.

Three of the library's own example cases prove it. Their root causes never appear in the case text at all:

Library root causeWhat the case actually says
"Publisher paused since 4/3""We have a new issue for doordash. We are not receiving the full orders and have a delivery line with a $ amount…"
"Drive mapping set to D: instead of C:"Subject: "Menu Sync". Body: a routine request to sync two item categories before 11am.
"Print on Held checked on affected items"A forwarded internal note looping support in.

So chowly publisher paused matches nothing, while not receiving the full order matches. The symptom is in the case. The cause is in the thread.

What was deliberately not done: tune the terms until all six known cases lit up. That is scoring against the answer key. It produces a better-looking number that means nothing, because the terms would then be fitted to six cases rather than describing a symptom. The rule stays principled and the score is whatever the rule produces.

3. The audit

Three checks were run against the classifier itself, not against its output summary.

PASSCheck 1 — do matched cases really contain their signal?

Sampled matched cases, pulled each one's real subject and description back out of the store, and looked for the term. Every sampled case genuinely contained it. No phantom matches, no indexing error.

PASSCheck 2 — does substring matching create false hits?

Matching is substring, not whole-word, so seat 1 would also match "seat 10" through "seat 19". Tested directly: seat 10 and seat 11 return zero matches in this corpus, so the exposure is real in principle and empirically nil here. Worth re-testing on any future corpus rather than assuming.

FAILCheck 3 — are the matched cases actually about the pattern?

Eight matched cases per pattern were sampled and read by hand. This is where it broke.

Weight 2 is supposed to mean "distinctive enough to classify a case on its own." Nine ordinary English phrases had been given weight 2 — menu sync, open ticket, not printing, does not print, missing item, item missing, items not showing, duplicate item, seat 1. One unremarkable sentence was therefore enough to classify a case. What came in as a result:

CP-004 sync failurefour of eight sampled cases were "Price Change Request_ Approval/Denial Letter" — they merely used the words "menu sync"
CP-002 open-ticket failure"SFG open tickets", "RE: one dine ticket" — ordinary correspondence
CP-008 bump-to-print"Receipt not printing order details" — a printing complaint, but not this failure
CP-001 overpayment"Backdated refunds available — don't delay" — a marketing email

Meanwhile the distinctive technical tokens behaved exactly as intended throughout: pos_failure, com_error_code, chowly, expo printer, price discrepancy, menu.zip, eod sync. The rule was sound; the weights were wrong.

4. The fix and what it changed

All nine generic phrases demoted to weight 1, so they now require corroboration from a second signal before a case is classified.

Ground truth holding at 4/6 through a 41% cut is the whole argument. If the removed cases had contained signal, the proven cases would have fallen out with them. They didn't. A big number nobody trusts is worth less than a small number somebody acts on.

CP-004 is the clearest case: 322 down to 3, and re-reading those three, all of them are genuine sync failures — a missing menu file, an EOD sync tool not working, an EOD reset — instead of price-change letters.

5. What this number is, and what it is not

It is a symptom-level triage filter, not a root-cause classifier. A match means: this case speaks the vocabulary of this pattern. It does not mean the pattern's root cause has been confirmed on that case. The library itself draws exactly this line — a pattern only earns its number once a real case is worked end to end and the cause is confirmed. This tool finds candidates for that work; it does not do that work.

Even after the fix, precision varies by pattern, and it varies with one thing: how distinctive the vocabulary is. Patterns anchored on technical tokens read clean. Patterns that can only be described in ordinary English still pull in neighbours. CP-008 remains the weakest — "device group" appears in configuration requests as readily as in bump-to-print failures.

6. Known limits, stated rather than buried

  1. Recall is capped by a bug in the store's search. It stops collecting past roughly 2,000 distinct matched strings, and returns at most 500 results per query, while still reporting a complete-looking answer. Three patterns hit that ceiling. Both ground-truth misses are on patterns that hit it — a measured cost, not a mystery. The fix is written and committed; it is not deployed, because rebuilding that service needs a library snapshot that is not on this machine.
  2. We only see the opening message. 87% of cases arrive by email and we hold 0.39 comments per case. Everything above is what the first message alone can tell you.
  3. Matching is substring, not whole-word. Harmless on this corpus, verified, not guaranteed on the next one.
  4. Precision was estimated by reading samples — eight per pattern, by hand. It is an informed estimate, not a measured rate. A real number needs a labelled set, and the honest way to get one is to work cases through the patterns and record the outcome, which is what the library's own confidence rule already prescribes.
  5. The corpus is 16 days stale and there is no automated refresh yet.

7. How to check any of this yourself

  • Open the tab, click any pattern. It lists every signal, its weight, how many cases it hit, and whether it hit the recall ceiling — then the matched cases. Click a case to open it in the raw drill and read the actual text.
  • Signals returning zero are shown as zero rather than dropped, so a pattern with no evidence in the corpus looks empty, because it is.
  • The tab leads with what it does not cover before showing a single match.
  • The matcher is one file, one pass, no hidden state. Same input, same output, every time.

Comments are open below. If a matched case looks wrong, say which one — that is exactly the feedback that improves the signal list.
