D16 — what "execute first" actually costs

You asked for D16 to execute first and to make sense when you discuss it, and whether the ordering is implied. It is not. There are three independent orderings in a Pure Intent card, and the demand number controls none of them.

The three orderings

OrderingSet byControls
Demand block order.piHow it reads in the document. Presentation only.
Unit order.siWhat actually executes, and in what sequence.
The number D16—Neither. It is a label.

They are wired to nothing in common. Moving a demand up the .pi changes the document and nothing else; changing execution means editing the .si.

Where D16 executes today: second

mendo-nps-detractor-triage.si

  index 0   - unit: scan_alert      why: D1          ← READS + parses the ticket
  index 1   - unit: gate_handled    why: D2,D16      ← the lane test lives here
  index 2   - unit: reduce_feedback why: D3
  index 3   - unit: illness_check   why: D4,D5       ← the only model cost

So on every sweep, Argus reads and parses the other arm's ticket — guest email, feedback text, store — and only then asks whose lane it is.

The obvious fix is a trap

Both units declare in: [ticket] and neither consumes the other's output, so swapping them looks free. And it would load and run — biRT permits it, nothing refuses it. It is forbidden by consequence, not by the machine.

scan_alert is the filter. The sweep hands over every ticket created in the window — that is deliberate (mendo-nps-sweep.pi D1: no filter, dedup is the filter) — and scan_alert aborts the non-alerts at index 0.

Put gate_handled first and it claims — it merges argus_nps_handled onto every own-lane ticket in the window, alert or not, before anything establishes the ticket is even an NPS alert. That includes Argus's own recovery follow-ups, escalation artifacts, and any human or test ticket — the default brand is ~89% of everything Argus touches.

Corrected after review: an earlier cut of this page said "every ticket in the account." That overstated it — the lane guard sits inside tag-claim before the merge, so even in the swapped order the other arm's tickets are still refused. The trap protects Lane A's own hygiene, not Lane B. The conclusion stands; the blast radius was wrong.

What is already true

D16 already executes before any write, and before any model cost. The bridge is what enforces it — not the prime. The guard derives the arm from ?env= with no caller cooperation, so it holds regardless of which pi_run binary the prime is running. Verified live: /version reports ZBR1k … D16 LANE GUARD, and tag-claim, internal-alert and nps-cc all return lane:"foreign" and write nothing. gate: exit then ends the run, so the panel, escalation, code-claim and send units never execute on a foreign ticket.

Lane B receives no writes today. What still happens is a read: Argus fetches and parses Lane B's ticket content on each sweep. Harmless to the A/B result — it is the other arm's guest data being touched for no reason.

Three separable pieces

1 — Reads sensibly when you discuss it free

Move the demand block to the top of the .pi. The parser is order-blind — it stores clauses in file order and matches by string, never by number — so this ships against the binary running on the LA prime today with no rebuild, and the seal is untouched (the seal covers words: blocks only). Zero code, zero risk, reversible.

2 — Executes before any write already shipped

Done and verified. Nothing further required.

3 — Executes before the read needs a prime rebuild

A new read-only lane unit at index 0, before scan_alert. That needs a new skill/slot binding in pi_run — compiled C on the LA prime. It is the one item here that cannot be done by editing cards. Marginal gain, stated honestly: exactly one thing — skipping the foreign ticket's content read. The write path is already sealed bridge-side and live. This buys privacy hygiene, not protection.

The number itself

If it presents first and executes first, D16 is an accession number — like an RFC number: minted once, permanent, never a rank. In conversation it is "the lane rule," cited as triage/D16 when the card matters.

Making the token literally read D1 is a different job: a renumber. The numbers are referenced ~400+ times, including a working agreement written around "the 15 rules, D1–D15" — and the demands cite each other inside their own prose, so a renumber corrupts text within the card as well as outside it. Worth doing only as a decision about identity, not to tidy a document. That design is published separately.
