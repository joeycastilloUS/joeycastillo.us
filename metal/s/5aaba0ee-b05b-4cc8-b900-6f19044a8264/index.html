Pulse REST API

A read-only REST surface for Norman Campbell's Pulse Suite POS hardware-health telemetry — modeled exactly on how Argus already exposes Meraki. Mesh gives him a way to give us data at light speed; we serve it up REST style. design only read-only-provable pure C99

1 · Need

Norman's Pulse Suite (Status Report Ver 1.6, 22 Aug 2026) already measures everything that matters on a POS terminal's hardware: load-test GFLOPS, package power, per-core temps, per-drive temps and wear-out arithmetic, throttle behavior, firmware inventory. Today that lives in per-run CSVs and a status report on one bench. There is no way for Argus — or anyone — to ask a fleet-wide question: which drives are running hot right now? which terminal crossed a wear-out threshold? which sites are still on Pulse-Link fw 1.0.0?

Argus already solved this exact problem for Meraki: one read-only-provable source seam, a declared catalog, GET-only wire. Pulse needs the same seam — not a new idiom. The operator's directive is the whole spec: "the mesh gives him a way to give us data at light speed, then we serve it up REST style" — and "c99 and raw ids as much as possible, light speed for the win."

Non-need, stated to kill it early: this is NOT a control surface, NOT multi-tenant (one operator, implicit), and it NEVER touches the payment path — Pulse law is one-way observe-only, fail-independent, coprocessor carries decoded records only.

2 · Raw user stories

  • As Norman, I want to hit one URL and see fleet health — how many terminals are green / warn / critical — so I don't open 40 CSVs.
  • As Norman, I want terminals/{serial} keyed by the Pulse-Link per-unit serial — the hardware id I already ship on every unit — so identity is the physical thing, not an invented database id.
  • As an Argus dashboard, I want per-drive health with the honest numbers: 56°C Kingston NVMe, 69°C Silicon Power SATA, and a USB stick that reports no temp shown as null, never a fake number.
  • As Norman, I want the wear-out estimate served with its honest range and duty-cycle caveat — "November 2026" is the all-day-load-test arithmetic, not what a till sees — so nobody panics off a worst-case number.
  • As an Argus dashboard, I want the second-by-second series (the 599-row shape) for any run or time window, so I can draw the speed bars shortening as the case heats and the CPU throttles.
  • As Argus ops, I want every health flag across the fleet in one call — drive-temp, wear-out crossing, sustained throttle — so the fleet-flags view is one GET, not N.
  • As Argus ops, I want firmware inventory across the fleet (Pulse-Link fw, VCD2x20, OPOS drivers) to plan rollouts.
  • As the Argus browser, I want Pulse to be just another ISource — same catalog, same /read wire, same fail-closed path builder — so zero new client code is written.
  • As the operator, I want the read server in C99 over raw ids — no ORM, no framework, no managed runtime between Norman's data and the wire.

3 · Sourced solution — mirror the Meraki seam

The idiom (ground truth from Argus's own code)

Argus exposes every source through ONE read-only-provable seam, bridge/ISource.cs:

interface ISource {
  string Name;
  IReadOnlyList<CatalogEntry> Catalog;
  string? ScopeTokenEnv;
  Task<JsonElement> ReadAsync(string path);
}
record CatalogEntry(string Id, string Label, string PathTemplate, string[] Params)
  • The SOURCE declares the path template. The caller only fills {param} placeholders — it can never invent a path.
  • SourceDispatch.TryBuildPath() substitutes each {param} URL-encoded and fails closed on: missing param, value >200 chars, control chars, or any leftover {/}. A stray / in a value becomes %2F — traversal is impossible by construction. This is what makes the browser provably read-only: no arbitrary-path passthrough exists.
  • Wire: GET /catalog lists entries; GET /read?source=<name>&id=<entryId>&<param>=<value> runs ONE entry and returns raw JSON.
  • Per-source scope: ScopeTokenEnv names the env var that authorizes THIS source; unlocking one source never unlocks another.

bridge/MerakiSource.cs instantiates this for Meraki with the org id pre-substituted server-side (never from the caller): organizations · networks · config-templates · network (show) networks/{networkId} · devices networks/{networkId}/devices · clients · switch-ports devices/{serial}/switch/ports · wireless-ssids. Meraki's hierarchy is org → network → device → ports.

The transpose

MerakiPulseNote

So: operator (implicit) → Site → Terminal → Device → Run, exposed as a PulseSource catalog identical in mechanism to Meraki's. ScopeTokenEnv = ARGUS_PULSE_TOKEN — unlocking Pulse never unlocks Meraki, and vice versa.

The backend — pure C99 over a RAW sealed IDS (ARCHITECTURE.md §7, §12)

The REST server is pulse-rest, pure C99/nous (operator: "c99 as much as possible, light speed"). It serves derived views over a RAW sealed IDS (§7): each pushed Pulse record is atomized once into (site, terminal serial, device, metric, value, timestamp) triples; every endpoint below is a deterministic derivation over that store. No schema is invented — Pulse's record format is deliberately undefined until Track C (§12), and the triple store doesn't need one.

Ingest is a separate binary: pulse-ingest RECEIVES pushed batches (HTTPS now, nous mesh store-and-forward later — "light speed in, REST out") and is the ONLY writer. The read surface is GET-only, honoring the read-only invariant (§3, §12). Zero C# — Pulse is the first Argus source with no foreign API to jacket, so the Language Boundary law leaves it entirely C99.

Sources read: bridge/ISource.cs · bridge/MerakiSource.cs · ARCHITECTURE.md §3 (read-only invariant), §7 (RAW sealed IDS), §12 (Pulse track: record format deferred to Track C, observe-only laws).

4 · Name it true

  • pulse-rest — the C99 read server. It serves Pulse over REST. That's the name.
  • pulse-ingest — the C99 writer. It ingests Pulse pushes. Only writer.
  • PulseSource — the ISource registration. Sits next to MerakiSource, same seam.
  • Endpoint ids are literal nouns for what they return: fleet-health returns fleet health. terminal-drives returns a terminal's drives. run-series returns a run's series. No themes, no cleverness — every id reads as the answer to "what do I get back?"
  • {serial} is named serial because it IS the Pulse-Link per-unit serial — a raw hardware id, not a surrogate key. Raw ids as much as possible.

Read-only-provable rules (identical to Meraki, restated as law)

  • The source declares every path template above; callers only fill {param} slots. There is no raw-path endpoint.
  • TryBuildPath() URL-encodes every substitution and fails closed on missing param, value >200 chars, control chars, or leftover {/}. A serial containing / becomes %2F — it matches no terminal, it traverses nothing.
  • The operator is pre-substituted server-side (there is exactly one) — the caller can never name a tenant, same as Meraki's server-side org id.
  • pulse-rest compiles with no write handler. GET-only isn't policy, it's the binary.
  • ScopeTokenEnv = ARGUS_PULSE_TOKEN — per-source scope; Pulse access grants nothing else.

Choices + Consequences

ChoiceChoseConsequence
REST over derived views vs raw-record passthroughDerived views over the triple storeWe never commit to Norman's record format (deliberately undefined until Track C, §12) — the triples absorb any shape he pushes; endpoints stay stable while his format evolves. Cost: a derivation layer to keep deterministic. Passthrough would freeze his format into our API on day one — exactly wrong.
HTTPS ingest now vs mesh from the startHTTPS now, mesh laterNorman can push tonight with curl; the mesh ("light speed in") slots in behind pulse-ingest without touching the read surface. Cost: one transport migration later — contained entirely inside the one writer binary.
Canned demo vs live C99 server nowCanned demo tonight, C99 as the buildNorman reacts to real shapes with his real numbers tonight; the catalog gets corrected by use before a line of C99 hardens around it (Rule 7 — plans are wrong by default). Cost: the demo isn't production — and it says so on its face.

Escape Routes

  • Catalog is wrong-grained (Norman thinks in runs, not terminals — or vice versa): entries are additive; add/deprecate CatalogEntry rows without breaking the seam. The ISource wire never changes.
  • Triple store too slow for series endpoints (599 rows × fleet): add a per-run derived cache keyed by runId — still deterministic derivation, still one writer, read surface unchanged.
  • Mesh slips: HTTPS ingest is not a stopgap, it's a full transport — Pulse ships on it indefinitely with zero read-side change.
  • Track C defines the record format differently than expected: only the atomizer in pulse-ingest changes; triples and every endpoint derivation survive.
  • Serial collision or reprovisioned hardware: serial stays the key (raw ids law); a supersededBy field on the terminal view handles unit swaps without inventing surrogate ids.

Pure Metal Test

  • Load-bearing deps: nous TripleStore (the RAW sealed IDS) and nous understand() for the atomize step — both ours, both C99, both deterministic. That's the point.
  • Replaceable: Cloud Run hosting is a convenience shell; pulse-rest is a static C99 binary that runs anywhere a socket opens — including bare metal under Purcius later.
  • ZERO C#: no foreign manufacturer API exists here — Norman pushes to us — so the Language Boundary law leaves nothing to jacket. First Argus source that is pure metal end to end: C99 in, triples at rest, C99 out, JSON on the wire.
  • No frameworks, no ORM, no schema migration ever: triples don't migrate.
