How I’ll protect your data

I know Editor access sounds like a lot. Here’s the guardrail, and it’s a technical one, not a promise:

  • My automated tooling gets a read-only key. Airtable lets you scope an access token separately from your role. The token my system uses will be scoped read only — it is incapable of changing a cell. Not “won’t” — can’t. The API rejects it.
  • Every Site Status change is made by me, by hand. The software’s job is to tell me “this store looks like an issue, here’s why.” I review it, then I make the change. No robot writes to your base.
  • Nothing is deleted or restructured. I’m only ever touching Site Status and the comments column — the two fields you asked me to use.

If you’d still rather I have Read only, that works too — I’ll send you a list of stores needing Site Status = Issues instead of setting it myself. You lose nothing except a step.

What I’m building, and why it helps you

The field crew fills out the Inventory / Installation / Decommission JotForms, and those land in the base. Right now, catching a problem in that data means someone reading every row. I’m automating the reading part.

CheckWhat it catches
Serial number formatA serial that can’t be right for that device. Lorraine confirmed the correct value. Of the 12 rows I could see, that was the only serial that failed — a simple rule found it instantly.
Photo vs. typed serial
next up		Every submission is supposed to include a photo of each device. Next up: I’ll read the serial off the photo and compare it to what was typed — catching transposed digits, the kind of error a format check can’t see. A photo too blurry to read gets flagged too, early enough to fix the same night rather than on a return visit.
Duplicate serialsThe same device recorded at two different stores.

The result for you: when something is wrong at a store, it gets flagged the same night — that’s the standard I’m building to — not discovered weeks later when someone needs that serial number. And Site Status reflects it, the way you asked.

The other reason I need the photos

I’m generating the ops report for this rollout from your Airtable photos. The per-store record — what was installed, what it looks like, the serials that back it up — comes straight from what the crew submitted. That means the photos aren’t just for spot-checking serials; they’re the evidence the report is built on. Without base access I can’t pull them, and the report has to be assembled by hand from screenshots.

How Site Status will get set

  1. A submission lands, or something happens on an install night.
  2. The checks run automatically and flag anything that looks like an issue — a NO GO, a device not working, a return visit needed, bad data.
  3. I review the flag and decide if it’s real.
  4. I set Site Status = Issues and write what happened in the comments column.
  5. It goes in the after-action record, so nothing gets lost between install night and the end of the rollout.

Step 3 is deliberate. I’d rather show you one real issue than ten false alarms, so a human decides before anything reaches your base.
