Team Velocity — one line for the whole crew

Paired (Rule 1): Opus (driver) and Fable (navigator) ran independent passes and converged — both landed on a rate (points per hour), not raw points per night. Fable held two calls (rate over raw; penalize only open issues, never logged ones); driver folded to both. No disagreement to surface. Fable’s flag — the phase weights are eyeballed from one night — is carried as the Escape Route.

1 Need

The team runs an install night, then another, then another. Every night throws off a pile of metrics — four stores × four phases of timestamps, issues logged, delays, C1 reports. Today those live in separate charts (the nightly gantt, the night-vs-night comparison). Nobody can answer the one question that matters in a glance: are we, as a whole crew, getting faster and cleaner — or slipping? The operator wants a single number per night, plotted as one line, so the trend is the answer.

2 Raw user stories

  • As the operator, I want one velocity number per night, so I can tell at a glance if we’re trending up or down.
  • As the crew, we want the whole night’s effort in one line, so improvement shows as a trend, not four charts to cross-read.
  • As a reviewer (CIO / IT), I want a single tracking line, so I know we’re on pace without reading the details.
  • As a lead, I want logging an issue to not hurt our number, so I keep surfacing problems loudly.

3 Sourced solution (mine before inventing)

  • Scrum velocity — Jeff Sutherland’s framework, the operator’s own training. Story points per sprint. Adopted with one inversion: a sprint is fixed time, variable scope; an install night is fixed scope (4 stores × 4 phases), variable duration. So velocity here is points per hour, not points per night. Source: Scrum Guide / Sutherland.
  • Our own artifacts — the golden transcript (raw timestamps), the Night-4 gantt + the Night-4-vs-Night-3 comparison chart (phase timings, milestone deltas), the AAR (18 issues logged, 2 residual), the kaizen. Every input the formula needs already exists. Source: this rollout.
  • Firestore — acmedev (konducter-estimates DB, already live for the estimate app). Natural home for one velocity record per night. Reuse, don’t build. Source: our infra.
  • a-d-d / nous — no existing velocity/metric primitive found. This becomes the first metric primitive (deterministic: timestamps in → number out — Tier-0-friendly, no model). Gap noted.

4 Naming (literal)

  • Team Velocity — the score, in pts/hr. Literal: work ÷ time.
  • Install Points — the work units (phase points).
  • Night — the iteration (Scrum’s “sprint”).
  • Net Hours — elapsed from scheduled start to all-systems-go, minus excused external delay.
  • Residual — an issue still open at close (the only kind that costs points).
  • Yesterday’s Weather — Scrum’s own term; the projection basis for a night still in progress.
  • Velocity Line — the single tracking line.
  • Collision check: “velocity” is overloaded in software, but here it’s literal (crew work ÷ time) and clashes with no repo or product name.

5 Shape (minimum viable)

Team Velocity = ( Earned Points − Residual Penalty ) ÷ Net Hours Earned Points = Σ per store: Inventory 1 + Decommission 2 + Install 5 + Release 2 + C1 report 1 ( 11 pts/store · full 4-store board = 44 ) Residual Penalty = 1 pt per issue still OPEN at close ( logged-and-closed = 0 ) Net Hours = ( all-systems-go − 8:30 PM start ) − ExcusedDelay ExcusedDelay = external delay hrs × ( stores affected ÷ stores scheduled )
  • Inputs (all already captured): per night, phase-completion timestamps (4×4) + start + all-systems-go + open-issue count at close + any external-delay note.
  • Partial night (tonight): don’t plot raw run-rate — it’s inflated by the cheap early phases. Project all-systems-go via yesterday’s weather (prior nights’ remaining-phase durations), show a hollow, dashed marker with a best/worst band that collapses as phases close.
  • Store: one record per night in Firestore — velocity collection: {night, date, points, netHours, tv, residuals, projected}.
  • Show: the Velocity Line — x = night, y = TV pts/hr; solid through closed nights, dashed + band for tonight, a dotted benchmark reference. The slope IS the answer.
  • Out of scope (v1): per-person velocity (this is team-level, on purpose), forecasting beyond the next milestone, automated defect clawback (manual redraw for now).

● Choices + consequences

Rate (pts/hr) vs. raw points/night. Scope is fixed at 44, so raw points/night is a flat line forever — zero signal. The rate captures speed and quality and stays auditable straight from timestamps (an index would need weight-tuning and hide its units). Pick: RATE.
Penalize all logged issues vs. only residual-open ones. If logging costs points, the crew goes quiet and problems surface after release — the exact opposite of what you want. Night 3 logging 18 issues loudly is an asset, not a debt. Pick: only issues still OPEN at close cost points; logging is free. Guard: a defect found after a store is released claws back that store’s 11 pts retroactively — so rushing to close is never profitable.

↩ Escape route

The whole metric is a pure function of recorded timestamps — fully recomputable, nothing irreversible. The one load-bearing guess is the phase-weight scheme (1 / 2 / 5 / 2), eyeballed from a single night. Freeze it after Nights 1–4 actuals; re-derive from real per-phase durations if it’s off. Reversible by design.
